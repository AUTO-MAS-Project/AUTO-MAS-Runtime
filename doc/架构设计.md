## 背景

AUTO-MAS 当前由 Vue 渲染进程、Electron 主进程和 Python 后端组成。Electron 主进程除桌面窗口能力外，还承担了 Python、uv、Git 安装，源码获取，依赖部署，插件 bootstrap，后端进程启停和 Windows 进程清理等职责。Python 后端同时承担 AUTO-MAS 整包更新的检查、下载和安装器拉起。

这些能力与桌面 UI、业务后端耦合后，会产生以下问题：

1. Electron 主进程包含大量与 UI 无关的本机运行时逻辑。
2. 环境安装、更新和修复难以脱离 GUI 独立执行与诊断。
3. 应用更新同时跨越 Electron、Python 和安装器，责任边界不清晰。
4. Electron 直接管理 Python 进程树时，容易把进程识别和清理策略散落在多个位置。
5. 相同能力难以复用于安装器、命令行诊断和未来的其他桌面外壳。

## 目标

新建独立项目 `AUTO-MAS-Runtime`，使用 Go 实现 Windows 本机运行时管理程序，输出单个可执行文件：

```text
auto-mas-runtime.exe
```

该程序统一负责：

- 本机运行环境检测与部署；
- 受管后端源码仓库更新；
- Python 依赖部署；
- Python 后端启动、监督、停止和异常报告；
- 运行环境诊断、修复与清理。

Electron 通过命令行启动 Runtime，并通过标准输入、标准输出和退出码与其通信。

## 范围

### 本方案包含

- 终端用户 Windows 机器上的环境安装与运行时生命周期；
- Electron 与 Runtime 的本机进程通信；
- Runtime 对 Python 后端的进程监督；
- 受管后端源码和运行环境的更新、修复与诊断；
- 可由用户独立执行的诊断 CLI。

### 本方案不包含

- 将 Vue 或 Electron 改写为 Go；
- 将 Python 业务后端改写为 Go；
- 让 Runtime 代理 Python HTTP 或 WebSocket 业务接口；
- 将 GitHub Actions、CNB 构建发布流程迁入 Runtime；
- 在首个版本中安装常驻 Windows Service。

GitHub/CNB CI/CD 继续负责 Vue、Electron 和 Runtime 自身的构建、签名与发布。Python 后端不生成更新压缩包，Runtime 根据目标版本获取对应 Git 发布分支。

## 已确认的总体架构

系统分成控制面和业务面。

### 控制面

```text
Electron 主进程
    │
    │ CLI + stdin/stdout NDJSON + exit code
    ▼
AUTO-MAS-Runtime
    │
    │ 进程启动、监督、停止
    ▼
Python 后端进程
```

控制面负责环境、更新和进程生命周期，不承载 AUTO-MAS 业务请求。

### 业务面

```text
Vue 渲染进程
    │
    ├── HTTP
    └── WebSocket
         │
         ▼
    Python 后端
```

Vue 继续直接访问 Python 后端。Runtime 不增加 HTTP 代理层，避免引入额外端口、业务协议映射、WebSocket 转发和故障定位成本。

## 组件职责

### Vue 渲染进程

负责：

- 展示初始化、更新、修复和后端状态；
- 通过安全的 preload API 向 Electron 主进程发起操作；
- 后端就绪后直接调用 Python HTTP API 和 WebSocket。

不负责：

- 直接启动外部程序；
- 解析 Runtime 原始标准输出；
- 执行下载、解压、Git 或依赖安装。

### Electron 主进程

负责：

- 窗口、托盘、文件选择、系统对话框等桌面能力；
- 以参数数组方式启动 `auto-mas-runtime.exe`；
- 将 Runtime NDJSON 事件映射为类型化 IPC 事件；
- 把后端地址和就绪状态传给渲染进程；
- 在应用退出时请求 Runtime 停止后端；
- 保留少量与 Electron 自身有关的升级退出协调。

不负责：

- Python、uv、Git 的安装；
- 源码、依赖或插件部署；
- 下载镜像选择和重试；
- Python 后端 PID 扫描及进程树清理；
- AUTO-MAS 更新包的下载、解压与安装。

### AUTO-MAS-Runtime

负责：

- 检查、部署和修复运行环境；
- 根据目标版本解析并校验 Git 发布分支和目标提交；
- 浅克隆、校验并整体替换受管后端仓库；
- 管理镜像源和失败重试；
- 启动并监督指定的 Python 后端；
- 通过健康检查判断后端是否真正就绪；
- 记录结构化日志和操作状态；
- 只终止自己明确启动和持有的进程树。

Runtime 是本机运行时策略的唯一所有者。

### Python 后端

负责：

- AUTO-MAS 配置和业务模型；
- 脚本、队列、计划和任务调度；
- HTTP API 和 WebSocket 业务接口；
- 插件包、插件依赖、插件运行目录和插件生命周期；
- 业务域服务。

不再负责：

- AUTO-MAS 整包更新的下载与安装；
- 拉起 AUTO-MAS 安装器；
- 部署自身 Python 运行环境。

### GitHub/CNB CI/CD

负责：

- 构建 Vue/Electron 应用；
- 准备 Lite/Full 发行制品；
- 构建和签名 Runtime；
- 发布桌面端、Runtime 和其他仍需构建的 Release 制品。

CI/CD 与 Runtime 共享后端版本与发布分支协议，但不共享运行进程。

## Runtime 进程模型

采用混合式 CLI，而不是纯一次性 CLI 或常驻 Windows Service。

### 一次性命令

环境检查、初始化、更新和修复等操作执行结束后退出：

```text
auto-mas-runtime doctor
auto-mas-runtime bootstrap --version v5.4.0-beta.1
auto-mas-runtime workspace sync --version v5.4.0-beta.1
auto-mas-runtime dependencies sync
auto-mas-runtime repair
auto-mas-runtime cleanup
```

### 长驻监督命令

后端使用长驻子命令：

```text
auto-mas-runtime backend supervise --mode managed
```

Electron 持有该 Runtime 子进程。Runtime 通过 `uv run` 持有并监督 Python 后端进程树，并持续输出状态事件。

这种方式兼顾：

- CLI 可独立使用；
- 无需安装系统服务；
- Electron 可以实时接收后端状态；
- Runtime 可以集中处理 Python 退出、崩溃和进程树清理。

## 后端启动流程

1. Vue 通过 preload API 请求启动后端。
2. Electron 主进程执行 `auto-mas-runtime.exe backend supervise`。
3. Runtime 检查应用根目录、`uv.exe`、项目环境、入口文件和必要依赖。
4. Runtime 使用参数数组执行 `uv run --no-sync main.py`，不直接调用 `python.exe`。
5. Runtime 捕获 Python 的标准输出、标准错误和退出状态，并将启动日志包装为 NDJSON `log` 事件。
6. Runtime 轮询 Python 后端的 HTTP 健康检查接口。
7. 健康检查成功后，Runtime 输出 `type=state`、`stage=backend.run`、`status=running` 事件，其中包含 PID 和后端地址。
8. Electron 将后端地址和状态通过 IPC 发给 Vue。
9. Vue 建立到 Python 后端的 HTTP 和 WebSocket 连接。

示例状态事件：

```json
{"protocol":1,"type":"state","operationId":"01J...","sequence":8,"timestamp":"2026-07-27T14:30:00.000+08:00","stage":"backend.run","status":"running","details":{"pid":12345,"baseUrl":"http://127.0.0.1:36163"}}
```

## 后端关闭流程

Electron 不再通过进程名查找或全局执行 `taskkill python.exe`。

退出应用时，Electron 向 Runtime 标准输入发送关闭命令：

```json
{"protocol":1,"command":"shutdown","commandId":"01J..."}
```

Runtime 随后：

1. 停止接受新的控制命令；
2. 请求 Python 后端优雅退出；
3. 等待配置的关闭超时；
4. 仅在超时后终止自己持有的 Python 进程树；
5. 输出最终状态事件；
6. 清理 PID、锁和临时状态；
7. 以确定的退出码退出。

## 后端启动失败通知与日志

后端尚未启动成功时，HTTP 服务可能不存在，因此启动失败不能依赖 Python HTTP API 通知前端。失败信息通过控制面传递：

```text
Python stdout/stderr
        │
        ▼
AUTO-MAS-Runtime
        │ stdout NDJSON
        ▼
Electron 主进程
        │ IPC
        ▼
Vue 启动界面
```

### 双通道信息

Runtime 同时提供两类互补信息：

1. 结构化状态、错误码和处理建议，用于 Electron 和 Vue 判断状态及可用操作；
2. Python 原始 stdout/stderr，用于用户查看完整启动日志和排查问题。

结构化错误不能代替原始日志，原始日志也不能作为 Electron 判断业务状态的依据。

### 原始日志事件

Python 启动阶段产生的 stdout/stderr 由 Runtime 包装为 NDJSON `log` 事件：

```json
{
  "protocol": 1,
  "type": "log",
  "operationId": "01J...",
  "sequence": 4,
  "timestamp": "2026-07-27T14:30:00.000+08:00",
  "source": "backend",
  "stream": "stderr",
  "message": "Traceback (most recent call last):"
}
```

Runtime 同时把完整日志写入轮转日志文件。标准错误保留给 Runtime 自身的诊断信息，Python 的用户可见启动日志通过标准输出中的 `log` 事件传递，以保持机器协议可解析。

### Electron 兼容结果

Electron 主进程按 `operationId` 累积本次启动的 `log` 事件，分别保留 stdout 和 stderr，并在失败时组装成当前前端已经使用的格式：

```text
[stdout]
后端普通输出……

[stderr]
Traceback……
```

Electron 向 Vue 返回：

```json
{
  "success": false,
  "code": "BACKEND_EXITED_BEFORE_READY",
  "error": "后端进程在服务就绪前退出",
  "logs": "[stdout]\n...\n\n[stderr]\n...",
  "logPath": "D:\\AUTO-MAS\\logs\\runtime\\backend-20260727.log",
  "retryable": true,
  "remediation": ["retry", "rebuild-environment", "open-log"]
}
```

`logs` 保留现有初始化页面直接展示完整日志的行为。`code`、`retryable` 和 `remediation` 用于决定重试、修复环境、打开日志等操作，Vue 不能解析日志或中文文案来判断状态。

### 首版界面行为

首版迁移保持当前交互：

1. 启动过程中显示阶段和进度；
2. 启动成功后清理启动日志缓存；
3. 启动失败后一次性展示完整 stdout/stderr；
4. 提供重试、查看文档和打开日志文件等操作。

Runtime 的 `log` 事件允许未来增加实时日志展示，但实时展示不作为首版迁移要求。

### 失败事件顺序

Python 在就绪前退出时，Runtime 按以下顺序输出并主动刷新标准输出：

1. 最后一批 `log` 事件；
2. 一个结构化 `error` 事件；
3. 唯一的最终 `result` 事件；
4. Runtime 以退出码 `60` 退出。

Electron 以 `result` 为正常协议终点。如果 Runtime 未发送 `result` 就退出，Electron 生成统一的 `RUNTIME_EXITED_UNEXPECTEDLY` 错误，并附带已经收集的原始日志。

### Runtime 自身启动失败

Runtime 可执行文件尚未成功运行时不存在 NDJSON 输出，因此由 Electron 生成同形错误：

| 错误码 | 场景 |
| --- | --- |
| `RUNTIME_NOT_FOUND` | Runtime 可执行文件不存在 |
| `RUNTIME_SPAWN_FAILED` | Windows 拒绝或无法创建进程 |
| `RUNTIME_HANDSHAKE_TIMEOUT` | 启动后未在限定时间内收到 `hello` |
| `RUNTIME_PROTOCOL_ERROR` | 标准输出包含非法协议数据 |
| `RUNTIME_PROTOCOL_MISMATCH` | Electron 与 Runtime 协议版本不兼容 |
| `RUNTIME_EXITED_UNEXPECTEDLY` | Runtime 未发送最终结果就退出 |

Vue 最终只处理一套失败模型：

```text
code + stage + message + retryable + remediation + logs + logPath
```

## CLI 设计

CLI 是 Runtime 的稳定公开接口，不是只供 Electron 使用的内部脚本。

### 命令树

```text
auto-mas-runtime
├── version
├── doctor
├── bootstrap
│   └── --version <version>
├── workspace
│   ├── check
│   └── sync --version <version>
├── environment
│   ├── check
│   ├── ensure
│   └── repair
├── dependencies
│   ├── check
│   ├── sync
│   └── rebuild
├── backend
│   └── supervise
├── repair
└── cleanup
```

涉及网络访问的命令统一消费以下全局选项：

- `--mirror <kind>=<key>`：可重复指定，`kind` 固定为 `git`、`uv`、
  `python`、`package-index`，`key` 选择该类别中的首选源；
- `--offline`：禁止任何网络尝试；需要网络的操作返回
  `NETWORK_UNAVAILABLE`；
- `--mirror-only`：允许配置的镜像源，但排除官方源兜底。

`--offline` 与 `--mirror` / `--mirror-only` 互斥，冲突时按参数错误处理。
`internal/mirror` 只消费已经解析并校验的策略值；CLI 参数注册和语法错误映射
由 T3.1 统一实现。

`bootstrap --version` 是准备阶段的编排命令，固定按以下顺序执行：

1. `environment ensure`：准备并校验 Runtime 固定版本的 uv；
2. `workspace sync --version`：获取并替换目标发布分支；
3. 从新仓库读取并校验 `.python-version`；
4. 通过 `uv python install` 准备精确 Python；
5. `dependencies sync`：执行主项目锁定依赖同步。

`bootstrap` 只完成可重复执行的准备工作，不启动后端。Electron 在其成功后另行启动 `backend supervise`。下层命令保持可独立执行，以支持初始化界面单步重试和用户在 PowerShell 中独立诊断。

正式安装版通过 `workspace sync` 使用内置 Go Git 能力更新受管后端仓库，不要求目标机器额外安装 Git。开发模式只启动用户指定的源码目录，默认不自动更新或清理该目录。降级不设专用回滚命令，调用 `workspace sync --version <旧版本>` 即可按同一确定性流程重新获取旧发布分支。

除 `backend supervise` 外，所有命令执行完成后退出。每次调用只创建一个执行单一顶层操作的 Runtime 进程，不实现通用常驻 RPC 服务。

### Electron 调用

```powershell
& ".\auto-mas-runtime.exe" `
  "--app-root" "D:\AUTO-MAS" `
  "--output" "ndjson" `
  "--protocol" "1" `
  "bootstrap" `
  "--version" "v5.4.0-beta.1"
```

上例仅用于说明参数。Electron 实际实现必须使用可执行文件路径和参数数组启动子进程，不能拼接 Shell 命令字符串。

### 输出模式

Runtime 提供两种输出模式：

```text
--output human
--output ndjson
```

`human` 是用户在 PowerShell 中直接运行时的默认模式。`ndjson` 供 Electron 等机器调用方使用，并遵守以下规则：

1. 标准输出每行只能包含一个 JSON 对象；
2. 标准错误用于诊断日志；
3. 标准输出禁止混入普通文本、颜色控制字符或回写式进度条；
4. 每个事件都包含协议版本、操作 ID、递增序号和时间戳。

### NDJSON 公共结构

```json
{
  "protocol": 1,
  "type": "progress",
  "operationId": "01J...",
  "sequence": 12,
  "timestamp": "2026-07-27T14:10:00.123+08:00"
}
```

`hello` 必须是首个事件，`sequence` 从 `1` 开始：

```json
{
  "protocol": 1,
  "type": "hello",
  "operationId": "01J...",
  "sequence": 1,
  "timestamp": "2026-07-27T14:10:00.000+08:00",
  "runtimeVersion": "v1.0.0",
  "command": "bootstrap",
  "capabilities": ["stdin.cancel", "state.v1", "log.stream"]
}
```

协议版本 1 的能力标识固定如下。调用方据此判断本次操作支持哪些可选交互，不得从命令名推断：

| 能力标识 | 含义 |
| --- | --- |
| `stdin.cancel` | 本次操作接受 stdin `cancel` 控制命令 |
| `state.v1` | 本次操作发射 v1 生命周期 `state` 事件 |
| `log.stream` | 本次操作把受管进程的 stdout/stderr 转发为 `log` 事件 |

新增能力标识可以追加，既有标识不得改名；删除或改变既有语义必须升级协议版本。调用方对未知能力标识必须忽略而不是拒绝整个协议。

Runtime 在参数无法解析时可以直接向 stderr 输出诊断并以 `2` 退出，此时不承诺 `hello/result`。参数解析成功后，所有终点都必须遵循 NDJSON 契约。

事件类型固定为：

| 类型 | 语义 |
| --- | --- |
| `hello` | 协议握手、Runtime 版本和能力 |
| `progress` | 可量化的阶段进度 |
| `state` | 生命周期状态变化 |
| `log` | 可展示的过程日志 |
| `warning` | 不阻止操作继续的警告 |
| `error` | 操作失败 |
| `result` | 顶层操作的最终结果 |

事件中的容器字段遵循统一的非空约定：`details`、`remediation` 和 `capabilities` 在所属事件类型中恒存在，且恒为 JSON object 或 array，**不得输出 `null`**。空值分别表示为 `{}` 和 `[]`。调用方因此只需处理"空集合"一种情况，不必为同一字段区分缺失、`null` 和空容器三种形态。

进度事件必须包含稳定的机器字段。Electron 根据 `stage` 和 `status` 驱动界面，`message` 只用于展示。

```json
{
  "protocol": 1,
  "type": "progress",
  "operationId": "01J...",
  "sequence": 8,
  "timestamp": "2026-07-27T14:10:00.123+08:00",
  "stage": "dependencies.sync",
  "status": "running",
  "current": 18,
  "total": 42,
  "percent": 42.86,
  "message": "正在安装 Python 依赖"
}
```

`progress.status` 在协议版本 1 中只能是 `pending`、`running`、`succeeded`、`skipped`、`failed` 或 `cancelled`。`current`、`total` 和 `percent` 只在总量可知时出现，Electron 不能假定每个阶段都有百分比。

协议版本 1 的 `stage` 标识固定如下；没有子步骤的命令使用最接近的上层标识：

| 领域 | stage |
| --- | --- |
| Runtime | `runtime.handshake`、`doctor`、`bootstrap`、`repair`、`cleanup` |
| uv | `uv.check`、`uv.download`、`uv.verify` |
| Git | `workspace.check`、`workspace.clone`、`workspace.verify`、`workspace.swap`、`workspace.cleanup` |
| Python | `python.check`、`python.install` |
| 主环境 | `dependencies.check`、`dependencies.sync`、`dependencies.rebuild` |
| 后端 | `backend.spawn`、`backend.health`、`backend.run`、`backend.restart`、`backend.shutdown`、`backend.cleanup` |

新增 stage 可以追加，但既有标识不得改名。Electron 对未知 stage 使用通用进行中/失败展示，不能拒绝整个协议。

### 状态事件全集

`state` 事件表示产品运行时生命周期，而不是某条日志的严重级别：

```json
{
  "protocol": 1,
  "type": "state",
  "operationId": "01J...",
  "sequence": 10,
  "timestamp": "2026-07-27T14:10:04.000+08:00",
  "stage": "dependencies.sync",
  "status": "syncing_environment",
  "message": "正在精确同步 Python 环境",
  "details": {}
}
```

协议版本 1 的 `state.status` 取值固定如下：

| 状态 | 含义 | 是否允许启动后端 |
| --- | --- | --- |
| `uninitialized` | 尚无可验证的受管工作区或环境 | 否 |
| `preparing_uv` | 正在准备固定版本 uv | 否 |
| `syncing_repository` | 正在解析、克隆、校验或替换 Git 仓库 | 否 |
| `preparing_python` | 正在校验或安装精确 Python | 否 |
| `syncing_environment` | 正在执行锁定依赖同步 | 否 |
| `ready_to_start` | 仓库、Python 和主项目环境已就绪 | 是 |
| `starting_backend` | 已创建后端进程，正在等待健康检查 | 不适用 |
| `running` | 后端身份校验和连续健康检查均通过 | 已运行 |
| `restarting` | 后端异常退出后正在执行唯一一次自动重启 | 不适用 |
| `stopping_backend` | 正在请求优雅关闭或等待进程退出 | 不适用 |
| `environment_broken` | Git 源码有效，但当前 revision 的 Python 主环境尚未证明可用或已失败 | 否 |
| `backend_failed` | 后端启动、健康检查、唯一一次重启、关闭或进程树清理失败 | 否 |
| `stopped` | 后端已退出且受管进程树已清理 | 否 |

主准备路径固定为：

```text
uninitialized
  -> preparing_uv
  -> syncing_repository
  -> preparing_python
  -> syncing_environment
  -> ready_to_start
```

`uv sync` 失败时进入可持久化的 `environment_broken`。环境准备除首次 bootstrap 主路径外，还允许从 `environment_broken` 执行 repair 或依赖重试、从 `ready_to_start` 执行幂等 bootstrap 或显式依赖同步。Git revision 一旦实际替换，旧主环境立即失效并持久化 `environment_broken/repository_changed`，即使独立 `workspace sync` 的 Git 操作成功；只有目标 revision 的锁定依赖同步成功才能恢复 `ready_to_start`。确认同一 active revision 且未执行替换的 no-op sync 保留原稳定状态。其他受管变更失败必须进入 `environment_broken`，变更前失败只能回到该操作开始时的稳定状态。

后端正常路径固定为 `ready_to_start -> starting_backend -> running -> stopping_backend -> stopped`。首次意外退出使用 `running -> restarting -> running`，进入 `restarting` 即消耗唯一自动重启次数；第二次意外退出进入 `backend_failed`。启动、重启期间可以转入 `stopping_backend` 响应关闭或取消，关闭后无法确认进程树清空时进入 `backend_failed`。完整迁移表、强类型字段和只读命令 API 边界见 [T1.3 stage 与生命周期状态机设计](./设计-T1.3-生命周期状态机.md)。

插件初始化和插件降级属于 Python 后端内部状态，不进入 Runtime 生命周期状态机。

一次性检查命令不改变持久化生命周期状态，只输出 `progress` 和最终 `result`。任何状态跳转都必须输出事件；Electron 不根据缺失事件自行推测中间状态。

`warning` 与 `error` 使用相同的 `code`、`stage`、`message`、`retryable`、`remediation` 和 `details` 字段；区别是 warning 不会终止顶层操作。所有生命周期状态都会写入操作日志，但只有 `environment_broken`、`ready_to_start` 和最近一次成功的版本/Commit 需要跨 Runtime 进程持久化。

### 错误契约

```json
{
  "protocol": 1,
  "type": "error",
  "operationId": "01J...",
  "sequence": 9,
  "timestamp": "2026-07-27T14:10:03.000+08:00",
  "code": "DEPENDENCY_SYNC_FAILED",
  "stage": "dependencies.sync",
  "message": "Python 依赖安装失败",
  "retryable": true,
  "remediation": ["retry-sync", "rebuild-environment", "open-log"],
  "details": {
    "package": "example-package",
    "exitCode": 1
  }
}
```

Electron 根据 `code`、`stage` 和 `retryable` 决定是否提供重试、更换镜像或查看日志等操作，不能解析错误文案来判断业务状态。

`remediation` 只使用以下稳定动作标识：`retry`、`retry-sync`、`retry-other-mirror`、`rebuild-environment`、`stop-backend`、`restart-backend`、`select-version`、`update-desktop`、`run-doctor`、`cleanup`、`open-log`、`contact-support`。Electron 可以按产品能力隐藏某个动作，但不能改变其语义。

`retryable=true` 只表示在输入和安全边界不变时允许重试，不表示 Runtime 自动无限重试。镜像内的有限网络重试由 Runtime 自己完成；事件中的重试动作表示整条顶层操作可以由用户或 Electron 再次发起。

### 最终结果契约

每个成功启动的 Runtime 顶层命令都必须输出且只输出一个最终 `result` 事件：

```json
{
  "protocol": 1,
  "type": "result",
  "operationId": "01J...",
  "sequence": 20,
  "timestamp": "2026-07-27T14:10:15.000+08:00",
  "success": false,
  "code": "DEPENDENCY_SYNC_FAILED",
  "stage": "dependencies.sync",
  "status": "environment_broken",
  "message": "Python 依赖同步失败",
  "retryable": true,
  "remediation": ["retry-sync", "rebuild-environment", "open-log"],
  "details": {
    "logPath": "D:\\AUTO-MAS\\logs\\runtime\\dependencies-20260727.log"
  }
}
```

成功结果的 `code` 固定为 `OK`。失败结果必须重复主错误的 `code`、`stage`、`retryable` 和 `remediation`，便于调用方只消费终点事件。`warning` 不会把成功结果改为失败，但必须在 `result.details.warnings` 中汇总。发送 `result` 后不得再发送任何协议事件。

### 标准输入控制

耗时操作可以接收取消命令：

```json
{"protocol":1,"command":"cancel","commandId":"01J..."}
```

`backend supervise` 额外接收：

```json
{"protocol":1,"command":"shutdown","commandId":"01J..."}
{"protocol":1,"command":"status","commandId":"01J..."}
```

首个协议版本不提供多请求复用。一个 Runtime 进程只执行一个顶层操作。

Runtime 接受控制命令后，在下一条相关 `state`、`warning` 或最终 `result` 的 `details.controlCommandId` 中回显 `commandId`。`status` 只返回当前状态快照，不改变状态；重复 `shutdown` 和 `cancel` 必须幂等。无法解析或不适用于当前命令的控制输入产生 `INVALID_CONTROL_COMMAND` warning，但不允许因此遗留正在运行的后端或破坏当前更新事务。

### 已确认决策

1. 对外提供编排命令和可单步执行命令；
2. 正式版后端源码全部通过 Git 更新，不生成后端更新压缩包；
3. 每次操作启动一个独立 Runtime 进程，不实现通用常驻 RPC 服务。

## 纯 Git 后端更新

Python 后端源码在正式安装模式和开发模式下都来自 Git，不生成后端更新压缩包。正式安装模式的仓库由 Runtime 完全管理，本地代码修改、未跟踪文件、本地分支和旧 Git 对象都不属于需要保留的数据。

本方案不使用 A/B Slot，不在同一台机器上长期维护多个可运行后端版本，也不在旧工作区上执行 Merge、Pull 或 Stash。

### 目录模型

```text
AUTO-MAS/                       # 根目录，后端工作目录
├── repo/                       # 唯一正式后端仓库和运行目录
├── repo.update-<operationId>/  # 仅更新期间存在的临时浅克隆
├── runtime-state/
│   ├── backend.json
│   ├── mutation.json
│   ├── update.json
│   ├── environment.json
│   ├── <StateFiles 私有 guard>    # 每 kind 固定、持久的协调 leaf
│   └── <StateFiles 私有事务对象> # 固定 intent 与随机 staging/temp/backup，仅事务或恢复现场存在
├── runtime/
│   ├── tools/uv/<version>/
│   ├── environment/python/
│   ├── environment/venv/
│   └── cache/
│       ├── uv/
│       ├── downloads/
│       └── build/
├── config/                     # 以下均为受保护持久数据
├── data/
├── history/
├── script/
├── debug/
├── plugins/
└── logs/runtime/
```

后端始终从固定的 `repo` 路径启动，注意需设定其工作目录为项目根目录。临时更新目录只用于保证网络失败或克隆中断不会破坏当前仓库，完成替换后必须删除；它不是第二个长期运行 Slot。

用户配置、数据库、日志、下载内容和其他需要跨版本保留的数据必须位于
`repo` 外部。上图中的根级持久目录是 `user-data` 概念的实际布局，不再额外
创建名为 `user-data/` 的聚合目录。更新替换 `repo` 时，Runtime 不承诺保留
其中的任何本地修改或未跟踪文件。

`runtime-state/` 中只有四个 JSON 文件名是稳定业务路径。StateFiles 在已经固定的
`runtime-state` 目录 handle 下，为每个 kind 私有管理一个固定、持久的普通 guard leaf
`G`；它是 shared/exclusive namespace gate，不是业务状态，cleanup 永不删除。固定 sealed
intent `I`、随机 intent staging `J`、payload temp `T` 和 backup `B` 则只在写事务或
崩溃恢复现场存在。`G/I/J/T/B` 都不是 `config.Layout` 的稳定 getter，也不向 state 包
或其他业务包暴露；POSIX unlink 能力探测使用的随机 create-exclusive probe leaf 同样
完全私有，只能由本次精确 handle 收口。尚未由 sealed intent 引用的孤立 `J/T` 只能
报告，自动流程不得按名称前缀猜测并删除。

### 版本到分支的映射

目标发布分支由目标版本决定，例如：

```text
v5.3.0 -> release/v5.3.0
v5.4.0-beta.1 -> release/v5.4.0-beta.1
v5.2.0-withplugin.0.0.1 -> release/v5.2.0-withplugin.0.0.1
```

Runtime 只接收目标版本，不接收调用方提供的分支和 Commit：

```powershell
& ".\auto-mas-runtime.exe" workspace sync --version "v5.4.0-beta.1"
```

Runtime 保留版本字符串中的 `v`，并根据内部固定模板生成 `release/<完整版本>`。考虑到已有发布版本不全是严格 SemVer，校验规则采用安全标识符而不是强制 SemVer：必须以 `v` 开头，只允许 ASCII 字母、数字、点、连字符和下划线，限制总长度，禁止斜杠、反斜杠、空白、`..`、`@{` 和结尾点。分支模板属于 Runtime 协议的一部分，不能由 Electron 传入任意 Ref。

### 分支信任模型（不使用版本索引）

按 2026-07-27 用户决策，本方案不实现签名版本索引与 Commit 钉扎（原方案见本文档 Git 历史）。版本到分支的信任建立在三点之上：

1. 传输安全：Git 克隆与所有下载均走 HTTPS，默认禁止关闭 TLS 校验；
2. 发布纪律：发布分支和同名 Tag 在发布时必须指向同一 Commit，发布后视为不可变；已发布版本需要修复时必须发布新版本，不允许移动原发布分支或 Tag；
3. 结果校验：克隆完成后校验仓库版本文件等于目标版本。

Runtime 解析目标的流程为：

1. 校验版本字符串符合安全标识符规则；
2. 按内部模板生成 `release/<完整版本>` 分支名；
3. 浅克隆该分支；
4. 校验远端来源属于配置源列表、分支正确、仓库版本文件等于目标版本。

已知放弃的保护：若发布分支被误移动或镜像内容被篡改，Runtime 仅能依靠版本文件校验兜底，无法发现同版本号下的内容替换。该剩余风险已由用户确认接受。

Runtime 不通过枚举和比较全部远端发布分支来猜测目标版本，也不自行判断哪个产品版本“最新”。版本选择由前端更新流程完成，Runtime 只负责把明确版本解析为后端发布分支。

### 更新方式

首版不实现后台预下载或跨 Runtime 进程的 `prepare/apply` 事务。Electron 是停机与更新编排者：

1. Electron 向当前 `backend supervise` 的标准输入发送 `shutdown`；
2. Electron 等待该监督进程输出最终 `result` 并退出；
3. Electron 调用 `bootstrap --version <目标版本>`；
4. `workspace sync` 取得 `mutation` 锁并确认 `backend` Mutex 未被持有，否则返回 `BACKEND_STILL_RUNNING`；
5. Runtime 校验版本字符串并按内部模板生成目标发布分支；
6. Runtime 创建唯一操作 ID 和临时目录；
7. 使用内置 Go Git 能力按单分支、深度 1、无 Tags 浅克隆；
8. 校验远端来源、分支和仓库版本文件；
9. 克隆或校验失败时删除临时目录，继续保留当前 `repo`；
10. 确认没有进程占用正式仓库；
11. 将当前 `repo` 重命名为同一事务的旧目录；
12. 将临时仓库重命名为固定的 `repo`；
13. 删除旧仓库，从而舍弃代码修改、未跟踪文件和旧 `.git`；
14. 若发生实际替换，原子持久化 `environment_broken/repository_changed`，保留上次真正依赖同步成功的 revision；状态写失败时返回 `STATE_WRITE_FAILED` 并保留 update transaction；
15. 实际 swap 的 `workspace sync` 以 `success=true`、
    `status=environment_broken` 输出最终版本、分支和 Commit；同 revision no-op
    以 `success=true` 返回经 `RollbackPreparation` 恢复后的原稳定状态；
16. `bootstrap` 继续准备 Python 并同步主项目依赖；
17. `bootstrap` 成功退出后，Electron 启动新的 `backend supervise`。

`workspace sync` 只负责 Git 工作区，不停止或启动后端，也不同步主项目依赖。它不能尝试向另一个 Runtime 进程的标准输入写入控制命令。

逻辑流程：

```text
目标版本
    │
    ▼
Electron 停止当前 backend supervise
    │
    ▼
按内部模板解析目标发布分支
    │
    ▼
临时目录中单分支、Depth 1、NoTags 克隆
    │
    ▼
校验仓库版本文件
    │
    ▼
整体替换固定 repo 目录
    │
    ▼
删除旧仓库，workspace sync 成功
    │
    ▼
bootstrap 同步主项目环境
    │
    ▼
Electron 启动新的 backend supervise
```

Runtime 不能先删除当前仓库再开始网络下载。旧仓库可以无条件舍弃，但必须等新仓库完整克隆并通过静态校验后再替换，避免普通网络故障让安装立即不可用。

### 本地修改处理

正式安装模式不把本地工作区视为用户数据：

1. 不尝试 Merge；
2. 不创建 Stash；
3. 不保存本地提交或本地分支；
4. 不询问是否覆盖跟踪文件；
5. 不保留未跟踪文件；
6. 替换成功后删除整个旧仓库及其 `.git`。

因此，用户可持久化内容必须通过明确的共享数据目录、配置目录或插件数据目录保存，不能依赖把文件放进受管仓库。

### 失败处理

失败分为两个阶段：

1. 替换前失败：删除临时仓库，继续使用原 `repo`；
2. 替换后：Git 仓库保持目标版本，并在 swap 生效后立即标记
   `environment_broken/repository_changed`；若后续准备失败则更新为
   `operation_failed`，由上层提供重试同步、重建环境或选择旧版本重新更新等操作。

实际 swap 与环境状态写入共同构成 `workspace sync` 的成功边界。swap 后状态写入失败时
返回 `STATE_WRITE_FAILED` 并保留 `update.json`，不得报告成功；下次 T4.5 恢复确认唯一
active repo 后必须补写 repository_changed。确认同一 active revision 且没有执行 swap 的
no-op sync 不改写环境状态。

本方案不实现自动 A/B 回滚。需要降级时，调用方传入旧版本，Runtime 内部生成对应发布分支，并按同一更新流程整体替换当前仓库。

### 正式安装模式与开发模式

正式安装模式使用 Runtime 管理的固定仓库：

```powershell
& ".\auto-mas-runtime.exe" backend supervise --mode managed
```

Runtime 可以无条件替换该仓库。

开发调试使用开发者明确指定的源码目录：

```powershell
& ".\auto-mas-runtime.exe" backend supervise `
  --mode development `
  --repo "<AUTO-MAS 源码目录的绝对路径>"
```

开发模式默认不自动更新、不清理 `.git`、不舍弃本地修改。它只检查显式源码目录、入口文件、Runtime 管理的 uv、进程启动和健康协议，不要求 managed 工作区、发布版本、锁文件、受管 venv 或持久化环境状态；具体边界见 [协议 v1 契约补充](./契约补充-v1.md#c5development-模式检查边界)。这样正式版的确定性更新策略不会影响开发者 Debug。

## Git 仓库体积与发布分支

### 客户端仓库

远端存在多个发布分支，不等于客户端需要下载所有发布分支。客户端 `.git` 体积增长主要取决于实际获取和保留的对象。

Runtime 每次只对目标版本分支执行一次全新的浅克隆：

- `SingleBranch = true`；
- `Depth = 1`；
- `Tags = NoTags`；
- 不使用会抓取全部 `release/*` 的默认 RefSpec；
- 更新后删除旧仓库和旧 `.git`。

因此，客户端不会因为连续安装多个版本而在同一个 `.git` 中累积所有历史，也不需要依赖长期 Git GC 来维持安装体积。

### 发布分支

当前发布模型仍允许一个版本对应一个发布分支。Runtime 根据版本精确选择分支，不要求先迁移现有发布流程。

但分支本身只是指向提交的引用，不会为每个分支复制一份完整历史。中央仓库或开发者完整克隆的 `.git` 变大，主要还受到以下因素影响：

1. 不同发布分支保留的独有提交；
2. 历史中的二进制、模型、压缩包和其他大文件；
3. Tags 和其他引用继续使历史对象可达；
4. 本地重复或过期的 pack；
5. 完整克隆获取了所有长期发布引用。

删除发布分支之前必须检查是否存在未被 Tag 或其他分支覆盖的独有提交。仅删除分支引用也不一定明显缩小仓库，因为仍被 Tag 或其他引用指向的对象不会被清理。

### 历史治理边界

仓库历史重写、旧发布分支清理和大型二进制治理是独立项目，不由 Runtime 自动执行。使用 `git filter-repo` 等工具会改变提交 ID，并影响分支、Tags、Fork 和开发者本地仓库，必须单独设计备份、迁移窗口和协作者通知。

### 已确认决策

1. Python 后端正式更新全部通过 Git，不生成后端更新压缩包；
2. 目标发布分支根据目标版本确定；
3. Runtime 只接收 `--version`，内部按固定模板生成发布分支；
4. Runtime 每次在临时目录中对目标分支执行单分支、Depth 1、NoTags 克隆；
5. 新仓库校验完成后整体替换固定 `repo`，旧代码、本地修改、未跟踪文件和旧 `.git` 全部舍弃；
6. 不执行 Merge、Pull、Stash 或多版本分支切换；
7. 不实现 A/B Slot；需要降级时重新获取旧版本分支；
8. 正式安装模式仓库由 Runtime 完全管理，开发模式仓库默认不自动修改；
9. 用户数据必须与受管 Git 仓库分离；
10. 发布分支与同名 Tag 在发布后不可移动；
11. 发布分支和历史大文件治理作为独立工作处理。

## uv 环境与后端运行

Runtime 不自行实现 Python 版本解析、虚拟环境创建或依赖安装，也不直接调用 Python 和 pip。Go 只负责 bootstrap、调用和监督 `uv.exe`，其余 Python 工具链能力全部交给 uv：

```text
AUTO-MAS-Runtime
        │
        ├── 下载并校验 uv.exe
        ├── uv python install
        ├── uv sync
        └── uv run main.py
                    │
                    ▼
              Python 后端进程
```

### 禁止与允许的调用

Runtime 禁止直接执行：

```text
python.exe
python main.py
pip.exe
pip install
python -m pip
.venv\Scripts\python.exe
```

Runtime 允许执行：

```text
uv.exe --version
uv.exe python ...
uv.exe sync ...
uv.exe run ...
```

项目主环境必须使用项目模式的 `uv sync`，不能退回 `uv pip install -r requirements.txt`。Runtime 不执行 `uv pip`；Python 后端可以使用 Runtime 注入的固定 uv 路径管理独立的插件目标目录。

### uv bootstrap

uv 是唯一需要由 Go 自行准备的 Python 工具。Runtime 不通过 pip 安装 uv，也不执行在线 PowerShell 安装脚本。

uv 版本由 Runtime 固定。发布分支不能要求 Runtime 临时自升级到未经当前 Runtime 验证的 uv 版本；如果目标分支需要更高的 uv 能力，应先通过前端发布流程升级 Runtime。

推荐目录：

```text
runtime/
├── tools/
│   └── uv/
│       └── <version>/
│           └── uv.exe
├── environment/
│   ├── python/
│   └── venv/
└── cache/
    └── uv/
```

bootstrap 流程：

1. Runtime 从配置中读取固定的 uv 版本；
2. 按镜像优先级下载对应的 Windows uv 发布文件；
3. 先写入 `.part` 临时文件；
4. 校验文件大小和 SHA-256；
5. 解压到版本化临时目录；
6. 原子移动到正式工具目录；
7. 执行 `uv.exe --version`；
8. 只有实际版本与目标版本一致时才标记 uv 可用。

Runtime 不调用 `uv self update`。uv 升级由 Runtime 版本策略控制，避免用户机器上的 uv 在未经过兼容验证时自行变化。

### uv 受管 Python

Python 由 uv 下载和管理。精确版本由目标发布分支中的 `.python-version` 提供，例如：

```text
uv.exe python install 3.12.10 `
  --managed-python `
  --install-dir <runtime>/environment/python `
  --no-bin `
  --no-registry
```

正式版必须固定 Python 补丁版本，不能只请求未固定的 `3.12` 后长期依赖“当时最新”的解析结果。`pyproject.toml` 继续使用 `requires-python` 声明兼容范围，Runtime 在安装和启动前同时检查：

1. `.python-version` 能否被当前固定版本的 uv 识别和安装；
2. 精确 Python 版本是否满足 `pyproject.toml` 的 `requires-python`；
3. 当前 uv 是否支持该 Python 分发版本；
4. 已安装的 uv 受管 Python 是否与目标精确版本一致。

任一检查失败都返回明确的兼容性错误，不允许回退到系统 Python。

Runtime 为每个 uv 子进程显式设置：

```text
UV_PYTHON_INSTALL_DIR=<runtime>/environment/python
UV_CACHE_DIR=<runtime>/cache/uv
UV_PROJECT_ENVIRONMENT=<mode-specific-environment>
UV_MANAGED_PYTHON=1
UV_NO_MODIFY_PATH=1
UV_PYTHON_INSTALL_BIN=0
UV_COLOR=never
UV_NO_PROGRESS=1
```

`UV_PROJECT_ENVIRONMENT` 在 managed 命令中取 `<runtime>/environment/venv`，在 `backend supervise --mode development` 中取开发仓库现有的 `<repo>/.venv`。development 模式不创建、同步或重建该环境。

这些变量只注入 Runtime 创建的 uv 子进程，不修改用户级环境变量、PATH 或 Windows Python 注册表。`--no-bin`、`--no-registry` 和 `UV_PYTHON_INSTALL_BIN=0` 共同避免受管 Python 向用户环境暴露额外入口。Python 下载镜像和包索引镜像也通过 uv 参数或 uv 环境变量传入。

### 项目依赖同步

后端 Git 仓库替换完成后，Runtime 执行：

```text
uv.exe sync `
  --project <repo> `
  --python <fixed-python-version> `
  --locked `
  --no-default-groups `
  --no-install-workspace
```

该命令保持当前主环境边界：

1. 只同步根项目运行依赖；
2. 不安装默认开发依赖组；
3. 不把根项目及 workspace 成员本身安装进主环境；
4. 仍按 `uv.lock` 解析 workspace source 元数据，避免运行参数与锁文件生成方式不一致；
5. 依赖结果必须与发布分支中的 `uv.lock` 一致；
6. 不允许正式安装过程隐式生成或修改锁文件。

正式 Runtime 不得禁用锁文件中的 sources。当前锁文件包含 workspace/editable source 关系，强行忽略 sources 会让用户机器的解析语义与 CI 生成锁文件时不一致。运行环境通过 `--no-install-workspace` 排除源码包本身，锁文件一致性则由发布 CI 的 `uv lock --check` 保证。

依赖同步是后端启动的独立前置阶段。`uv sync` 失败时：

1. 不回滚已经替换成功的 Git 源码；
2. 将运行环境状态原子标记为 `environment_broken`；
3. 返回 `DEPENDENCY_SYNC_FAILED`，不能继续尝试启动后端；
4. Electron 启动界面提供“重试同步”和“重建环境”；
5. “重试同步”保留现有受管环境并重新执行精确 `uv sync --locked`；
6. “重建环境”删除受管 venv，随后重新执行 `uv sync --locked`；
7. 两种操作都不能修改 Git 源码、锁文件或用户数据。

`environment_broken` 必须包含目标版本、分支、Commit、reason、stage、退出码和日志路径。
reason 固定为 `repository_changed` 或 `operation_failed`。前者只表示实际 Git swap 后旧
环境失效，固定 `stage=workspace.swap`、`exitCode=0`，Python/uv 版本允许为空表示 unknown；
后者保存具体失败叶子阶段与非零退出码。active repo 已确认但尚未经过
`python.check` 的结构化 `.python-version` 解析时（首版为 `workspace.cleanup` 或
`python.check`），Python/uv 版本都允许为空表示 unknown；进入 `python.install` 或依赖阶段
后必须保存精确工具版本。`lastSuccessful` 始终保留上次真正完成锁定依赖同步的 revision，
只有目标 revision 的 `uv sync --locked` 成功后才能清除此状态并更新 lastSuccessful。

### 后端启动

Runtime 在依赖同步成功后执行：

```text
uv.exe run `
  --project <repo> `
  --no-sync `
  main.py
```

使用 `--no-sync` 的原因：

1. 环境已经由独立的 `uv sync --locked` 阶段准备；
2. 后端启动阶段不得隐式修改环境或访问包索引；
3. 依赖错误和应用启动错误可以使用不同错误码；
4. Electron 可以准确展示当前失败阶段。

Runtime 启动并监督的是 uv 进程及其 Python 子进程树：

```text
AUTO-MAS-Runtime
    └── Windows Job Object
        └── uv.exe run --no-sync main.py
            └── python.exe
```

Runtime 创建带 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 的 Windows Job Object。为避免 uv 在被纳管前已经生成 Python 子进程，必须使用 `CREATE_SUSPENDED` 创建 uv 主进程，先把它分配到 Job Object，再恢复主线程。后续 Python 子进程继承该 Job，形成唯一受管进程树。Python 的 stdout/stderr 通过 `uv run` 的管道进入 Runtime，并继续按照既定 `log` 事件协议传给 Electron。

### 插件调用 uv 的边界

Runtime 启动后端时通过 `AUTO_MAS_UV_EXE` 注入固定且已校验的 `uv.exe` 路径。Python 后端的 `PluginManager` 自行决定何时安装、更新或卸载插件包，并自行调用该 uv 执行 `uv pip install/uninstall --target`。

Runtime 不提供插件 CLI，不读取插件声明，不解析插件依赖，不维护插件安装清单，也不判断核心插件、可选插件或兼容性。插件目标目录必须与主项目 venv 分离，避免主项目下一次精确 `uv sync` 删除插件依赖。后端不得自行下载或升级 uv；注入路径不可用时应通过后端日志和健康状态报告初始化失败。

### Go 侧 uv 执行器

Go 侧提供唯一的 uv 进程封装，不允许环境、主项目依赖和后端监督模块各自拼装 `exec.Command`：

```go
type UVRunner struct {
    Executable       string
    ProjectDir       string
    PythonInstallDir string
    ProjectEnvDir    string
    CacheDir         string
}

type UVResult struct {
    ExitCode int
    Stdout   string
    Stderr   string
    Duration time.Duration
}
```

`ProjectEnvDir` 在 managed 命令中指向 Runtime 受管 venv；在 `backend supervise --mode development` 中固定指向开发仓库现有的 `<repo>/.venv`。development 启动不创建或同步该目录，缺失时直接失败。

统一执行入口负责：

1. 使用 `exec.CommandContext` 和参数数组调用，不经过 Shell；
2. 设置工作目录和受控环境变量；
3. 捕获并逐行转发 stdout/stderr；
4. 应用超时、取消和镜像重试策略；
5. 以挂起状态创建长驻 `uv run`，分配到启用 `KILL_ON_JOB_CLOSE` 的 Windows Job Object 后再恢复；
6. 将退出码映射为 Runtime 结构化错误；
7. 保留完整原始日志，不通过解析 uv 文案判断操作成功；
8. 记录 uv 版本、Python 版本、项目分支和 Commit。

一次性 `uv python install`、`uv sync` 和 `uv pip` 命令执行完即退出。只有 `uv run main.py` 由 `backend supervise` 长期持有。

### 已确认决策

1. 除 uv 自身 bootstrap 外，所有 Python 环境操作都通过 uv；
2. Runtime 不直接调用 Python、pip 或虚拟环境解释器；
3. uv 使用固定版本，由 Go 下载、校验和管理；
4. Python 精确版本来自发布分支的 `.python-version`，由 `uv python install` 管理；
5. 项目主环境由 `uv sync --locked` 精确同步；
6. 后端由 `uv run --no-sync main.py` 启动；
7. Runtime 通过 `AUTO_MAS_UV_EXE` 向 Python 后端提供固定 uv 路径，但不管理插件依赖；
8. Runtime 统一捕获自己启动的 uv 和 Python 的 stdout/stderr；
9. `.python-version` 和 `uv.lock` 纳入 Git 的工作以 TODO 记录，完成前不能宣称正式环境可复现；
10. 正式安装模式使用 Runtime 受管 venv；开发模式只消费开发仓库现有的 `<repo>/.venv`，两者都通过 uv 运行；
11. `uv sync` 失败不回滚 Git 源码，状态进入 `environment_broken`，由重试同步或重建环境修复。

## 镜像与网络策略

系统涉及四类网络源，不能用一个通用镜像地址混合替代：

| 类型 | 用途 | 主要调用方 |
| --- | --- | --- |
| Git 仓库源 | 读取发布分支和浅克隆后端源码 | Go Git |
| uv 二进制源 | bootstrap 固定版本 `uv.exe` | Runtime 下载器 |
| Python 分发源 | `uv python install` 下载受管 Python | uv |
| Python 包索引 | Runtime 的主项目 `uv sync`；Python 后端的插件包安装 | Runtime 与 Python 后端分别调用 uv |

前三类源和主项目依赖同步由 Runtime 管理；Python 后端独立管理插件安装对 Python 包索引的使用。两者可以读取同一份用户镜像配置，但重试、失败状态和操作日志分别归各自所有者管理。轮换规则：

1. 用户明确选择的源优先；
2. 未指定时按项目配置顺序尝试；
3. 单个源只执行有限次数重试；
4. 连接超时、读取超时、HTTP 状态和完整性失败分别记录；
5. 完整性校验失败的源本次操作不再重试；
6. 所有镜像失败后再尝试官方源，除非用户选择离线或仅镜像模式；
7. 切换源不能改变目标版本及其派生发布分支、uv 版本、Python 版本或锁文件；
8. 默认禁止关闭 TLS 校验，不自动使用 `--allow-insecure-host`。

按 D6，Runtime 不在换源前解析或钉扎 Git Commit。不同源可能因同步延迟暂时
指向不同 Commit；每次克隆后必须校验发布分支和仓库版本文件，并记录最终实际
Commit。镜像只改变下载位置，不能把请求改写为其他版本或分支。

Runtime 对自己负责的网络操作只根据退出码和自身网络状态机判断成功，不解析 uv 的自然语言输出驱动业务分支。Python 后端同样不能让 Runtime 解析插件安装文案；原始输出仍通过后端日志转发和落盘。

## 插件环境职责边界

插件系统完全属于 Python 后端。当前后端已有 `PluginManager`、插件 API 和 uv 调用封装，Runtime 不复制这些策略。

### Runtime 只负责

1. 准备并校验固定版本的 `uv.exe`；
2. 启动后端时注入 `AUTO_MAS_UV_EXE`；
3. 把后端工作目录设为 AUTO-MAS 项目根目录；
4. 在 Git 更新、repair 和 cleanup 中保护根目录下的插件运行包、插件配置和插件数据；
5. 转发 Python 后端产生的插件初始化日志和健康状态。

### Python 后端负责

1. 解析插件声明和包规格；
2. 安装、更新、卸载插件包及其依赖；
3. 管理 `plugins/pypi/site-packages` 和插件安装状态；
4. 选择插件包索引、执行镜像重试并处理依赖冲突；
5. 判断系统插件、必需插件和可选插件；
6. 决定插件失败是阻止初始化、禁用插件还是降级运行；
7. 通过插件 API、WebSocket、健康状态和日志向前端暴露结果。

推荐的调用关系：

```text
AUTO-MAS-Runtime
    ├── 管理 uv.exe、Python、主项目 venv
    ├── uv sync --locked
    └── AUTO_MAS_UV_EXE=<runtime-managed-uv>
              │
              ▼
        Python PluginManager
            └── uv pip ... --target plugins/pypi/site-packages
```

Runtime 管理 uv 工具本身，不等于管理插件依赖。Runtime 不读取插件安装清单，不执行插件依赖同步，不提供任何插件同步或重建命令，也不产生插件专用状态或错误码。

插件依赖失败不进入 `environment_broken`，因为主项目 venv 仍可能完全有效。Python 后端负责生成插件域错误并决定是否继续初始化；Runtime 只根据后端进程退出和 `/api/core/health` 的通用结果输出后端启动错误，同时保留完整 stdout/stderr。需要安装、修复或删除插件时，Electron/Vue 通过 Python 插件 API 操作，不通过 Runtime CLI。

## 后端健康检查与关闭契约

Runtime 复用现有后端核心接口，不新增语义重复的 `/api/runtime/*` 路径：

```http
GET /api/core/health
POST /api/core/close
```

协议 v1 固定连接 `127.0.0.1:36163`，并在就绪事件中返回无结尾斜杠的 `baseUrl=http://127.0.0.1:36163`；v1 不提供动态端口参数。具体地址规则见 [协议 v1 契约补充](./契约补充-v1.md#c1固定后端端口与地址)。

managed 模式创建后端进程前必须读取 `environment.json` 并核对 active repo：
状态必须为 `ready_to_start`，且 `lastSuccessful.version/commit` 必须分别精确等于仓库版本
文件与 HEAD。状态缺失、broken 或任一 revision 不一致都返回
`ENVIRONMENT_BROKEN`，在 details 保留具体 state/read 原因，并且不得创建 uv/Python 进程。
这是 swap 后状态持久化之外的纵深防线；development 模式按 C5 跳过该受管环境校验。

`GET /api/core/health` 在保留现有字段的基础上增量扩展：

```json
{
  "ready": true,
  "backgroundStatus": "ready",
  "backgroundError": null,
  "protocol": 1,
  "version": "v5.4.0-beta.1",
  "commit": "0123456789abcdef0123456789abcdef01234567"
}
```

Runtime 通过 `AUTO_MAS_RUNTIME_PROTOCOL`、`AUTO_MAS_EXPECTED_VERSION` 和 `AUTO_MAS_EXPECTED_COMMIT` 把预期身份注入 `uv run`，并通过 `AUTO_MAS_SUPERVISED=1` 标记受监督进程。managed 模式后端健康接口回显注入值；development 模式只强制核对协议，不以版本或 Commit 拒绝脏工作区。具体字段和模式矩阵见 [协议 v1 契约补充](./契约补充-v1.md#c2身份注入与-health-回显)。Runtime 不能只检查端口已监听，还必须核对：

1. HTTP 状态为 `200`；
2. `ready` 为 `true`；
3. `backgroundStatus` 为 `ready`；
4. `backgroundError` 为空；
5. 协议版本兼容；
6. 后端版本等于目标完整版本；
7. Commit 等于当前受管仓库 HEAD；
8. uv 子进程和 Python 子进程仍处于受管 Job Object；
9. 以上结果连续成功两次。

首版时间参数：

| 参数 | 默认值 |
| --- | ---: |
| 总启动超时 | 60 秒 |
| 健康检查间隔 | 500 毫秒 |
| 单次请求超时 | 2 秒 |
| 连续成功次数 | 2 次 |

后端初始化期间允许接口尚不可连接，或返回 `200` 且 `backgroundStatus=starting` / `running`。Runtime 把它视为尚未就绪而非立即失败；`backgroundStatus=failed`、`backgroundError` 非空、身份不匹配、进程提前退出或超过总超时才结束启动操作。失败字面量与其他状态的完整定义见 [协议 v1 契约补充](./契约补充-v1.md#c3后台初始化状态字面量)。

收到 stdin `shutdown` 后，Runtime 调用 `POST /api/core/close` 请求优雅关闭，然后等待受管进程退出。`AUTO_MAS_SUPERVISED=1` 的优先级高于 `AUTO_MAS_DEV=1`，受监督 development 后端也必须真实退出。接口无法连接、返回失败或超过关闭超时时，Runtime 关闭 Job Object 作为兜底；只要确认进程树已经清空，就输出 `BACKEND_FORCE_TERMINATED` 警告并正常完成关闭。Electron 不直接调用该 HTTP 接口，也不直接终止 Python。

这两个接口是 Runtime 与 Python 后端的共同开发契约。任一侧修改字段、语义或协议版本时必须同步更新另一侧及对应测试。后端 schema 变更后通过 OpenAPI 生成器更新前端客户端，不能手工修改生成文件。

## 后端异常重启

`backend supervise` 每次生命周期最多自动重启一次：

1. 首次成功进入 `running` 后发生非预期退出，等待 2 秒后重新执行 `uv run --no-sync main.py`；
2. 重启前重新检查 `environment_broken`、仓库 Commit 和项目环境；
3. 第二次启动仍失败或再次非预期退出时，不再自动重启；
4. Runtime 输出最终失败结果和两次启动的完整日志；
5. Electron 展示“重试启动”和“重建环境”等操作。

用户主动关闭、Electron 请求 shutdown、更新流程要求停机、取消操作和 Runtime 正常退出都不消耗或触发自动重启次数。自动重启次数按单个 `backend supervise` 进程计算，不跨应用启动持久累计。

## 并发、锁与中断恢复

Runtime 使用 Windows 命名 Mutex 保证进程级互斥，同时写入只用于诊断和恢复的状态文件：

```text
runtime-state/
├── backend.json
├── mutation.json
├── update.json
└── environment.json
```

按应用根目录规范化路径计算互斥名称，至少分为：

1. `backend`：保证同一安装目录只有一个 `backend supervise`；
2. `mutation`：串行化 Git 替换、uv/Python 主环境修改、repair 和 cleanup。

只读 `doctor`、版本查询和远端检查可以与后端运行并发。会修改源码或环境的操作必须取得 `mutation` 锁，并确认 `backend` Mutex 未被持有；否则返回 `BACKEND_STILL_RUNNING`。首版由 Electron 先通过当前监督进程的 stdin 停止后端，再调用更新。一次性 Runtime 不寻找另一个 Runtime 的标准输入、不按 PID 注入控制命令，也不在后台强制杀掉正在运行的后端。

首版不在后端运行期间预克隆下一版本，避免引入跨进程临时目录所有权和过期 Commit 事务。若未来确有停机时间压力，再独立设计 `workspace prepare` 与 `workspace apply`，并要求准备结果绑定目标版本、Commit、操作 ID 和有效期；该能力不属于协议版本 1。

`backend.json`、`mutation.json` 和 `update.json` 是事务状态，包含操作 ID、
命令、PID、开始时间、目标版本和阶段。Runtime 启动时验证 PID 和 Mutex
实际状态，不能只因状态文件存在就判断另一个进程仍存活。
`environment.json` 是稳定环境状态，保存 `environment_broken` 或
`ready_to_start`、最近一次成功的版本和 Commit；进入
`environment_broken` 时还保存目标分支、Python/uv 版本、reason、stage、退出码和
日志路径。`repository_changed` 固定对应成功 swap 后的 `workspace.swap` 与
`exitCode=0`；`operation_failed` 对应具体失败叶子与非零退出码。active repo 已确认但
尚未经过 `python.check` 的结构化解析时允许 Python/uv 版本为空表示 unknown。
事务状态与稳定环境状态不得复用同一文件
或以文件存在性互相推断。

四个状态文件只能通过 StateFiles 访问。每次操作先相对打开对应 kind 的持久 guard `G`；
缺失时以 create-exclusive/open 竞态安全建立，随后在同一 handle 上验证 ordinary、
non-reparse、same-parent、same-volume 与 link count 1。所有 gate handle 的 desired
access 恰为 `FILE_READ_DATA | FILE_READ_ATTRIBUTES` 且不含 `SYNCHRONIZE`。create/open
都使用 root-relative `NtCreateFile`，CreateOptions 恰为
`FILE_OPEN_REPARSE_POINT | FILE_NON_DIRECTORY_FILE`，禁止 synchronous I/O flags；
CreateDisposition 分别恰为 create-exclusive `FILE_CREATE` 与 open-existing
`FILE_OPEN`；reader ShareAccess 为 `FILE_SHARE_READ`，writer、W0、rollback、finalize
和 conditional remove 为 `0`。不得使用 attributes-only、DesiredAccess `0`、
`FILE_OPEN_IF` 或其他 access/options/disposition/share。Windows 双向 share
compatibility 中，exclusive handle 的 share `0`
拒绝既有/新 handle 的 read-data desired access，因此多个 reader 可并行，而 reader
与 writer、writer 与 writer 跨进程互斥。两类 handle 都拒绝 share-write/share-delete，
并在操作期间固定 `G` 名称；Reparse Point、硬链接或身份未知的 `G` 不覆盖、不删除并
失败关闭。

WriteAtomic 在任何 `I/D` 判断与 W0 前取得 exclusive `G` 并完成只读 preflight，持有它
穿过 POSIX unlink 能力探测、payload temp 创建、目标 existing/absent 的重新判定、全部
正向 rename、rollback/finalize 及协议 handle close，最后才关闭 `G`。每次 WriteAtomic
即使 preflight 得到 fixed `I/D` stable absent，也必须在任何 W0、`T/J` 创建或其他可能
需要 unlink 收口的副作用前，用同一 pinned volume 下随机 create-exclusive/
delete-on-close probe leaf 证明 `FileDispositionInfoEx` 的
`FILE_DISPOSITION_FLAG_DELETE | FILE_DISPOSITION_FLAG_POSIX_SEMANTICS` 会在独立短生命
周期删除 handle 关闭后 unlink namespace，同时身份锚点 handle 仍可读取且身份不变；
不支持、名称仍可重开或 probe 无法精确收口时，在任何本次副作用前失败关闭，不回退
classic disposition、关闭身份锚点后删除或路径删除。写入
新 payload 时先写入并 flush 随机 `T`；在 gate 内重新确认 `I` 不存在且目标不存在时，
才直接以 no-replace rename 提交。目标存在时，
writer 用允许 read/delete share 但拒绝 write share 的同一旧目标身份锚点固定旧对象；
share-delete 只允许经 exclusive `G` 授权并验证同一身份的独立删除 handle 工作，
再把完整、已 flush 且已重验的 intent envelope 从随机 `J` 以 no-replace rename 发布到
固定 `I`。envelope 绑定 kind、目标/临时/备份 leaf、随机 nonce、state-root 身份、
intent 身份以及旧/新对象的 volume、file ID、大小和 SHA-256。fixed intent 一旦可见
就必然完整，内容不带可变 phase，恢复只能根据该 envelope 与当前 namespace 身份推导。

sealed intent 发布后，旧目标由其同一 handle 以 no-replace rename 移到随机 backup，
再由新 temp 的同一 handle 以 no-replace rename 到固定目标；第二次 rename 成功是新
payload 的唯一提交点。所有正向、恢复和回滚 rename 的 flags 都为 `0`，StateFiles
禁止覆盖任何既有 destination。提交前失败时若旧对象已在 backup，只能用同一旧对象
handle 尝试 no-replace 回滚；若目标或任一保留 leaf 被普通文件、Reparse Point 或硬链接
竞争者占据，绝不覆盖或删除竞争者，而是保留可证明对象并要求恢复。提交后只按
backup → intent → handles 的顺序收口：用仍持有的身份锚点与独立删除 handle 按上述
POSIX flags unlink backup，证明删除 handle 已关闭且名称 absent 后才 unlink intent，绝不把 delete-pending 当作
absent，也绝不把新目标回滚为旧值。W0 的 unlink 故障归 recover，当前请求 rollback/
post-commit unlink 故障归 finalize，最终 handle/`G` close 故障归 close；result 始终
保留真实 `MutationApplied/RecoveryRequired`。

StateFiles `Read` 取得 shared `G` 后，在 gate 内解析 sealed `I` 与 `D/B` namespace，
并打开可证明的权威 payload leaf handle；只有在 gate 内确认无 intent 且 `D` missing
时，才能形成稳定 `not found` 决策，包括 direct-absent commit 前 crash 只留下未引用
随机 `T/J` 的情况；既往 orphan 只报告、不按前缀猜删，只有创建它的当前操作可用精确
handle 收口。该逻辑结果以专用 `ErrStateFileNotFound` 暴露并支持 `errors.Is`；raw
`fs.ErrNotExist`、Win32 name-not-found、事务 gap 或祖先 open 失败均不得映射为它。
权威 payload handle 拒绝 share-write、允许
share-delete，Read 可在打开它后释放 `G` 再执行有界读取，使后续 writer 继续而旧 reader
仍引用原对象。intent 二次探测可以保留为防御，但不得作为线性化或关闭 ABA 的根基。
sealed `I` 的 `D=X/B=O/T=N` 只有在 `X` 可从 same-parent handle 打开、ordinary/
non-reparse/single-link、identity/digest 可查询且已证明非 `O/N` 时，才从 `B=O` 返回
old，`X` 保持不变；opaque/unopenable/Reparse/hardlink/identity 不可证明的 `D` 即使
`B` 看似 `O` 也失败关闭。foreign 目标永不作为 state 结果，内部事务缺口也不得误报为
`not found`。active writer
期间 Read 可以 context-aware 等待 gate，并在 writer 完成或崩溃释放 handle 后返回
old/new；不承诺在 raw gap 中即时返回 old。因此仓内唯一合法读取入口只观察完整
old/new；绕过 StateFiles 的 raw path reader 在两次 no-replace rename 之间可能观察到
`NOT_FOUND`，不在承诺内。
conditional remove 返回同时携带 `MutationApplied` 与 `RecoveryRequired` 的专用 result：
gate 内证明 sealed `I`/`D` absent 时在零次 POSIX probe 下幂等返回 `false/false`，即使
平台 unsupported 也成功，orphan `J/T` 只报告；stable `D` snapshot mismatch 同样先于
probe 决定；该 zero-probe/only-if 规则仅属于 conditional remove，不适用于 WriteAtomic。
clean mismatch 直接返回 ErrTransactionChanged，不包装 WriteError；若随后
最终 `G` close 失败，则为 `false/true` 的 WritePhaseRemove WriteError，identity 主因与
close CleanupError 均可达。权威 `D` POSIX unlink 后成功收口为 `true/false`，commit 后
任一 finalize/leaf close/最终 `G` close 失败为 `true/true`。state 只消费专用 result/
error 和稳定 sentinel，不解析本地 Operation。
T2.4 业务 Lease 用于上层编排，不是该文件协议的安全前提；intent、强 share mode 与
no-replace rename 必须在合作进程误用时仍保证不覆盖未知对象。

guard 获取的 sharing violation 使用响应 context 的重试等待；生产实现通过 timer/select，
不调用 `time.Sleep`，测试注入 wait/barrier。进程退出会由 Windows 自动关闭 `G` handle，
因此 crash 不遗留锁所有权；所有 acquire/close 故障仍保留底层 Win32 链。

该协议承诺进程崩溃后的可判定恢复，不承诺断电时目录项已经持久化。payload 与 sealed
intent 都执行 `FlushFileBuffers`；Windows 不提供这里所需的目录项 write-through
保证，文档和实现不得把进程崩溃恢复表述为断电耐久性。

中断恢复规则：

1. 克隆未完成：删除经过路径校验的 `repo.update-<operationId>`；
2. 临时仓库已验证但未替换：保留当前 `repo`，删除临时仓库；
3. 正式目录重命名中断：根据 `update.json` 和目录身份恢复唯一的 `repo`；
4. Git 已替换但环境状态尚未同步：确认唯一 active revision 后补写
   `environment_broken/repository_changed`，再继续或结束恢复；
5. venv 重建中断：保持 `environment_broken`，下次继续重建；
6. 无法唯一判断目录身份：停止自动清理并返回 `UPDATE_STATE_AMBIGUOUS`。

## Lite、Full 与离线边界

两种桌面发行版都通过 Git 获取后端源码：

| 发行版 | 预置内容 | 首次运行仍需获取 |
| --- | --- | --- |
| Lite | Electron、Runtime | uv、Python、后端 Git 仓库、Python 依赖 |
| Full | Electron、Runtime、固定 uv、受管 Python、可选 uv 缓存 | 后端 Git 仓库和可能缺失的依赖 |

Full 不内置后端源码压缩包，也不改变“版本映射发布分支”的更新协议。首版不承诺完全离线首次安装，因为后端源码仍必须从 Git 获取；离线导入如果未来需要，应作为独立功能设计，不能隐式退回压缩包更新。

Full 中预置的 uv 和 Python 必须经过与 Runtime 相同的版本校验。不匹配时由 Runtime 重新准备，不能因为文件存在就直接使用。

## Runtime 自身更新

Runtime 不实现自更新。`auto-mas-runtime.exe` 跟随 Electron 桌面应用的更新流程一起发布和替换：

1. 前端更新包携带与其协议兼容的 Runtime；
2. Electron 启动 Runtime 后先完成 `hello` 握手；
3. 协议不兼容时停止后端操作并提示更新桌面应用；
4. Runtime 不执行 `uv self update`，也不自行替换自身可执行文件；
5. Python 后端 Git 版本与 Runtime 兼容性由版本映射和健康检查协议共同约束。

## 文件与删除安全边界

### 当前后端生成目录

当前源码已确认后端会相对工作目录创建：

```text
config/
data/
debug/
history/
plugins/pypi/
```

仓库忽略规则还覆盖：

```text
runtime/
script/
environment/
.venv/
logs/
__pycache__/
build/
dist/
wheels/
app/core/plugins/_generated/
```

这些路径不能因为都在 `.gitignore` 中就被视为同一类数据。

### 数据分类

| 类别 | 路径示例 | Runtime 权限 |
| --- | --- | --- |
| Git 管理源码 | `repo/app`、`repo/res`、`repo/plugins` 中已跟踪文件 | 更新时整体替换 |
| 用户业务数据 | `config/`、`data/`、`history/`、`script/` | 自动更新绝不能删除 |
| 诊断数据 | `debug/`、`logs/`、Runtime 日志 | 更新不删除，只按明确保留策略轮转 |
| 插件持久化数据 | 插件安装清单、插件配置和插件 `data/` | 自动更新绝不能删除 |
| 插件运行包 | `plugins/pypi/site-packages/` | Runtime 永不修改；只能由 Python 插件系统重建 |
| 可重建主环境 | 受管 venv、受管 Python | Runtime 的 repair/rebuild 可以删除并重建 |
| 可丢弃缓存 | uv 缓存、临时下载、`__pycache__`、构建缓存 | cleanup 可以删除 |
| 更新临时目录 | `repo.update-<operationId>`、经确认的旧 repo 临时目录 | 仅在状态匹配时删除 |
| 外部脚本目录 | 用户配置中的 `RootPath` 等任意外部路径 | Runtime 永不递归删除或移动 |

`debug/` 虽然由后端生成，但包含定位启动和任务问题的日志，不能随着 Git 仓库替换被静默删除。
`logs/runtime/` 只能由日志保留策略删除经过重新验明身份的单个旧日志文件；
创建、轮转、列举和删除都必须固定应用根到日志目录的祖先句柄并拒绝
Junction、符号链接和其他 Reparse Point。保留删除使用 filesystem 返回的
不可伪造文件 token，并在删除前重验文件 ID；不得把普通路径字符串直接交给
`os.OpenFile` 或 `os.Remove`。

### 删除实现约束

任何递归删除前都必须：

1. 将目标解析为规范化绝对路径；
2. 验证目标位于明确的 Runtime 受管根目录内；
3. 验证目标不是安装根、用户数据根、盘符根或空路径；
4. 拒绝跟随未知 Junction、符号链接或其他 Reparse Point；
5. 依据操作状态和允许列表确认目录身份；
6. 记录删除目标、原因、操作 ID 和结果；
7. 路径身份不明确时失败关闭，不尝试猜测。

## Go 项目结构

独立项目采用常规 Go CLI 布局，首版不引入插件式框架：

```text
AUTO-MAS-Runtime/
├── cmd/
│   └── auto-mas-runtime/
│       └── main.go
├── internal/
│   ├── cli/
│   ├── config/
│   ├── protocol/
│   ├── gitrepo/
│   ├── uv/
│   ├── backend/
│   ├── process/
│   ├── health/
│   ├── state/
│   ├── lock/
│   ├── mirror/
│   ├── filesystem/
│   └── logging/
├── testdata/
├── go.mod
└── go.sum
```

包边界：

- `cli` 只解析参数和调用应用服务；
- `protocol` 只定义 NDJSON 事件和错误契约；
- `gitrepo` 只负责版本到分支映射和受管仓库替换；
- `uv` 只负责 uv bootstrap、Python、主项目环境和后端启动命令；
- `backend` 编排启动、健康检查、单次重启和关闭；
- `process` 封装 Windows Job Object 和子进程管道；
- `state` 与 `lock` 管理事务状态和并发；
- `filesystem` 集中实现路径校验、原子移动和受控删除；
- `mirror` 管理不同网络源的轮换；
- 业务包不能直接向 stdout 写普通文本，机器事件统一经过 `protocol`。

### 发布验收标准

首版进入正式发布前必须同时满足：

1. 协议契约测试证明所有命令都有 `hello`、递增事件和唯一最终 `result`，失败日志不会丢失；
2. 错误码全集均有至少一个自动化映射测试，Electron 对未知新增错误码有通用降级展示；
3. 全新安装、同版本重同步、升级和显式降级均成功，最终健康响应的版本等于目标版本、Commit 等于受管仓库 HEAD；
4. 网络、Git 校验或克隆在仓库替换前失败时，原 repo 可继续启动；
5. 仓库实际替换后立即持久化 `environment_broken/repository_changed`，`uv sync` 失败时不回滚源码并更新为 `operation_failed`，重试同步和重建环境均可恢复；
6. Runtime 更新、repair 和 cleanup 不执行插件依赖命令，也不删除插件运行包、配置或数据；插件错误由 Python 后端报告和处理；
7. 后端启动失败仍能在现有界面展示完整 stdout/stderr、稳定错误码和日志路径；
8. 后端就绪后首次意外退出仅自动重启一次，第二次失败明确结束监督；
9. 正常退出、强制兜底和 Runtime 异常退出场景均无 uv、Python 或其孙进程残留；
10. 任意受控更新、repair 或 cleanup 都不能删除 AUTO-MAS 根目录中的用户数据目录、外部脚本目录或受管根以外的路径；
11. 开发模式不会修改开发者仓库、分支、`.git` 或未提交文件；
12. `.python-version` 与 `uv.lock` 已纳入发布分支，CI 的 `uv lock --check` 已成为发布门禁；
13. Lite 和 Full 安装包均通过真实 Windows 冒烟测试，Runtime 与 Electron 握手协议匹配；
14. 旧 Electron/Python 更新入口已停止承担正式更新职责，且没有两个组件同时管理同一进程或目录。

## 分阶段迁移计划

迁移采用“先建立契约，再替换所有权”的顺序。各阶段可以由 Runtime、Electron 和 Python 两侧并行开发，但必须通过阶段门禁后才能删除旧路径。

### 阶段 0：发布与契约前置

- 固化本文档中的 CLI、NDJSON、错误码、状态值、健康检查和根目录协议；
- 完成 `.python-version`、`uv.lock` 入库及 `uv lock --check` 门禁；
- 明确发布分支和同名 Tag 不可移动。

门禁：给定任一计划支持的版本，发布流程能唯一产出 `release/<完整版本>` 分支，且该分支与同名 Tag 发布后不再移动。

### 阶段 1：Python 工作目录与生命周期契约

- 明确 AUTO-MAS 根目录为后端工作目录，后端入口和源码从固定 `repo` 路径加载；
- 验证配置、数据、history、script、debug 和插件状态均位于仓库替换边界外；
- 由 Python 后端继续拥有插件包和插件依赖生命周期，并接收 Runtime 注入的 `AUTO_MAS_UV_EXE`；
- 将当前 Electron `PluginBootstrapService` 承担的系统插件 bootstrap 语义收归 Python `PluginManager`；
- 增量扩展 `GET /api/core/health`；
- 保持并验证 `POST /api/core/close`；
- 移除 Python 后端对整包更新和安装器拉起的正式职责，但在 Electron 尚未切换前允许旧入口保持兼容。

门禁：Python 单元测试和迁移 E2E 证明替换整个 `repo` 后根目录中的用户数据与插件目录不变，后端仍能解析所需资源，健康接口能返回准确协议、版本和 Commit。

### 阶段 2：Runtime 基础与工作区同步

- 建立 Go 项目、CLI、human/NDJSON 输出、状态文件、日志、Mutex 和路径安全模块；
- 实现镜像策略、单分支浅克隆、版本文件校验和原子目录替换；
- 实现 `version`、`doctor`、`workspace check/sync` 和 `cleanup`；
- 完成中断恢复与危险路径测试。

门禁：不启动 Python 也能完成全套 Git 更新、降级、故障注入和恢复测试。

### 阶段 3：uv、Python 与主项目依赖

- 实现固定 uv bootstrap 和统一 `UVRunner`；
- 实现精确 Python 校验/安装、`dependencies check/sync/rebuild`；
- 实现 `bootstrap --version`、`repair` 和 `environment_broken` 持久化。

门禁：全新临时目录可从版本号准备到 `ready_to_start`；同步失败可由重试或重建恢复，且不修改 Git 和用户数据。

### 阶段 4：后端监督

- 实现挂起创建、Job Object 纳管、stdout/stderr 事件和日志轮转；
- 实现健康检查、身份校验、一次自动重启、stdin 控制和 HTTP 优雅关闭；
- 使用假后端完成进程树、崩溃、超时和事件顺序测试。

门禁：所有后端生命周期 E2E 通过，Runtime 退出后无受管进程残留。

### 阶段 5：Electron 双链路接入

- Electron 使用参数数组启动 Runtime，完成握手、NDJSON 解析和类型化 IPC 映射；
- 初始化界面消费稳定阶段、错误码和 remediation，同时保持现有完整日志展示；
- 在开发/灰度开关下保留旧启动链路，单次应用生命周期只能选择一条链路；
- 更新时由 Electron 先关闭 supervisor，再执行 `bootstrap`，最后启动新的 supervisor。
- Electron 不再在 Runtime bootstrap 前后执行插件依赖安装，插件操作统一调用 Python API。

门禁：Lite/Full、首次安装、正常启动、更新失败、环境修复和退出场景均通过桌面 E2E；两条链路的用户可见关键行为对齐。

### 阶段 6：正式切换与旧逻辑移除

- 正式版默认且只使用 Runtime 链路；
- 删除 Electron 中 Python、uv、Git 安装、仓库更新、插件 bootstrap、PID 扫描和全局进程清理逻辑；
- 删除 Python 整包更新下载和安装器拉起逻辑；
- 保留开发模式的显式源码目录入口；
- 更新用户文档、诊断指引、隐私说明和日志收集说明。

门禁：全量验收标准通过，发布包内 Electron、Runtime 和后端协议版本兼容，旧逻辑不存在可被正式路径再次调用的入口。

### 阶段 7：发布观察

- 先灰度发布并统计错误码、失败阶段、镜像切换和强制关闭比例；
- 只收集不含用户业务数据和绝对路径的运行指标；
- 对未知错误保留原始日志路径和通用修复入口；
- 稳定后再清理仅为迁移保留的兼容配置。

此阶段的发布回退是重新发布上一版桌面安装包或让用户显式同步旧后端版本，不在 Runtime 内引入 A/B Slot 或隐藏的自动源码回滚。

## 核心约束

1. Electron 只能使用参数数组启动 Runtime，不拼接 Shell 命令字符串。
2. Runtime 的机器可读输出只能写到标准输出；诊断日志写到标准错误和日志文件。
3. 标准输出采用逐行 JSON，并带协议版本。
4. Runtime 不根据进程名批量终止 Python、Git 或 Electron。
5. 更新必须先在临时目录完成浅克隆和 Commit 校验，再整体替换当前受管仓库。
6. Runtime 不接管 Python 的业务 HTTP 路由。
7. Runtime 项目可以独立构建、测试和通过命令行运行。
8. 首个版本仅支持 Windows，与 AUTO-MAS 当前桌面发布平台保持一致。
9. 必须保留后端启动失败时直接展示原始 stdout/stderr 的现有体验。
10. 受管后端仓库与共享用户数据必须分离，整体替换仓库不得覆盖用户数据。
11. 目标版本必须映射到固定发布分支，Runtime 在克隆后记录实际 Commit，不得通过枚举全部远端分支猜测更新目标或在换源前自行钉扎 Commit。
12. Runtime 不得直接调用 Python、pip 或虚拟环境解释器；Python 工具链统一通过受管 `uv.exe`。
13. 正式依赖同步必须消费发布分支中的锁文件，不能在用户机器上隐式更新依赖解析结果。
14. Git revision 实际替换后必须先持久化 `environment_broken/repository_changed`；
    `uv sync` 失败不回滚 Git 源码，并更新为可诊断、可重试和可重建的
    `environment_broken/operation_failed` 状态。
15. `backend supervise` 每次生命周期最多自动重启后端一次。
16. Runtime 自身只能跟随 Electron 桌面应用更新，不实现独立自更新。
17. 启用整体仓库替换前，必须先把用户业务数据、诊断日志和插件数据从 Git 工作区解耦。
18. Electron 是停机与更新编排者；一次性 Runtime 不跨进程控制正在运行的 supervisor。
19. 发布版本通过固定模板 `release/<完整版本>` 唯一映射到发布分支；发布分支与同名 Tag 发布后不可移动，镜像只能改变下载位置。
20. 所有顶层命令在参数解析成功后必须发送首个 `hello` 和唯一最终 `result`。
21. 协议消费者必须按稳定字段和错误码判断，不解析中文文案、uv 输出或 Git 输出驱动流程。
22. Runtime 只向 Python 后端提供固定 uv 路径，不解析、安装、更新、卸载或重建任何插件依赖。
