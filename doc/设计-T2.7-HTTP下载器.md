# T2.7 HTTP 下载器设计

## 文档状态

- 日期：2026-07-29
- 状态：已批准，采用方案 A
- 任务：[T2.7 HTTP 下载器](./任务拆分.md)
- 架构基线：[架构设计](./架构设计.md)
- 代码基线：AUTO-MAS Runtime `fb06f57`

本文冻结 `internal/mirror` 中通用 HTTP Downloader 的请求校验、TLS 与重定向策略、
`.part` 生命周期、超时分类、完整性验证、进度和失败清理。Downloader 只完成一次确定的
资源传输；源轮换由 T2.6 负责，uv 领域错误映射由 T5.1 负责。

## 目标与范围

T2.7 交付：

1. 使用默认 TLS 验证的 `http.Client` 下载单个已确定资源；
2. 禁止生产 HTTPS 请求通过重定向降级到 HTTP；
3. 先写同目录 `.part`，严格验证正文件大小和 64 hex SHA-256；
4. 区分连接阶段超时与响应体读取超时，并贯通 context 取消；
5. 提供单调进度回调，供上层转换为 `progress` 事件；
6. 通过 T2.5 DownloadSession 按 `write -> verify -> Flush -> handle-relative
   no-replace rename -> close` 发布最终文件；
7. 任意失败都通过同一 `.part` handle 清理并等待读取 goroutine 退出；
8. 返回通用 `FailureKind`，供 mirror 与 T5 分层映射。

本任务不负责：

- 选择 Source、构造镜像尝试顺序或执行重试；
- 生成 uv/Python 资源 URL、版本、目标文件名、大小或 SHA-256；
- 下载未知大小、没有校验和的生产制品；
- 解压 zip、检查 `uv.exe --version` 或安装 Python；
- 续传、分片下载、并发下载或带宽限速；
- 映射 `UV_DOWNLOAD_FAILED`、`UV_CHECKSUM_MISMATCH` 等 uv 领域错误；
- 直接调用 protocol Emitter 或写 stdout；
- 递归删除目录；失败清理只调用 DownloadSession.Abort。

## 方案选择

采用方案 A：**单次流式下载器 + 上层 Rotator 重试**。

备选方案 B 是 Downloader 内部同时选择镜像并重试。它会把网络传输、目标不变量和 uv
错误映射耦合到一个类型中，难以复用于其他固定制品，因此不采用。

备选方案 C 是把整个响应读进内存后一次写盘。uv 和 Python 制品可能较大，且无法稳定
报告进度，因此不采用。

Downloader 是 `internal/mirror` 中独立主题：


## API

### 请求与结果

```go
type DownloadRequest struct {
    URL            string
    FileName       string
    ExpectedSize   int64
    ExpectedSHA256 string
    Progress       ProgressFunc
}

type DownloadProgress struct {
    Received int64
    Total    int64
    Percent  float64
}

type ProgressFunc func(progress DownloadProgress) error

type DownloadResult struct {
    Path   string
    Size   int64
    SHA256 string
}

func (d *Downloader) Download(
    ctx context.Context,
    request DownloadRequest,
) (DownloadResult, error)
```

`FileName` 是 download cache 下的一个安全文件名 segment，不是绝对/相对路径。
最终路径和 `.part` 路径只由 Layout + DownloadFiles 生成。成功结果的 Path 为
session 返回的最终绝对路径，SHA-256 为小写 64 hex。

Progress 为 nil 时不回调。非 nil 时：

- 首次写入前报告 `Received=0`；
- Received 只增不减，Total 恒等于 ExpectedSize；
- 回调按配置间隔节流，但最后一个字节写入后必报告 `Received=Total`；
- 回调在 Download 当前 goroutine 同步执行，不并发重入；
- 回调返回错误会中止下载、清理 `.part` 并返回 `FailureProgress`。

上层若在回调中发 protocol 事件，必须保留 Emitter 的原始错误链，以便映射
`OUTPUT_WRITE_FAILED`；Downloader 不自行判断该领域码。

### 构造器与注入

```go
type httpClient interface {
    Do(request *http.Request) (*http.Response, error)
}

type timer interface {
    C() <-chan time.Time
    Stop() bool
    Reset(delay time.Duration) bool
}

type timerFactory func(delay time.Duration) timer

type downloadSession interface {
    Write(p []byte) (int, error)
    Path() string
    PartPath() string
    PublishNoReplace(ctx context.Context) (filesystem.PublishResult, error)
    Abort(ctx context.Context) (filesystem.AbortResult, error)
}

type sessionFactory interface {
    Begin(ctx context.Context, name string) (downloadSession, error)
}

type cleanupContextFactory func(
    operationCtx context.Context,
) (context.Context, context.CancelFunc)

type Downloader struct {
    // 构造后配置只读。
}

type DownloaderOption func(*downloaderOptions) error

func NewDownloader(
    layout *config.Layout,
    options ...DownloaderOption,
) (*Downloader, error)
func WithDownloaderTimeouts(
    connectTimeout time.Duration,
    readTimeout time.Duration,
) DownloaderOption
func WithDownloaderProgressInterval(interval time.Duration) DownloaderOption
```

nil layout、nil/重复 option 以及非正超时由 NewDownloader 包装
`ErrInvalidDownloaderOption`，不能静默忽略。构造器创建不可变
`filesystem.DownloadFiles`，并由私有 `filesystemSessions` adapter 把具体 session
映射为上述消费方小接口；后者每次 Begin 才持有 session 级 OS handle。

同包私有 `newDownloaderWithDependencies` 在任何 Begin、网络或 timer 操作前注入
`sessionFactory`、httpClient、clock、timer factory 和 cleanup context factory；它拒绝
任一 nil 依赖。
生产 cleanup factory 固定返回
`context.WithTimeout(context.WithoutCancel(operationCtx), 5*time.Second)`；它保留必要的
context value，不受原操作取消影响。5 秒是协作式 deadline，不承诺强行中断不响应 ctx 的
同步 Abort/Win32 调用；session 实现必须在可取消边界检查 ctx，测试替身必须响应 ctx。
session/factory 和 cleanup factory 均不导出为用户配置。

默认值：

| 参数 | 默认值 |
| --- | ---: |
| 连接阶段超时 | 15 秒 |
| 响应体读取空闲超时 | 30 秒 |
| 进度最小间隔 | 200 毫秒 |
| 最大重定向次数 | 10 |

生产构造始终使用本包创建的 `http.Client`；不存在公开 client/TLS、clock 或 timer 注入
Option。网络客户端、时钟和 timer 只经同包私有构造器注入，单元测试不依赖公网或
`time.Sleep`。

## HTTP 与 TLS 策略

### 默认客户端

默认客户端从 `http.DefaultTransport` 的 Clone 构造，保持 Go 系统根证书验证：

- 不设置 `TLSClientConfig.InsecureSkipVerify`；
- 不提供跳过证书、允许任意 HTTP 或 `--allow-insecure-host` 的配置；
- 使用标准代理解析、连接池和 TLS hostname 校验；
- `DisableCompression=true`，请求显式发送 `Accept-Encoding: identity`，确保大小与
  SHA-256 针对服务器制品原始字节而不是自动解压后的内容；
- 不设置会掩盖读取空闲超时的 `http.Client.Timeout`，连接与读取由下述阶段 timer 管理。

注入 httpClient 只用于同包测试和受控组件测试，不暴露到 CLI、其他包或用户配置。即便使用注入
客户端，Download 仍检查初始 URL 和 `response.Request.URL`；生产安全性以默认客户端的
重定向前检查为准。

### URL 策略与本地测试边界

DownloadRequest URL 必须是无 userinfo、无 fragment 的绝对 `https` URL。HTTP 即使指向
loopback 也在发起请求前返回 `FailureURLPolicy`；Downloader 不含仅靠 host 判断的明文
例外或生产可达的绕过开关。

本地组件测试使用 `httptest.NewTLSServer`，并只通过
`newDownloaderWithDependencies` 注入显式信任该测试证书的 Root CA/client；测试 client
同样不得设置 `InsecureSkipVerify`。这样测试仍覆盖真实 TLS 传输，而不扩大生产 URL
策略。

### 重定向

默认 client 的 `CheckRedirect` 固定执行：

1. 最多 10 次；
2. 初始 HTTPS 的任一后续 URL 必须仍为 HTTPS；
3. 每个 Location 都重新校验 userinfo、fragment、scheme 和 host；
4. HTTPS 降级在发送下一请求前失败为 `FailureRedirectDowngrade`。

HTTPS 到其他 HTTPS host 允许，以兼容 GitHub Release 到 CDN 的正常跳转。请求不携带
Cookie、Authorization 或用户凭据；不得把查询参数写入错误文本或进度 details。

响应最终 URL 还会再次检查。这样测试注入客户端若返回不符合策略的
`response.Request.URL`，结果仍失败；生产默认客户端则在发送降级请求前已经阻断。

签名下载 URL 可以含 query，但任何错误对象都必须净化。`http.Client.Do` 返回
`*url.Error` 时，Downloader 不把该对象本身放进 `DownloadFailure.Err`：私有
`transportError` 保存经过白名单归一化的 operation 和底层 cause，自己的 Error 只输出
稳定诊断词，Unwrap 才保留 cause 的 `errors.Is/As` 链。外层
`DownloadFailure.Error()` 只输出稳定
FailureKind/HTTP status，不拼接原始 URL 或底层任意文案。需要记录 URL 时只允许使用删除
userinfo、RawQuery 和 fragment 的副本；初始 URL、每次重定向 URL 和
`response.Request.URL` 都执行同一净化。这样 Rotator 把 `outcome.Err.Error()` 写入
AttemptReport 时也不会泄露 CDN 签名 query。

## 请求前校验

发起网络或触碰 `.part` 前必须完成：

1. ctx 非 nil；
2. URL 满足上述 scheme/host 策略；
3. FileName 非空且能同时通过 `Layout.DownloadFile` 与
   `Layout.DownloadPartFile` 的单 segment 校验；
4. ExpectedSize 严格大于 0；
5. ExpectedSHA256 恰为 64 个十六进制字符，可解码为 32 字节；
6. Progress 之外没有未知可变目标字段。

SHA-256 输入大小写归一化为小写。空 SHA、短 SHA、非 hex、零大小和负大小都是
`FailureInvalidRequest`，不通过“下载后再看”放行。

Downloader 不接受 Destination；DownloadFiles 把 FileName 绑定到
`Layout.DownloadCacheDir()` 并拒绝祖先 Reparse Point、硬链接和身份变化。

## `.part` 生命周期

单次 Download 固定执行：

1. 完成请求校验；
2. 调用 DownloadFiles.Begin(ctx, FileName)；它固定祖先 handle、安全删除陈旧
   单链接 `.part`、拒绝既有 final，并 create-exclusive 返回 session；
3. 保存 session.Path() 作为最终结果路径；
4. 发起完整 GET，不发送 `Range`，要求成功状态 `200 OK`；
5. 流式写入 session，同时累计字节和 SHA-256；
6. 若收到字节超过 ExpectedSize，立即失败；
7. EOF 后要求实际大小恰等于 ExpectedSize，并用常量时间比较 SHA-256；
8. 关闭 response Body 并确认 read pump 已退出；
9. 调用 session.PublishNoReplace(ctx)；它在同一已验证 part handle 上执行
    Flush + handle-relative no-replace rename，并返回显式 Published 结果；
10. `Published=true` 且 error=nil 时返回成功，确认 `.part` 不存在；若 rename 已生效但
    handle close 失败，按下文返回 `Published=true` 的失败，不执行 Abort。

不接受 `206 Partial Content`。Content-Length 存在且与 ExpectedSize 不等时可在读取前
直接作为 `FailureSizeMismatch`；Content-Length 缺失时允许继续，但最终实际大小仍必须
精确匹配。

最终文件与 `.part` 在固定 download cache 目录。Publish 保持经过 SHA-256 校验的
同一个 part handle 打开，不存在 Close→按路径 rename 的替换窗口；目标父目录 handle
作为 FileRenameInfoEx RootDirectory，flags 为 0，不含 replace-if-exists。数据在 rename
前已调用 `FlushFileBuffers`；Windows SDK 不存在 rename write-through flag，因此不虚构
目录项持久化保证。
若发布前有竞争者创建 final，返回 `FailureDestinationOccupied`，随后只 Abort 本次
session，绝不删除或覆盖竞态赢家。

mirror 包不调用 `os.Rename`、`MoveFileExW` 或任何路径删除原语。
缓存命中与既有制品校验由 T5.1 在调用前处理。

## 超时与取消

### 连接阶段

“连接阶段”从调用 httpClient.Do 开始，到收到响应 headers 为止，包括 DNS、代理、
TCP、TLS、重定向和响应头等待。

Downloader 为请求创建继承调用方 ctx 的可取消 context，并启动受 timerFactory 管理的
连接 timer。httpClient.Do 在一个由 Download 拥有的 goroutine 中执行：

- ctx 先取消：取消请求，返回 `FailureCancelled`；
- 连接 timer 先触发：取消请求，返回 `FailureConnectTimeout`；
- headers 先返回：停止连接 timer，进入读取阶段；
- Do 结果 channel 固定容量为 1；goroutine 恰好发送一次结果且不会因 request context
  已取消而丢弃结果；
- 无论哪条路径都 cancel 并接收这一个最终结果，不遗留 goroutine。禁止使用“send 与
  ctx.Done 二选一”的无缓冲 channel，否则取消路径可能丢失结果并让 join 永久等待。

默认 `http.Transport` 会在 request context 取消时中断 DNS、连接和 TLS。注入 fake
client 也必须遵守 Do 的 context；不遵守者属于测试替身契约错误。

### 读取阶段

收到 `200 OK` 后启动唯一的 body read pump。pump 是 response.Body 的唯一 Reader，把
非空字节块或错误发送给 Download 主循环。主循环的读取 timer 只覆盖“已经准备好接收
下一块、但网络尚未交付”的等待区间：

- 每个成功 read 都把 `buf[:n]` 复制到本次 chunk 独占的新 slice 后再发送；pump 不得在
  主循环完成 Write/hash/Progress 前复用或改写该 backing array。chunk channel 是否有
  buffer 都不能替代所有权协议；
- chunk 同时携带本次 Read 的 error；Go Reader 合法返回 `n>0, err!=nil`，主循环必须先
  完整处理这 n 个字节，再处理 EOF 或其他 error，不能丢失最后一块；
- 等待第一块前启动 timer；收到非空 chunk 时先 Stop 并安全排空 timer，再执行本地
  Write/hash/Progress，处理完成且主循环准备等待下一块时才 Reset；
- 本地 writer、hash 或 Progress callback 执行期间 timer 必须停止；它们即使阻塞超过
  readTimeout 也不能被误报为网络读取超时；
- EOF 正常进入大小与摘要校验；
- timer 先触发时取消请求并关闭 Body，返回 `FailureReadTimeout`；
- 调用方 ctx 先取消时取消请求并关闭 Body，返回 `FailureCancelled`；
- pump 向 chunk channel 发送时必须 select request context 的 done，主循环不再接收时
  可以退出；
- 主循环发生写盘、大小上溢或 Progress 错误时，固定执行
  cancel request → Close Body → 等待 pump 退出；
- 正常 EOF 也必须 Close Body 并检查 close error，之后才允许发布；
- 所有终点都等待 read pump 退出，谁启动 goroutine 谁 join。

标准 net/http Body 在 Close 或 request context 取消后必须解除 Read。测试 fake Body
也必须满足该契约。实现不能用 `time.Sleep` 模拟或判断超时。

context 取消与 timer 同时可见时，若调用方 ctx 已完成，优先分类为
`FailureCancelled`；只有调用方 ctx 仍有效才分类阶段超时。

## 完整性与进度

SHA-256 通过 `io.MultiWriter(downloadSession, hasher)` 或等价单次数据路径计算，禁止先写文件
再重新打开计算摘要。这样进度 Received、写盘字节和摘要字节来自同一流。

每个 chunk 的 `downloadSession.Write` 必须返回 `n == len(p)` 且 `err == nil`；
任意短写立即按 `FailureFilesystem` 失败并进入 Abort，其中 `n < len(p)` 且 err 为空时
规范化为 `io.ErrShortWrite`，不得循环补写当前 chunk。只有完整成功的 Write 才把同一
chunk 送入 hasher 并增加 Received。进度百分比为
`float64(Received) / float64(ExpectedSize) * 100`，限制在 `[0,100]`，但业务判断只用
整数 Received/Total。

大小上溢判断不得计算可能溢出的 `Received + chunkLen`。始终维持
`0 <= Received <= ExpectedSize`，把成功写入数转换为 int64 后先判断
`written > ExpectedSize-Received`；只有不超限才执行加法。ExpectedSize 可以到
`math.MaxInt64`，该减法顺序仍安全。超过目标立即返回 `FailureSizeMismatch`。

节流使用注入 clock，不丢失初始与最终回调。进度回调失败发生在 rename 前，因此仍可
清理 `.part`，不会产生“最终文件已发布但协议失败”的矛盾。

## 失败清理

一旦本次 `.part` 创建成功，所有 **尚未发布** 的返回路径统一经过清理：

1. cancel 本次 request context；
2. 若 response Body 仍打开，Close；
3. 等待 Do/read goroutine 全部退出；
4. 通过私有 cleanup context factory 创建保留 values、忽略原取消但最长 5 秒的 ctx；
5. 调用 session.Abort(cleanupCtx)，通过仍打开的同一 part handle 标记删除并关闭祖先，
   记录 `AbortResult.Removed`，最后 cancel cleanup ctx；调用方取消不能跳过清理；
6. rename 尚未发生时，最终文件永不因失败被创建、截断或覆盖。

网络错误、HTTP 非 200、超时、取消、进度错误、大小/SHA 不匹配、Body Close 和 Publish
的 `Published=false` 失败都必须满足上述规则。响应 ctx 的 Abort 观察到 cleanup deadline
时允许 `.part` 残留，但必须返回 cleanup error，不能谎称清理成功；deadline 不保证硬
抢占任意同步 Win32 调用。

清理错误不能覆盖主失败。`DownloadFailure` 保留 `CleanupErr` 并通过 `errors.Join`
暴露两条链；FailureKind 保持主失败类别。若只有 Begin 清理 stale `.part` 失败，主类别为
`FailureFilesystem`，网络请求尚未发生。

Publish rename 成功后先冻结 `Published=true`。即使随后关闭 part/祖先 handle 失败，
也不得 Abort，因为 part handle 已经指向 final；Downloader 返回包含最终 Path/Size/SHA
的 DownloadResult 和 `Published=true` 的 `DownloadFailure`，让调用方知道制品已经落位。
实现必须避免在 rename 后再调用 progress/report 等外部 callback。

## FailureKind

Downloader 定义领域无关分类：

```go
const (
    FailureInvalidRequest       FailureKind = "invalid_request"
    FailureURLPolicy            FailureKind = "url_policy"
    FailureRedirectDowngrade    FailureKind = "redirect_downgrade"
    FailureConnectTimeout       FailureKind = "connect_timeout"
    FailureReadTimeout          FailureKind = "read_timeout"
    FailureNetwork              FailureKind = "network"
    FailureHTTPStatus           FailureKind = "http_status"
    FailureSizeMismatch         FailureKind = "size_mismatch"
    FailureChecksumMismatch     FailureKind = "checksum_mismatch"
    FailureCancelled            FailureKind = "cancelled"
    FailureProgress             FailureKind = "progress"
    FailureDestinationOccupied  FailureKind = "destination_occupied"
    FailureFilesystem           FailureKind = "filesystem"
)

type DownloadFailure struct {
    Kind       FailureKind
    StatusCode int
    Published  bool
    Err        error
    CleanupErr error
}

var ErrInvalidDownloaderOption = errors.New("downloader option is invalid")

func (e *DownloadFailure) Error() string
func (e *DownloadFailure) Unwrap() []error
```

`Unwrap` 按主错误、cleanup error 顺序返回非 nil 原因。调用方必须用 `errors.As`
与 Kind 判断，
不得匹配错误字符串。

`Published` 只在 session rename 已成功、后续 handle close 失败时为 true；此时
Download 同时返回已填充的 DownloadResult，CleanupErr 必须为空，且 final 不被删除。

推荐分层映射：

| FailureKind | T2.6 AttemptOutcome | T5.1 典型映射 |
| --- | --- | --- |
| connect/read timeout、network、HTTP 429/5xx | `retry_same_source` | 最终为 `UV_DOWNLOAD_FAILED` |
| HTTP 4xx | 由资源语义决定 switch/target failure | 最终通常为 `UV_DOWNLOAD_FAILED` |
| size/checksum mismatch | `integrity_failure`，本次拉黑 Source | `UV_CHECKSUM_MISMATCH` |
| redirect downgrade、URL policy | `switch_source` 并记录安全诊断 | `UV_DOWNLOAD_FAILED` |
| cancelled | 停止 Rotator | `OPERATION_CANCELLED` |
| progress | 停止 Rotator | 保留 `OUTPUT_WRITE_FAILED` 原因 |
| filesystem/destination occupied | `target_failure` | T5.1 按本地阶段映射 |

Downloader 本身不导入 protocol，也不返回任何 `UV_*`、`GIT_*` 或
`MIRROR_EXHAUSTED` 码。

## 首版不续传

首版明确不实现续传：

- 不读取 `.part` 的已下载长度；
- 不发送 `Range` 或 `If-Range`；
- 不接受 `206`；
- 每次尝试先删除陈旧 `.part`，从字节 0 开始；
- context 取消或服务器中断后 `.part` 不保留。

将来若引入续传，必须单独设计 ETag/Last-Modified 绑定、Range 校验、跨镜像内容身份和
partial digest；不能只因发现 `.part` 就盲目追加。

## 并发语义

- Downloader 构造后只读配置，可被多个 goroutine 并发调用；
- 同一 FileName 的并发 Begin 由 create-exclusive part handle 确定性拒绝第二个
  session；上层 mutation lock 仍负责业务级串行；
- Downloader 不维护全局下载 map，也不在包级保存可变 client；
- 每次 Download 只拥有自己的 request context、timer、`.part` 和 read pump；
- 谁启动 Do/read goroutine，谁在返回前等待其退出；
- Progress 回调不并发执行，回调不得再次对同一 FileName 启动 Download。

## 测试与验收

### 请求与 TLS

必须覆盖：

1. FileName 非法、ExpectedSize 为零/负数，SHA 为空、非 64 长度或非 hex，
   均在网络和 Begin 前失败；
2. 相对 URL、userinfo、fragment 和任意 HTTP（含 loopback）失败；
3. `httptest.NewTLSServer` 配合显式测试 Root CA/client 成功，测试与生产都不设置
   `InsecureSkipVerify`；
4. 默认客户端拒绝不受信任 TLS 证书，且不存在 InsecureSkipVerify 配置；
5. HTTPS 重定向到 HTTP 在发送降级请求前失败；
6. HTTPS 到 HTTPS 重定向成功，超过 10 次失败；
7. `Accept-Encoding: identity` 且自动解压关闭；
8. 初始请求、重定向和最终 response 的签名 query 在 network/redirect/TLS 错误、
   `DownloadFailure.Error()` 和 Rotator AttemptReport 中均不出现，`errors.Is/As`
   仍能取得净化 wrapper 下的底层 cause。

### 成功与完整性

本地 httptest 覆盖：

1. 已知 Content-Length 正常下载，最终 bytes、size、SHA 全匹配；
2. Content-Length 缺失但最终大小匹配；
3. Content-Length 预先不匹配、响应过短、响应过长；
4. SHA-256 不匹配；
5. HTTP 404、429、500 只返回结构化状态，不解析 body 文案；
6. stale `.part` 被删除后从零开始，server 断言请求没有 Range；
7. 成功后 `.part` 不存在，session Path 内容正确；
8. ExpectedSize=`math.MaxInt64` 和 Received 接近边界时，`written >
   ExpectedSize-Received` 精确拒绝超限，不发生 int64 wrap 或进度回绕。

### 超时、取消与进度

使用 barrier、fake httpClient、fake Body、fake clock/timer，禁止 `time.Sleep`：

1. Do 阶段连接 timer 触发为 `FailureConnectTimeout`；
2. 已收到 headers 后 body 停滞为 `FailureReadTimeout`；
3. 连接和读取阶段分别取消 ctx，均为 `FailureCancelled`；
4. 取消或超时后 Do/read goroutine 已退出；
5. Progress 为 0、单调递增、最终等于 Total，节流不丢终点；
6. Progress 返回错误后 cancel/Close，pump 的 channel send 可观察 done 并退出；
7. 成功 EOF、HTTP 错误和所有本地失败都恰好一次关闭 response Body；
8. Do goroutine 在 ctx 取消后仍向容量 1 的 result channel 发送恰好一个终值，主流程
   join 不会因结果被丢弃而死锁；
9. writer 或 Progress 用 barrier 阻塞超过 readTimeout 时 timer 保持停止，不产生
   `FailureReadTimeout`；释放本地处理后才重新计时下一次网络等待；
10. writer barrier 阻塞首块处理并驱动 pump 完成下一次 Body.Read，首块 bytes 保持不变；
    `go test -race` 不报告 pump/main 对 backing array 的竞态；
11. fake Body 返回 `n>0, io.EOF` 和 `n>0, otherErr` 时先写入/hash/计数最后 n 字节，再
    分别进入完整性校验或传播读取错误。

### 文件失败与清理

通过受控文件操作替身或 Windows 故障夹具覆盖：

1. Begin、write、Flush、Body Close、Publish、Abort 各自失败；
2. final 已存在时内容不变；
3. stale `.part` 无法删除或不是普通文件时不发网络请求，外部链接目标不变；
4. 主失败与 `.part` 清理失败同时保留；
5. 网络中断、HTTP 错误、超时、取消、校验失败且 Abort 成功后均无 `.part`；cleanup
   deadline 到期时返回 CleanupErr 并允许显式报告残留；
6. 发布顺序严格为 verify、Body Close/pump join、同一 part handle Flush/rename；
7. Begin 后注入竞争者创建 final，发布返回
   `FailureDestinationOccupied`，竞争者内容逐字节不变且本次 `.part` 被清理；
8. 校验后尝试按路径替换 `.part` 不会改变 session 持有的 file ID，最终只能发布
   已校验对象；
9. app-root/runtime/cache/downloads 任一祖先 Junction/Reparse Point 均在网络前
   失败关闭，外部目录不变；
10. FileRenameInfoEx flags 为 0 且不含 replace-if-exists，mirror 包不含
    `os.Rename`、`MoveFileExW`、`os.Remove`；
11. 发布成功后不再调用可失败回调；
12. rename 成功、handle close 失败时 `DownloadFailure.Published=true`、结果含完整
    Path/Size/SHA、final 保持不变且 Abort 调用数为 0；
13. 原 ctx 取消后使用独立 cleanup ctx 调 Abort；响应 ctx 的 fake Abort 在 5 秒 deadline
    到期后返回主错误与 cleanup deadline 两条错误链，不把 deadline 当作同步调用硬上限；
14. session 短写且 err 为空时规范化为 `io.ErrShortWrite`，返回
    `FailureFilesystem` 并 Abort；短写字节不进入 hash/Received，且不重试当前 chunk。

实现完成后执行标准验证门。T5.1 接入还需增加组件测试，证明 Downloader 的通用
FailureKind 被明确映射为 uv 协议错误，且 Rotator 的同源重试与换源不会改变固定
uv 版本、目标大小或 SHA-256。
