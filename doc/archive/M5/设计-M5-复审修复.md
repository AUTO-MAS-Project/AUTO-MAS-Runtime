# M5 复审修复设计

日期：2026-08-09

本设计修正 `e67a548` 与 `doc/archive/M5/` 中已经被真实 uv 0.12.3 资产和完整复审否定的
假设。未在本文件明确修订的 M5 边界继续服从 `契约补充-v1 > 架构设计 > 任务拆分`。

## 1. 范围与不负责

本轮修复 T5.1~T5.8：真实 uv 资产兼容、UVRunner 环境与网络策略、M5 mutation 恢复、
repair 阶段和 durable state、依赖只读检查、`requires-python` 规范语义、CLI 契约以及
组件/真实集成证据。

本轮不实现 M6 的 `CREATE_SUSPENDED -> AssignProcessToJobObject -> ResumeThread` 启动原子性，
不实现 backend supervise，不改变协议字段、错误码、stage、目录布局或插件所有权。

## 2. 官方 uv 资产契约

- 固定资产仍为 D-open-6 的 uv `0.12.3` Windows x64 ZIP 和既有 SHA-256。
- ZIP 根目录只允许普通文件 `uv.exe`、`uvw.exe`、`uvx.exe`；只把 `uv.exe` 写入 staging，
  其他两个已知成员验证形状后忽略。目录、链接、重复成员、子目录、未知成员、绝对路径、
  `..` 和超限内容继续失败关闭。
- `uv --version` 只接受单行 `uv <version>`，其后可带一个不含换行的括号构建元数据段；
  `<version>` 必须与固定版本逐字一致。测试必须直接运行官方资产，不能再用单文件自制 ZIP
  冒充真实发行包。

## 3. UVRunner 与网络策略

- 子进程仍继承 Windows 运行所需的普通环境，但所有大小写形式的 `UV_*` 先全部清除；
  调用方只能通过 `RunOptions.Environment` 注入 Runner 明确允许的 `UV_*` 键。
- Runtime 固定注入目录、managed Python、颜色和进度变量；禁止注入
  `UV_INSECURE_HOST`、`UV_NO_SOURCES`、`UV_NO_VERIFY_HASHES`、`UV_NO_SYNC`、
  `UV_CONFIG_FILE` 等可放宽安全或改变锁定语义的变量。
- Python 分发使用 `UV_PYTHON_INSTALL_MIRROR=<source.BaseURL()>`；包索引使用
  `--default-index <source.BaseURL()>`。两者通过 `mirror.BuildPlan` 与 `mirror.Rotator`
  执行有界同源重试和换源，目标分别密封精确 Python 版本与 `uv.lock` SHA-256。
- 离线模式不构造网络 Source 尝试，而以 `UV_OFFLINE=1` 执行同一确定目标；本地事实/缓存足够
  时允许成功，确需网络而失败时映射 `NETWORK_UNAVAILABLE`。
- Python/依赖的 check 路径固定离线执行；不得访问网络，也不得修改 venv 或 lock。
- 不使用 `--allow-insecure-host`，不关闭 TLS，不使用 `--no-sources`。项目
  `[tool.uv.sources]` 继续由受管 `pyproject.toml` 提供。

> 2026-08-17 修订：上述“依赖 check 路径固定离线”把只读检查错误地等同为离线检查，
> 已由 T5.10 纠正。`uv lock --check` 遵循 package-index `MirrorPolicy`，仅显式
> `--offline` 时注入 `UV_OFFLINE=1`；环境同步状态检查仍保持只读且不修改 venv 或 lock。

## 4. 崩溃恢复与持久状态

- 发现遗留 M5 mutation 时，只有尚未进入任何可变更 uv/Python/venv 的阶段才可删除事务并
  保留原稳定状态。
- 已进入 `uv.bootstrap`、`python.install`、`dependencies.rebuild` 或
  `dependencies.sync` 的陈旧事务，必须先原子写 `environment_broken/operation_failed`，
  保留 `lastSuccessful` 和事务内 target/tool/stage/log 事实，再条件删除事务。
- state 写失败保留事务并返回 `STATE_WRITE_FAILED`；不能删除唯一恢复证据。
- M5 编排在每个真实阶段开始前发对应 progress/state 并推进 mutation；不得提前宣称后续阶段。
- 从 `.python-version` 成功解析后即保留 `PythonSpec`；进入 `python.install` 或依赖阶段后的
  任意失败都把精确 uv/Python 版本写入 broken 状态。

## 5. Repair 与只读检查

- `environment repair` 和顶层 `repair` 都重新下载/校验 uv，并使用
  `uv python install --reinstall` 强制重装精确 managed Python。
- 顶层 `repair` 随后受控删除 managed venv，再执行 locked sync；`environment repair`
  不删除或同步 venv。
- `dependencies check` 先执行 `uv lock --check`，再执行与生产同步参数一致的
  `uv sync --check --locked --no-default-groups --no-install-workspace`，两步都离线且只读。
- `~=X.Y` 按 PyPA 兼容版本语义解释为 `>=X.Y, ==X.*`；`~=X` 非法；三段形式把兼容前缀
  收窄到 major.minor。TOML 解析不得把 array-of-tables 内的键误认成根 `[project]`。

## 6. CLI 与测试完成定义

- 仅实际发 state 事件的命令声明 `state.v1`；M5 错误 stage 使用当前命令/事务阶段。
- `repair --help` 明确其覆盖 uv、Python、venv；`dependencies rebuild --help` 明确只重建
  managed venv 和锁定依赖，不修复 uv/Python。
- M5 顶层命令接入 `contracttest.Register`；组件测试覆盖全新受管根、每个中断点重跑、
  stale-ready 恢复和保护目录快照。
- `-tags=integration` 测试直接消费由显式环境变量提供的官方 uv ZIP 或可执行文件；缺少资产时
  可 skip，但本地最终验收必须实际运行并通过，且记录资产 SHA-256。
