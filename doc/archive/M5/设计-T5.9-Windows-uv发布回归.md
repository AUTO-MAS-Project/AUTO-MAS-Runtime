状态：已完成并归档

## 1. 背景与证据

从提交 `83094ef39f1573e790324bcf5fad5ba426a774a2` 构建的真实 EXE
`blackbox-2026.08.10-m6` 在沙盒外 Windows 当前目录黑盒中暴露五项 M5 回归：

1. 官方 `uv-x86_64-pc-windows-msvc.zip` 已下载、按固定 SHA-256 校验并成功解压，解压后的
   `uv.exe` 也能报告 `0.12.3`，但最终发布稳定返回 `DIRECTORY_OCCUPIED`；Runtime 退出后，
   PowerShell 可立即移动同一 staging 目录。
2. `--offline environment ensure` 在空缓存时零网络结束，却把 mirror 层
   `NETWORK_UNAVAILABLE` 过度包装成 `UV_DOWNLOAD_FAILED`。
3. 上述普通失败在 `runtime-state/mutation.json` 留下 `uv.download` 事务。
4. `--mirror git=github --mirror-only workspace sync` 尚未执行任何 source attempt，却把
   BuildPlan 策略拒绝映射为 `INTERNAL_ERROR`。
5. 指向缺失 app-root 的 `environment check` 把普通未初始化状态映射为 `INTERNAL_ERROR`；
   预先创建空目录后才返回 `OK`。

这些问题均为既有实现未满足已冻结 M2/M5 设计，不需要新增协议能力或重开协议决策。

## 4. 根因与调用边界

### 4.1 Windows 发布句柄

`Bootstrapper.ensure` 通过 `filesystem.PrepareManagedDirectory` 创建 staging 并取得
`DirectoryLease`。当前 lease 延迟到整个 ensure 返回才关闭；随后同一函数调用
`Publisher.Publish`，最终进入 `filesystem.AtomicRename`。该 lease 的 Windows 分享模式不允许
delete/rename，因此 AtomicRename 在 pin source 时看到的“占用者”正是 bootstrap 自身。
Runtime 退出执行 defer 后 lease 被释放，所以外部 `Move-Item` 随即成功。

冻结修复顺序如下：

1. 下载器已经发布并关闭缓存归档后，读取并校验 ZIP；
2. 每个 ZIP 输入与解压输出文件显式关闭，任何 Close 错误进入错误链；
3. 版本探测子进程完成 `Wait`，相关 pipe 收口；
4. 从 staging lease 提取不可伪造的目录身份 token；
5. 显式关闭不再需要、会阻塞 rename 的 staging lease，并检查 Close 错误；
6. 把身份 token 传给现有 filesystem 发布能力；AtomicRename 在固定父句柄下重新 pin source，
   对 token 做 volume/file-ID 重验，然后执行 no-replace rename；
7. 仅发布完成后从最终路径执行 `uv.exe --version`。

关闭 lease 不等于放弃身份：路径可能被替换时，AtomicRename 的新 pin 必须与关闭前 token 一致；
不一致时失败关闭且零目标副作用。Win32 细节仍只存在于 `internal/filesystem`。

### 4.2 离线错误保真

offline BuildPlan 是合法的零 source 计划。有效本地缓存先于 source rotation 使用；缓存缺失时，
Rotator 在零 attempt 下返回 typed `NETWORK_UNAVAILABLE`。`Bootstrapper.download` 只对实际在线
下载/传输失败包装 `UV_DOWNLOAD_FAILED`，通过 `errors.Is`/`errors.As` 保留离线 typed code。
校验和错误仍为 `UV_CHECKSUM_MISMATCH`，实际执行过镜像并耗尽仍遵循既有 mirror/download 语义。

### 4.3 mutation 终态收口

事务收口集中在 M5 CLI 小型 helper，输入包含当前 operation ID 对应的事务 snapshot。规则为：

- pre-mutation 失败回滚原稳定生命周期；
- 已进入可能修改 uv/Python/venv 的阶段时，先按既有 M5 规则持久化
  `environment_broken`；无 active revision 的全新根保持 uninitialized；
- success、已安全回滚的 failure 与 cancel，始终使用
  `context.WithTimeout(context.WithoutCancel(ctx), 30*time.Second)` 条件删除自己的事务；
- 删除前重读 StateFiles 并核对 snapshot，底层仍使用 StateFiles 的 expected snapshot 条件删除；
- operation ID/snapshot 不匹配、状态写失败、身份不确定或 cleanup 失败时，不删除证据，并按既有
  错误优先级合并主错误与收口错误；
- 不对任意 `mutation.json` 做无条件删除，也不在 check 命令创建事务。

### 4.4 mirror policy 参数错误

mirror 包为“`mirrorOnly` + official preferred”暴露专用 typed policy rejection。workspace service
在日志、锁、StateFiles、临时目录和网络之前构造计划：该 typed policy rejection 映射为既有
`INVALID_ARGUMENT`；内部 Catalog 不变量错误不被一并降格。合法 CNB mirror-only 和真正执行
attempt 后的 `MIRROR_EXHAUSTED` 保持原语义。

### 4.5 缺失 app-root 的只读检查

`environment check` 不打开会要求 app-root 已存在的操作日志，也不创建 layout。它通过
filesystem 的受管路径检查识别明确的“目标不存在”，返回 `uvReady=false`；权限错误、普通文件
冒充目录、损坏状态、未知身份及任一 Reparse/Junction 仍失败关闭。适配限定于受控检查 API 的
typed absence，不在 CLI 广泛吞掉任意 `fs.ErrNotExist`。

## 5. 不变量

- stdout 仍只有进程入口持有，所有七类 NDJSON 事件经唯一 Emitter；
- hello 首发、sequence 连续、result 唯一且最后；错误与 result 四元组一致；
- 最终目录只接受已校验官方资产，no-replace、固定父句柄、身份重验与 Reparse 拒绝不回退；
- 失败仅清理由当前 operation ID 和身份 token 证明归属的临时对象；
- 用户目录 `config/data/history/script/debug/plugins` 及其身份和内容不变；
- offline 空缓存零 HTTP/Downloader/source attempt；check 缺失根零创建；
- 正常终态不残留 mutation，无法证明安全收口时保留恢复证据。
