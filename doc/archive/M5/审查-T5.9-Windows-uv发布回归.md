## 2. 根因与安全边界

`internal/uv.Bootstrapper.ensure` 从 `filesystem.PrepareManagedDirectory` 取得 staging
`DirectoryLease` 后，把 `Close` 延迟到整个 ensure 返回；同一函数随后调用
`filesystemPublisher.Publish`，最终由 `filesystem.AtomicRename` 重新 pin source。Windows 上原
lease 不共享 delete/rename，Runtime 因而把自己识别成 `DIRECTORY_OCCUPIED`。进程返回后 defer
关闭 lease，所以同一 staging 可被 PowerShell `Move-Item` 立即移动。

修复先从 lease 取得 `DirectoryIdentity`，显式检查并关闭 archive/staging lease，再把 token 交给
现有受控发布器。AtomicRename 仍在固定父句柄下重新 pin source，复验 volume/file-ID 后才执行
no-replace rename；未退回裸路径 `os.Rename`，也未增加 sleep 或重试来掩盖句柄泄漏。ZIP reader、
entry reader、解压输出文件的 Close 错误全部进入错误链，最终版本检查仍在发布后的正式路径执行。

M5 事务收口新增 `state.Store.RemoveOwnedTransaction`：先比较完整业务 snapshot，再复用
StateFiles 的物理 token 条件删除。另一 operation、stage 或读取后文件替换均不会被误删；取消后的
清理使用 `WithTimeout(WithoutCancel(ctx), 30s)`。普通成功、失败和取消删除自己的事务；状态写入、
身份不确定或删除失败保留恢复证据。
