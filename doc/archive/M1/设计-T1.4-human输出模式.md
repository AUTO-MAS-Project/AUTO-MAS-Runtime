# T1.4 human 输出模式设计

## 1. 目标

在不改变协议 v1 NDJSON wire format 的前提下，为同一组语义事件增加
确定性、可重定向、可快照测试的 human 文本渲染。

本设计采用已批准的方案 A：

> `Emitter` 只产生一次语义事件并补齐 `Common`；`ProcessOutput` 在同一
> 串行化临界区内把该事件交给选定的 NDJSON 或 human renderer。

两种输出共享 operationId、sequence、timestamp、事件顺序和错误传播，
不得各自维护一套 `Emit*` 业务路径。

## 2. 范围

T1.4 负责：

- 抽出可替换的事件 renderer；
- 保持 `NewProcessOutput(io.Writer)` 为 NDJSON 兼容入口；
- 增加显式 human renderer 构造入口；
- 定义七类事件的确定性 human 文本；
- 定义 stdout/stderr 路由、多行消息和 flush 规则；
- 证明同一 emitter 路径在两种 renderer 下收到相同的完整语义事件序列；
- 用 golden/snapshot 测试锁定 human 输出。

T1.4 不负责：

- CLI 参数解析、`--output human|ndjson` 接线和进程入口 writer 选择；
- 把 human 设为真实 CLI 默认值；T1.4 交付默认 human renderer，T3.1
  完成参数解析、模式接线和 CLI 默认值；
- ANSI 颜色、TTY 探测、原地刷新进度条或交互式终端 UI；
- stdin 控制、`commandId` 回显和状态查询；
- `result` 恰好一次且最后、warning 汇总和有界反压；
- 文件日志、状态持久化或命令编排。

## 3. 方案选择

### 3.1 采用：共享事件流水线后选择 renderer

优点：

- 语义事件、序号和时间戳只生成一次；
- NDJSON 与 human 不会分叉生命周期、终态或控制语义；
- `ProcessOutput` 的现有锁继续保证并发事件块不交错；
- T1.5 只需向语义事件写入控制信息；
- T1.6 可在 renderer 之前的同一锁内增加 terminal gate 和反压。

### 3.2 不采用：NDJSON 输出后再反解析

该方案引入无意义的序列化/解析往返，把 human 可用性绑定到机器协议二次
解析，并产生额外错误边界。

### 3.3 不采用：两套独立 `Emit*`

该方案会复制 sequence、错误、终态和控制回显逻辑，无法可靠证明两种
模式语义等价。

## 4. 组件与 API

### 4.1 EventRenderer

renderer 只投影已经补齐 `Common` 的事件，不创建事件、不修改事件、不
推进 sequence，也不参与生命周期判断。

```go
type EventRenderer interface {
    RenderHello(HelloEvent) error
    RenderProgress(ProgressEvent) error
    RenderState(StateEvent) error
    RenderLog(LogEvent) error
    RenderWarning(WarningEvent) error
    RenderError(ErrorEvent) error
    RenderResult(ResultEvent) error
}
```

采用七个强类型方法，不用 `any` 或反射作为公开分发契约。

### 4.2 构造入口

```go
func NewProcessOutput(output io.Writer) (*ProcessOutput, error)
func NewProcessOutputWithRenderer(renderer EventRenderer) (*ProcessOutput, error)

func NewNDJSONRenderer(output io.Writer) (*NDJSONRenderer, error)
func NewHumanRenderer(stdout, stderr io.Writer) (*HumanRenderer, error)
```

约束：

- `NewProcessOutput` 保持现有签名和 NDJSON 行为，内部创建
  `NDJSONRenderer`；
- 所有构造器拒绝 `nil`；
- 只有进程入口拥有 `os.Stdout` / `os.Stderr`；
- 业务包只接收 emitter 能力接口，不接收 writer 或 renderer；
- `OperationEmitter` / `LifecycleEmitter` 方法集合不变；
- `EmitLog` 不加入 `OperationEmitter`，后端日志能力以后单独定界。

### 4.3 ProcessOutput 与 Emitter

`ProcessOutput` 继续拥有：

- 唯一 emitter 预约状态；
- 全局 `nextSequence`；
- renderer 调用的互斥锁；
- 首次输出错误的 sticky 状态。

`Emitter.emit` 在持有同一把写锁时依次执行：

1. 若已有 sticky 输出错误，直接返回该错误；
2. 写入完整 `Common`；
3. 按事件强类型调用对应 renderer 方法；
4. renderer 完成写入和目标流 flush；
5. 成功后才递增 sequence；
6. write/flush 失败时保存并持续返回 `write protocol event: ...`；
7. NDJSON encode 失败保持现有的 `encode <type> event: ...` 非 sticky
   行为，不递增 sequence，也不污染后续合法事件。

renderer 调用全过程都在锁内，因此一个多行 human 事件是不可交错的输出块。
renderer 不得回调 emitter 或 `ProcessOutput`，避免重入死锁。

实现使用包内错误分类区分非 sticky 的 encode/format 错误和可能已经产生部分
输出的 sticky I/O 错误。普通第三方 renderer 返回的错误按 sticky 处理；
内置 NDJSON renderer 的 marshal 错误使用非 sticky 分类，以保持
`NewProcessOutput` 的既有错误语义。

## 5. Human 文本契约

### 5.1 通用规则

- UTF-8 纯文本，每个物理行以 `\n` 结束；
- 不输出 ANSI 转义序列，不探测 TTY；
- 类型标识、字段顺序、空值表示和标点固定；
- `—` 两侧各一个 ASCII 空格；
- 列表保持事件中的原始顺序，用逗号连接；
- 空列表显示为 `-`；
- 所有非 message 字符串先用 U+FFFD 替换非法 UTF-8，再依次把反斜杠、
  CR、LF 显示为 `\\`、`\r`、`\n`；
- 其余 Unicode control rune 必须显示为可见转义：U+0000～U+00FF 用
  `\xNN`，更高码位用 `\uNNNN`；因此 ESC 固定显示为 `\x1b`，不能形成
  ANSI 控制序列；
- 非 message 的空字符串显示为 `-`；
- 布尔值固定为小写 `true` / `false`，整数固定为十进制；
- 合法 v1 progress 事件的 percent 必须是可被 JSON 编码的有限数值，human
  使用 `strconv.FormatFloat(value, 'f', -1, 64)`；
- `details` 不做通用展开，避免巨大、不稳定或不可序列化值污染 human 输出；
- human 不承诺机器可解析，协议调用方仍必须使用 NDJSON。

### 5.2 七类事件格式与流路由

#### hello

目标流：stdout。

```text
HELLO runtime=<runtimeVersion> command=<command> capabilities=<a,b|->
```

#### progress

目标流：stdout。

```text
PROGRESS [<stage>] <status> [current=<n>] [total=<n>] [percent=<n>%] — <message>
```

可选字段只在事件中存在时输出，固定顺序为 `current`、`total`、`percent`。
百分比使用 `strconv.FormatFloat(value, 'f', -1, 64)`，不自行舍入。

#### state

目标流：stdout。

```text
STATE [<stage>] <status> — <message>
```

#### log

`stream == "stdout"` 时写 stdout；其他值写 stderr，以未知流失败关闭到诊断
通道。原始 `source` 和 `stream` 保留在前缀中。

```text
LOG [<source>:<stream>] — <message>
```

#### warning

目标流：stderr。

```text
WARNING [<stage>] <code> retryable=<bool> remediation=<a,b|-> — <message>
```

#### error

目标流：stderr。

```text
ERROR [<stage>] <code> retryable=<bool> remediation=<a,b|-> — <message>
```

#### result

`success == true` 时写 stdout；失败时写 stderr。

```text
RESULT success=<bool> code=<code> stage=<stage> status=<status> retryable=<bool> remediation=<a,b|-> — <message>
```

### 5.3 多行消息

所有 `message` 先用 U+FFFD 替换非法 UTF-8，再把 `\r\n` 和裸 `\r`
规范化为 `\n`，然后按逻辑行拆分，并保留中间空行和尾部空行。每个逻辑
行再执行与标量相同的反斜杠和 Unicode control rune 可见转义；逻辑换行
本身由 renderer 输出新的带前缀物理行，不参与转义。

首行使用完整前缀和 ` — `；后续每一行重复相同前缀并使用 ` | `：

```text
LOG [backend:stderr] — Traceback
LOG [backend:stderr] | second line
```

因此任何受管进程内容都不能伪装成无前缀的 Runtime 输出。
尾部空逻辑行仍输出续行前缀和 ` | `；这里用文字描述，避免 Markdown
源文件本身引入尾随空白。
输入中的 ESC、CSI 和其他控制字符也只能显示为可见文本，不能清屏、回写
或移动终端光标。

## 6. NDJSON 兼容性

`NDJSONRenderer` 从现有 `Emitter.emit` 迁移以下机械职责：

- `json.Marshal`；
- 追加单个 `\n`；
- buffered write；
- buffer flush；
- 对底层 `Flush() error` / `Flush()` 的兼容调用。

以下行为必须逐字节保持：

- hello 首发；
- 每行一个 JSON 对象；
- Common 字段和值不变；
- sequence 从 1 严格递增；
- 每个事件立即 flush；
- 并发输出不交错；
- 第二个 emitter 被拒绝；
- 首次 write/flush 错误成为 sticky 错误；
- marshal 失败继续返回 `encode <type> event: ...`，保持非 sticky。

## 7. 语义等价

对合法、可被 NDJSON 序列化的协议 v1 事件，“等价语义输出”定义为：

> 在固定 operationId 和 clock 下，同一组 `Emit*` 调用经 NDJSON 或 human
> renderer 时，共享流水线交给 renderer 的七类强类型事件序列完全相同，
> 包括 Common 和 payload；两种 renderer 只允许在文本投影和目标流路由上
> 不同。

测试使用 recording renderer 证明共享流水线补齐后的完整事件，不从 human
文本反向解析。相同事件夹具分别交给两个真实 renderer：NDJSON 做
wire/golden 断言，human 分别对 stdout/stderr 做 golden 断言。

该等价性不覆盖不可被 NDJSON 序列化的非法事件，例如 `details` 中含 channel
或函数值；human 忽略 details 不代表这类事件获得协议合法性。

## 8. 错误处理

- renderer 构造器的 nil writer/renderer 返回明确错误；
- marshal、write、buffer flush、底层 flush 任一失败都返回错误；
- NDJSON marshal 错误保持非 sticky：不写入、不递增 sequence，后续合法
  事件仍可输出；
- `ProcessOutput` 记录首次 write/flush 或普通第三方 renderer 错误，后续
  输出直接返回同一个 sticky 错误，不继续写入，也不递增 sequence；
- human 单个事件只路由到一个目标流，避免一次事件跨两个流部分成功；
- renderer 不自行向另一个流打印诊断，诊断展示由进程入口负责；
- human 不验证业务字段取值，未知 stage/code/status 仍按原字符串降级显示。

## 9. 并发与后续协议任务

T1.4 保留一个明确的串行化位置：

```text
Emitter.emit
  -> ProcessOutput lock
  -> Common/sequence
  -> future T1.6 terminal/backpressure gate
  -> EventRenderer
  -> flush
```

与后续任务的边界：

- T1.5 在语义层把 `controlCommandId` 写入事件；human 不推断控制确认；
- T1.5 的 status 快照作为普通 `STATE` 渲染，不触发生命周期迁移；
- T1.6 在 renderer 之前实现 `result` 恰好一次且最后；
- T1.6 的 warning 汇总由语义层完成，renderer 不吞掉或合并 warning；
- T1.6 若引入有界队列，其消费者仍必须在单一顺序域调用 renderer。

## 10. 测试矩阵

### 10.1 NDJSON 回归

- 现有七类事件字节格式、hello 首发和 sequence 测试全部保留；
- flush 与 sticky write error 行为不变；
- `NewProcessOutput` 仍默认创建 NDJSON renderer。

### 10.2 Human golden

- 七类事件的精确 stdout/stderr 快照；
- progress 的无可选字段、current、total、percent 及组合；
- warning/error/result 的 retryable 和 remediation 顺序；
- 成功/失败 result 的流路由；
- stdout/stderr/未知 log stream 路由；
- LF、CRLF、裸 CR、中间空行、空消息和尾随换行；
- 未知 stage/status/code 的透明降级文本；
- 所有非 message 字符串的反斜杠、CR、LF、空值、非法 UTF-8 和 Unicode
  control rune 规范化；
- message/log.message 中 ESC、C0/C1 control rune 的可见转义，断言输出
  不含原始 U+001B 或其他终端控制字符；
- stdout write 失败、stdout buffer/destination flush 失败；
- stderr write 失败、stderr buffer/destination flush 失败；
- 任一目标流失败后另一流也不再写，sequence 不递增且返回同一个 sticky
  错误；
- 每个事件只 flush 其目标流，非目标流不被 flush。

### 10.3 共享流水线

- recording renderer 接收 hello 和后续六类事件；
- 固定 clock/operationId 下 Common 与 payload 完整一致；
- NDJSON marshal 失败非 sticky，write/flush 和普通 renderer 失败 sticky；
- 并发多行 human 事件的输出块不交错；
- 不能创建第二个 emitter；
- `OperationEmitter` / `LifecycleEmitter` 方法集合无变化。

### 10.4 验收门禁

```powershell
$env:GOCACHE = Join-Path $env:TEMP "codex-auto-mas-runtime-gocache"
$unformatted = & gofmt -l .
if ($LASTEXITCODE -ne 0) { throw "gofmt failed" }
if ($unformatted) { $unformatted; throw "gofmt found unformatted files" }
& go vet ./...
if ($LASTEXITCODE -ne 0) { throw "go vet failed" }
& go test ./... -count=1
if ($LASTEXITCODE -ne 0) { throw "tests failed" }
& go build -buildvcs=false ./...
if ($LASTEXITCODE -ne 0) { throw "build failed" }
& git diff --check
if ($LASTEXITCODE -ne 0) { throw "diff check failed" }
```

并发相关改动还要按 `AGENTS.md` 第 5.3 节提升 GCC 目录优先级并执行
`go test -race ./... -count=1`；只有完整命令退出码为 0 才能声称 race 通过。

## 11. 验收标准

- 同一 emitter 路径支持 NDJSON 和 human renderer；
- 现有 NDJSON 输出逐字节兼容；
- human 七类事件格式、流路由和多行规则均被 golden 锁定；
- 两种 renderer 接收完全相同的语义事件序列；
- human 并发事件块不交错；
- 未扩大 operation/lifecycle emitter 能力；
- 未实现 T1.5、T1.6 或 T3.1 范围；
- 完整门禁通过后，`doc/任务拆分.md` 的 T1.4 才可勾选。
