# T7.6 发布成品版本命名设计

## 1. 目标与边界

后续 GitHub Release 直接发布的 Windows EXE 使用 `auto-mas-runtime-<version>.exe`，例如
`auto-mas-runtime-v0.1.0-beta.4.exe`。`<version>` 直接取 workflow 已完成安全校验的 release tag，
保留 `v` 前缀，不追加日期、时间或 Commit hash。

本任务只改变 Release 成品文件名以及 workflow 内传递该文件名的链路，不改变：

- Go 命令名、模块路径、版本协议或 `hello.runtimeVersion`；
- GitHub Actions 内部用于 job 间传递的 `runtime-release-assets` artifact 名；
- Electron 安装目录中的稳定运行名 `auto-mas-runtime.exe`；
- `SHA256SUMS.txt` 的文件名、两空格格式和 SHA-256 算法；
- 不签名、不创建 zip、不可覆盖既有 Release 的现有策略。

AUTO-MAS 集成流程下载某个已固定版本的 Release 时，应使用该版本精确构造 Release EXE 文件名，
校验 `SHA256SUMS.txt` 后再以 `auto-mas-runtime.exe` 落入 Electron 打包目录。

## 2. 名称来源

metadata 步骤在 release tag 通过既有安全校验后生成：

```text
auto-mas-runtime-<release tag>.exe
```

现有 tag 规则只允许 ASCII 字母、数字、点、连字符和下划线，并排除 Git ref 危险模式，因此可安全
用作 Windows 文件名的一部分。文件名与 linker 注入的 `Version` 共用同一个 release tag 来源。

## 3. Workflow 数据流

`package` 的 metadata 步骤生成唯一 `binary_name` 输出。构建、SHA-256 生成和 artifact 上传均
使用该输出；`publish` 通过 `needs.package.outputs.binary_name` 精确发布对应文件；`smoke` 使用同一
输出从 Release 精确下载并验证唯一 EXE。任何一步找不到该精确名称或发现额外 EXE 都失败关闭。

`SHA256SUMS.txt` 的记录对象必须是动态 EXE 文件名。后续消费者不得假设 Release 资产仍固定为
`auto-mas-runtime.exe`，也不得用不受约束的通配符静默选择多个文件。

## 4. 验收

- 静态契约测试固定 release tag 与文件名、linker `Version` 的共源关系；
- 动态名称贯通构建、上传、发布和下载；
- 原有裸 EXE、SHA-256、不可变 Release 和 NDJSON smoke 契约继续成立；
- PowerShell 7 AST 能解析 workflow 全部 `run` block；
- `gofmt`、`go vet`、`go build`、`go test` 和 `git diff --check` 全绿。
