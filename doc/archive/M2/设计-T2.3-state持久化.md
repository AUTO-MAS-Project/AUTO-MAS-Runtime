- 架构基线：[架构设计](../../架构设计.md)

本文冻结 `runtime-state` 中四个 JSON 文件的职责、schema、原子写入、
错误分类和陈旧事务判定。事务状态只辅助诊断与中断恢复，Windows 命名
Mutex 才是跨进程占用的真实依据。

## 目标与范围

T2.3 交付以下能力：

1. 分别读写 `backend.json`、`mutation.json`、`update.json` 三类事务状态；
2. 独立读写 `environment.json` 稳定环境状态；
3. 冻结 `schemaVersion=1`、完整结构体字段和严格语义校验；
4. 通过 T2.5 StateFiles 固定祖先目录句柄，以每 kind 持久 shared/exclusive guard、
   sealed intent、两次 no-replace rename 和 intent-aware Read 提供逻辑 old/new 与
   进程崩溃恢复；
5. 区分文件不存在、损坏、schema 不支持、普通读取故障和写入故障；
6. 将所有持久化写故障稳定映射为 `STATE_WRITE_FAILED`；
7. 通过 Mutex 与 PID 两个独立探针分类 active、stale、inconsistent 和
   unknown；
8. 提供基于 Windows 进程查询 API 的 `SystemPIDProbe` 生产实现；
9. 只允许 stale 事务进入自动清理流程；
10. 注入时钟，确定性生成开始与更新时间。

本任务不实现 Windows 命名 Mutex、进程枚举或终止、目录替换恢复、生命周期
状态机迁移、协议事件输出或业务命令编排。PID 探针只按已知 PID 查询单个
进程是否仍存活。

## 文件职责

所有路径必须来自同一个 `*config.Layout`：

| 文件 | 结构 | 所有权与用途 |
| --- | --- | --- |
| `backend.json` | `TransactionState` | 当前 `backend supervise` 的诊断状态；真实占用由 `backend` Mutex 决定 |
| `mutation.json` | `TransactionState` | 当前受管变更顶层操作；真实占用由 `mutation` Mutex 决定 |
| `update.json` | `TransactionState` | mutation 内部 Git 替换阶段的恢复线索；与 `mutation` 共用同一 Mutex |
| `environment.json` | `EnvironmentState` | 跨 Runtime 进程保留的稳定环境真相，不表示事务占用 |

四个文件不得合并或通过彼此是否存在推断状态。特别是：

- `backend.json`、`mutation.json`、`update.json` 残留不表示进程仍活跃；
- `environment.json` 不存在表示尚无持久化稳定环境，由上层解释为
  `uninitialized`，不得写入 `status=uninitialized`；
- `environment.json` 存在时只允许 `environment_broken` 或
  `ready_to_start`；
- `update.json` 可以在崩溃后脱离 `mutation.json` 单独残留，此时由 T4.5
  结合目录身份恢复，state 包不得擅自判定或删除目录。

## Schema 版本与公共约束

四类顶层对象均固定包含：

```json
{
  "schemaVersion": 1
}
```

`schemaVersion` 必须是 JSON integer，首版唯一支持值为 `1`。未来版本只能
新增版本并提供显式迁移；不得把未知版本按 v1 尝试解码或原地覆写。

状态文件使用 UTF-8、单个 JSON object 和一个结尾换行。读取器施加
256 KiB 上限，并严格拒绝：

- 空文件、`null`、数组或多个顶层 JSON 值；
- BOM、非法 UTF-8 和截断 JSON；
- 重复字段、未知字段和缺失的必需字段；
- 类型不匹配、非整数数值和违反下文语义的值。

读取先用严格 token 扫描确认对象、重复键和 `schemaVersion`，再使用
`json.Decoder.DisallowUnknownFields` 解码具体结构，并确认 EOF。缺失或
类型错误的 `schemaVersion` 属于损坏；合法整数但不是 `1` 属于不支持的
schema。

## 事务状态

### 文件类型

```go
type TransactionKind string

const (
    TransactionBackend  TransactionKind = "backend"
    TransactionMutation TransactionKind = "mutation"
    TransactionUpdate   TransactionKind = "update"
)

func (k TransactionKind) String() string
func (k TransactionKind) Valid() bool
```

未知类型不能映射到任意路径，必须在文件 I/O 前返回校验错误。

### 数据结构

三类事务文件共享同一个完整结构：

```go
type TransactionState struct {
    SchemaVersion int            `json:"schemaVersion"`
    OperationID   string         `json:"operationId"`
    Command       string         `json:"command"`
    PID           uint32         `json:"pid"`
    StartedAt     time.Time      `json:"startedAt"`
    TargetVersion string         `json:"targetVersion"`
    Stage         protocol.Stage `json:"stage"`
}

type TransactionInput struct {
    OperationID   string
    Command       string
    PID           uint32
    TargetVersion string
    Stage         protocol.Stage
}

type TransactionSnapshot struct {
    // kind、state 与 filesystem snapshot 均不导出。
}

func (s TransactionSnapshot) Kind() TransactionKind
func (s TransactionSnapshot) State() TransactionState
```

所有 JSON 字段始终存在，不使用 `omitempty`。没有目标版本的合法命令用空
字符串表示 `targetVersion`，而不是缺失或 `null`。

示例：

```json
{
  "schemaVersion": 1,
  "operationId": "01ARZ3NDEKTSV4RRFFQ69G5FAV",
  "command": "workspace sync",
  "pid": 12345,
  "startedAt": "2026-07-29T09:10:11.1234567Z",
  "targetVersion": "v5.4.0-beta.1",
  "stage": "workspace.swap"
}
```

### 事务语义校验

`ValidateTransaction` 对内存值和磁盘值执行同一组规则：

1. `SchemaVersion` 必须为 `1`；
2. `OperationID` 必须是 26 字符的大写规范 ULID；
3. `Command` 必须是下表对应类型允许的稳定命令名；
4. `PID` 必须大于 `0`；
5. `StartedAt` 必须非零且能以 RFC 3339 Nano 表示；不按当前时间拒绝“未来”
   时间，避免系统时钟回拨导致状态不可读；
6. `Stage` 必须是 `protocol.IsKnownStage` 接受的值，并属于对应文件的阶段
   集；
7. 非空 `TargetVersion` 必须通过包内共享的 product-version validator：以 `v` 开头，
   仅含 ASCII 字母、数字、点、连字符和下划线，长度不超过 128，且不含
   `..`、`@{` 或结尾点；要求目标版本的命令中不得为空，其他命令中允许
   为空；
8. 字符串不得含 NUL，错误文本不得回显未经清洗的文件内容。

类型、命令和阶段约束固定为：

| 类型 | 合法命令 | 合法 stage | `targetVersion` |
| --- | --- | --- | --- |
| `backend` | `backend supervise` | `backend.spawn`、`backend.health`、`backend.run`、`backend.restart`、`backend.shutdown`、`backend.cleanup` | schema 允许空；managed 调用方必须传非空，development 固定传空 |
| `mutation` | `bootstrap`、`workspace sync`、`environment ensure`、`environment repair`、`dependencies sync`、`dependencies rebuild`、`repair`、`cleanup` | 对应命令使用的 `bootstrap`、`repair`、`cleanup`、`uv.*`、`workspace.*`、`python.*`、`dependencies.*` | `bootstrap`、`workspace sync` 必须非空；其余允许空 |
| `update` | `bootstrap`、`workspace sync` | `workspace.clone`、`workspace.verify`、`workspace.swap`、`workspace.cleanup` | 必须非空 |

`mutation` 的 command-stage 对应关系进一步冻结为：

| command | 合法 stage |
| --- | --- |
| `bootstrap` | `bootstrap`、全部 `uv.*`、`workspace.*`、`python.*`、`dependencies.*` |
| `workspace sync` | `workspace.check`、`workspace.clone`、`workspace.verify`、`workspace.swap`、`workspace.cleanup` |
| `environment ensure` | `uv.check`、`uv.download`、`uv.verify` |
| `environment repair` | `uv.check`、`uv.download`、`uv.verify`、`python.check`、`python.install` |
| `dependencies sync` | `dependencies.check`、`dependencies.sync` |
| `dependencies rebuild` | `dependencies.check`、`dependencies.rebuild`、`dependencies.sync` |
| `repair` | `repair`、全部 `uv.*`、`python.*`、`dependencies.*` |
| `cleanup` | `cleanup`、`workspace.cleanup` |

state 包只校验目标版本的安全结构，不负责验证 SemVer、发布分支存在性或
仓库版本文件；完整版本语义属于 T4.1。stage 更新必须保留原
`OperationID`、`Command`、`PID`、`StartedAt` 和 `TargetVersion`。

同一 product-version validator 还用于环境状态的 `LastSuccessful.Version` 和
`Broken.TargetVersion`，不能让磁盘读取绕过事务输入规则。Python/uv 版本使用共享
tool-version validator：1～128 个 ASCII 字母、数字、点、连字符或下划线，不含 `..`、
`@{`、尾点、NUL 或控制字符；它只验证安全结构，不代替 T5 的精确版本选择。

## 稳定环境状态

### 数据结构

```go
type Revision struct {
    Version string `json:"version"`
    Commit  string `json:"commit"`
}

type BrokenReason string

const (
    ReasonRepositoryChanged BrokenReason = "repository_changed"
    ReasonOperationFailed   BrokenReason = "operation_failed"
)

func (r BrokenReason) String() string
func (r BrokenReason) Valid() bool

type BrokenEnvironment struct {
    TargetVersion string         `json:"targetVersion"`
    Branch        string         `json:"branch"`
    Commit        string         `json:"commit"`
    PythonVersion string         `json:"pythonVersion"`
    UVVersion     string         `json:"uvVersion"`
    Reason        BrokenReason   `json:"reason"`
    Stage         protocol.Stage `json:"stage"`
    ExitCode      int            `json:"exitCode"`
    LogPath       string         `json:"logPath"`
}

type EnvironmentState struct {
    SchemaVersion  int                  `json:"schemaVersion"`
    Status         protocol.StateStatus `json:"status"`
    UpdatedAt      time.Time            `json:"updatedAt"`
    LastSuccessful Revision             `json:"lastSuccessful"`
    Broken         *BrokenEnvironment   `json:"broken"`
}
```

`lastSuccessful` 始终是 object，不输出 `null`。从未成功到达
`ready_to_start` 时，它的 `version` 和 `commit` 同时为空。`broken` 字段
始终存在：ready 状态固定为 `null`，broken 状态固定为完整 object。

ready 示例：

```json
{
  "schemaVersion": 1,
  "status": "ready_to_start",
  "updatedAt": "2026-07-29T09:20:00Z",
  "lastSuccessful": {
    "version": "v5.4.0-beta.1",
    "commit": "0123456789abcdef0123456789abcdef01234567"
  },
  "broken": null
}
```

broken 示例：

```json
{
  "schemaVersion": 1,
  "status": "environment_broken",
  "updatedAt": "2026-07-29T09:22:00Z",
  "lastSuccessful": {
    "version": "v5.3.0",
    "commit": "89abcdef0123456789abcdef0123456789abcdef"
  },
  "broken": {
    "targetVersion": "v5.4.0-beta.1",
    "branch": "release/v5.4.0-beta.1",
    "commit": "0123456789abcdef0123456789abcdef01234567",
    "pythonVersion": "3.12.10",
    "uvVersion": "0.8.0",
    "reason": "operation_failed",
    "stage": "dependencies.sync",
    "exitCode": 1,
    "logPath": "D:\\AUTO-MAS\\logs\\runtime\\dependencies-sync-20260729.log"
  }
}
```

独立 `workspace sync` 实际替换 active revision 后、尚未同步依赖时使用
`reason="repository_changed"`、`stage="workspace.swap"`、`exitCode=0`。此时
Python/uv 版本可以为空表示 unknown；它描述的是“新仓库对应的主环境尚未重新证明可用”，
而不是把成功的 Git 操作伪装成失败。

### 环境语义校验

`ValidateEnvironment` 固定执行：

1. `SchemaVersion == 1`；
2. `Status` 只能是 `protocol.StateEnvironmentBroken` 或
   `protocol.StateReadyToStart`；
3. `UpdatedAt` 非零且可表示为 RFC 3339 Nano；
4. `LastSuccessful.Version` 与 `Commit` 必须同时为空或同时非空；非空 Version 必须
   通过共享 product-version validator；
5. 非空 Commit 必须是 40 个小写十六进制字符；
6. `ready_to_start` 要求 `LastSuccessful` 两字段非空且 `Broken == nil`；
7. `environment_broken` 要求 `Broken != nil`，允许
   `LastSuccessful` 两字段同时为空；
8. broken 的目标版本、分支、Commit、Reason、Stage 和日志路径非空；
   TargetVersion 必须通过 product-version validator，uv/Python 的非空值必须通过
   tool-version validator，Reason 必须通过 `BrokenReason.Valid()`；
9. `Branch` 必须精确等于 `"release/" + TargetVersion`，Commit 为 40 个
   小写十六进制字符；
10. `reason=repository_changed` 固定要求 `Stage=workspace.swap`、`ExitCode=0`；
    PythonVersion/UVVersion 均允许为空表示 unknown；
11. `reason=operation_failed` 的 Stage 必须是 `workspace.cleanup`、
    `python.check/install` 或 `dependencies.check/sync/rebuild` 之一；保存具体失败
    叶子阶段，不保存 `workspace.swap`、`bootstrap` / `repair` 包装阶段或任何后端、
    只读阶段；
12. operation_failed 在 `workspace.cleanup` 或 `python.check` 时允许
    PythonVersion/UVVersion 为空表示 unknown；进入 `python.install` 后 uv 版本和
    Python 版本必须非空，进入 `dependencies.*` 后两者同样必须非空；
13. operation_failed 的 `ExitCode` 必须大于 0；子进程尚未启动的失败保存该结构化
    主错误的 Runtime 退出码；
14. `LogPath` 必须是 `config.Layout.RuntimeLogDir()` 内的绝对路径；这里只做
    词法归属校验，Reparse Point 安全仍属于 T2.5；
15. 版本、分支、工具版本和路径不得含 NUL 或控制字符，并施加合理长度
    上限。

进入 broken 时必须保留最近一次成功 revision，不能把目标 revision 误写成
`lastSuccessful`。只有目标环境完整同步成功并进入 `ready_to_start` 后，
ready 构造器才把本次版本和 Commit 写入 `lastSuccessful` 并清空 broken
详情。

`environment_broken` 的前置事实是：调用方已经通过仓库版本文件和 Git HEAD 确认 active
`RepoDir()` 对应 Broken 的 TargetVersion/Branch/Commit，且本次操作已经改变受管 repo、
Python 或 venv，使主环境不可启动。Store 只验证字段结构，无法替调用方证明磁盘事实。

准备 uv (`uv.check/download/verify`) 失败不会改变 active Git 或主环境，因此首次
bootstrap 保持无 environment 文件，已有 ready/broken 状态则保持原值；不得写入假的
Commit 或假定目标 branch。`workspace.swap` 失败时 active repo 身份可能未决，只保留
update transaction 供 T4.5 恢复，也不得写 environment_broken。只有实际 swap 已生效且
active revision 已确认时才写 `repository_changed`；确认 active revision 与目标完全相同、
没有执行 swap 的 no-op sync 必须逐字节保留原 ready/broken 状态。swap 生效后若状态写入
失败，调用方必须返回 `STATE_WRITE_FAILED`、保留 update transaction，且不得把 workspace
sync 报告为成功；T4.5 恢复在确认唯一 active repo 后补写 `repository_changed`。
`workspace.cleanup` 失败则把同一 active revision 更新为 `operation_failed`。

## Store API

```go
const SchemaVersion = 1

type Option func(*options) error

func WithClock(clock func() time.Time) Option

type Store struct {
    // 具体字段不公开；Store 只能通过指针使用。
}

func NewStore(
    ctx context.Context,
    layout *config.Layout,
    options ...Option,
) (*Store, error)

func (s *Store) NewTransaction(
    kind TransactionKind,
    input TransactionInput,
) (TransactionState, error)

func (s *Store) NewReadyEnvironment(
    version string,
    commit string,
) (EnvironmentState, error)

func (s *Store) NewBrokenEnvironment(
    lastSuccessful Revision,
    broken BrokenEnvironment,
) (EnvironmentState, error)

func ValidateTransaction(
    kind TransactionKind,
    value TransactionState,
) error

func (s *Store) ValidateEnvironment(value EnvironmentState) error

func (s *Store) ReadTransaction(
    ctx context.Context,
    kind TransactionKind,
) (TransactionSnapshot, error)

func (s *Store) WriteTransaction(
    ctx context.Context,
    kind TransactionKind,
    value TransactionState,
) error

func (s *Store) RemoveTransaction(
    ctx context.Context,
    snapshot TransactionSnapshot,
) error

func (s *Store) ReadEnvironment(
    ctx context.Context,
) (EnvironmentState, error)
func (s *Store) WriteEnvironment(
    ctx context.Context,
    value EnvironmentState,
) error
func (s *Store) Close() error
```

`NewStore` 接受具体 `*config.Layout`，不接受任意路径 map；nil ctx/layout、
nil clock 和非法 option 在任何文件 I/O 前拒绝。生产构造器内部创建
`filesystem.NewStateFiles(ctx, layout)` 并由 Store 拥有，所有 read/write/remove
都通过该能力；同包 `newStoreWithDependencies` 在任何 state I/O 前注入 files/clock
替身。默认 clock 为 `time.Now`。构造器把 clock
结果规范为 UTC、去除 monotonic 部分，并且每次构造状态只调用一次 clock。
每 kind 持久 guard `G` 与 `I/J/T/B` 事务 leaf 都是 StateFiles 私有实现；Store
不接收、不返回、不探测这些名称或 handle，也不新增对应 `config.Layout` getter。
Store 的 Read 是业务状态只读：不得写、rename 或 unlink 四个权威 JSON payload 和
sealed-intent 现场；但首次 StateFiles 操作允许竞态安全创建缺失的持久 `G`，这是唯一
由读取触发的协调元数据副作用，不得被解释为业务状态变更。
全部 I/O 方法拒绝 nil ctx。读取可在 StateFiles 返回后再次检查取消；写入与删除只在
开始副作用前检查，并在 StateFiles 返回后优先保留底层结果和
`MutationApplied/RecoveryRequired`。若 commit、恢复、finalize 或 disposition 已经产生
磁盘事实，返回前恰好发生的取消不能把它改写成普通 context error，也不能触发 Store
自行回滚或删除新目标。Store 完成自身 context 预检后、StateFiles 执行其 I/O 前预检前，
context 仍可能合法地被取消或超时；此时
`WriteAtomicResult{MutationApplied: false, RecoveryRequired: false}`，StateFiles
直接返回未包装成
`StateWriteError` 的 `context.Canceled` / `context.DeadlineExceeded`，Store 原样透传，
不包装 `WriteError`。

`NewTransaction` 设置 `SchemaVersion` 和 `StartedAt`。
`NewReadyEnvironment` / `NewBrokenEnvironment` 设置 `SchemaVersion`、
`Status` 和 `UpdatedAt`，随后立即执行完整校验。`Write*` 不暗中修改调用方
时间或字段；同一事务推进 stage 时必须保留原始 `StartedAt`。

`ReadTransaction` 把已校验 TransactionState 与 T2.5 不可伪造的 StateFileSnapshot
绑定；getter 返回值拷贝，调用方不能改写删除 token。`RemoveTransaction` 只接受同一
Store 读取的 TransactionSnapshot，用于正常所有者完成或 stale 协调后的条件清理。
`RemoveTransaction` 使用的 StateFiles conditional remove 必须先取得 exclusive `G`
并完成只读 namespace/identity preflight。若 fixed `I` 与 `D` 均 stable absent，则在
任何 POSIX probe 前直接返回
`StateRemoveResult{MutationApplied:false, RecoveryRequired:false}, nil`。namespace 已稳定、
fixed intent 不存在且 `D` 存在时，才重新打开 `D` 并在同一 handle 上重验 file ID 与
完整 payload；snapshot mismatch 同样在 probe 前适配为 `ErrTransactionChanged`。只有
preflight 确认本请求确实要执行 W0 recovery/cleanup 或已匹配 snapshot 的权威 `D`
同 leaf handle POSIX unlink 时，才探测并证明该能力；此时 unsupported 才返回错误且无
fallback。active/foreign/不一致现场直接拒绝删除。StateFiles 持有 gate 穿过 W0、恢复、
unlink 与所有协议 handle 关闭。事务内部 gap 不得当作文件不存在；同名替换、原地修改或
无法恢复返回 `ErrTransactionChanged` / recovery 错误，且不删除当前对象。

Store 完整保留 StateFiles 的
`StateRemoveResult.MutationApplied/RecoveryRequired`：POSIX namespace unlink 已成功
但 CloseHandle/最终 `G` close 失败时，返回
`WriteError{Phase: WritePhaseRemove, MutationApplied: true,
RecoveryRequired: true}`；stable missing 或 snapshot mismatch 后最终 `G` close 失败
则返回 `false/true`。调用方不得把已 unlink 的事务文件当作仍存在，也不得从本地
Operation 字符串猜测 recovery。
state 包不提供删除 `environment.json` 的通用 API，避免普通 cleanup 把稳定
环境退化成隐式 `uninitialized`。未来若需要卸载或显式重置，必须另行设计
带业务授权的操作。

`Close` 幂等关闭 StateFiles 固定的目录句柄；第一次结果被缓存。Close 后
全部 I/O 方法返回 `ErrClosed`，构造状态和纯校验函数仍可使用。Store 不依赖
垃圾回收释放句柄。

## 严格读取与错误分类

提供以下 sentinel 和类型化错误：

```go
var (
    ErrNotFound          = errors.New("state file not found")
    ErrCorrupt           = errors.New("state file is corrupt")
    ErrUnsupportedSchema = errors.New("state schema is unsupported")
    ErrTransactionChanged = errors.New("state transaction changed")
    ErrClosed            = errors.New("state store is closed")
)

type NotFoundError struct {
    File string
    Path string
}

type CorruptError struct {
    File  string
    Cause error
}

type ValidationError struct {
    Field string
    Cause error
}

type UnsupportedSchemaError struct {
    File string
    Got  int
}

type ReadError struct {
    File  string
    Cause error
}

func (e *NotFoundError) Error() string
func (e *NotFoundError) Is(target error) bool
func (e *CorruptError) Error() string
func (e *CorruptError) Is(target error) bool
func (e *CorruptError) Unwrap() error
func (e *UnsupportedSchemaError) Error() string
func (e *UnsupportedSchemaError) Is(target error) bool
func (e *ReadError) Error() string
func (e *ReadError) Unwrap() error
func (e *ValidationError) Error() string
func (e *ValidationError) Unwrap() error
```

`ValidationError` 的 Field 使用稳定 Go/JSON 字段短名，Cause 包装具体 sentinel；
不得回显原始文件值。`File` 使用固定逻辑名 `backend`、`mutation`、`update` 或 `environment`。
路径来自受管布局，可以进入本地诊断日志，但错误字符串不得包含原始 JSON。
`NotFoundError`、`CorruptError`、`UnsupportedSchemaError` 的 `Is` 分别匹配对应
sentinel；`ValidationError` 不在该 `Is` 约定内，`ReadError` 保留底层错误链。

分类规则：

| 场景 | 返回 |
| --- | --- |
| StateFiles 返回 `filesystem.ErrStateFileNotFound` | `NotFoundError`，`errors.Is(err, ErrNotFound)` 为 true |
| JSON/UTF-8/大小/字段/语义非法 | `CorruptError`，`errors.Is(err, ErrCorrupt)` 为 true |
| `schemaVersion` 是合法 integer 但不是 `1` | `UnsupportedSchemaError`，`errors.Is(err, ErrUnsupportedSchema)` 为 true |
| 权限、共享冲突或普通读取 I/O 失败 | `ReadError`，保留底层错误链 |
| sealed intent 无法恢复、fixed intent 非 sealed 或 namespace 身份不一致 | `ReadError`，保留 `filesystem.ErrStateRecoveryRequired` / `filesystem.ErrIdentityChanged` 链 |

StateFiles 读取超限时必须保留
`errors.Is(err, filesystem.ErrStateFileTooLarge)`；Store 只通过该 sentinel 把错误转换为
`CorruptError{File: file, Cause: err}`，不得依赖错误文本，也不解析
`FileError.Operation`。这样分配前的大小检查和有界读取发现的竞态增长使用同一稳定分类，
同时保留 `ErrStateFileTooLarge` 与底层 `FileError` 链。

`NotFoundError` 只能由 adapter 在
`errors.Is(err, filesystem.ErrStateFileNotFound)` 为 true 时构造；该 sentinel 只来自
StateFiles 持有 shared `G` 时确认 fixed intent 与 `D` 均不存在，并且成功关闭 gate 后
返回的稳定 missing 结果。底层 raw `fs.ErrNotExist`、Win32 name-not-found 或普通
`FileError` 即使文本相似也必须包装成 `ReadError`，不得误分类。direct-absent commit
前 crash 遗留的未引用 `T/J` 不改变 stable missing 结论，只报告且不猜删。active writer
持有 exclusive `G` 时 Read 必须 context-aware 等待，不能观察 `D -> B` 与 `T -> D`
之间的内部 gap。sealed `I` 且 `D=X/B=O/T=N` 时，`X` 必须能从 same-parent handle
安全打开、ordinary/non-reparse/single-link、identity/digest 可查询且已证明既非 `O`
也非 `N`；StateFiles 才能由 envelope 与 `B=O` 唯一证明 old，Store 必须通过真实
adapter 解码该 old snapshot，inspectable foreign `X` 保持原 file ID 与字节不变，这
不是 ReadError。不存在可唯一证明 old 的 `B/envelope`，或 `D` opaque/unopenable、
Reparse/hardlink/identity 不可证明，或 `B`/intent 的 ordinary、identity、size、digest、
root/kind/leaf 条件不成立时，才返回保留 recovery/identity 链的 `ReadError`。上述情况以及 `G` close
失败都不得映射为 `ErrNotFound`。Store 不读取 raw `D/B` 路径，也不把 `G/B` 是否存在
暴露给调用方。

损坏和不支持 schema 都不得自动覆写、降级为空状态或删除。调用方可以在
doctor 中报告差异；涉及 Git 恢复时由 T4.5 按 `UPDATE_STATE_AMBIGUOUS`
失败关闭。

## 原子写入

### Store 与 StateFiles 边界

每次 `WriteTransaction` 或 `WriteEnvironment` 固定执行：

1. 对内存结构执行完整校验，失败时不触碰文件系统；
2. 以 `json.MarshalIndent` 生成稳定 UTF-8 object 并追加一个换行；
3. 把 TransactionKind 或 environment 映射为 T2.5 的封闭 StateFileKind；
4. 调用 `StateFiles.WriteAtomic(ctx, kind, payload)`，保留
   `WriteAtomicResult.MutationApplied/RecoveryRequired` 和 typed error；
5. 仅根据返回的 commit/recovery 事实分类，不自行打开、rename 或删除任何 raw
   destination、intent、backup 或 temp leaf。

StateFiles 独占 guard 与 sealed-intent 协议：WriteAtomic 每次都在任何 W0/`I/D` 判断前
取得 exclusive `G` 并完成只读 preflight；即使 fixed `I/D` 均 stable absent，也必须在
任何 W0、`T/J` 创建或其他可能需要 unlink 收口的副作用前证明
`FileDispositionInfoEx(FILE_DISPOSITION_FLAG_DELETE |
FILE_DISPOSITION_FLAG_POSIX_SEMANTICS)` 会立即移除 namespace 名称。不支持或语义不明时
在任何本次副作用前失败关闭，且无 classic/path fallback。目标不存在时在 gate 内重新确认
namespace，再以 payload temp 到固定目标的 no-replace rename 提交；目标存在时发布完整 sealed intent，
以旧对象同一 handle `D -> B`，再以新对象同一 handle `T -> D`，两次 rename 均
no-replace。第二次 rename 成功是新 payload 的唯一 commit 点。StateFiles 的持久
guard、固定 intent、随机
intent-staging、payload temp 与 backup leaf 都是固定 `runtime-state` 目录 handle 下的
私有对象，不是 `config.Layout` getter，也不得泄露给 Store；cleanup 永不删除 `G`。

Store 只通过 `StateFiles.Read` 读取逻辑值。该入口取得 shared `G`，在 gate 内根据 sealed
intent 与 `D/B/T` 选择权威 payload handle，或形成稳定 missing；选中 handle 后可释放
gate 再有界读取。active writer 的 raw `D` gap 期间 Read 等待 exclusive gate 释放，
随后返回 commit 后的 new 或 rollback 后的 old，不在 gap 中即时读取 `B`。raw path
reader 可能看到 `NOT_FOUND`，但 Store 不得看到内部 gap、foreign `D`、guard 或 backup
名称；`D=X/B=O` 时只得到已证明的 `B=O` old payload，绝不把 `X` 作为结果。intent
二次探测只能是 StateFiles 的防御性检查，不承担 ABA 或线性化正确性。
固定 intent 损坏、reserved leaf 身份不一致或无法唯一判断 old/new 时，Store 返回保留
稳定 filesystem recovery/identity sentinel 的 `ReadError`。

进程内同一 `Store` 的写入和删除仍由 mutex 线性化。上层业务正常持有 T2.4 对应 Lease，
但 Lease 不是 StateFiles 文件协议的正确性前提；Store 不因自己持有 Lease 而跳过 intent、
share mode、no-replace 或 identity 检查。

### 失败、提交与恢复

`WriteAtomicResult` 的语义固定为：

- `MutationApplied=true`：当前请求的新 payload 已越过 `T -> D` commit 点；
- `MutationApplied=false`：新 payload 未 commit，不表示 raw `D` 从未移动；旧对象可能
  已由同一 handle 移到 `B`，Read 仍可返回逻辑 old；
- `RecoveryRequired=true`：返回时仍有未完成 rollback/finalize、无法证明关闭的 handle，
  或存在必须保留的 intent/reserved-name 身份异常；
- nil error 的成功结果固定为
  `{MutationApplied: true, RecoveryRequired: false}`。

commit 前失败时，StateFiles 只能用原 `O` handle 执行 `B -> D` no-replace rollback；
竞争者 `X` 占据 `D` 时绝不覆盖或删除 `X`，并保留 sealed intent、`B=O` 和 `T=N`。
commit 后只按 backup → intent → handles 顺序 finalize，绝不 rollback `D=N`。
post-commit finalize 或 close 失败固定返回
`MutationApplied=true, RecoveryRequired=true`。Store 必须原样保留这些事实并返回
`STATE_WRITE_FAILED`，不能因 `MutationApplied=false` 就假定 raw 目标未变化，也不能因
`MutationApplied=true` 重新写入同一业务状态。

post-commit finalize 固定先以精确 POSIX flags unlink `B`，在旧 reader/原 handle 仍
打开时证明名称 absent，再 unlink `I`。W0 探测/恢复故障映射 recover，当前请求
rollback/finalize unlink 故障映射 finalize，namespace unlink 后 close 故障映射 close；
Store 只消费 typed phase/result，不解析 Win32 或 Operation 文本。

没有 sealed intent 引用的孤立 intent-staging/payload-temp 是 publish 前 crash 的
sidecar；Store 与 StateFiles.Read 都忽略它们，自动流程不得按名称前缀猜测删除。
StateFiles 只承诺进程崩溃后的可判定恢复；payload 与 intent 虽执行
`FlushFileBuffers`，但不承诺断电后的目录项耐久性。

`RemoveTransaction` 把 snapshot 交回 StateFiles。StateFiles 必须先恢复或拒绝 fixed
intent；它在任何 W0/intent/`D` 判断前取得 exclusive `G`，持有 gate 穿过恢复、对稳定
`D` 的同一 leaf handle 重读/比对/POSIX namespace unlink 和全部协议 handle close，最后关闭
`G`。snapshot 来自逻辑 `B=O` 时也不能直接删除 `B`。active writer 期间等待 gate 或
响应 context；identity/payload 已变化映射为
`ErrTransactionChanged`，recovery/identity 错误保留原链。除该单独分类外，Store 按当前
调用语境把条件删除故障标记为 `WritePhaseRemove`，完整复制
`StateRemoveResult.MutationApplied/RecoveryRequired`，不检查或解析
`FileError.Operation`。StateFiles 在 gate 内证明 sealed `I` 与 `D` 均 absent 后，必须
不调用 POSIX probe 而直接返回 `{false,false}, nil`；unsupported 平台仍幂等成功，
orphan `J/T` 只报告。stable `D` snapshot mismatch 也在 probe 前决定。固定分类为：
pre-I/O 或 gate wait cancel 是 `false/false`；
foreign/未恢复 intent、unlink 不明确，或尚未发生权威 `D` POSIX unlink commit 时最终
`G` close 失败，是 `false/true`；stable missing 与 snapshot mismatch 正常收口是
`false/false`；`D` unlink 后正常收口是 `true/false`，commit 后任何 finalize/leaf
close/最终 `G` close 失败都是 `true/true`。

clean snapshot mismatch（result `{false,false}` 且只有
`filesystem.ErrIdentityChanged`）直接返回匹配 `ErrTransactionChanged` 的错误，不包装
`WriteError`。若 mismatch 之后最终 `G` close 又失败，filesystem 以
`StateRemoveError` 分离 identity 主因与 close 次因；Store 返回
`*WriteError{Phase:WritePhaseRemove, MutationApplied:false, RecoveryRequired:true}`，
`Cause` 映射后匹配 `ErrTransactionChanged`，`CleanupError` 保留 close 链，
`WriteError.Unwrap()` 使 `errors.Is` 同时命中两者。权威 `D` unlink commit 后的
finalize/close 故障仍为 `true/true`。

```go
type WritePhase string

const (
    WritePhaseEncode   WritePhase = "encode"
    WritePhaseRecover  WritePhase = "recover"
    WritePhaseCreate   WritePhase = "create"
    WritePhaseWrite    WritePhase = "write"
    WritePhaseSync     WritePhase = "sync"
    WritePhaseRename   WritePhase = "rename"
    WritePhaseFinalize WritePhase = "finalize"
    WritePhaseClose    WritePhase = "close"
    WritePhaseRemove   WritePhase = "remove"
)

func (p WritePhase) String() string
func (p WritePhase) Valid() bool

type WriteError struct {
    File             string
    Phase            WritePhase
    MutationApplied  bool
    RecoveryRequired bool
    Cause            error
    CleanupError     error
}

func (e *WriteError) Error() string
func (e *WriteError) Unwrap() []error
func (e *WriteError) Code() protocol.Code
```

Store 调用 `StateFiles.WriteAtomic` 后，非 nil 错误必须先做 typed 判定，再考虑 context。
分类伪代码如下，辅助函数名只表达分支语义，不属于公共 API：

```go
var writeErr *filesystem.StateWriteError
if errors.As(err, &writeErr) {
    return mapTypedWriteError(result, writeErr)
}
if !result.MutationApplied &&
    !result.RecoveryRequired &&
    (errors.Is(err, context.Canceled) ||
        errors.Is(err, context.DeadlineExceeded)) {
    return err
}
if result.MutationApplied || result.RecoveryRequired {
    return failClosedWriteError(err)
}
return rawWriteFallback(err)
```

分类顺序冻结如下：

1. 只要 `errors.As` 能取得 `*filesystem.StateWriteError`，无论其 `Cause` 是否包装
   `context.Canceled` / `context.DeadlineExceeded`，都必须按 typed phase 返回 state
   `WriteError`，保留 `CleanupError`，并通过 `Code()` 映射 `STATE_WRITE_FAILED`；
2. 只有完全非 typed、result 的两个 bool 都为 false 且错误链匹配上述两个 context
   sentinel 时，才原样返回 err、不包装 `WriteError`；这是 Store 预检与 StateFiles
   预检之间允许发生的生产竞态；
3. 完全非 typed 但 `MutationApplied=true` 或 `RecoveryRequired=true` 时，不论错误链
   是否匹配 context，都以 `WritePhaseWrite` 和 result 的真实 bool 返回 `WriteError`
   失败关闭；
4. 其余非 context、非 typed 错误才进入 `WritePhaseWrite` raw fallback。

七个 filesystem phase 只允许如下精确映射：

| filesystem phase | state phase |
| --- | --- |
| `filesystem.StateWritePhaseRecover` | `WritePhaseRecover` |
| `filesystem.StateWritePhaseCreate` | `WritePhaseCreate` |
| `filesystem.StateWritePhaseWrite` | `WritePhaseWrite` |
| `filesystem.StateWritePhaseSync` | `WritePhaseSync` |
| `filesystem.StateWritePhaseRename` | `WritePhaseRename` |
| `filesystem.StateWritePhaseFinalize` | `WritePhaseFinalize` |
| `filesystem.StateWritePhaseClose` | `WritePhaseClose` |

识别到合法类型时，`WriteError.Cause` 保留 `StateWriteError.Cause`，
`CleanupError` 直接复制；`MutationApplied/RecoveryRequired` 分别对 typed error 与
`WriteAtomicResult` 做逻辑或后保留。T2.5 生产契约保证 result 与 typed error 的两个
bool 一致；Store 仍以逻辑或失败关闭，避免测试替身或未来失配把已 commit 或仍需恢复的
写误报为普通未生效失败。state 绝不解析 `FileError.Operation` 推断阶段。

未知 typed phase 或缺失主 Cause 只允许由消费方单元测试替身制造；它们仍停留在 typed
分支，适配器保留完整 typed 错误链并防御性使用 `WritePhaseWrite`，不得因 Cause 匹配
context 而原样透传。raw fallback 则严格限于非 context、非
`*filesystem.StateWriteError` 的测试替身错误，同样保留原始错误链。跨包契约测试必须
使用真实 T2.5 `StateFiles` 的全部 I/O 故障注入点证明生产 filesystem I/O 失败永不经过
raw fallback；两次预检之间、两个 bool 均为 false 的 context 竞态是上面明确允许的唯一
生产 untyped 路径。

`WriteError.Unwrap()` 返回主错误，并在非 nil 时同时返回清理错误，保证
`errors.Is` / `errors.As` 不丢失任一原因。`WriteError.Code()` 固定返回
`protocol.CodeStateWriteFailed`。调用层使用
协议包既有定义得到退出码 `70`、`retryable=true` 和 remediation
`retry` / `run-doctor`；state 包不自行复制四元组，也不直接发射 error 或
result 事件。

对 `WriteTransaction` / `WriteEnvironment`，`WriteError.MutationApplied` 只表示新
payload commit，不描述旧对象是否曾移动；`RecoveryRequired` 才表示 namespace 是否仍需
恢复或人工检查。对 `RemoveTransaction`，两个字段逐位复制
`StateRemoveResult`：POSIX namespace unlink 已成功但 close 失败时
`MutationApplied=true, RecoveryRequired=true`；intent 无法恢复或 stable
missing/mismatch 后最终 `G` close 失败时为 `false/true`。两个字段共同区分
“新 payload 未 commit 但旧对象需恢复”“新 payload 已 commit 但 finalize 未完成”和
“已完全收口”。

内存结构校验失败返回 `ValidationError`，表示调用方违反 API，不伪装成
磁盘写故障。读取到非法结构则转换为 `CorruptError`。

## 事务活跃度分类

### 消费方小接口

state 包作为消费方定义两个最小接口：

```go
type PIDProbe interface {
    Alive(ctx context.Context, pid uint32) (bool, error)
}

type MutexKind string

const (
    MutexBackend  MutexKind = "backend"
    MutexMutation MutexKind = "mutation"
)

func (k MutexKind) String() string
func (k MutexKind) Valid() bool

type MutexProbeResult struct {
    Held      bool
    Recovered bool
}

    Probe(ctx context.Context, kind MutexKind) (MutexProbeResult, error)
}

type SystemPIDProbe struct {
    // 零值可直接使用。
}

func NewSystemPIDProbe() *SystemPIDProbe
func (p *SystemPIDProbe) Alive(
    ctx context.Context,
    pid uint32,
) (bool, error)
```

`InspectTransaction` 根据 TransactionKind 在 state 包内绑定 MutexKind：

- `backend.json` 绑定 `backend`；
- `mutation.json` 和 `update.json` 绑定 `mutation`。

这样调用方不能把 backend 状态与 mutation 探针自由错配。state 不导入
`internal/lock`，T2.4 的 `Set.Probe` 由应用层用一个小 adapter 原样映射
MutexKind。`InspectTransaction` 仍只依赖小接口；生产调用方传入
`SystemPIDProbe`，单元测试传入可控替身。

`Recovered=true` 表示 Probe 消费并立即释放了 abandoned Mutex。它不改变 Held=false
之后的 PID 分类，但必须进入 Inspection，让调用方在 stale、inconsistent 或 unknown
结果旁记录恢复事实，不能因没有 Lease 而丢失。

### Windows `SystemPIDProbe`

`SystemPIDProbe` 位于 Windows build constraint 文件中，使用
`golang.org/x/sys/windows`，固定按以下顺序查询：

1. 在任何 Win32 调用前检查 `ctx.Err()`；
2. 拒绝 `pid == 0`，返回可由 `errors.Is` 判断的 `ErrInvalidPID`；
3. 调用 `OpenProcess(SYNCHRONIZE, false, pid)`；
4. `OpenProcess` 返回后再次检查 `ctx.Err()`；取消与 open 结果同时可见时，
   context 优先；
5. 明确表示 PID 不存在的 `ERROR_INVALID_PARAMETER` / `ERROR_NOT_FOUND`
   返回 `alive=false, err=nil`；
6. `ERROR_ACCESS_DENIED` 和其他 open 故障返回 `PIDProbeError`，不得猜测
   dead；
7. 成功取得 handle 后若第二次 context 检查已取消，先关闭 handle，再同时保留
   context 与 close 错误链，不得继续 wait；
8. 调用 `WaitForSingleObject(handle, 0)`；`WAIT_TIMEOUT` 为 alive，
   `WAIT_OBJECT_0` 为 dead；`WAIT_FAILED` 或其他结果
   返回 `PIDProbeError`，不能用 `STILL_ACTIVE` 区分，因为进程可以真实以 259 退出；
9. 关闭 process handle 并检查 `CloseHandle` 错误；
10. 在返回结果前第三次检查 `ctx.Err()`。

只请求 `SYNCHRONIZE`，不得请求 query、terminate、VM read 或调试权限。
`WaitForSingleObject`、`CloseHandle` 或成功 open 后任一次 context 检查失败
都返回 error，使 `InspectTransaction` 分类为 unknown；同时发生的错误必须保留完整错误链。
查询过程中进程退出时，以零等待观察到的状态为准。

```go
var ErrInvalidPID = errors.New("pid is invalid")

type PIDProbeError struct {
    Operation string
    PID       uint32
    Cause     error
}

func (e *PIDProbeError) Error() string
func (e *PIDProbeError) Unwrap() error
```

`Operation` 只使用 `open-process`、`wait-process` 或 `close-handle`。错误
保留 Win32 原因，但不读取进程名称、命令行或可执行文件路径。PID free 后
可能被系统复用，所以 Mutex free 且 `SystemPIDProbe` 返回 alive 仍必须按
下文归类为 inconsistent，而不是推断它就是原 Runtime。

### 分类 API

```go
type Activity string

const (
    ActivityActive       Activity = "active"
    ActivityStale        Activity = "stale"
    ActivityInconsistent Activity = "inconsistent"
    ActivityUnknown      Activity = "unknown"
)

func (a Activity) String() string
func (a Activity) Valid() bool

type Inspection struct {
    Activity       Activity
    MutexHeld      bool
    MutexRecovered bool
    PIDChecked     bool
    PIDAlive       bool
    ProbeError     error
}

func InspectTransaction(
    ctx context.Context,
    kind TransactionKind,
    value TransactionState,
    pidProbe PIDProbe,
    mutexProbe MutexProbe,
) Inspection

func (i Inspection) CanAutoClean() bool
```

探测顺序和结果固定为：

| Mutex | PID | 分类 | 自动清理 |
| --- | --- | --- | --- |
| held | 不探测 | `active` | 否 |
| free | dead | `stale` | 是，但须完成下文受锁重验 |
| free | alive | `inconsistent` | 否 |
| 探测失败 | 不探测 | `unknown` | 否 |
| free | 探测失败 | `unknown` | 否 |

未知 TransactionKind、nil 探针或 value 未通过该 kind 的
`ValidateTransaction` 时不调用任何探针，固定分类为 unknown 并保存
`ValidationError`。Mutex 是权威占用依据，因此一旦确认 held 就直接分类为 active，PID 探测失败
不能把它降级为 unknown。Mutex free 但 PID alive 可能表示 PID 复用、异常
丢锁或不合规进程，必须保留文件并报告 inconsistent；不得按 PID 杀进程。
任一必要探针失败或 context 取消都返回 unknown，并把原因保存在
`ProbeError`。

`StartedAt` 的新旧程度不参与分类，不设置“超过 N 分钟即陈旧”的阈值。系统
时钟、长时间下载和暂停调试都不能改变 Mutex/PID 真相。
`CanAutoClean()` 只在 `Activity == ActivityStale` 时返回 true。

### 消费方的无竞态 stale 清理

`InspectTransaction` 只分类，不自行删除，也不接受 Lease。另一个进程自动清理
stale 文件时
必须按以下顺序：

1. 读取文件并保留 stale 候选的 TransactionSnapshot；
2. 成功取得该文件对应的 T2.4 Lease；
3. 在持有 Lease 时重新读取精确目标，得到新的 TransactionSnapshot；
4. 确认 `OperationID`、`PID` 和其他事务身份字段仍与候选一致；
5. 再次确认旧 PID 已 dead；
6. 把第 3 步 snapshot 交给 `RemoveTransaction`；StateFiles 先恢复或拒绝 fixed intent，
   再只对稳定 `D` 在同一 leaf handle 上比较 file ID 与完整 payload 后 conditional
   disposition；
7. 清理完成后释放 Lease。

取得 Lease 后不再用 `MutexProbe` 分类，因为当前进程自己持有 Mutex。若
获取冲突、文件变化、PID alive、PID 探测失败或重读失败，立即放弃自动清理。
conditional remove 遇到同名替换或原地改写时返回 `ErrTransactionChanged`，立即放弃；
遇到 recovery-required、foreign reserved leaf 或内部 gap 时同样立即放弃且不删除任何
对象。该顺序防止 stale 探测、重读与新事务写入之间的 TOCTOU 删除。

正常事务所有者在结束时删除自己的事务文件不属于 stale 自动清理，但同样
必须仍持有对应 Lease，并先读取当前 snapshot、核对 OperationID 后执行 conditional
remove；不能只凭 kind 删除。`environment.json` 永远不参与 stale 分类或事务清理。

上述跨包协调不属于 T2.3 的生产 API：state 不能导入 lock，lock 也不能导入 state。
T3 doctor 只分类不删除；T4.5/T4.6 等同时拥有 lock + state 的应用服务若需要自动清理，
在那里实现并测试完整协调函数。T2.3 只测试 kind 绑定、分类和 CanAutoClean，不伪造
一个无法执行 Lease 协议的半成品 helper。

## 并发与失败语义

- `Store` 通过指针共享，内部 mutex 线性化 clock 采样、全部 StateFiles I/O、
  close 和 closed 状态；注入 clock/files 不得回入同一 Store；
- 读取不取得 T2.4 业务 Mutex，进程内仍经 Store mutex；StateFiles.Read 会取得每 kind
  shared `G`，active writer 持有 exclusive `G` 时 context-aware 等待，gate 释放后只
  观察逻辑 old/new；raw `D` 在两次 no-replace rename 间仍允许出现 gap；
- Store mutex 不替代 T2.4 Windows 命名 Mutex；
- Read 不修改四个权威 JSON payload 或 sealed-intent namespace；首次 StateFiles Read
  可以 create-exclusive/open 建立缺失的持久 `G`，仅产生协调元数据副作用。StateFiles
  的 Write/conditional remove 在 exclusive `G` 内按 sealed intent 恢复，Store 自身不
  回退、rename、删除 raw leaf 或管理 `G`；
- 不因 corrupt、unsupported、inconsistent 或 unknown 自动清理；
- 不枚举、猜测或删除没有 sealed intent 引用的孤立 intent-staging/payload-temp；
- 不缓存读取结果，调用方每次恢复决策都读取当前磁盘值；
- 不把 `context.Context` 存入 `Store`；
- 本任务不启动 goroutine，不使用 `time.Sleep`。

## 不负责范围

T2.3 明确不负责：

- app-root 解析、固定路径拼接和目录保护名单；
- Windows 命名 Mutex 的创建、获取、探测或释放；
- 枚举进程、读取进程名/命令行或终止任何进程；
- 决定工作区目录身份、重命名恢复和
  `UPDATE_STATE_AMBIGUOUS` 的业务分支；
- 执行 lifecycle 迁移或持久化瞬态
  `uninitialized/preparing_*/syncing_*/running/...`；
- 解析 Git、uv 或 Python 自然语言输出；
- 写操作日志、stderr 或 stdout；
- 自动迁移未知 schema、猜测损坏 JSON，或绕过 StateFiles 从 raw sidecar 恢复目标；
- 删除 `environment.json`、用户数据、日志、插件目录或任何仓库目录。
