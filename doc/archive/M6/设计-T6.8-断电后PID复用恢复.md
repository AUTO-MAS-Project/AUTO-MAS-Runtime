# T6.8 断电后 backend 事务 PID 复用恢复

## 问题与边界

2026-09-27 用户机器在后端运行中断电。`backend.json` 可留在磁盘，backend Mutex 随进程消失；重启后旧 PID 若被复用，现有代码只判断 PID 存活，返回 `UPDATE_STATE_AMBIGUOUS`，阻止启动。用户提供的日志没有事务快照，具体 PID 未核实；本任务针对代码中可复现的误判路径。

只修改后端监督的陈旧事务判定和 Windows PID 探针。不更改状态 schema、协议、mutation/update 恢复、目录清理或进程终止行为。

## 判定

先取得 backend Mutex，再读取旧事务。若 PID 不存在，沿现有快照条件删除。若 PID 存活，查询该 PID 当前进程的创建时间；它严格晚于事务 `startedAt` 时，当前进程不可能写下该事务，按旧进程已失活执行相同条件删除。否则报告原有 `UPDATE_STATE_AMBIGUOUS`。创建时间查询失败不作推断，返回状态检查失败。查询后的 PID 退出或复用不改变旧进程已经失活的事实；条件删除仍校验原快照。

`startedAt` 只作为进程创建时间的上界，不作为「事务太旧」的超时阈值。这个判定依赖 Windows 时钟在进程创建到事务写入期间没有回拨；异常回拨可能使时间先后关系失去证明力，是本修复的剩余限制。无法读取创建时间或不满足严格先后关系时失败关闭。Windows 查询句柄需 `PROCESS_QUERY_LIMITED_INFORMATION`，关闭错误不能被忽略。

## 验收

- 旧 PID 已复用并且新进程创建时间晚于事务：删除旧事务、继续启动。
- 原 PID 对应进程创建时间早于或等于事务、查询失败：零删除、零 spawn，维持失败关闭。
- 条件删除失败：阻止启动；不得按 PID 杀任何进程。
- 真实 Windows PID 探针返回当前进程创建时间，错误路径无句柄泄漏。
