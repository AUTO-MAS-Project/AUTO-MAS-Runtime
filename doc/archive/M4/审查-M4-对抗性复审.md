# M4 工作区同步对抗性复审

日期：2026-08-07
范围：T4.0~T4.7 的 `internal/gitrepo`、`internal/filesystem`、`internal/cli`、
`internal/protocol` 变更，以及对应设计、任务和组件夹具。
结论：Critical = 0；Important = 0；M4 可验收。审查中发现的 Critical/Important 均已先登记
文档、补充回归测试，再以独立修复改动收口。

## 审查方法

审查按多轮独立进行，覆盖契约、恢复、安全、并发、取消、测试真实性和最终边界：

1. 契约、错误码和生命周期状态机；
2. 崩溃恢复、原子替换和 Windows 目录安全；
3. 并发、取消、协议输出和测试真实性；
4. 目录身份竞态、版本边界、错误链和组件服务完整流程；
5. 正常 swap 成功边界、租约收口和最终静态门禁。

除单元测试外，复核了组件夹具是否使用真实 go-git HTTPS upload-pack、是否保持 TLS 校验、
是否产生真实浅克隆边界与只读 pack index，以及 stdout、系统 Git、Shell 和保护目录边界。

## 第一轮：契约与状态机

### 重要：恢复 revision 等价错误

**发现**：恢复逻辑把 `repositoryIdentity.sourceKey` 纳入 revision 等价判断。同一
`version/branch/Commit` 从不同受信镜像取得时，会被错误分类为 `UPDATE_STATE_AMBIGUOUS`，
阻止本应幂等的恢复。

**修复**：按设计裁决，`sourceKey` 只保留来源 provenance，不参与 revision 唯一性；恢复比较
只使用版本、分支和 Commit。新增跨镜像恢复测试，并更新设计与任务变更记录。

**证据**：`TestRecovery_PreSwapSameTargetCommitFromDifferentSourcesIsEquivalent` 及完整
`internal/gitrepo` 测试通过。

### 重要：T4.7 的 Depth 1 证据不真实

**发现**：早期夹具在收到 `deepen 1` 后仍返回完整历史，再手工写入 shallow 元数据，只能证明
请求参数，不能证明父 Commit 未下载。

**修复**：服务端用 go-git pack encoder 仅生成目标 Commit 及其 tree/blob 闭包；测试同时断言
shallow boundary 等于 HEAD 且父 Commit 读取返回 `ErrObjectNotFound`。

**证据**：`TestComponent_GitAcquisitionMatrix/real_depth_one`，以及 `TestComponent_GitAcquisitionMatrix`
完整矩阵通过。

### 重要：版本 `.lock` 后缀未被拒绝

**发现**：`ParseTarget` 原先允许 `vfoo.lock`，生成 Git 禁止的
`release/vfoo.lock`；后续会把输入错误误报为 `GIT_BRANCH_NOT_FOUND`，而不是 T4.1 要求的
`INVALID_VERSION`。state/mirror 的对应安全版本校验也接受该值，造成跨包合法集合不一致。

**修复**：安全版本规则明确拒绝以 `.lock` 结尾的值，并在 gitrepo、state 和 mirror 三个验证器中
同步实现；CLI workspace sync 在服务创建前映射 `INVALID_VERSION`。补充 ParseTarget、CLI、state
和 mirror 回归测试，规则与 Git `check-ref-format` 的 `.lock` 保留名保持一致。

**证据**：`TestParseTarget_InvalidVersions/lock_suffix`、
`TestWorkspaceSyncCommand_ValidatesVersion`、state/mirror lock-suffix 子测试均以 count=10 通过。

## 第二轮：恢复、目录安全与控制通道

### 重要：控制读取缺少 completion/join

**发现**：CLI 启动控制读取 goroutine 后直接返回，可能漏掉并发完成的 reader 错误、迟到
`cancel` 或遗留测试 goroutine。

**修复**：为每个会话增加有缓冲 completion channel；先 `StopAccepting`，对可结束的非真实 stdin
关闭 owner 并有界等待，再读取控制错误和首个 `controlCommandId`。真实 `os.Stdin` 不关闭且不
无限等待；非真实 `io.Closer` 的 bounded-return 是 owner contract。

**证据**：`TestWorkspaceSyncCommand_CancelFromStdin`、`TestWorkspaceSyncResult_MergesLateControlCommandID`
及控制 join/关闭测试通过。

### 重要：部分 swap 回滚未编排

**发现**：第一次 rename 已成功、第二次 rename 失败时，`RepositoryActivated=false`，旧逻辑会
直接回滚生命周期并报告旧 `ready_to_start`，但正式 `repo/` 此时可能不存在。

**修复**：只要已发生目录 mutation 且新 revision 尚未 active，Service 先用独立 30 秒 cleanup
context 调 Recovery 回滚 `previous -> repo`；仅恢复成功后才回滚生命周期并发旧 stable state，
恢复失败则保留 transaction/现场并禁止伪造稳定状态。

**证据**：`TestService_PartialSwapRecoversBeforeStableState`、
`TestService_PartialSwapRecoveryFailureDoesNotEmitStableState`、
`TestRecovery_BetweenRenamesRollsBack` 通过。

### 重要：错误主次顺序不稳定

**发现**：active repo 后的环境写失败可能被先前 cleanup 错误遮蔽；输出通道写失败与取消并存时
也可能退化为取消，造成错误码与持久化事实不一致。

**修复**：提交边界后的环境/transaction 写失败固定以 `STATE_WRITE_FAILED` 为主并保留错误链；
类型化或原始 `OUTPUT_WRITE_FAILED` 优先于取消；控制通道基础设施故障优先于业务取消并保留业务
错误链。

**证据**：`TestService_StateWriteFailureOutranksPriorCleanupFailure`、
`TestClassifyFailure_FallbackCodes`、`TestWorkspaceControlErrorOutranksBusinessCancellation` 通过。

### 重要：独立收口 context 与 stage 未贯通

**发现**：收口 context 只在调用前已取消时脱离父 context，检查后取消仍会中断 cleanup；Fetcher、
Swapper、Recovery 内部的 progress/warning 又可能沿用旧 stage。

**修复**：所有取消后精确收口统一使用 `context.WithTimeout(context.WithoutCancel(ctx), 30s)`；
StageReporter 在 transaction 推进前更新并下传到 Fetcher/Swapper/Recovery，cleanup 事务失败映射
固定到 `workspace.cleanup`。

**证据**：`TestServiceCleanupContext_IgnoresCancellationAfterCreation`、各服务 stage 回归测试、
`TestRecovery_TransactionRemovalFailureRetainsTransaction` 通过。

### 重要：Inspect-to-open 目录替换竞态

**发现**：先 `Inspect` 再让 go-git 以路径打开 update 根，在同一用户可控的窗口中可把目录替换为
Junction，导致 I/O 越出受管根。

**修复**：新增 `filesystem.PrepareManagedDirectory`，在固定父句柄下以
`CREATE_NEW + FILE_DIRECTORY_FILE` 原子创建 update 目录，并在 clone/verify 期间持有不共享
delete 的目录租约；预存目标、重解析或租约身份变化均保留现场并失败关闭。

**证据**：`TestPrepareManagedDirectory_*`、`TestFetcher_PrepareDirectoryRace`、目录祖先 Junction
与保护目录快照组件测试通过。

### 次要：T4.7/目录检查覆盖不足

**发现**：第二轮还发现组件测试使用手工 `pack.idx`、取消只覆盖部分网络阶段，目录检查缺少
不存在、普通文件、直接/祖先 Junction、权限、取消和零创建矩阵。

**修复**：改为真实 clone 产生的只读 pack index，加入 discovery/pack/response 三阶段 barrier，
补齐 `InspectManagedDirectory` 矩阵及保护目录内容/身份快照。

**证据**：`TestComponent_GitAcquisitionMatrix`、`TestComponent_GitReplacementMatrix`、
`TestComponent_GitRecoveryMatrix` 和 `internal/filesystem` 定向测试通过。

## 第三轮：并发、取消和输出收口

### 重要：激活后 cleanup deadline 的错误码

**发现**：第二次 rename 后使用独立 cleanup context 的 `DeadlineExceeded` 会沿普通取消映射为
`OPERATION_CANCELLED`，掩盖已经跨过的提交边界。

**修复**：active 后 transaction/environment 写失败固定为 `STATE_WRITE_FAILED`；retired/previous
删除失败固定为 `GIT_REPO_CLEANUP_FAILED`；错误链保留底层 deadline。Recovery 与 Service 同步采用
该 committed mapping。

**证据**：`TestSwapper_ActiveCleanupDeadlineUsesCommittedErrorCodes`、
`TestRecovery_ActiveCleanupDeadlineUsesCommittedErrorCodes`、
`TestService_ActiveCleanupDeadlineIsStateFailure` 通过。

### 重要：早期 transaction 失败的状态回滚

**发现**：创建或首次写入 mutation transaction 失败时，生命周期已进入
`syncing_repository`，却可能直接返回，留下瞬态状态而没有恢复原稳定状态。

**修复**：在 pre-swap 任一失败路径统一执行 `finishPreSwap`，回滚生命周期、发出 cleanup stage 的
原稳定 state；仅在 update transaction 身份已明确且需要诊断时保留它。

**证据**：`TestService_EarlyMutationTransactionFailureRollsBackStableState` 四个子用例通过。

### 重要：Recovery stage/classification 边界

**发现**：clone 阶段普通但不完整目录的读错误被当成身份不明，无法清理；verify/swap 阶段又有
误把普通错误当成可删除候选的风险。

**修复**：已通过安全目录检查的 clone update 路径，普通非取消 reader 错误归类为不完整并允许精确
清理；verify/swap 仍保持 `UPDATE_STATE_AMBIGUOUS` 与零副作用。事务删除和 previous cleanup
统一报告真实 `workspace.cleanup` stage。

**证据**：`TestRecovery_CloneReaderFailureTreatsOrdinaryUpdateAsIncomplete`、
`TestRecovery_NonCloneReaderFailureRemainsAmbiguous` 及 Recovery 全量测试通过。

### 重要：renderer 输出错误 sentinel

**发现**：renderer 的底层写失败未稳定保留 typed sentinel，version/cleanup 等直接发射 progress
的命令会被 session 兜底为 `INTERNAL_ERROR`。

**修复**：新增 `protocol.ErrOutputWriteFailed`，renderer sticky 返回该 sentinel；session 同时识别
typed/raw 输出错误并映射 `OUTPUT_WRITE_FAILED`。

**证据**：`TestRendererFailureIsSticky`、`TestClassifyFailure_FallbackCodes` 通过。

### 重要：rename retry 误报收窄

**发现**：把 pin 阶段的 access-denied 一律映射为 `DIRECTORY_OCCUPIED` 会跳过 T2.5 已冻结的有限
重试，也会把父目录身份/权限错误误报成占用。

**修复**：仅 source leaf 的 sharing/lock/access-denied 进入有限重试并每次重验身份；父目录、目标或
身份错误保持原错误语义。

**证据**：`TestAtomicRename_RetriesPinSharingViolationBeforeRename`、rename 错误分类和占用组件测试通过。

### 重要：StageReporter 被 progress 覆盖

**发现**：Fetcher 的 progress 事件会把控制 warning stage 从业务 verify 覆盖回 clone，导致无效
cancel 的 stage 与状态机不一致。

**修复**：progress 只在 control stage 未被业务显式设置时提供默认值；Service 在 transaction
推进前先设置真实 stage。

**证据**：`TestWorkspaceStageEmitter_DoesNotOverwriteBusinessStage` 及 stage 回归测试通过。

### 重要：DeadlineExceeded、迟到 commandId 与控制优先级

**发现**：CLI 仅映射 `context.Canceled`；Service 返回后已接受的迟到 cancel 可能不回显
`controlCommandId`；控制 reader 故障与业务取消的主码顺序不明确。

**修复**：`DeadlineExceeded` 按取消契约映射；停止接收并 join 后重新读取首个 commandId；控制
基础设施错误保持主码 `INTERNAL_ERROR`，业务错误作为错误链保留；reader-originated 的包装 context
错误不被误吞。

**证据**：`TestClassifyFailure_FallbackCodes`、`TestWorkspaceSyncResult_MergesLateControlCommandID`、
`TestWorkspaceControlReaderContextCancellation_DistinguishesReaderOrigin` 通过。

### 次要：DirectoryLease close 失败后不可重试

**发现**：租约关闭部分失败时过早标记 closed，后续调用无法重试剩余句柄关闭。

**修复**：仅全部句柄关闭成功才进入幂等终态；失败保留可重试状态。

**证据**：`TestDirectoryLease_RetriesAfterCloseFailure` 通过。

### 重要：retired cleanup 未绑定 active repo 身份

**发现**：替换完成后的 `repo.previous-*` 清理若只按路径和目录类型操作，攻击者可在
active repo 已切换后替换旧目录叶子，令 cleanup 递归处理不属于本次事务的目录。

**修复**：Swapper 将旧 active repo 的 volume/file-ID token 传给 retired cleanup；受控删除
在固定句柄上重新比较 token，身份变化立即失败关闭并保留现场。

**证据**：`TestSwapper_RetiredIdentityChangeFailsClosed`、`TestSwapper_PropagatesDirectoryIdentityTokensToRenames`
通过。

### 重要：损坏 active repo 丢失 token 后被错误清理

**发现**：现有 `repo/` 损坏时若分类结果不保留叶子身份 token，恢复或替换流程可能把之后
被换入的目录误认为原 active repo，破坏“身份不明即失败关闭”的边界。

**修复**：普通但损坏的现有 repo 仍保留可证明的叶子 token；仅遇到 Reparse、权限错误或
无法取得身份时才拒绝继续。Recovery、Fetcher 和 Swapper 全链路传递并校验该 token。

**证据**：损坏 repo 保留 token 的恢复矩阵、缺失/不匹配 token 零副作用测试通过。

### 重要：Recovery 激活后的迟到取消

**发现**：第二次 rename 已激活新 repo 后，原业务 context 的迟到取消可能中断环境补写、
旧目录清理或 transaction 收口，最终把已提交的新 repo 误报为普通取消，留下不一致状态。

**修复**：任一激活 rename 成功后，Recovery 切换到脱离取消但有 30 秒上限的收口 context，
统一完成 environment、cleanup 和 transaction 条件删除；收口失败按实际持久化事实映射
`STATE_WRITE_FAILED` 或 cleanup 错误。

**证据**：`TestRecovery_CancellationAfterActivationStillCompletesCommit` 通过。

### 重要：已提交 Recovery cleanup 的身份错误码

**发现**：Recovery 已确认 active target 后，`previous` retired cleanup 的叶子身份变化仍
先按通用路径竞态映射为 `UPDATE_STATE_AMBIGUOUS`，与已跨过提交点后的错误码契约不符。

**修复**：`removeRecoveryTree` 在 `committed=true` 时优先将身份变化映射为
`GIT_REPO_CLEANUP_FAILED`，保留 active repo、previous 和 transaction；未提交阶段仍返回
`UPDATE_STATE_AMBIGUOUS` 并零副作用。

**证据**：`TestRecovery_CommittedRetiredIdentityChangeFailsCleanup` 与
`TestRecovery_DirectoryIdentityChangeFailsAmbiguous` 通过。

### 重要：普通损坏 active repo 的 token 保留

**发现**：Recovery 已取得 `repo/` 叶子 token 后，若 go-git 读取内容失败，原实现仍直接返回
ambiguous，无法按冻结规则仅清理 pre-swap 的 update；这会把可安全替换的普通损坏仓库与
Reparse/权限等身份不可证明场景混为一谈。

**修复**：clone/verify 阶段仅将已通过目录身份校验、但底层内容读取失败的普通目录分类为带
token 的 incomplete active repo，保留 `repo/` 并受控清理 update；权限错误、Reparse、非目录
和身份获取失败继续失败关闭。swap/cleanup 阶段对 incomplete repo 不做自动副作用。

**证据**：`TestRecovery_DamagedRepositoryKeepsIdentityForPreSwapCleanup` 通过。

### 重要：verify 阶段未知 Git 源被误当成普通损坏

**发现**：上述分类收窄前，`repositoryIdentityFromSnapshot` 的所有错误都会在 clone/verify 阶段
被 `preserveDamaged` 转成 incomplete。一个 Git 结构完整但 remote 不属于受信镜像的
`repo/` 因而可以让 Recovery 删除目标 update 并移除 transaction；未知来源本应属于
`unsafe/unknown`，必须零副作用。

**修复**：删除对身份校验错误的 incomplete 兜底；只有 go-git 底层内容读取失败且目录叶子 token
已证明时才允许 clone 阶段的精确 update cleanup。remote、branch、shallow、Commit、版本结构
等身份校验失败统一返回 `UPDATE_STATE_AMBIGUOUS`。

**证据**：`TestRecovery_VerifyUnknownRemoteHasNoSideEffects` 及恢复矩阵重复测试通过。

### 重要：首次安装的空 clone transaction 被误判

**发现**：首次安装写入 clone transaction 后、update 目录创建前崩溃时，repo/update/previous
均缺失；原 guard 把任何“repo 缺失且 update 非 incomplete”都判为 ambiguous，导致可确定的
空事务永久阻塞后续同步。

**修复**：仅当 repo 缺失且 update 已能证明为目标 revision 时保留现场并返回
`UPDATE_STATE_AMBIGUOUS`；三个固定目录均缺失时仅条件删除 transaction，不执行目录副作用。

**证据**：`TestRecovery_PreCloneFirstInstallWithoutDirectoriesClearsTransaction` 与
`TestRecovery_PreSwapMissingRepositoryHasNoSideEffects` 通过。

## 第四轮：最终协议与提交前副作用复审

### 重要：Mutex join 包装丢失真实冲突码

**发现**：生产 `lock.Set.AcquireMutation` 在 backend Mutex 已持有时，会先释放临时取得的 mutation
Mutex，再用 `errors.Join` 返回 `ConflictError` 与 release 错误。Service 原先只对顶层错误做直接
type assertion，导致真实 `BACKEND_STILL_RUNNING` 被误映射为 `MUTEX_OPERATION_FAILED`；同一路径的
取消在 Service 层也会被误分类。

**修复**：`mapMutexFailure` 先用 `errors.Is` 识别 `Canceled`/`DeadlineExceeded`，再用
`errors.As` 从完整错误链提取冻结锁码，最后才使用 `MUTEX_OPERATION_FAILED` 兜底。

**证据**：`TestMapMutexFailure_WrappedCodesAndCancellation` 覆盖 join 包装的 backend 冲突、取消和
deadline，重复测试通过。

### 重要：CLI 覆盖已提交收口错误

**发现**：Swapper、Recovery 与 Service 已把激活后的 cleanup deadline 映射为
`STATE_WRITE_FAILED`/`GIT_REPO_CLEANUP_FAILED`，但 CLI 在读取类型化错误前检查整条错误链中的
`DeadlineExceeded`，最终仍输出 `OPERATION_CANCELLED`、status=`cancelled` 和退出码 130。为失败
补充迟到 `controlCommandId` 的包装还可能丢失已提交标记或新增 details。

**修复**：`gitrepo.Error` 显式携带 committed 标记；CLI 的稳定顺序固定为输出故障、控制基础设施
故障、已提交类型化错误、通用取消、普通业务错误、内部兜底。`addControlCommandID` 同时传播该标记
和补充后的 details，底层 deadline 继续保留在错误链中。

**证据**：`TestWorkspaceSyncCommand_CommittedDeadlineKeepsBusinessFailure` 覆盖 state/cleanup 两类
完整 NDJSON 终态；`TestWorkspaceSyncCommand_PreCommitCleanupDeadlineKeepsCleanupFailure` 固定
提交前独立 cleanup deadline 的 `GIT_REPO_CLEANUP_FAILED` 不被误报为取消；
`TestAddControlCommandID_PreservesCommittedClassification` 证明迟到命令 ID 与已提交错误码同时
保留；Service/Swapper/Recovery deadline 测试同时断言真实错误携带 committed。

### 重要：固定句柄后仍执行已取消的目录副作用

**发现**：`PrepareManagedDirectory` 固定父目录后直接执行 `CREATE_NEW`，`AtomicRename` 固定 source
和目标父目录后直接执行 rename；若 context 在最后一次身份检查完成后已取消，两个能力仍会创建或
移动目录，与 M4 “提交前操作响应取消”的冻结要求不一致。

**修复**：两项能力都在固定句柄与身份校验完成后、系统调用前最后检查 `ctx.Err()`；已观察到取消
则关闭全部 pin 并以零副作用返回。文档明确该检查不宣称能把 Win32 系统调用与 context 原子化；
系统调用已开始后的结果仍以 `MutationApplied` 为准。

**证据**：`TestPrepareManagedDirectory_CancellationAfterParentPinStopsBeforeCreate` 与
`TestAtomicRename_CancellationAfterPinStopsBeforeMutation` 使用确定性 API barrier 触发该窗口，重复
测试通过。

## 残余边界与裁决

### 重要：恢复分类后的目录身份竞态（补充复审）

**发现**：Recovery 的 `classifyPath` 原先释放检查句柄后仅保存 Git revision，再按路径调用
`RemoveTree`/`AtomicRename`。同一用户可把已分类的 `repo.update-*` 换成普通的受保护目录；操作器
只重新确认“路径位于受管根内且是目录”，可能递归删除被搬入该叶子的用户数据。复审代理提出的
“换成普通目录仍可删除”攻击链基于旧 token 补丁快照；当前实现已在每次递归删除/rename 前于
固定句柄上比较 volume/file-ID token。

**修复**：`InspectManagedDirectory` 返回叶子 volume/file-ID token；Recovery 将 token 随候选
传给受控删除/重命名，操作器在自己的固定 source/root 句柄上比较 token。token 不一致立即以
`UPDATE_STATE_AMBIGUOUS`/身份错误失败关闭并保留现场。补充了操作器 mismatch 测试和 Recovery
token 传播回归测试。

**结论**：该发现已修复，不计入最终 Important 遗留；`TestRecovery_DirectoryIdentityChangeFailsAmbiguous`
覆盖普通目录替换和身份变化。后代 path-based I/O 的同用户 tamper/DoS
边界仍按下文残余策略保留。

### 重要：Recovery active target 的环境状态提交顺序（2026-08-07）

**发现**：active target 恢复原先先清理 `previous`、后写 `repository_changed`；旧目录清理失败
时，新的 Git 仓库已经 active，但 durable environment 仍可能保持旧的 `ready_to_start`。

**裁决与修复**：按 `doc/架构设计.md` 的成功边界，Recovery 先在独立收口 context 中写入
`environment_broken/repository_changed`，再执行 retired cleanup。清理失败保留 `previous` 和
transaction，并映射 `GIT_REPO_CLEANUP_FAILED`；环境写失败则映射 committed
`STATE_WRITE_FAILED`。回归测试同时断言 cleanup 失败时 `EnvironmentWritten=true`。

### 重要：正常 swap 的验证后目录身份竞态（补充复审）

**发现**：Fetcher 原先只返回 update 路径与 Revision；verify 后释放租约，Swapper 的两次
`AtomicRename` 未携带分类 token。同一用户可在 verify 后把 update 或现有 repo 替换成普通的
config/data 目录，随后被 swap 移动，违反用户数据不得由更新流程移动的边界。

**修复**：workspace check 在读取 Git 身份时保存 active `repo/` 叶子 token；Fetcher 在租约
仍持有时取得 update 叶子 token。Service 通过 `SwapRequest` 传递两个 token，Swapper 将其
分别传给受控 rename；操作器在固定句柄上重验，不一致映射 `UPDATE_STATE_AMBIGUOUS` 并保留
现场。补充 Fetch/Swap token 传播测试和缺失 token 的零副作用测试。

**结论**：该发现已修复，不计入最终 Important 遗留。

### 重要：pre-swap 缺失 repo 的恢复形状

**发现**：`recoverBeforeSwap` 原先允许 clone/verify 事务出现 `repo` 缺失、`update` 为目标
revision、`previous` 缺失，随后删除唯一有效 update 并移除 transaction，留下不可启动的
缺失 repo。这超出“替换前失败保留 current repo”的冻结边界。

**修复**：clone/verify 阶段若 `repo` 缺失且 update 已可证明为目标 revision，即返回
`UPDATE_STATE_AMBIGUOUS`，不调用任何 rename/delete，也不删除 transaction；clone 阶段普通
不完整 update 仍按既有规则受控清理。补充目标 update 目录形状的零副作用回归测试。

**结论**：该发现已修复，不计入最终 Important 遗留。

### 重要：cleanup 计划后的 `repo.update-*` 目录身份竞态（2026-08-07）

**发现**：cleanup 枚举状态匹配的 `repo.update-*` 后，原计划只保存路径和
`operationId`。同一用户可在枚举结束后把目录 A 替换为受管根内的普通目录 B；执行阶段
若仅按路径调用 `RemoveTree`，会把 B 当成已授权的 stale update 递归删除。

**修复**：枚举可清理条目时同时调用 `InspectManagedDirectory` 保存目录叶子的
volume/file-ID token，并把 token 放入 `planItem`。执行阶段将其作为
`DeleteRequest.ExpectedIdentity` 传给 `filesystem.Operator`；固定句柄上的身份复验失败时
失败关闭，保留替换目录和原审计事实，不按同名路径继续删除。缓存和其他非
`repo.update-*` 条目继续使用既有布局授权，不引入无关 token。

**证据**：`TestCleanup_RepoUpdateReplacementAfterPlanningFailsClosed` 先完成计划枚举，再
用确定性目录替换将 A 换成 B，断言执行结果为 failed 且 B 内 sentinel 保留；修复前该测试
稳定观察到 `cleaned` 并删除 B。cleanup 包全量定向测试与 `git diff --check` 通过。

### 重要：正常 swap 的环境提交顺序（2026-08-07）

**发现**：正常 Swapper 原先在第二次 rename 后先删除 `previous`，Service 返回后才写
`environment_broken/repository_changed`。进程若在该窗口退出，active 新仓库与 durable
`ready_to_start` 会不一致，且旧目录已不可恢复。

**修复**：`SwapRequest.CommitEnvironment` 成为提交后的必需回调。Swapper 写入
`workspace.cleanup` transaction 后先调用回调；Service 在回调内推进 mutation transaction、
写入 `repository_changed`、推进生命周期并发射状态事件，回调成功后才调用
`RemoveTree(DeleteRepositoryRetired)`。回调缺失或失败均失败关闭并保留 `previous` 与 transaction；
旧目录清理失败则返回 committed `GIT_REPO_CLEANUP_FAILED`，环境事实保持已写入状态。首次安装也
走同一回调边界。

**证据**：`TestSwapper_CommitsEnvironmentBeforeRetiredCleanup`、
`TestSwapper_EnvironmentCommitFailurePreservesRetiredRepository`、
`TestSwapper_MissingEnvironmentCommitFailsBeforeMutation`，以及真实 Service 降级组件测试
`TestService_SyncVersionDowngradeUsesSameFlow`。

### 重要：Fetcher 租约关闭与创建后取消收口（2026-08-07）

**发现**：Fetcher 在 verify 后只尝试一次关闭目录租约；短暂关闭失败可能遗留句柄并继续后续
流程。另有目录刚 `CREATE_NEW` 成功后 context 取消的窗口，原实现只关闭句柄而留下临时目录。
审查补丁若让创建句柄请求 `DELETE`，又会阻塞 go-git 打开 clone 根。

**修复**：Fetcher 对租约关闭执行固定三次同步重试；三次仍失败时映射
`GIT_REPO_CLEANUP_FAILED`、停止清理并保留现场，不能成功 swap。创建目录句柄继续保持
clone/verify 所需的不共享 delete 且不请求 `DELETE`；创建后失败时先关闭该句柄，再通过固定父句柄
重新打开删除句柄，复验原叶子 token、父身份和重解析点后按句柄删除。任何重开、复验或关闭失败
均保留现场并失败关闭。

**证据**：`TestFetcher_DirectoryLeaseCloseRetriesUntilSuccess`、
`TestFetcher_DirectoryLeaseCloseExhaustionPreservesTemporaryRepository`、
`TestPrepareManagedDirectory_CancellationAfterCreateRemovesCreatedTarget`、
`TestPrepareManagedDirectory_CloseFailurePreservesCreatedTarget`，以及完整
`internal/gitrepo`/`internal/filesystem` 组件测试。

### 重要：创建租约关闭失败后仍继续 DELETE 重开（2026-08-07）

**发现**：创建后失败路径原先把“关闭创建句柄”和“以 DELETE 权限重开并删除目录”作为
`errors.Join` 的并列参数。Go 会在调用 `errors.Join` 前求值全部参数，因此三次关闭均失败时仍会
执行删除重开；这违反“只有创建租约确认关闭后才允许删除”的冻结顺序，也会把未释放句柄下的
sharing violation 与真实 cleanup 事实混合。

**修复**：失败收口改为显式顺序：先执行固定三次关闭重试；只有关闭成功才进入固定父句柄下的
DELETE 重开、身份复验和按句柄删除。关闭重试耗尽时立即返回聚合错误并保留新建目录，不触发任何
DELETE 重开。

**证据**：`TestPrepareManagedDirectory_CloseFailurePreservesCreatedTarget` 注入三次确定性关闭失败，
断言 DELETE 重开调用次数为 0、目录仍存在，并以 `-count=20` 重复通过；实现尾提交 `9890144`。

以下不是未修复的 Critical/Important，而是已写入设计的明确边界：

1. go-git 对目录内部后代文件使用 path-based I/O；同一用户若在租约期间篡改后代内容或插入重解析
   点，Runtime 无法把每一次后代打开提升为固定句柄。该场景按同用户 tamper/DoS 残余处理：身份校验、
   租约关闭和受控清理均失败关闭并保留现场，不作为远端攻击路径。
2. 非真实 stdin 的 `io.Closer.Close()` 必须 bounded-return，这是调用方 owner contract。Runtime
   不为不合作 Close 启动不可回收 goroutine；真实 `os.Stdin` 不关闭，由进程退出终结读取。
