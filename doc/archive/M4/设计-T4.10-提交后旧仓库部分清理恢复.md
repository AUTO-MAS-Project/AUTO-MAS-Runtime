# T4.10 提交后旧仓库部分清理的确定性恢复设计

## 1. 问题与目标

`Swapper.Swap` 已把目标仓库激活为 `repo/`，写入 `workspace.cleanup` transaction，并持久化
`environment_broken/repository_changed` 后，才删除 `repo.previous-<operationId>/`。Windows 删除可能
已经移除一部分子项再因占用或安全软件拦截失败；此时 transaction 正确保留，但下一次 Recovery
仍把 previous 当作完整 Git 仓库解析。若 `.git/HEAD`、`.git/config` 等先被删除，分类会返回
`previous_unknown`，永远到不了本应继续执行的 retired cleanup。

本任务让这一已跨过 swap 提交点的现场可确定收口：保持目标 repo 和环境状态不变，继续删除同一
transaction 的 previous 残留，然后条件删除 transaction。

## 2. 可恢复形状

只有同时满足以下条件时，previous 的 Git 内容错误才可降级为 incomplete retired 残留：

- transaction stage 精确为 `workspace.cleanup`，且记录非空 `targetCommit`；
- 正式 `repo/` 是受信 Git 仓库，version 与 Commit 都精确匹配 transaction 目标；
- 同一 transaction 的 `repo.update-<operationId>/` 缺失；
- `repo.previous-<operationId>/` 是普通受管目录，可被重新 pin，并在读取前后取得相同的 volume/file-ID token；
- Git 读取失败不是取消或权限错误，或 Git 快照不满足受信 remote、HEAD、Commit、shallow、version 等身份约束。

Recovery 使用本次重新固定的目录 token 调用既有 `DeleteRepositoryRetired`，不从残留内容推断版本、
Commit 或回滚资格。环境写入仍先于删除且保持幂等；删除成功后才条件删除 transaction。

## 3. 失败关闭边界

以下现场继续返回 `UPDATE_STATE_AMBIGUOUS`，且在分类完成前不执行目录副作用：

- stage 为 clone、verify 或 swap；
- transaction 没有 `targetCommit`，或正式 repo 不是该 Commit；
- update 存在、损坏或无法分类；
- previous 是 Reparse、普通文件、权限不可读、无法 pin、token 缺失或发生变化；
- 环境状态损坏，或受控删除/环境写入/transaction 条件删除失败。

本任务不识别最初阻止删除的进程，不扩大受信 Git remote，不重建 previous，不回滚已经激活的
目标仓库，也不删除用户数据或 transaction 路径之外的目录。

## 4. 验收

- 现场形态红灯准确复现为 `previous_unknown`；
- 修复后 incomplete previous 被按固定 token 删除，transaction 被移除，active repo 内容不变；
- 已匹配的 `repository_changed` 环境状态不被重写；
- 相同残留在 swap 阶段、缺少 target Commit、update 存在或 active repo 不匹配时继续失败关闭；
- 定向重复测试、Git Recovery/Replacement 组件矩阵、标准验证门与完整 race detector 全绿。
