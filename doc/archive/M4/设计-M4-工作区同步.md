本文冻结 `internal/gitrepo` 的版本目标、Git 获取、静态校验、目录替换、中断恢复和
`workspace check/sync` 应用服务契约。实现必须把网络失败限制在临时目录，把实际 swap
与 `environment_broken/repository_changed` 持久化作为成功边界，并在目录身份不能唯一
判断时失败关闭。

## 1. 目标与边界

M4 交付以下能力：

1. 把安全产品版本唯一映射为 `release/<完整版本>`；
2. 使用固定版本 go-git 按 `SingleBranch + Depth:1 + NoTags` 获取受管仓库；
3. 按现有 mirror Plan 轮换 Git 源，不改变目标版本和分支；
4. 校验 remote、当前分支、HEAD Commit 和 `res/version.json`；
5. 通过 T2.5 受控 rename 和删除能力整体替换 `repo/`；
6. 通过 `update.json` 与目录身份恢复中断事务；
7. 接通 `workspace check` 和 `workspace sync --version`，包括 Mutex、生命周期、
   stdin cancel、环境失效持久化和稳定 result；
8. 用本地裸仓库与本地智能 HTTPS Git 服务覆盖获取、替换、恢复和降级矩阵。

本阶段不负责：

- 不安装 uv、Python 或主项目依赖，不创建、删除或修改 venv；
- 不启动、停止或强制终止后端；运行中的后端只通过 Mutex 冲突拒绝更新；
- 不实现后台预下载、prepare/apply、A/B Slot、Merge、Pull、Stash 或自动回滚；
- 不接收调用方提供的 Ref、Tag、Commit 或 remote URL；
- 不校验远端 Tag 与分支 Commit 相等，不恢复 D6 已移除的版本索引和 Commit 钉扎；
- 不解析 go-git、服务器或 Git progress 的自然语言文本驱动业务分支；
- 不改变用户数据、诊断日志、插件目录或受管根之外的任何内容；
- 不实现进程信号取消。协议 v1 的取消入口仍是 stdin NDJSON。

## 2. 已定方案

### D1 go-git 版本与职责

固定 `github.com/go-git/go-git/v5 v5.19.2`。T4.0 必须先对 GitHub 和 CNB 的真实
`release/v5.3.1` 完成浅克隆 spike，记录耗时、目录体积、HEAD、shallow 与 Tag
事实；任一远端失败则停止 T4.1 之后的实现并登记决策项。

go-git 只负责：

- HTTPS Git reference discovery、pack 获取、checkout 和仓库语义读取；
- 通过带 worktree 的 `git.CloneContext` 贯通取消；Runtime 以只暴露 `storage.Storer` 的窄适配器
  保留 PlainClone 的非 bare 仓库语义，并避开 go-git 截断 pack writer 的句柄泄漏；
- 提供 remote、HEAD、reference、Commit 和 shallow 信息。

go-git 不负责 mirror 排序、错误码、目录命名、目录删除、整体替换、状态文件、日志或协议
事件。`CloneOptions.Progress` 只能交给受控 writer；不得连接 stdout/stderr，也不得解析
其文本。

### D2 版本目标

`Target` 是不可伪造的值对象，由 `ParseTarget(version)` 创建：

- 总长度 2~128 字节；
- 第一个字节必须是小写 ASCII `v`；
- 后续仅允许 ASCII 字母、数字、点、连字符和下划线；
- 拒绝 `..`、`@{`、结尾点、`.lock` 后缀、斜杠、反斜杠、空白、控制字符和非 ASCII；
- 分支固定为 `release/` + 原始完整版本，不做大小写转换或 SemVer 规范化。

长度沿用 state/mirror 已实现的 128 字节上限，避免同一产品版本在三个包中出现不同合法
集合。CLI 空值、重复 `--version` 或调用方 Ref/Commit 都在创建业务服务前映射
`INVALID_VERSION`。

### D3 包边界与依赖方向

```text
internal/cli
    -> internal/gitrepo
        -> config / filesystem / lock / mirror / state / protocol
        -> go-git/v5
```

建议文件按职责拆分：

```text
internal/gitrepo/
├── doc.go
├── target.go                 # T4.1
├── errors.go                 # 稳定业务错误
├── repository.go             # 只读仓库快照
├── clone.go                  # reference discovery + clone + mirror attempt
├── verify.go                 # remote/branch/version/Commit 校验
├── swap.go                   # 两步 rename 与旧目录收口
├── recovery.go               # update transaction 恢复矩阵
├── service.go                # check/sync 编排
└── *_test.go
```

`cli` 只解析 flag、建立 logger/control/session 并调用服务；`gitrepo` 不持有 Cobra 类型、
stdin/stdout/stderr 或 `os.Stdout`。网络、go-git 调用、文件系统操作、Store、Mutex、时钟、
PID 与事件出口均通过窄接口或构造依赖注入，单元测试不访问公网和系统 Git。

## 3. Git 获取与镜像轮换

### 3.1 固定目标

每次 sync 先从 `Target` 构造 `mirror.Target`，其字段固定为产品版本和发布分支。所有 Source
attempt 必须接收同一 `mirror.Target.Fingerprint()`；任何 attempt 不得改写版本、分支或
回退到默认分支。

### 3.2 单个 Source attempt

一个 attempt 固定执行：

1. 用 go-git `Remote.ListContext` 获取公开 refs；
2. 按结构化 reference name 查找 `refs/heads/<目标分支>`；
3. 不存在时返回 Source 级 `branch_not_found`，切换到下一源；
4. 创建 `repo.update-<operationId>`；目标已存在时先按恢复/清理规则处理，绝不覆盖；
5. 调用带受控 filesystem storage 的 `git.CloneContext`，保持 PlainClone 的非 bare 语义；选项
   固定为目标 branch、`SingleBranch=true`、`Depth=1`、`Tags=NoTags`、TLS 校验开启；
6. 在同一 attempt 内执行第 4 节静态校验；
7. 只有校验成功才向 Rotator 返回 `OutcomeSucceeded` 和实际 HEAD Commit。

把静态校验放在 mirror attempt 内，才能让版本不匹配或仓库损坏按
`OutcomeIntegrityFailure` 拉黑当前源并尝试下一源。若在 Rotator 成功后才校验，落后的首选
镜像会过早终止整条操作，与 T2.6 的完整性失败换源契约冲突。

### 3.3 失败分类

错误分类只使用 context、go-git 导出 sentinel/type、HTTP 状态类型和本包哨兵，不匹配
`Error()` 文本：

| Source 事实 | Rotator outcome | 顶层码 |
| --- | --- | --- |
| ctx 取消 | 取消，立即停止 | `OPERATION_CANCELLED` |
| offline plan | 不发起 attempt | `NETWORK_UNAVAILABLE` |
| reference discovery 传输失败 | 同源有限重试，再切源 | `GIT_REMOTE_RESOLVE_FAILED` |
| 该源缺目标 branch | 立即切源 | 全部可达源均缺失时 `GIT_BRANCH_NOT_FOUND` |
| clone 传输/checkout 失败 | 同源有限重试，再切源 | `GIT_CLONE_FAILED` |
| remote/branch/仓库结构不合法 | 完整性失败并拉黑源 | `GIT_REPOSITORY_INVALID` |
| version 文件与目标不一致 | 完整性失败并拉黑源 | `GIT_VERSION_MISMATCH` |
| 所有源失败且事实混合 | 按最强未决事实选择 | clone > resolve > branch missing |

只有在所有成功完成 reference discovery 的源都明确缺少目标 branch、且没有未决传输失败时，
才能断言 `GIT_BRANCH_NOT_FOUND`。否则不能把“未能查询”误报成“分支不存在”。

临时目录的“检查不存在”只用于报告事实，不能作为后续路径 I/O 的安全凭据。真正开始
clone 前必须调用 `filesystem.PrepareManagedDirectory`：该能力在受管 app-root 的固定父句柄
下以 `CREATE_NEW + FILE_DIRECTORY_FILE` 原子创建 `repo.update-<operationId>`，拒绝已存在的
普通目录、文件或重解析点，并在整个 go-git clone/verify 期间持有不共享 delete 的目录租约。
租约关闭后才允许受控清理；任何创建或租约校验失败都保留现场并映射
`UPDATE_STATE_AMBIGUOUS`，不得回退到 `osfs.New(path)` 的无保护 `MkdirAll` 语义。
父目录固定句柄及身份校验全部完成后、执行 `CREATE_NEW` 前必须最后检查一次 `ctx.Err()`；若已
观察到取消，关闭父链并保持目标 leaf 不存在。取消与 Win32 创建调用之间仍只能提供 Go context
可表达的提交前检查，不宣称能把系统调用与 context 原子化。

若 `CREATE_NEW` 已完成但随后 context 或身份校验失败，创建句柄仍不请求 `DELETE`（否则会阻塞
go-git 打开 clone 根）；Runtime 先关闭该不共享 delete 的租约，再在固定父句柄下重新打开目标，
复验原叶子 volume/file-ID token、父身份和重解析点属性，最后通过该新固定句柄设置删除 disposition。
重开、复验或关闭失败都保留现场并失败关闭，绝不按路径猜删。Fetcher 对租约关闭执行固定次数的
同步重试；达到上限仍未关闭时返回 `GIT_REPO_CLEANUP_FAILED`，不继续清理或 swap。

该租约把目标目录叶子和受管父目录固定在句柄上，消除检查后到 clone/verify 打开目标根之间的
同用户 Junction 替换窗口；go-git 对目录内部的后代文件仍使用 path-based I/O，Runtime 不宣称
能阻止同一用户在租约范围内篡改内容或重解析点。此类本机篡改属于可检测的 DoS/tamper 残余边界：
静态身份校验、租约关闭和受控清理均失败关闭并保留现场，不把它视为远端攻击路径。

### 3.4 临时目录清理与取消

每次失败 attempt 在切源或返回前清理精确的 `repo.update-<operationId>`。清理必须调用
`filesystem.Operator.RemoveTree(DeleteRepositoryUpdate)` 并写双阶段审计；禁止使用
go-git 内部 cleanup 成功与否作为安全删除证据，禁止 `os.RemoveAll`。

失败或取消后的精确收口始终使用
`context.WithTimeout(context.WithoutCancel(ctx), 30s)`；不能先检查 `ctx.Err()` 再决定是否
脱离取消，因为取消可能恰好发生在检查之后。清理失败时保留 update transaction 和目录，
错误链同时保留取消与清理事实；不得把残留现场伪装成已清理成功。若独立收口 context
确实返回类型化的 `GIT_REPO_CLEANUP_FAILED`（stage=`workspace.cleanup`），CLI 必须保留
该清理事实，即使其 cause 是 `context.DeadlineExceeded`；若只是业务 context 被取消而没有
独立 cleanup 失败，仍按 `OPERATION_CANCELLED` 处理。

progress writer 只把“收到新的传输进度片段”转成有上限的 `workspace.clone/running` 脉冲，
不转发或解析原文本，不计算虚假百分比。每个 attempt 另发 start 与 succeeded/failed 事件。
协议输出失败必须优先映射 `OUTPUT_WRITE_FAILED`，不能继续 swap。错误链同时含已类型化输出
故障和取消时仍以输出故障为主错误；除上述独立 cleanup 失败外，其他业务错误链继续保持
取消优先。

## 4. 克隆后静态校验

验证器返回不可变 `Revision`：`Version`、`Branch`、40 位小写 Commit、Source key。固定校验：

1. `repo.update-*` 能被 go-git 作为非 bare 仓库打开；
2. 只有名为 `origin` 的目标 remote，fetch URL 恰有一个；该 URL 必须等于当前 attempt
   Source 且属于本次 Git Plan；不得存在调用方注入的任意 remote；
3. HEAD 必须是指向 `refs/heads/<目标分支>` 的 symbolic branch，不能 detached；
4. HEAD hash 必须是 40 位小写十六进制，并可读取 Commit object；
5. 仓库不得包含本次克隆得到的 Tag refs；shallow 边界必须包含 HEAD；
6. `res/version.json` 限制为 1 MiB，使用 JSON decoder 读取顶层 `version` 字段，拒绝缺失、
   非字符串、重复 `version`、非法 JSON 和尾随值；其他发布元数据字段允许存在；
7. 文件中的 `version` 必须逐字节等于 Target.Version。

remote、branch、Commit、shallow 或 JSON 结构故障映射 `GIT_REPOSITORY_INVALID`；版本值不匹配
映射 `GIT_VERSION_MISMATCH`。不比较远端 Tag，不把 reference discovery 得到的 Commit 当作
安全钉扎值；最终 Commit 只取克隆并校验后的本地 HEAD。

任何校验失败都先尝试清理临时目录并保留现有 `repo/`。若目录身份不安全或清理本身失败，
失败关闭并保留现场供 T4.5 恢复，不能为了满足“失败即删除”而绕过 T2.5。

## 5. 原子替换事务

### 5.1 update transaction

`state.TransactionUpdate` 使用既有 schema，不追加未冻结字段。单次事务保持同一
`OperationID/Command/PID/StartedAt/TargetVersion`，只推进 Stage：

```text
workspace.clone -> workspace.verify -> workspace.swap -> workspace.cleanup
```

每次推进都通过 `state.Store.WriteTransaction` 原子写 `update.json`。顶层 sync 同时维护
`mutation.json` 供诊断；二者不能代替 Mutex。update 事务只有在目录收口、环境状态成功提交且
事务文件条件删除完成后才结束。

### 5.2 swap 顺序

持有 mutation Lease 时固定执行：

1. 写 `workspace.swap` update transaction；
2. 若 `repo/` 存在，调用 `AtomicRename(RenameRepositoryToRetired)`：
   `repo` -> `repo.previous-<operationId>`；
3. 调用 `AtomicRename(RenameUpdateToRepository)`：
   `repo.update-<operationId>` -> `repo`；
4. 第二次 rename 成功是“新 Git revision active”的唯一提交点；
5. 写 `workspace.cleanup` transaction；
6. 原子写 `environment_broken/repository_changed`；
7. 通过 `RemoveTree(DeleteRepositoryRetired)` 删除 previous 目录；
8. 条件删除 update/mutation transaction。

正常 Swapper 在第 6 步通过 `CommitEnvironment` 提交回调串行化该边界；回调缺失或返回错误时失败关闭，
保留 active target、previous 和 transaction，不能退回旧 `ready_to_start`。因此“环境写入失败不删除
previous”和“previous 清理失败时环境已是 repository_changed”都属于组件验收，而不是仅靠 Recovery
补救的实现约定。

不存在旧 repo 的首次安装跳过第 2 步。不能先删除旧 repo，不能覆盖 destination，不能把
previous 当长期 Slot。

Fetcher 在仍持有 update 目录租约时取得叶子 volume/file-ID token，并随 `FetchResult` 传给
Swapper。workspace check 在读取当前 Git 身份时同时保存 active `repo/` 的叶子 token，
Swapper 必须把它作为第一次 rename 的 `ExpectedSourceIdentity`，把 FetchResult token 作为
第二次 rename 的 `ExpectedSourceIdentity`。操作器在固定句柄上重验 token；分类后 update 或
repo 被替换成普通目录、用户数据目录或其他对象时，返回
`UPDATE_STATE_AMBIGUOUS` 并保留现场，不能只按路径继续移动。没有 update token 的 swap 请求
在任何目录副作用前失败关闭。

第一次 rename 取得的 active token 还必须随同一对象传给后续
`RemoveTree(DeleteRepositoryRetired)`；retired 叶子身份变化按已提交后的
`GIT_REPO_CLEANUP_FAILED` 失败关闭，不能按 previous 路径删除未知目录。普通但内容损坏的现有
`repo/` 在 clone/verify 尚未提交 swap 时仍可保留叶子 token，安全清理 update 并等待后续整体
替换；只有 Reparse、权限或其他无法证明叶子身份的情况才返回 `UPDATE_STATE_AMBIGUOUS`。

go-git 在 Windows 上会把 pack index 标记为 `FILE_ATTRIBUTE_READONLY`。T2.5
`RemoveTree` 的句柄相对删除必须在 `FileDispositionInformationEx` 中同时使用
`FILE_DISPOSITION_DELETE | FILE_DISPOSITION_IGNORE_READONLY_ATTRIBUTE`，使受控删除能收口
真实 clone 产生的 update/previous 目录；不得先按路径清除属性，也不得退回 `os.RemoveAll`。
Windows 10/11 是首版冻结平台，均支持该 disposition flag；原有不支持 extended disposition
时的 legacy fallback 保留，但只读对象在 legacy 路径失败关闭。

go-git `v5.19.2` 的 `PackWriter.Close` 在截断 pack 上可能在返回解析错误前遗留临时 pack
句柄。Runtime 的 clone 适配器因此只向 `git.CloneContext` 暴露 `storage.Storer`，刻意不暴露
可选的 `storer.PackfileWriter`，让 go-git 使用官方同步 loose-object fallback；这样传输失败
仍返回原始 clone 错误，且不会把未关闭的 `tmp_pack_*` 句柄带入受控清理。该实现细节绑定
当前 go-git 版本，升级依赖时必须重新验证中断响应和临时目录收口；对外 Git 获取参数与
仓库结构契约不变。

### 5.3 目录占用与错误

不增加“先打开再关闭”的占用预探针，因为它与随后 rename 之间存在 TOCTOU。T2.5
`AtomicRename` 会固定源和目标父目录句柄并有限重试；其最终 sharing/lock/access-denied 结果是
`DIRECTORY_OCCUPIED` 的权威判定。其他 rename 故障映射 `GIT_REPO_SWAP_FAILED`。

若持有者先于 Runtime 打开源目录且不共享 delete，Runtime 可能在取得自身 rename pin
之前就收到 sharing/access-denied；该同一占用事实也必须映射为 `DIRECTORY_OCCUPIED`，不能
因失败发生在 pin 阶段而降级为通用 swap 错误。pin 阶段与实际 rename 阶段必须共用同一组
有限延迟、context 等待和每次重试前的路径/身份重验证；只有耗尽延迟序列后才返回稳定占用码。
每次 source 与目标父目录固定句柄、身份 token 重验完成后，实际 rename 系统调用前还必须最后
检查一次 `ctx.Err()`；已观察到取消时关闭本次全部 pin 并以零 mutation 返回。系统调用开始后的
取消按 rename 的真实 `MutationApplied` 事实处理，不把已生效 rename 伪装成提交前取消。

第二次 rename 失败时不得删除 previous/update；保留 `update.json` 让恢复逻辑可判定。新 repo
active 后 previous 删除失败映射 `GIT_REPO_CLEANUP_FAILED`，同样保留事务；不得回滚已经 active
的 Git revision。

previous 是第一次 rename 刚移入的旧 repo 叶子，删除时必须使用该 active token 并在固定句柄
上重验；token 不匹配时保留 previous 与 transaction。

若第一次 rename 已实际生效而第二次未激活新仓库，顶层 Service 必须用最长 30 秒的独立收口
context 调用同一 Recovery，把 `previous` no-replace 回到 `repo` 并清理 update。只有 Recovery
完整成功才允许 `RollbackPreparation`、删除 mutation transaction 和发出原稳定状态；恢复失败
保留 update 现场，且不得发出旧稳定状态。

## 6. 中断恢复

任何 mutation 命令在创建新 update transaction 前，先在持有 mutation Lease 时恢复已有
`update.json`。恢复只查看事务精确派生的三个路径：`repo`、`repo.update-<id>`、
`repo.previous-<id>`；不枚举前缀猜测所有权。

每个存在目录都按“不跟随重解析点 + go-git 静态身份”分类为：目标 revision、其他有效
revision、普通但不完整、unsafe/unknown。仅当目录叶子身份已证明且 go-git 内容读取本身失败时，
普通内容损坏的 active `repo/` 才在 clone/verify 阶段按“不完整”保留并允许仅清理 update；
remote/branch/shallow/Commit/版本结构等身份校验失败、Reparse Point、非目录占位、权限错误、
同版本不同 Commit 的双候选、状态损坏或无法取得叶子身份，返回
`UPDATE_STATE_AMBIGUOUS`，且不删除、不移动任何目录。`sourceKey` 只是受信来源的 provenance，
不是 revision 唯一性的一部分；同一 version/branch/Commit 从不同配置镜像恢复时仍按同一
revision 处理。

分类时还必须取得受管目录叶子的不可变 volume/file-ID token，并把 token 传给后续受控
`RemoveTree`/`AtomicRename`。操作器在固定句柄上重新校验 token；分类后目录被同用户替换为普通
目录、用户数据目录或其他对象时，必须返回 `UPDATE_STATE_AMBIGUOUS` 并保留现场，不能只按
相同路径和“仍是目录”继续删除或移动。token 只保护目录叶子身份；目录内部后代仍遵循本设计
的 path-based I/O 残余边界。

确定性恢复矩阵：

| transaction/目录事实 | 恢复动作 |
| --- | --- |
| 首次安装 clone 阶段，repo/update/previous 均缺失 | 空事务现场，仅条件删除 transaction |
| clone 未完成，previous 不存在 | 受控删除 update，保留 repo |
| verify 可重新证明目标有效，尚未进入 swap | 保留 repo，受控删除 update |
| clone/verify 阶段 repo 缺失，update=目标 | 身份形状不完整，返回 `UPDATE_STATE_AMBIGUOUS`，不删除 update |
| swap：repo=旧、update=目标、previous 缺失 | 视为 rename 前，保留 repo、删除 update |
| swap：repo 缺失、update=目标、previous=旧 | 视为两次 rename 之间，previous no-replace 回到 repo，再删除 update |
| swap：首次安装 repo/previous 都缺失、update=目标 | update no-replace 前移为 repo |
| repo=目标、update 缺失、previous 可有可无 | 目标已 active；删除 previous，补写 repository_changed |
| repo 缺失、update 缺失、previous=唯一有效 revision | previous no-replace 恢复为 repo，不声明 swap |
| environment 已是同一目标的 repository_changed | 不重复改写，只收口残留 transaction |
| 只有 environment_broken/operation_failed 且无 Git transaction | 保持原值；M4 不碰 venv |
| 任一身份不能唯一证明 | `UPDATE_STATE_AMBIGUOUS`，零目录副作用 |

恢复 rename 仍只能调用 T2.5 封闭 RenameKind。为支持“previous -> repo”回滚，T4.4 可在同一
任务内向 filesystem 追加专用 `RenameRepositoryRollback`；它只接受同一 operation ID 的精确
previous/repo 路径，不开放通用 rename。

补写 `repository_changed` 时保留旧环境状态的 `LastSuccessful`；没有环境文件时使用空
revision。Broken 固定为目标 version/branch/Commit、空 Python/uv、
`reason=repository_changed`、`stage=workspace.swap`、`exitCode=0` 和当前受管 Runtime log
绝对路径。写失败返回 `STATE_WRITE_FAILED` 并保留 update transaction。

Recovery 在任一目录 rename 已成功后，必须用最长 30 秒的
`context.WithTimeout(context.WithoutCancel(ctx), 30s)` 完成剩余 environment、cleanup 和
transaction 收口；提交前的分类、校验和 rename 仍响应业务取消，提交后的迟到取消不得把已
激活现场伪装成普通 `OPERATION_CANCELLED`。其中 active target 恢复必须先持久化
`environment_broken/repository_changed`，再清理 `previous`；旧目录清理失败时保留
`previous` 与 transaction，但不得让 durable environment 继续保持旧的 `ready_to_start`。

## 7. workspace 应用服务

### 7.1 workspace check

check 是只读操作：不创建 app-root、state、lock、log 或临时目录，不访问网络。它读取固定
`repo/` 并返回：

```json
{
  "healthy": true,
  "version": "v5.4.0-beta.4",
  "branch": "release/v5.4.0-beta.4",
  "commit": "<40 hex>",
  "source": "github",
  "reason": "ok"
}
```

缺失或损坏仓库仍表示“检查已完成”，成功 result 中 `healthy=false`，reason 使用稳定分类
`missing/invalid/version_mismatch/remote_unknown`，不包含绝对路径、remote URL 或原始错误串。
I/O/取消/协议输出基础设施错误才使命令失败。

### 7.2 workspace sync

固定顺序：

1. 校验 app-root 已存在且为目录；
2. 构造 Runtime logger；
3. 创建 `lock.Set` 并 `AcquireMutation`；该调用同时探测 backend Mutex；
4. `BACKEND_STILL_RUNNING`、`MUTATION_IN_PROGRESS` 和 Mutex 故障保留原冻结码；生产 lock 在释放
   临时取得的主 Mutex 后会用 `errors.Join` 返回冲突与 cleanup，Service 必须先识别整条错误链中的
   context 取消，再用 `errors.As` 提取冻结锁码，禁止直接 type assertion 丢失 join 内的冲突；
5. 打开 state Store，恢复旧 update transaction；
6. 读取环境稳定初态：环境文件不存在为 `uninitialized`，合法文件取其 status；损坏或未知
   schema 因无法保留 LastSuccessful 而返回 `UPDATE_STATE_AMBIGUOUS`；
7. 创建 LifecycleMachine，迁移并发出 `syncing_repository`；
8. 检查 active repo。若已严格匹配目标 version/branch 且仓库健康，走 no-op；
9. no-op 不访问网络、不写 environment、不执行 swap；调用 `RollbackPreparation`，发出原稳定
   状态快照，成功 result `changed=false`、status=原稳定状态；
10. 非 no-op 执行 clone/verify/swap/cleanup；第二次 rename 后立即按第 6 节提交 broken state；
11. 实际 swap 成功 result `changed=true`、status=`environment_broken`；
12. result details 返回最终 version/branch/Commit/source/changed，不含路径或 URL。

替换前失败或取消必须 `RollbackPreparation` 并发出原稳定状态；替换提交点之后绝不回到
旧 `ready_to_start`。两次 rename 之间发生失败时先按第 5.3 节恢复，不能把 repo 缺失现场当作
普通替换前失败。state 写失败不得报告成功，即使新 repo 已 active；若它与此前 cleanup 错误
并存，`STATE_WRITE_FAILED` 是主错误，cleanup 事实保留在错误链。协议 state/progress 发射失败
同理以 `OUTPUT_WRITE_FAILED` 为主错误。

第二次 rename 已激活目标后，业务 context 的迟到取消不能中断成功边界提交；mutation stage、
`repository_changed` 和两个 transaction 的条件删除统一改用最长 30 秒的
`WithTimeout(WithoutCancel(ctx))` 收口 context。此后失败按实际持久化事实返回
`STATE_WRITE_FAILED`，不能把 active 新仓库误报成普通用户取消。

提交后的类型化错误必须显式携带 committed 标记，并由 CLI 在通用取消分类之前保留其 code、stage、
message 和 details；底层 deadline 仍保留在错误链中供诊断。若 CLI 为失败补充迟到
`controlCommandId`，包装错误必须同时传播 committed 标记和已补充的 details，不能因重新分类丢失
命令关联，也不能把失败终态改成 `cancelled`。

`StageReporter` 必须下传到 Recovery、Fetcher 和 Swapper，而不是只在 Service 调用边界更新：
reference discovery/clone 为 `workspace.clone`，静态校验为 `workspace.verify`，rename 与环境补写为
`workspace.swap`，临时/previous 删除与事务收口为 `workspace.cleanup`。取消和无效控制 warning
都使用发生动作时的真实 stage。

### 7.3 stdin cancel

D-open-8 原文字面把落点写为 T4.3，但 T4.3 是业务包校验，stdin 只由 T4.6 CLI 持有。最终
分工为：

- T4.2/T4.3 的全部耗时 API 接受并贯通 `ctx`；
- T4.6 为 `workspace sync` 建立 `protocol.ControlReader`，hello capabilities 包含
  `stdin.cancel`；
- control handler 接受 cancel 后调用本操作的 cancel func，并保存 `controlCommandId`；
- stage-tracking emitter 让无效控制 warning 使用当前真实 stage；
- 最终相关 state/error/result details 回显已接受的 commandId；重复 cancel 幂等；
- 控制读取基础设施故障取消业务操作并映射稳定错误，不能静默继续 swap。

每个 CLI 进程最多启动一个控制读取 goroutine，并持有有缓冲 completion channel。Service 返回
后先 `StopAccepting`；对可结束或可关闭的非真实 stdin，在关闭 owner 后有界等待 completion，
再读取控制错误和首个 `controlCommandId`，从而不漏掉并发完成的 cancel/读取错误。真实
`os.Stdin` 不关闭，也不无限等待，其阻塞读取由一次性进程退出终结。`StopAccepting` 在 result
前阻止后续控制事件，确保 result 仍是最后事件。

非真实 stdin 若实现 `io.Closer`，其关闭行为属于调用方交付给 Runtime 的 owner contract，必须
在有界时间内返回；Runtime 不会为不合作的 `Close` 启动无法回收的后台 goroutine。真实
`os.Stdin` 不适用该 Close contract：Runtime 不关闭它，进程退出负责终结阻塞读取。

## 8. CLI 与会话框架变更

`sessionSuccess` 增加可选 `status`；为空时保持 M3 的 `succeeded`，避免改变 version/doctor/
cleanup。workspace sync 显式设置稳定生命周期状态。

CLI 增加 workspace service factory 与 logger factory 注入点，契约测试不访问真实网络、Git、
Mutex 或文件系统。`workspace sync --version` 必填且只出现一次；Cobra 位置参数仍为
`NoArgs`。所有业务事件继续经唯一 Emitter；go-git Progress、logger 和 auditor 都不得写
stdout。

## 9. 本地 Git 组件夹具

测试不调用系统 `git.exe`。夹具用 go-git 在 `t.TempDir()` 创建文件系统裸仓库和提交图，
再用 `plumbing/transport/server` 提供 upload-pack session，由 `httptest.NewTLSServer` 包装为
智能 Git HTTP：

- `GET /<repo>.git/info/refs?service=git-upload-pack` 返回 advertisement；
- `POST /<repo>.git/git-upload-pack` 解码请求并流式返回 pack；
- TLS 证书以测试 CA bundle 注入 go-git List/Clone options，`InsecureSkipTLS` 始终为 false；
- handler 可用 channel barrier 模拟卡在 discovery、pack 和响应中断，不用 `time.Sleep`；
- 同一服务可暴露落后镜像和官方源，移动 branch ref，构造同版本不同 Commit；
- 每个测试结束断言没有 `repo.update-*` / `repo.previous-*` 残留，除非场景明确验证保留现场。
- 夹具至少包含一个真实 go-git pack index，并证明其只读属性不会阻止受控清理。
- Depth 1 证据必须同时断言 shallow boundary 等于目标 Commit、父 Commit 对象不可读取；测试
  server 不得只记录 `deepen 1` 后返回完整历史并手工伪造 shallow 元数据。
- 取消矩阵分别在 reference discovery、pack 生成/写入和响应读取三个 barrier 注入，并证明
  `OPERATION_CANCELLED`、精确临时目录收口及无 goroutine/句柄残留。
- 真实 pack index 用正常 go-git clone 产生并实测 `FILE_ATTRIBUTE_READONLY`；再把仓库放入精确
  `repo.previous-<operationId>`，通过 `DeleteRepositoryRetired` 证明受控删除，不用手工同名文件
  代替 pack 证据。

任务文本写“本地 HTTP Git 服务”是协议类别描述；采用本地 TLS server 是更严格实现，既能覆盖
真实 HTTP transport，又不破坏架构“TLS 默认开启且无关闭开关”的上位约束。

## 10. 测试矩阵与门禁

必须覆盖：

- 版本：标准版本、预发布版本、历史 withplugin、空值、斜杠、反斜杠、空白、`..`、`@{`、
  结尾点、`.lock` 后缀、非 ASCII、129 字节；
- 获取：首选成功、首选分支落后切官方、两个源均缺分支、resolve 失败、pack 中断、取消、
  Depth1、NoTags、SingleBranch；
- 校验：remote 非配置源、多 URL、branch 不符、detached HEAD、损坏仓库、版本缺失/重复/非法/
  不匹配、同版本分支移动；
- 替换：旧 repo 脏文件/未跟踪文件消失、首次安装、第一/第二 rename 故障、目标占用、旧目录
  清理失败、state 写失败；
- 恢复：六条架构规则及本设计矩阵、状态损坏、Reparse Point、同版本不同 Commit、零副作用
  ambiguous；
- 服务：ready/broken/uninitialized 三种初态、actual swap、no-op、backend 持锁、mutation 冲突、
  lastSuccessful 保留、降级；
- 协议：check/sync 的 success/warning/failure 公共契约、首 hello、cancel capability、state 顺序、
  error/result 四元组和 result 最后；
- 安全：stdout 所有权、无系统 Git、无 shell 字符串、无用户数据变更、无绝对路径/remote URL
  泄漏；组件操作前后快照验证 `config/data/history/script/debug/plugins/logs/runtime` 的目录身份
  与内容不变；目录检查覆盖 app-root/目标不存在、普通文件、直接/祖先 Junction、权限错误、取消
  和零目录创建。

逐任务执行定向测试；M4 收口执行标准验证门、`internal/gitrepo` 高重复测试、相关 CLI 契约测试、
stdout 扫描和全仓 race detector。对抗性 review 至少独立执行三轮：契约/状态机、崩溃恢复/目录
安全、并发/取消/测试真实性；Critical/Important 全部修复后才验收。
