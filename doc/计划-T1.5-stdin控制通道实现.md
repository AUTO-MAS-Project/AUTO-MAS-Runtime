# T1.5 stdin 控制通道实现计划

> 实施方式：严格按测试驱动开发执行；每个任务先写失败测试并确认失败原因，
> 再写最小实现，运行局部与全量验证后提交。每个任务提交后进行独立审查，
> 重要问题在进入下一任务前修复。

**目标：** 在 `internal/protocol` 交付有界、严格、幂等且可停止的 stdin
控制读取器，并提供 commandId 关联辅助函数，不越过 T1.6 终态契约边界。

**架构：** `ControlReader` 单线程读取物理行，在一个处理互斥门内完成解析后
路由、commandId 去重、handler prepare/action 和 warning 发射。调用方通过
窄 `ControlHandler` 先无副作用地准备 action；reader 对 accepted shutdown
先关闭接收门再执行 action。现有 `Emitter` 继续唯一拥有协议输出。

**技术栈：** Go 标准库（`bufio`、`context`、`encoding/json`、`io`、
`sync`、`unicode/utf8`），现有 protocol 事件/错误/stage API。

## Task 4：实现停止接收门与 status 快照证明

**文件：**

- 修改：`internal/protocol/control.go`
- 修改：`internal/protocol/control_test.go`

**红灯：**

1. 用阻塞 recording handler 证明 `StopAccepting` 等待在途调用；
2. 证明 `StopAccepting` 返回后新完整行不会调用 handler 或发 warning；
3. 用 `io.Pipe`、显式关闭 writer 和有超时的完成 channel 证明：停止门不
   打断当前 read，但下一完整行到达后 `Run` 返回 nil；
4. 证明 StopAccepting 后关闭 owner 的 reader 解阻时 `Run` 返回 nil，
   不泄漏底层 close error；
5. accepted shutdown 先置 stopped 再执行 action，同批后续命令不执行；
6. 同一输入连续两个不同 ID 的 shutdown 只有首个进入 handler；
7. 第二次和并发 `Run` 返回 one-shot error；
8. 证明 StopAccepting 前置/重复调用幂等，已取消 context 返回
   `context.Canceled` 且不处理输入；
9. 用真实 `LifecycleMachine` 和 recording emitter 构造 status handler：
   发射带 `details.controlCommandId` 的当前 state 快照，并断言 machine 状态
   前后不变；
10. 用 fake handler/event 路径证明 cancel result、shutdown state、status
   state 的下一条相关事件携带 commandId，且原 details 不变；
11. 并发重复运行测试以放大竞态。

**绿灯：**

1. stdin read 不持有处理门；
2. 解析后的停止检查、seen、handler prepare/action 和 warning 都在同一门内；
3. `StopAccepting` 同步设置停止状态；
4. accepted shutdown 在调用 action 前于同一临界区自动设置停止状态；
5. `Run` 在门内登记 one-shot started；
6. context 在读取前和处理完整行前检查；
7. 任意 read 返回后按 stopped、context、EOF/read error 顺序判断；
8. 明确 `StopAccepting` 不关闭 reader、不保证打断阻塞 read。
