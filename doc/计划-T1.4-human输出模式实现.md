# T1.4 human 输出模式实现计划

> **面向 AI 代理的工作者：** 必需子技能：使用
> superpowers:subagent-driven-development 逐任务实现此计划。每个新增生产
> 行为严格执行测试先行的 RED → GREEN；任务 3 是对任务 1/2 已实现行为的
> 契约补强，不伪造失败。步骤使用复选框跟踪进度。

**目标：** 在保持协议 v1 NDJSON 字节与错误语义兼容的前提下，让同一条
语义事件流水线支持确定性的 human stdout/stderr 文本投影。

**架构：** `Emitter` 在 `ProcessOutput` 的唯一互斥临界区中补齐
`Common`，随后把强类型事件分发给 `EventRenderer`。现有
`NewProcessOutput(io.Writer)` 内部使用 `NDJSONRenderer`；显式注入
`HumanRenderer` 时仍共享 operationId、sequence、timestamp、事件顺序、
sticky I/O 错误和单 emitter 所有权。

**技术栈：** Go 1.26、标准库 `bufio` / `encoding/json` / `fmt` / `io` /
`reflect` / `strconv` / `strings` / `sync` / `unicode`、PowerShell 7、
Go `testing`。

---

## 全局约束

1. `NewProcessOutput(io.Writer)` 的签名和 NDJSON 行为逐字节兼容。
2. NDJSON marshal 失败继续返回 `encode <type> event: ...`，非 sticky，
   sequence 不递增；write/flush 失败继续返回 sticky
   `write protocol event: ...`。
3. `EventRenderer` 只接收已经补齐 `Common` 的值，不创建或修改事件。
4. `ProcessOutput` 的同一把锁覆盖 Common、renderer、flush 和 sequence。
5. `OperationEmitter` 精确保持四个方法；`LifecycleEmitter` 只额外包含
   `EmitState`；不得加入 `EmitLog` 或 writer。
6. Human 无 ANSI/TTY 行为。所有 control rune 都显示为可见转义。
7. Human 格式、字段顺序、空值、多行前缀和 stdout/stderr 路由严格按
   `doc/设计-T1.4-human输出模式.md`。
8. `details` 不在 human 中通用展开；renderer 不推断业务状态。
9. T1.4 不实现 CLI 参数接线、stdin 控制、terminal result gate、warning
   汇总、反压、持久化或文件日志。
10. 当前 Windows 环境不可运行 race detector 时，不声称 race 通过；使用
    定向并发测试和 100 轮协议包压力运行。

在 `renderer.go` 添加：

```go
type EventRenderer interface {
    RenderHello(HelloEvent) error
    RenderProgress(ProgressEvent) error
    RenderState(StateEvent) error
    RenderLog(LogEvent) error
    RenderWarning(WarningEvent) error
    RenderError(ErrorEvent) error
    RenderResult(ResultEvent) error
}

type nonStickyRenderError struct {
    err error
}

func (e *nonStickyRenderError) Error() string { return e.err.Error() }
func (e *nonStickyRenderError) Unwrap() error { return e.err }
```

的 kind 调用 `IsNil`，因此直接 nil 和 typed nil writer/renderer 都被拒绝。

`TestNDJSONMarshalFailureIsNotSticky`：

1. 用现有 `NewProcessOutput` 创建 emitter，hello sequence 为 1；
2. 发射 `StateEvent{Details: map[string]any{"bad": make(chan int)}}`；
3. 断言错误包含 `encode state event:`，不包含
   `write protocol event:`；
4. 再发射合法 log；
5. 解码输出，断言合法 log 使用 sequence 2，而不是 3；
6. 输出中没有失败 state 的部分 JSON。

三个 NDJSON I/O 用例分别使用独立 sentinel error，并覆盖：

- direct write：发射大于 `bufio` 默认容量的消息，让底层 `Write` 直接失败；
- buffered flush：发射短消息，让 `bufio.Writer.Flush` 才触发底层 write 失败；
- destination flush：底层 write 成功，但目标对象的 `Flush() error` 返回 sentinel。

每个用例都先成功发射 hello，再让下一事件失败，并逐项断言：

- renderer 返回原始底层 I/O error，`ProcessOutput` 外层精确只增加一次
  `write protocol event: <sentinel>`；
- 后续发射返回与首次失败完全相同的 error 值；
- 失败后底层 write/flush 计数不再变化；
- `renderer_internal_test.go` 直接断言 `nextSequence` 保持失败前的值；
- 输出没有失败事件的完整 JSON 行。

`TestRendererFailureIsSticky` 让 recording renderer 在 warning 返回
`errors.New("renderer failed")`：

- warning 返回 `write protocol event: renderer failed`；
- 后续 progress 返回同一错误；
- renderer 没有收到 progress；
- `renderer_internal_test.go` 必须断言 sequence 不因 warning 失败而推进。

`emitter.go` 改为：

```go
type ProcessOutput struct {
    mu             sync.Mutex
    renderer       EventRenderer
    nextSequence   uint64
    writeErr       error
    emitterCreated bool
}

func NewProcessOutput(output io.Writer) (*ProcessOutput, error) {
    renderer, err := NewNDJSONRenderer(output)
    if err != nil {
        return nil, err
    }
    return NewProcessOutputWithRenderer(renderer)
}

func NewProcessOutputWithRenderer(renderer EventRenderer) (*ProcessOutput, error)
```

`Emitter.emit` 补齐 Common 后调用 `renderEvent`：

```go
if err := renderEvent(e.output.renderer, event); err != nil {
    var nonSticky *nonStickyRenderError
    if errors.As(err, &nonSticky) {
        return nonSticky.err
    }
    return e.output.rememberWriteError(err)
}
e.output.nextSequence++
```

`rememberWriteError` 继续只包装一次
`write protocol event: %w`，后续返回同一个 error 值。

- [ ] **步骤 3：实现双流 HumanRenderer 和七类格式**

在 `human_renderer.go` 定义：

```go
type humanDestination struct {
    writer      *bufio.Writer
    destination io.Writer
}

type HumanRenderer struct {
    stdout humanDestination
    stderr humanDestination
}

func NewHumanRenderer(stdout, stderr io.Writer) (*HumanRenderer, error)
```

构造器通过任务 1 的 `interfaceIsNil` 分别拒绝直接 nil 和 typed nil
stdout/stderr。

七个方法严格使用设计文档的固定前缀和字段顺序，并在本步骤一次实现步骤 1
列出的全部 golden、契约矩阵和规范化行为。所有格式化先在
`strings.Builder` 中构造完整事件块，再写入一个目标 destination；单事件
不得跨两个流。

实现辅助函数：

```go
func humanScalar(value string) string
func humanList(values []string) string
func humanMessageLines(message string) []string
func appendHumanMessage(builder *strings.Builder, prefix, message string)
func (d *humanDestination) write(block string) error
```

`humanScalar`：

- `strings.ToValidUTF8(value, "\uFFFD")`；
- `\` → `\\`，CR → `\r`，LF → `\n`；
- `unicode.IsControl` 的 U+0000～U+00FF → `\xNN`；
- 其他 control rune → `\uNNNN`；
- 空字符串 → `-`。

`humanMessageLines`：

- 先替换非法 UTF-8；
- CRLF 和裸 CR 规范化为 LF；
- `strings.Split` 保留中间和尾部空行；
- 每个逻辑行执行与 scalar 相同的反斜杠/control 转义，但空行保持空。

`humanDestination.write`：

1. `writer.WriteString(block)`；

新增：

```go

```

`failWriteAt` / `failFlushAt` 使用 1-based 调用序号，0 表示不失败。测试先让
hello 成功，再把失败序号设为当前计数加一，因此能够证明“先成功、后失败”
的 sequence 边界，而不是让构造后的第一次写入就失败。

矩阵逐项覆盖：

- stdout/stderr 大块 direct write 失败：消息块大于 4096 bytes；
- stdout/stderr buffered flush 失败：短消息先进入 buffer，底层 Write 在
  `bufio.Writer.Flush` 时失败；
- stdout/stderr destination flush 失败：Write 成功，目标对象的
  `Flush() error` 返回独立 sentinel；
- 成功事件只 flush 目标流；
- stderr warning 失败后，stdout progress 不再写；
- stdout progress 失败后，stderr warning 不再写；
- 后续返回同一个 sticky error 值；
- 后续返回与首次失败完全相同的 error 值，且错误文本精确只包一层
  `write protocol event: <sentinel>`；
- 失败后 write/flush 计数不再变化；
- `renderer_internal_test.go` 使用 `package protocol`，必须直接断言
  `ProcessOutput.nextSequence` 不递增；不得为测试向生产 API 暴露 sequence。
