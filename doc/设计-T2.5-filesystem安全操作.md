# T2.5 filesystem 安全操作设计

## 文档状态

- 日期：2026-07-30
- 状态：已批准，采用方案 A；已修订 StateFiles guard/sealed-intent/POSIX unlink 协议
- 任务：[T2.5 filesystem 安全操作](./任务拆分.md)
- 架构基线：[架构设计](./架构设计.md)
- 代码基线：AUTO-MAS Runtime `fb06f57`

本文冻结 `internal/filesystem` 的 Windows 路径身份、Runtime 日志文件安全访问、
受控递归删除、删除审计和原子重命名契约。实现必须失败关闭：路径无法唯一规范化、
目录身份与允许列表不符、路径链出现 Reparse Point 或删除前审计无法落盘时，均不得
执行文件系统副作用。

## 目标与范围

T2.5 交付以下能力：

1. 将 Windows 路径绝对化、长路径化，并保留用于 Windows ordinal
   大小写无关比较的规范结构串；
2. 以 `config.Layout` 为唯一目录身份来源，证明目标位于受管根内；
3. 沿目标路径逐级拒绝 Junction、符号链接和其他 Reparse Point；
4. 固定 app-root、`logs/` 和 `logs/runtime/` 的目录句柄，安全创建、列举和按
   不可伪造 token 删除单个 Runtime 日志文件；
5. 固定 `runtime-state/` 祖先句柄，以每 kind 持久 shared/exclusive guard gate、
   sealed intent + 两次 no-replace rename 与经探测证明的 POSIX namespace unlink
   安全读写、恢复和按封闭 kind 删除事务 state 文件；
6. 固定 download cache 祖先句柄，以不可伪造 session 贯穿 `.part` 创建、写入、
   校验后发布和失败清理；
7. 以显式 `DeleteKind` 允许列表约束递归删除，并保护应用根、卷根和持久目录；
8. 在删除前后写入包含操作 ID、原因、目标与结果的审计记录；
9. 以封闭 `RenameKind` 把原子重命名绑定到精确源、目标与业务用途；
10. 提供支持 context、有限重试且等待器可注入的 Windows 原子重命名；
11. 对外稳定映射 `PATH_OUTSIDE_MANAGED_ROOT`、`UNSAFE_REPARSE_POINT` 和
   `DIRECTORY_OCCUPIED`。

本任务不负责：

- 拼接受管目录；所有路径必须来自 T2.1 的 `config.Layout`；
- 判断 Git 更新事务处于哪个阶段；调用方只把已经确认的操作 ID 和目录身份传入；
- 读取或修复 `update.json`，该职责属于 `internal/state` 与 T4.5；
- 决定 cleanup、repair 或 rebuild 应删除哪些内容；
- 通过通用递归删除接口删除用户业务数据、诊断日志、插件目录或任意外部脚本目录；
- 决定 Runtime 日志的命名、日期窗口或保留数量；专用日志文件接口只执行 logging
  已经决定的单文件操作；
- 向 stdout 发事件或把内部错误直接渲染为用户文案。

## 方案选择

采用方案 A：**规范路径值对象 + 显式操作种类 + Layout 身份核对**。

备选方案 B 是只做“目标位于 app root 下”的前缀检查，再调用
`os.RemoveAll`。它无法区分受管缓存与用户数据，也会在目录树中出现 Junction 时把
路径边界交给操作系统解释，因此不采用。

备选方案 C 是让每个业务包自行检查路径。它会重复 Windows 细节，并使新 cleanup
路径绕过同一安全门，因此不采用。

首版只支持 Windows。依赖 Win32 的实现使用 `_windows.go`；非 Windows 构建不提供

`internal/filesystem` 的 `_windows.go` 文件内以 `NewLazySystemDLL` 补齐最小调用；
不得在消费包复制 syscall struct。每个自定义 struct 的 size、UTF-16 name offset、
flags 和错误码都有 Windows 集成测试。

## Windows 路径身份

### CanonicalPath 值对象

路径规范化成功后返回不可变值对象：

```go
type CanonicalPath struct {
    display       string
    native        string
    comparisonKey string
    volumeKey     string
}

func Canonicalize(path string) (CanonicalPath, error)
func (p CanonicalPath) String() string
func (p CanonicalPath) Native() string
func (p CanonicalPath) Equal(other CanonicalPath) bool
func (p CanonicalPath) Contains(other CanonicalPath) bool
```

字段不导出，调用方不能伪造已经规范化的路径。语义如下：

- `display`：展开为绝对路径和长文件名后的常规 Windows 路径，用于诊断与审计；
- `native`：带 `\\?\` 或 `\\?\UNC\` 前缀的扩展长度路径，只用于 Win32 调用；
- `comparisonKey`：统一分隔符、去除非根尾部分隔符后的规范路径结构串，不执行
  lowercase、Unicode normalization 或其他大小写折叠；
- `volumeKey`：按同样规则规范化的 volume 结构串，用于拒绝跨卷重命名和识别卷根，
  同样不执行大小写折叠。

Windows 不提供与 `CompareStringOrdinal` 完全等价且可持久保存的折叠字符串。
`Equal` 必须分别对 `volumeKey` 和完整 `comparisonKey` 直接调用
`CompareStringOrdinal(..., TRUE)`；`Contains` 表示严格后代关系，不把路径本身视为
其后代，它先以相同方式比较 volume，再把规范路径切成完整组件并逐组件调用
`CompareStringOrdinal(..., TRUE)`。任一次 Win32 比较失败都返回 false，使授权失败关闭。
`comparisonKey` / `volumeKey` 不得通过 `==`、map key 或 `strings.HasPrefix` 承担身份
授权。因此 `D:\AUTO-MAS-2` 不是 `D:\AUTO-MAS` 的后代。

### 规范化步骤

`Canonicalize` 固定执行：

1. 拒绝空字符串、NUL、设备路径、全部相对路径（含 `C:repo`）和无法识别的 volume；
2. 对绝对路径按 Windows 规则完成 `.` / `..` 清理，不读取进程当前目录；
3. 对已存在的最长前缀展开 8.3 短路径和真实长文件名；不存在的尾部只能由普通路径
   组件组成，并拼接到已经规范化的父目录；
4. 生成扩展长度 `native` 路径，使超过 `MAX_PATH` 的合法受管路径不被截断；
5. 将统一分隔符且去除非根尾部分隔符的规范路径结构串保存为 `comparisonKey`，不得
   使用当前用户区域、lowercase 或 Unicode normalization 预先折叠；
6. 识别驱动器卷根和 UNC share 根，以同样的结构规范化规则生成 `volumeKey`；路径与
   volume 的大小写无关身份只在比较时由 `CompareStringOrdinal(..., TRUE)` 决定。

首版危险文件能力只支持本地 volume：`Canonicalize` 可以只读解析 UNC 供错误诊断，但
Operator、RuntimeLogFiles、StateFiles 和 DownloadFiles 构造时拒绝 UNC app-root /
`DRIVE_REMOTE`。对本地路径，从 app-root 父级到每个被授权目录都通过已打开 directory
handle 查询 `FileCaseSensitiveInfo`；任一级启用 `FILE_CS_FLAG_CASE_SENSITIVE_DIR`
就返回 `ErrUnsupportedCaseSensitivity`，不使用 ordinal ignore-case 比较做授权。查询
结果无法确定时同样失败关闭。这样 distinct 的 `uv` / `UV` 不会被误认后删除。

路径规范化不把 Junction 或符号链接解析到目标位置。Reparse Point 检查是下一道独立
安全门；不能以“最终路径仍在受管根内”为理由允许路径链中的链接。

### 已存在前缀与不存在目标

受控删除为支持幂等清理而允许最终目标不存在；原子重命名的 destination 通常也尚不
存在。规范化器允许不存在尾部，但必须满足：

- 最近的已存在父目录能够被完整规范化；
- 不存在尾部不含 `.`、`..`、空组件、保留设备名或替代数据流分隔符；
- 每个已存在祖先均在随后安全检查中按句柄重新核对。

大小写、尾部斜杠、8.3 短路径和 `\\?\` 表达相同对象时，`Equal` 必须返回 true，
`Contains` 必须给出相同的严格后代判断；不同大小写的规范结构串不要求字节相同。
审计记录保存 `display`，授权判断只使用上述 ordinal 比较方法，不直接比较或索引
`comparisonKey` / `volumeKey`。

## 受管边界与 Reparse Point

### Guard

构造安全操作器时必须传入已经校验的 `config.Layout`：

```go
type Operator struct {
    // 字段不导出。
}

type Option func(*options) error

func New(
    ctx context.Context,
    layout *config.Layout,
    auditor Auditor,
    options ...Option,
) (*Operator, error)
```

`New` 拒绝 nil Layout、nil Auditor 和非法 Option，并立即规范化 app root、active
repo、runtime-state、runtime、RuntimeCacheDir、DownloadCacheDir、BuildCacheDir、
日志目录和全部保护目录，验证它们的相对关系。任一布局路径不在同一 app root、彼此身份
冲突或本身经过 Reparse Point 时构造失败。

每次操作仍重新检查路径链，不能把构造时的结论当作永久事实。命名 Mutex 只能串行化
合作的 Runtime 进程，不能阻止其他本机进程在检查后替换目录。

`Operator` 与下文的 `RuntimeLogFiles`、`StateFiles`、`DownloadFiles` 是独立
构造面。只有 Operator 需要 Auditor，避免 logging/state/downloader 构造前形成循环
依赖。filesystem 不导入这些消费包；logging 可以用 Logger 适配 Auditor 后再构造
通用 Operator。

Option 只用于 Operator 的 rename wait/delay 注入。Option 为 nil、同一类别重复配置、
nil Wait、空 delays、非正 delay 或超过 16 次重试均包装
`ErrInvalidArgument`；构造失败不得启动 goroutine 或留下 handle。
所有接收 ctx 的 API 拒绝 nil；构造、逐级打开、遍历和每个新副作用前检查取消。

Operator 另有同包私有 `newWithDependencies`，可注入收口 context factory。生产 factory
固定使用 `context.WithTimeout(context.WithoutCancel(operationCtx), 5*time.Second)`；
它保留必要的 context value，并防止调用方取消直接跳过副作用后的审计。5 秒是协作式
deadline，不承诺强行中断不响应 ctx 的同步 Auditor/Win32 调用；Auditor 契约要求在可取消
边界检查 ctx，测试替身必须响应 ctx。该 factory 不是公开 Option，测试通过 barrier
context 精确控制 finished 审计。

### 逐级检查

对源、目标和它们的已存在父链，Operator 从 app root 的父级开始逐级用
`FILE_FLAG_OPEN_REPARSE_POINT | FILE_FLAG_BACKUP_SEMANTICS` 打开对象并读取属性：

1. 任一组件带 `FILE_ATTRIBUTE_REPARSE_POINT`，返回
   `UNSAFE_REPARSE_POINT`；
2. 任一组件无法确定属性、文件 ID 或 volume，失败关闭；
3. 组件的规范路径、volume 或父子关系与先前值不一致，重新规范化一次；仍不一致则
   失败关闭；
4. 删除目录树时，每个子项在下降前按同一方式检查；Reparse Point 本身也不删除；
5. context 取消后不再进入新的目录或执行新的删除动作。

递归删除由本包逐项遍历，不直接把未经检查的树交给 `os.RemoveAll`。删除失败可能已经
移除部分普通文件；返回值和审计结果必须明确记录 `partial=true`，调用方不得把它描述为
原子删除。

### 从检查到副作用的句柄连续性

“逐级检查后再按路径操作”不能抵抗检查完成后的目录替换。所有会写入、删除或重命名的
实现必须满足：

1. 从 app-root 开始为目标祖先逐级保留不授予 `FILE_SHARE_DELETE` 的目录 handle，
   直到本次副作用完成；
2. 对将被修改的文件或目录保留已经核验属性、volume serial 和 file ID 的同一 handle；
3. 单文件和空目录删除通过该 handle 的 `FileDispositionInfo`/
   `FileDispositionInfoEx` 完成；
4. rename 通过源 handle 的 `FileRenameInfoEx` 完成，并把已固定的目标父目录 handle
   作为 RootDirectory；不先关闭源 handle 再调用路径版 `MoveFileExW`；
5. 递归遍历下降到子项前打开并固定子项 handle，完成子树后通过同一 handle 删除空目录；
6. 平台不支持所需 handle disposition/rename 语义时失败关闭，不回退到
   `os.RemoveAll`、`os.Remove`、`os.Rename` 或路径版 `MoveFileExW`。

只读规范化可以在关闭句柄后返回值对象；任何副作用授权都不能跨越“关闭已核验 handle
后再按同一路径重新打开”的窗口。

## Runtime 日志文件

### 专用构造面

T2.2 不直接按路径打开、列举或删除 `logs/runtime` 下的文件。filesystem 提供只针对
该固定目录的能力：

```go
type RuntimeLogFiles struct {
    // 字段不导出。
}

type RuntimeLogWriter struct {
    // 字段不导出。
}

type RuntimeLogFile struct {
    // 路径、文件 ID、volume 和 owner token 均不导出。
}

type RemoveResult struct {
    MutationApplied bool
}

func NewRuntimeLogFiles(
    ctx context.Context,
    layout *config.Layout,
) (*RuntimeLogFiles, error)

func (f *RuntimeLogFiles) OpenAppend(
    ctx context.Context,
    command string,
    localDate time.Time,
) (*RuntimeLogWriter, error)

func (f *RuntimeLogFiles) List(
    ctx context.Context,
) ([]RuntimeLogFile, error)

func (f *RuntimeLogFiles) Remove(
    ctx context.Context,
    file RuntimeLogFile,
) (RemoveResult, error)

func (f *RuntimeLogFiles) Close() error

func (w *RuntimeLogWriter) Write(p []byte) (int, error)
func (w *RuntimeLogWriter) Path() string
func (w *RuntimeLogWriter) Close() error

func (f RuntimeLogFile) Path() string
func (f RuntimeLogFile) Name() string
```

`RuntimeLogFile` 是值类型但不能由其他包构造有效身份。`List` 返回的每个 token 绑定
当前 `RuntimeLogFiles` 实例、规范路径、volume serial 和 file ID；`Remove` 拒绝零值、
其他实例产生的 token、路径或文件 ID 已变化的 token。调用方不能把任意字符串包装成
删除授权。

### 目录句柄与创建

`NewRuntimeLogFiles` 从已经存在的 app-root 开始，逐级创建缺失的 `logs/` 和
`logs/runtime/`。每创建一级都立即用
`FILE_FLAG_OPEN_REPARSE_POINT | FILE_FLAG_BACKUP_SEMANTICS` 打开并核验：

1. app-root、`logs/`、`logs/runtime/` 都是普通目录且不带 Reparse Point；
2. 最终物理路径和 volume 与 `config.Layout` 的预期关系一致；
3. 目录 handle 不授予 `FILE_SHARE_DELETE`，在实例存活期间固定三者身份，阻止重命名、
   删除或用 Junction 替换祖先；
4. 任一步创建后核验失败，只关闭本次持有的句柄，不递归删除现场。

`OpenAppend` 只能调用 `Layout.RuntimeLogFile(command, localDate)` 得到目标名，
以 create、write-only、append 语义打开普通文件。打开后通过同一 handle 确认文件不是
Reparse Point、物理父目录仍是固定的 Runtime 日志目录，且
`NumberOfLinks == 1`，再返回 `RuntimeLogWriter`。writer 每次 Write 前通过同一
handle 重验 link count，拒绝把内容写入同卷其他名称可见的硬链接对象。
日志 leaf 的 share mode 固定为 `FILE_SHARE_READ | FILE_SHARE_WRITE`，允许不同
Runtime 进程同时以 append 语义打开同一 command/date 文件；不得授予
`FILE_SHARE_DELETE`，因此任一 writer 存活期间该 leaf 不能被删除、重命名或替换。
跨进程只保证各次单独 `Write` 使用 append handle，不承诺多次 Write 组成事务或提供
跨进程行锁。

每个 writer 除文件 handle 外，还通过 `DuplicateHandle` 独立持有 app-root、`logs/`、
`logs/runtime/` 三层祖先 pin，且这些 handle 都不授予 `FILE_SHARE_DELETE`。只有文件
handle 和三层 pin 全部建立成功才返回 writer；中途失败关闭已取得的全部 handle。这样
RuntimeLogFiles 的 `Close` 可以关闭自己的 handle 并拒绝新的 open/list/remove，而不会
让尚未归还的 writer 失去受管根身份约束。writer `Close` 幂等并关闭文件 handle 与自己
的全部 pin；父能力不替调用方关闭 writer。

### 列举与非递归删除

`List` 只列出 `logs/runtime/` 的直接普通文件；子目录、Reparse Point、link count
不是 1 或无法取得稳定文件 ID 的对象一律不返回。logging 仍负责解析
`<command>-YYYYMMDD.log`、应用日期和数量策略，filesystem 不理解日志业务命名。

`Remove` 重新按 token 的固定路径打开目标，拒绝 Reparse Point，并比较 volume serial、
file ID 与 `NumberOfLinks == 1`。身份一致后使用该文件 handle 的 disposition API 标记删除，不先关闭 handle
再按字符串调用 `os.Remove`。文件已经不存在视为幂等成功；同名对象已被替换则返回身份
变化错误且不删除新对象。该接口只删除单个普通 Runtime 日志文件，不递归、不接受路径
字符串，也不暴露给 cleanup 作为通用诊断日志删除入口。

disposition 成功时先冻结 `RemoveResult.MutationApplied=true`，再关闭文件 handle；若关闭
失败，返回该结果与 close error，调用方不得把 token 当作仍未删除而重试。不存在时返回
`MutationApplied=false` 和 nil error，disposition 前失败也固定为 false。

Runtime 日志文件能力不写删除审计，因为 Logger 尚未构造时就需要创建和执行首次保留；
T2.2 在当前活动日志中记录保留结果和维护 warning。通用递归删除仍严格执行下节的双阶段
审计。

kind 到路径的映射只调用 Layout 的四个 state getter。unknown kind、非正或超过
`MaxStateFileBytes` 的 `maxBytes` 在 I/O 前拒绝；因此 `maxBytes+1` 不会整数溢出或允许
调用方请求无界分配。`Read` 的逻辑 stable missing 以公开
`ErrStateFileNotFound` 暴露并支持 `errors.Is`；该分类不等同于底层
`fs.ErrNotExist`。
`RemoveTransactionIfUnchanged` 拒绝零值、其他 StateFiles 实例产生的 snapshot 和
`StateEnvironment`，避免低层能力被普通 cleanup 用来删除稳定环境真相。payload 在调用
期间复制或同步写完，StateFiles 不保存调用方 slice；WriteAtomic 在 I/O 前拒绝空 payload
和 `len(payload) > MaxStateFileBytes`，保证自己写出的正式文件总能被同一能力读取。
Snapshot.Bytes 每次返回防御性副本。通用日志删除继续使用只有 `MutationApplied` 的
`RemoveResult`；StateFiles 条件删除必须返回独立 `StateRemoveResult`，使 state 无需解析
`FileError.Operation` 就能同时保留删除事实和恢复事实。

StateFiles 还在固定 state 目录 handle 下私有管理六类 leaf，以下仅用符号表示：

- `D`：kind 对应的固定 JSON destination，唯一来自 Layout getter；
- `G`：每个 kind 唯一、固定、持久的普通 guard leaf；
- `I`：每个 kind 唯一的固定 sealed-intent leaf；
- `T`：每次写入随机、create-exclusive 的 payload temp leaf；
- `B`：目标已存在时随机选择、必须不存在的 backup leaf；
- `J`：随机、create-exclusive 的 intent-staging leaf。

`G/I/T/B/J` 的 leaf 生成、长度、字符集和相对打开全部封装在 StateFiles 内，不暴露
path getter，不提升为 `config.Layout` 稳定业务路径。`G` 是零数据即可的持久协调对象，
不表示业务状态，任何 cleanup 都不得删除；其余 leaf 是固定目录能力内部的事务协议。
随机名使用密码学安全 nonce；碰撞只允许重新选择或失败，绝不打开、截断、覆盖或删除
碰撞对象。没有 sealed `I` 引用的孤立 `T/J` 不参与读取或恢复；即使能够按私有命名格式
识别，也只能报告，任何自动清理都不得按前缀猜测删除。

`NewStateFiles` 逐级创建并固定 app-root 与 `runtime-state/` 的普通目录 handle，
规则与 RuntimeLogFiles 相同：拒绝 Reparse Point、核对 volume/file ID、不授予
`FILE_SHARE_DELETE`，关闭前目录身份不可替换。Close 幂等，关闭后全部 I/O 返回
`ErrClosed`。

### 读、写入、恢复与事务删除

#### 持久 guard gate

每个 `StateFileKind` 对应一个固定、私有、持久的普通 guard leaf `G`。StateFiles 的每次
Read/Write/conditional remove 都从固定 state-root handle 相对打开它；若 missing，则先
create-exclusive 建立零数据普通文件，竞争进程得到 already-exists 后回到相对 open。
create/open 后在同一 handle 上验证：

1. 对象是 ordinary、non-reparse、`NumberOfLinks == 1`；
2. volume 与 state-root 相同，relative open 的 parent 仍是固定 state-root；
3. leaf 与 kind 的私有固定映射一致，且没有替代数据流或路径分隔符。

若 `G` 被 Reparse Point、硬链接或身份未知对象占据，StateFiles 绝不覆盖、删除或重建，
而是保留现场并失败关闭。合法 `G` 永不由 cleanup disposition；same-user 进程在操作间
替换普通单链接 `G` 或注入 POSIX/hardlink 仍属于已声明的可检测 DoS/tamper 边界，不把
该 leaf 误述为对同用户恶意代码的不可篡改锁。

`G` 的 create/open 两条生产路径都必须从 pinned state-root handle 调用 root-relative
`NtCreateFile`，并固定四组 native 参数：

1. `DesiredAccess` 恰为 `FILE_READ_DATA | FILE_READ_ATTRIBUTES`，明确不含
   `SYNCHRONIZE`、write 或 delete；attributes-only 与 `DesiredAccess=0` 均不构成合法
   gate handle；
2. `CreateOptions` 恰为
   `FILE_OPEN_REPARSE_POINT | FILE_NON_DIRECTORY_FILE`，禁止
   `FILE_SYNCHRONOUS_IO_ALERT` / `FILE_SYNCHRONOUS_IO_NONALERT` 及任何隐式同步选项；
3. create-exclusive 路径的 `CreateDisposition` 恰为 `FILE_CREATE`，已存在竞争返回
   collision 后只能转到 `FILE_OPEN` 的 open-existing 路径；不得使用
   `FILE_OPEN_IF`、`FILE_OVERWRITE*` 或 supersede；
4. `ShareAccess` 只允许以下两种精确值：

   - Read 使用 `FILE_SHARE_READ`，允许多个 reader 同时取得 shared gate；
   - WriteAtomic、W0、rollback、finalize 和 conditional remove 使用 `0`，取得
     exclusive gate。

create 与 open 必须按发起操作的 reader/exclusive 模式使用相同 DesiredAccess、
CreateOptions 和 ShareAccess；两者都不授予 share-write/share-delete，并持有 handle
固定 `G` 名称。所有生产与测试 gate hook 都逐位断言这四组参数，任何偏差都是实现错误。

Windows 对 existing desired access 与新 share mode、existing share mode 与新 desired
access 执行双向兼容检查。两个 reader 都请求 read-data/read-attributes 且都 share read，
所以 shared/shared 兼容；新 exclusive handle 的 share `0` 不允许既有 reader 的
read-data desired access，既有 exclusive handle 的 share `0` 也不允许任何新 handle
请求相同 read-data desired access，因此 shared/exclusive 与 exclusive/exclusive 都会
得到 sharing violation。互斥依据是该真实 desired-access/share 组合，不是文件内容、
attributes-only open 或进程内锁。sharing violation 只表示 gate 暂时被占用：获取循环
每次先检查 ctx，再通过 timer/select 等待固定短间隔后重试，直到成功或 ctx 结束；生产
和测试都不调用 `time.Sleep`。同包私有 `newStateFilesWithDependencies` 注入 wait/barrier
和 Win32 open/create hook，公共构造器不增加可改变安全语义的 Option。

进程正常或异常退出都会由 Windows 关闭 gate handle 并释放 shared/exclusive 占用。
Read 的 acquire/open/close 故障保留 `FileError` 与底层 Win32/context 链；WriteAtomic
的 acquire 与取得 gate 后的 preflight 归 `StateWritePhaseRecover`，`G` 最后关闭且其
close 故障归 `StateWritePhaseClose`。unknown `G` 身份同时置
`RecoveryRequired=true`；单纯等待被 context 取消、且尚未产生本次副作用时为 false。

所有 state leaf 都以 `FILE_FLAG_OPEN_REPARSE_POINT` 相对固定 state-root handle 打开。
作为协议对象使用前必须在同一 handle 上确认：普通文件、同一 volume、预期 file ID、
预期大小与 SHA-256、`NumberOfLinks == 1`。任一 Reparse Point、额外硬链接、ID/digest
失配或无法读取的对象都失败关闭。任何 rename，包括正向提交、恢复和回滚，都固定使用
源对象的同一 handle、state-root `RootDirectory` 和 flags `0`；StateFiles 没有覆盖既有
destination 的代码路径。

目标已存在时，旧对象 `O` 通过同一 handle 以
`FILE_READ_DATA | FILE_READ_ATTRIBUTES | DELETE` 打开，share mode 只允许
`FILE_SHARE_READ`。该 strong handle 在事务结束前一直保留：其他 reader 仍可读取，
但另一个 writer 不能取得 delete/write 能力，也不能原地改写、删除或重命名 `O`。
跨进程合作 writer 的 namespace 决策由 exclusive `G` 串行，`O` handle 负责固定已经
选择的旧对象；最终 `T -> D` no-replace 仍防止忽略 gate 的竞争者被覆盖。T2.4 Lease
继续用于业务编排，但不是 StateFiles 正确性前提；合作进程漏持 Lease 或误并发时也不得
覆盖未知对象。

#### POSIX namespace unlink

StateFiles 对 `T/J/I/B/D` 的任何事务清理或条件删除都通过同一个私有
`unlinkStateLeaf` 完成。该 helper 固定调用
`SetFileInformationByHandle(FileDispositionInfoEx)`，flags **恰好**为
`FILE_DISPOSITION_FLAG_DELETE | FILE_DISPOSITION_FLAG_POSIX_SEMANTICS`。相关 leaf
handle 必须预先请求 `DELETE`，并继续用同一 handle 验证 ordinary、non-reparse、
single-link、volume/file ID、leaf 与 digest。禁止回退到 classic
`FileDispositionInfo`、只带 `FILE_DISPOSITION_FLAG_DELETE`、close-then-delete、
`DeleteFile` 或按路径重开删除。

POSIX flags 成功的协议含义是 namespace unlink：即使 StateFiles 自己的 handle 或已经
允许 share-delete 的旧 reader handle 仍然打开，从固定 state-root handle 相对重开该
leaf 也必须立即得到 name-not-found；原 handle 仍固定原对象直到关闭。文档中的
“`B` absent”“`I` 已删除”“disposition 成功”都专指该可验证的 namespace 事实，不把
delete-pending 或“最后一个 handle 将来关闭”视为 absent。`B` unlink 成功并相对重验
名称 missing 后才允许 unlink `I`；`I` unlink 成功后，即使 intent handle 尚未关闭，
下一进程也必须观察 fixed `I` missing。

WriteAtomic 与 conditional remove 都先取得对应 kind 的 exclusive `G`，完成只读
namespace/identity preflight。WriteAtomic 每次都必须在任何 W0、`T/J` 创建或其他可能
需要 unlink 收口的副作用前执行同一 pinned state-root volume 的能力探测；即使 fixed
`I/D` 均 stable absent 也不得跳过，unsupported 必须在任何本次副作用前返回错误。
仅对 conditional remove，若 fixed `I` 与 `D` 均 stable absent，才在零次 probe 下直接
返回 `{false,false}, nil`；stable `D` snapshot mismatch 同样在 probe 前返回
`ErrIdentityChanged`。conditional remove 只有在 preflight 已确认本请求确实将执行 W0
recovery/cleanup 或已匹配 snapshot 的权威 `D` unlink 时才探测；Read 不需要该探测。
探测使用随机、
create-exclusive、`FILE_FLAG_DELETE_ON_CLOSE` 的私有普通 probe leaf：写入固定 marker，
调用上述精确 flags，并在 probe handle 仍打开时证明相对重开得到 name-not-found、原
handle 仍可读取同一 marker/file ID，最后关闭并再次证明名称 absent。若调用返回
unsupported，依靠预置 delete-on-close 关闭精确 probe handle 后也必须证明 probe 名称
消失；若任一步无法证明语义或清理，保留现场并失败关闭。probe leaf 不暴露 Layout
getter，不按名称前缀清理；只有本次持有的精确 probe handle 能授权收口。

探测不支持、成功却未立即 unlink namespace、或实际 `unlinkStateLeaf` 行为与已探测语义
不一致时返回保留 Win32 链的 `ErrPOSIXUnlinkUnsupported`。WriteAtomic 在任何本次协议
对象创建或既有现场恢复前遇到该错误时归 `StateWritePhaseRecover`，
`MutationApplied=false`；若 `I/D` 是稳定状态且 probe 已精确收口，
`RecoveryRequired=false`，若存在 sealed/foreign intent、协议 leaf 未收口或 probe
清理无法证明则为 `true`。W0 中的实际 unlink 故障同样归 recover；当前请求 rollback
或 post-commit finalize 中的 unlink 故障归 `StateWritePhaseFinalize`，并保留当时真实
commit 事实。所有 namespace unlink 已成功而后续 leaf/`G` close 失败仍归
`StateWritePhaseClose`，`RecoveryRequired=true`；close 失败不得反转已经冻结的
namespace unlink 或 payload commit。

#### Sealed intent

intent 使用固定版本、固定字段和固定上限的 canonical envelope。它至少绑定：

1. `StateFileKind`、固定 `D/I` leaf、随机 `T/B` leaf 和密码学安全 nonce；
2. state-root 的 volume serial + 128-bit file ID；
3. intent 对象的 volume serial + 128-bit file ID；
4. 旧对象 `O` 与新对象 `N` 各自的 volume serial、128-bit file ID、精确大小和
   SHA-256。

envelope 不含可变 phase。编码严格拒绝未知/重复/缺失字段、非法长度和尾随数据，并带有
覆盖 canonical body 的终端 SHA-256 seal。writer 先 create-exclusive 随机 `J`，通过同一
handle 写完整 envelope、`FlushFileBuffers`，再从该 handle 重读并重验 intent ID、精确
字节和 seal；`J/I` handle 的 share mode 只允许 read，seal 成功后实现不得再通过原
handle 写入该对象。随后保持同一 handle，以 flags `0` 将
`J -> 固定 I` no-replace 发布。固定 `I` 一旦在 namespace 中可见就必然是完整 sealed
envelope，不存在“合法 partial I”；截断、损坏或无法通过 seal 的固定 `I` 一律按未知对象
失败关闭，不得依据 `D` 猜测状态。

进程在 `I` 发布前崩溃只会留下未被任何 sealed intent 引用的随机 `J/T`，canonical `D`
未移动。Read 与恢复忽略这类孤立 sidecar；自动流程不得枚举名称前缀后猜测删除。

#### WriteAtomic 协议

每次 `WriteAtomic` 固定执行：

1. 在任何 W0、`I` probe 或 `D` existing/absent 判断前取得 exclusive `G`；
2. 持有 `G` 对 `I/D` 做只读 namespace/identity preflight；即使结果是 stable absent，
   每次 WriteAtomic 也必须在任何 W0 unlink、本次 `T/J` 创建或其他可能需要 unlink 收口
   的副作用前完成 POSIX namespace unlink 能力探测，unsupported 在副作用前失败；随后
   执行 `W0`，只有下文恢复矩阵能唯一证明的对象才可 rename/unlink；
   foreign/损坏 intent、noncooperative handle 占用、能力不支持或任何身份不一致均按
   上述 phase/result 失败关闭并保留不能安全处理的现场；
3. create-exclusive 随机 `T`，用同一 handle 写入完整 payload，
   `FlushFileBuffers`，重验 `N` 的 volume/file ID/link count/大小/SHA-256；
4. 仍在同一 exclusive gate 内重新确认 fixed `I` 不存在并判断 `D`。若 `D` 为稳定
   not-exist，保持 `T` handle 直接执行 `T -> D` no-replace；成功即为唯一 commit。
   不允许在 gate 外 precheck 后进入该分支，忽略 `G` 的竞争者先占 `D` 时仍失败且不覆盖；
5. 若 `D` 存在，以上述 strong handle 固定并有界读取 `O`，生成随机且当前不存在的
   `B`，再按 sealed-intent 规则构造 `J` 并发布固定 `I`；seal 完成前绝不移动 `O`；
6. 保持 `O` handle 执行 `D -> B` no-replace；
7. 保持 `T` handle 执行 `T -> D` no-replace；只有本步成功才把
   `MutationApplied` 冻结为 `true`；
8. commit 后先用仍持有的 `O` handle 对 `B` 执行精确 POSIX namespace unlink，证明
   相对重开 `B` 为 missing 后，再用 intent handle 对 `I` 执行相同 unlink，最后关闭
   全部 handles。unlink `I` 前必须再次确认 `B` 名称仍不存在；若竞争者 `X` 在 `B`
   unlink 后占位，则保留 `I/X` 并失败关闭。任一 post-commit finalize/close 故障都返回
   `MutationApplied=true`、`RecoveryRequired=true`，绝不 rollback `D=N`；
9. 无论成功或失败，都在所有 `T/J/I/O/N` 协议 handle 已完成关闭尝试后最后关闭 `G`。
   `G` close 失败进入主错误或 CleanupError，但不改变已经冻结的 commit 事实。

commit 前失败且 `O` 仍为 `D` 时，不改变 `D`，只通过当前持有的精确 handle 与 POSIX
namespace unlink 尽力清理
本次 `T/J/I`。若 `O` 已移到 `B`，必须先用同一 `O` handle 尝试
`B -> D` no-replace rollback；rollback 成功后才能继续清理本次对象。若普通文件、
Reparse Point 或硬链接竞争者 `X` 已占据 `D`，rollback 绝不覆盖或删除 `X`，并保留
`I/B/T` 供 Read 与后续恢复。清理与 rollback 只能操作 envelope 精确绑定且在当前
linearization point 重新通过 ID/digest/link-count 验证的对象；未知对象一律保留。
rollback、unlink cleanup 与所有失败收口始终在同一个 exclusive `G` 下完成；合作
writer 因而不能把别人的 `D -> B` gap 当作 absent-D 新建分支。POSIX unlink 成功后
crash 时，以已经从 namespace 消失为 durable cutpoint；尚未 unlink 的 leaf 则继续由
sealed intent 与恢复矩阵证明。

`MutationApplied=false` 只表示本次新 payload 尚未 commit，不再表示 raw `D` 从未移动、
旧名称始终存在或旧字节仍位于 `D`。若 clean rollback 与精确收口全部成功，
`RecoveryRequired=false`；若 intent/backup/temp 仍需恢复、reserved leaf 出现未知对象、
rollback/finalize/close 无法证明完成，则为 `true`。

#### 恢复矩阵

记 `O/N` 为 envelope 绑定的旧/新对象。矩阵中的 `X` 仅指可从 same-parent state-root
handle 安全打开、ordinary、non-reparse、single-link、volume/file ID/size/digest 均可
查询，且能证明既非 `O` 也非 `N` 的 **inspectable foreign object**；`X` 在所有路径都
保持 file ID 与字节不变。opaque/unopenable、Reparse Point、hardlink 或任一 identity/
digest 无法证明的 `D` 不属于 `X`，即使 `B` 看似 `O` 也必须失败关闭。Read 持有 shared
`G` 只推导逻辑值，不执行 rename/unlink；`W0` 和 conditional remove 持有 exclusive
`G` 才尝试右栏动作。

| sealed intent 与 namespace | Read 结果 | `W0` / remove 前处理 |
| --- | --- | --- |
| `I` 不存在，`D` 为普通文件；可有未引用孤立 `J/T` | 返回 `D` | 正常继续；孤立 sidecar 只报告、不删除 |
| `I` 不存在，`D` 缺失；可有 direct-absent commit 前遗留的未引用 `J/T` | 返回满足 `errors.Is(err, ErrStateFileNotFound)` 的稳定 not-exist | 正常继续或 remove 幂等成功；只报告既往 orphan，不猜删 |
| `I` sealed，`D=O`、`B` 不存在、`T=N` | old | POSIX unlink `T`，证明名称 absent 后再 unlink `I`；noncooperative handle 占用时拒绝 |
| `I` sealed，`D=O`、`B/T` 均不存在 | old | rollback 已完成；POSIX unlink `I` |
| `I` sealed，`D` 缺失、`B=O`、`T=N` | 从 `B` 返回 old | `B -> D` no-replace rollback，再依次 POSIX unlink `T/I` |
| `I` sealed，`D=X`（inspectable 且已证明非 `O/N`）、`B=O`、`T=N` | 从 `B` 返回 old；`X` 永不作为结果 | 不覆盖/unlink `X`；保留 `I/B/T/X` 并返回 recovery-required |
| `I` sealed，`D` opaque/unopenable/Reparse/hardlink/identity 不可证明；即使 `B` 看似 `O` | 错误 | 不把该对象降格为 `X`；保留全部现场并返回 identity/recovery 错误 |
| `I` sealed，`D=N`、`B=O`、`T` 名称缺失 | new | commit 已发生；先 POSIX unlink `B` 并证明 absent，再 unlink `I` |
| `I` sealed，`D=N`、`B` 缺失、`T` 名称缺失 | new | commit 已发生；POSIX unlink `I` |
| `B=X`，或任一 reserved leaf 为 Reparse Point/硬链接 | 错误 | 保留全部对象，返回稳定 identity/recovery 错误 |
| fixed `I` 非 sealed、ID/digest/root/kind/leaf 任一失配 | 错误 | 不存在合法 partial-intent 分支；保留全部对象并失败关闭 |

前两行穷尽 fixed `I` absent 的合法稳定态；未被 sealed intent 引用的随机 `J/T` 不改变
`D` 存在或 missing 的结论。创建它们的当前进程若仍持有精确 handle，可以在失败收口时
用 POSIX namespace unlink 清理；进程崩溃后其他实例无法证明 orphan 所属，只报告且不按
前缀猜删。catch-all 仅适用于 fixed `I` 已通过 seal/identity 验证、但其 namespace 组合
不能由同一 envelope 唯一归约到上表的情况，此时返回 `ErrStateRecoveryRequired` 或
`ErrIdentityChanged`；非 sealed fixed `I` 始终走表中最后一行。尤其 active transaction
的 `D` gap 不能误报 not-exist，foreign `D` 永不作为 state 结果，任何占据
`D/B/I/J/T` 的 hardlink 都不得被覆盖或删除。
进程崩溃恢复属于本协议承诺；payload 与 intent 都 flush，但 Windows 不提供所需的目录项
write-through 保证，因此不承诺断电后的目录项耐久性。

#### Read 线性化

`Read` 的 namespace 线性化根基是 shared `G`，不是 fixed `I` 名称的两次探测：

1. context-aware 取得 shared `G`；active writer 持有 exclusive `G` 时等待，直到 writer
   完成、ctx 结束或进程崩溃自动释放 handle；
2. 持有 `G` 解析 fixed `I`。`I` 不存在时相对打开 `D`；只有此时 `D` 也为 missing，
   才在线性化点形成稳定 not-exist 决策。该分支必须在返回前关闭 `G`；close 失败返回
   保留底层链的 `FileError`，不得用 NotFound 掩盖；全部关闭成功后返回满足
   `errors.Is(err, ErrStateFileNotFound)` 的专用逻辑错误；
3. `I` sealed 时按恢复矩阵核对 `D/B/T`：`D=N` 选择 new，`D=O` 或 `B=O`
   选择 old；`D=X/B=O` 只选择 `B=O`，其他组合返回稳定 recovery/identity 错误；
4. 仍持有 `G` 时，用拒绝 share-write、允许 share-read/share-delete 的同一 handle
   打开并固定所选权威 payload leaf，完成 ordinary/link count/volume/file ID/size
   预检；随后关闭 intent/非权威 leaf handles；
5. 已选中 payload 时，成功关闭 shared `G` 后才从已经固定的 payload handle 执行
   `maxBytes+1` 有界读取。`G` close 失败时关闭 payload handle 并返回 close 错误，
   不把尚未读取的对象作为成功 snapshot；超限统一返回
   `FileError{Operation: "size-limit", Err: ErrStateFileTooLarge}`。

普通 Read leaf 授予 `FILE_SHARE_READ | FILE_SHARE_DELETE`，拒绝
`FILE_SHARE_WRITE`。释放 `G` 后 writer 可以继续 rename/disposition，但旧 reader handle
仍引用同一不可原地改写对象。实现可以在 shared gate 内保留第二次 intent probe 作为
防御性一致性检查，但任何 absent/NotFound 决策都只由持有 `G` 的 namespace snapshot
授权；双 probe 本身不承担 ABA 防护。`StateFileSnapshot` 绑定 owner、kind、逻辑对象的
volume/file ID/大小/SHA-256 和 bytes，但不暴露该对象当时位于 `D` 还是 `B`。
Snapshot.Bytes 每次返回防御性副本。

active writer 期间 Read 只承诺 context-aware 等待并在 gate 释放后返回 old/new，不承诺
在 writer 的 raw gap 中即时从 `B` 返回 old。foreign actor 忽略 `G` 时，reserved leaf
的 no-replace、handle identity 与 link-count 重验仍失败关闭，但不把 same-user tamper
描述为可完全排除。

完整 old/new 只保证给仓内唯一合法读取入口 StateFiles.Read。绕过该能力的 raw path
reader 在 `D -> B` 与 `T -> D` 两次 no-replace rename 之间必然可能观察
`NOT_FOUND`，不在本仓库契约内。

#### Conditional remove

`RemoveTransactionIfUnchanged` 在任何 W0/intent/D 判断前 context-aware 取得 exclusive
`G`，先在 gate 内只读确认 `I/D`，再决定是否需要 POSIX probe。若 sealed `I` absent
且 `D` absent，必须在 **零次 probe hook 调用**下关闭 `G` 并直接返回
`StateRemoveResult{MutationApplied:false, RecoveryRequired:false}, nil`；平台即使明确
不支持 POSIX unlink 也仍幂等成功，orphan `J/T` 只报告不删除。若 namespace 已稳定且
`D` 存在，先以 strong handle 重验 ordinary、link count、volume/file ID、长度、
SHA-256 和完整 payload；snapshot mismatch 同样在零次 probe 下返回
`ErrIdentityChanged`。只有本请求确实将执行 W0 recovery/cleanup 或已匹配 snapshot 的
权威 `D` unlink 时，才在紧邻首个 mutation 前完成 POSIX probe。随后持有 `G` 穿过恢复/
unlink 与全部协议 handle close，最后关闭 `G`。无法恢复或 fixed `I` foreign/不一致时，
返回 recovery 错误且不 unlink 任一权威对象。intent 的可选二次 probe 只能是 gate 内
防御，不是删除授权。

snapshot 最初从 `B` 返回并不授权直接删除 `B`：必须先按 sealed intent 把 old 恢复到
稳定 `D`，再与 snapshot 比较。不存在仅在已经证明无 intent 的稳定 `D` 上幂等成功，
包括 `I/D` 均 absent 且只有未引用 orphan `J/T` 的稳定态；不得把 active 事务内部 gap
当作不存在。POSIX namespace unlink `D` 成功是条件删除的唯一 commit 点。

`StateRemoveResult` 在 nil/error 两条路径都返回真实事实；`MutationApplied` 只表示本次
权威 `D` 名称已经 unlink，`RecoveryRequired` 表示返回时仍有未完成恢复、无法证明的
namespace/probe/handle 或最终 `G` close 故障。固定真值表如下：

| 场景 | `MutationApplied` | `RecoveryRequired` | error / 结果 |
| --- | --- | --- | --- |
| 非法/跨实例 snapshot，或首次 I/O 前 ctx 已结束 | `false` | `false` | 原参数/context 错误；未 acquire `G` |
| active exclusive/shared gate 导致等待，ctx 在 acquire 前结束 | `false` | `false` | 保留 context 链；无本次 namespace 副作用 |
| `G` create/open/identity 无法证明 | `false` | `true` | 保留 `FileError`/identity 链并保留现场 |
| sealed `I` 与 `D` 均 absent，最终 `G` close 成功 | `false` | `false` | nil，零次 POSIX probe 的幂等成功；既往 orphan `J/T` 只报告 |
| stable `D` snapshot mismatch，最终 `G` close 成功 | `false` | `false` | `ErrIdentityChanged`，零次 POSIX probe；当前 `D` 不变 |
| stable `D` 已匹配、即将 unlink 时 POSIX probe 不支持且 probe 精确收口 | `false` | `false` | `ErrPOSIXUnlinkUnsupported`；权威 namespace 未变 |
| recovery/cleanup 确实需要 POSIX unlink，但 probe 不支持；或实际 W0 遇到 foreign、unsealed、未恢复 intent/协议 leaf | `false` | `true` | recovery/identity/unlink 错误；不删除 snapshot 对象 |
| stable missing 已确定但最终 `G` close 失败 | `false` | `true` | close 错误；不得把失败收口报告为幂等成功 |
| snapshot mismatch 后最终 `G` close 失败 | `false` | `true` | `StateRemoveError{Cause:ErrIdentityChanged, CleanupError:closeErr}`；`errors.Is` 同时命中 identity 与 close 链 |
| `D` unlink 调用已知未生效，且稳定 namespace 与全部 handle 均可证明 | `false` | `false` | 保留 Win32 错误链；当前 `D` 仍存在 |
| `D` unlink 返回或重验结果不明确 | `false` | `true` | 失败关闭；不得重试猜测或报告 missing |
| `D` POSIX namespace unlink 成功，全部 leaf/`G` close 成功 | `true` | `false` | nil，删除成功 |
| `D` POSIX namespace unlink 成功，随后任一验证/finalize/leaf close/`G` close 失败 | `true` | `true` | 保留 post-commit 与 close 链；不得把已 unlink 文件当作存在 |

W0 即使为恢复既有 intent 执行过安全 rename/unlink，也不把
`StateRemoveResult.MutationApplied` 置 true；只要 W0 已收口为稳定 namespace，
`RecoveryRequired` 仍可为 false。返回 error 时 state 只读取 result 两个 bool，再以
`errors.Is/As` 识别稳定 sentinel；不得解析 `FileError.Operation` 推导 recovery。若主因
之后发生收口错误，filesystem 返回 `StateRemoveError` 分离 `Cause/CleanupError`；
特别是 mismatch + `G` close 故障必须保留 identity 主因与 close 次因。

#### 阶段与失败结果

`WriteAtomic` 的参数与 context 预检在任何 I/O 前完成；非法 kind、空或超限 payload
继续返回原参数错误，已取消或超时的 context 继续返回原 context 错误。开始 I/O 后，
所有普通 I/O、身份、安全验证、恢复、提交与收口错误都返回 `StateWriteError`：

| 故障点 | `Phase` | `MutationApplied` | `RecoveryRequired` |
| --- | --- | --- | --- |
| exclusive `G` acquire、namespace preflight、POSIX unlink 能力探测、`W0` 解析或恢复既有 intent | `StateWritePhaseRecover` | 当前请求为 `false` | 稳定现场且 probe 精确收口为 `false`；gate/probe/intent 未证明时为 `true` |
| create-exclusive `T/J` 或创建本次协议对象 | `StateWritePhaseCreate` | `false` | 按精确清理结果 |
| 写 payload 或 envelope | `StateWritePhaseWrite` | `false` | fixed `I` 发布前通常可清理 |
| flush、seal 与同 handle 重读验证 | `StateWritePhaseSync` | `false` | 按精确清理结果 |
| 发布 `I`、`D -> B`、`T -> D` 正向 rename | `StateWritePhaseRename` | 仅 `T -> D` 成功后为 `true` | 按 rollback/现场结果 |
| rollback、当前请求 cleanup、post-commit `B/I` POSIX namespace unlink | `StateWritePhaseFinalize` | 保留 commit 事实 | 任一步未证明完成即为 `true` |
| 关闭协议 handles，并最后关闭 `G` | `StateWritePhaseClose` | 保留 commit 事实 | close 失败固定为 `true` |

最先发生的主错误保留在 `Cause`；rollback、POSIX namespace unlink 或 close 等次生错误进入
`CleanupError`，两条链都由 `StateWriteError.Unwrap()` 保留。返回 error 时，
`WriteAtomicResult` 与 `StateWriteError` 的 `MutationApplied/RecoveryRequired`
必须一致。success 固定返回 `{MutationApplied: true, RecoveryRequired: false}`。

same-user 进程可在 source 检查后注入额外 hardlink，Windows 没有把 source link count
断言与 rename 合并成一个 CAS 的接口。本实现只能在每个线性化点前通过同一 handle 重验
file ID、digest 和 `NumberOfLinks == 1`；一旦检测到注入立即失败关闭并保留对象。文档
不得宣称能原子排除该攻击，也不得因对象最初由 StateFiles 创建就覆盖或删除后来占据
`D/B/I/J/T` 名称的 hardlink。

## Download staging 文件

### Session API

Downloader 不接受任意 destination，也不直接创建或删除 `.part`。DownloadFiles 以
T2.1 的 download getter 生成路径，并为每次下载返回不可伪造 session：

```go
type DownloadFiles struct {
    // 只保存不可变 Layout。
}

type DownloadSession struct {
    // 祖先 handle、part handle、文件 ID 和状态均不导出。
}

type PublishResult struct {
    Published bool
}

type AbortResult struct {
    Removed bool
}

func NewDownloadFiles(layout *config.Layout) (*DownloadFiles, error)
func (f *DownloadFiles) Begin(
    ctx context.Context,
    name string,
) (*DownloadSession, error)

func (s *DownloadSession) Write(p []byte) (int, error)
func (s *DownloadSession) Path() string
func (s *DownloadSession) PartPath() string
func (s *DownloadSession) PublishNoReplace(
    ctx context.Context,
) (PublishResult, error)
func (s *DownloadSession) Abort(ctx context.Context) (AbortResult, error)
```

`Begin` 只接受一个能通过 `Layout.DownloadFile`/`DownloadPartFile` 的 segment。
每个 session 自己逐级创建、打开并固定 app-root、runtime、cache 和 downloads 目录，
因此同一个 DownloadFiles 可被多个 goroutine 并发使用而无需持有永久 OS handle。

固定祖先后，Begin 按顺序：

1. 若 final 已存在，确认它是直接普通单链接文件后返回 destination-occupied，不改动；
2. 若陈旧 part 存在，只在它是直接普通单链接文件时通过其 handle disposition 删除；
3. create-exclusive 新 part，以同一 handle 确认非 Reparse、link count 为 1，并保存
   volume/file ID；
4. 返回持有 part handle 和全部祖先 handle 的 session。

另一个活跃 session 的 part handle 不授予 `FILE_SHARE_DELETE`，因此不会被当成陈旧文件
删除；Begin 返回 occupied/sharing 错误。

### 发布与失败清理

`Write` 直接写入 session 持有的 part handle，并在每次写前重验 session 仍为 open、
file ID 与 link count。调用方完成大小和 SHA-256 校验后调用 PublishNoReplace：

1. 检查 ctx，重验同一 part handle 的 volume、file ID、普通文件和单链接身份；
2. `FlushFileBuffers`；
3. 保持 handle 打开，通过 `FileRenameInfoEx` 以固定 downloads 目录 handle 为
   RootDirectory，flags 为 0，不含任何 destination 替换标志；
4. final 已被竞争者创建时返回 occupied，绝不覆盖；
5. rename 成功时先把状态和结果冻结为 `published` / `Published=true`，再关闭 part 与
   祖先 handle。

`Abort` 在 open 状态通过同一 part handle disposition 标记删除，再关闭全部 handle；
disposition 成功时先冻结 `Removed=true` 和 aborted 状态，再关闭全部 handle；关闭失败
返回该结果与错误，重复 Abort 返回缓存结果且不再次删除。published 后调用返回状态错误且
不删除 final。rename 前 Publish 失败返回
`Published=false`，session 仍保持 open，调用方必须 Abort；rename 后 close 失败返回
`Published=true` 与 close error，调用方不得 Abort，且 final 必须保持不变。Downloader
只在 `Published=false` 时用 `errors.Join` 保留发布与 abort 两条错误链。
session 不提供“只 Close 不处理 part”的公开路径，避免泄漏未经验证的临时文件。

## 删除授权

### DeleteKind 允许列表

递归删除请求必须声明以下一种用途：

```go
type DeleteKind string

const (
    DeleteUVCache           DeleteKind = "uv_cache"
    DeleteManagedVenv       DeleteKind = "managed_venv"
    DeleteManagedPython     DeleteKind = "managed_python"
    DeleteRepositoryUpdate  DeleteKind = "repository_update"
    DeleteRepositoryRetired DeleteKind = "repository_retired"
    DeleteDownloadTemporary DeleteKind = "download_temporary"

    DeleteBuildCache        DeleteKind = "build_cache"
)

func (k DeleteKind) String() string
func (k DeleteKind) Valid() bool
```

允许列表是封闭枚举；未知值直接拒绝。每种用途必须与 `config.Layout` 产生的身份核对：

| DeleteKind | 允许的目标身份 |
| --- | --- |
| `DeleteUVCache` | 恰好等于 Layout 的 uv cache 目录 |
| `DeleteManagedVenv` | 恰好等于受管 venv 目录 |
| `DeleteManagedPython` | 恰好等于受管 Python 目录 |
| `DeleteRepositoryUpdate` | 恰好等于该 `operationId` 的 `repo.update-*` 目录 |
| `DeleteRepositoryRetired` | 恰好等于该 `operationId` 的事务旧 repo 目录，且不得等于 active repo |
| `DeleteDownloadTemporary` | 恰好等于 Layout 的 `DownloadCacheDir` |
| `DeleteUVStaging` | 恰好等于 Layout 的 `UVStagingDir(version, operationId)` |
| `DeletePythonCache` | 位于 active repo 内且目标基名恰为 `__pycache__` |
| `DeleteBuildCache` | 恰好等于 Layout 的 `BuildCacheDir` |

### DeleteRequest

```go
type DeleteRequest struct {
    Kind        DeleteKind
    Target      string
    OperationID string
    Version     string
    Reason      string
}

type DeleteResult struct {
    Removed        bool
    Partial        bool
    AuditCompleted bool
}

func (o *Operator) RemoveTree(
    ctx context.Context,
    request DeleteRequest,
) (DeleteResult, error)
```

`Kind` 与 `Target` 必须匹配上表的精确身份。`OperationID` 和 `Reason` 对所有 kind
都必须为非空、单行的安全诊断值；`OperationID` 用于审计，但只有
`DeleteRepositoryUpdate`、`DeleteRepositoryRetired` 和 `DeleteUVStaging` 会把它传入
Layout getter 参与目标身份。其余固定目录 kind 与 `DeletePythonCache` 更换为另一个安全
非空 `OperationID` 不改变授权结果。`Version` 仅 `DeleteUVStaging` 必填并参与 Layout
身份，其他 kind 必须为空；非 staging 请求携带非空 `Version` 时在 I/O 前返回
`ErrInvalidArgument`。这些字段不得参与 Layout getter 之外的自由路径拼接。

无论 `DeleteKind` 为何，以下目标始终拒绝：

- 空路径、app root、active repo 和 volume / UNC share 根；
- `config.Layout` 的全部受保护持久目录，包括
  `config/`、`data/`、`history/`、`script/`、`debug/`、`plugins/`；
- `runtime-state/` 与 `logs/`；
- 受保护目录自身及其任意后代；
- app root 之外、其他 volume 上或身份无法唯一确定的路径。

路径不存在时，身份检查和审计仍执行；若身份合法，操作作为幂等成功返回
`Removed=false`。路径身份不合法不能因“文件不存在”而放行。

## 删除审计

### Auditor 小接口

filesystem 只消费一个单方法接口：

```go
type Auditor interface {
    RecordDeletion(ctx context.Context, record DeleteAuditRecord) error
}

type DeleteAuditPhase string

const (
    DeleteAuditStarted  DeleteAuditPhase = "started"
    DeleteAuditFinished DeleteAuditPhase = "finished"
)

func (p DeleteAuditPhase) String() string
func (p DeleteAuditPhase) Valid() bool

type DeleteAuditRecord struct {
    Phase       DeleteAuditPhase
    OperationID string
    Kind        DeleteKind
    Target      string
    Reason      string
    Removed     bool
    Partial     bool
    Result      string
}
```

生产实现由 `internal/logging` 适配，记录进入轮转操作日志，不写 stdout。Operator 的固定
顺序为：

1. 完成全部路径、身份、保护名单和 Reparse Point 预检；
2. 写 `started` 记录；
3. 只有 `started` 成功后才执行删除；
4. 一旦 `started` 成功，无论删除成功、失败、部分完成或原 operation ctx 取消，都使用
   上述独立、最长 5 秒的收口 ctx 写 `finished`；结果固定为 `succeeded`、
   `not_found`、`failed` 或 `cancelled`。

`started` 记录失败时不删除任何对象。删除后 `finished` 记录失败时，不能撤销已经发生的
副作用；返回的 `DeleteResult` 保留真实 `Removed/Partial`，错误通过
`AuditError` 暴露 `MutationApplied`。删除错误与结束审计错误同时出现时必须保留两条错误
链，不能用审计错误覆盖原始删除失败；operation ctx 取消与 finished 审计失败也必须用
`errors.Join` 同时保留。响应 ctx 的 Auditor 观察到收口 deadline 后按 finished 审计失败
处理；deadline 本身不是对任意同步调用的硬抢占保证。

## 原子重命名

### API

```go
type RenameKind string

const (
    RenameRepositoryToRetired RenameKind = "repository_to_retired"
    RenameUpdateToRepository  RenameKind = "update_to_repository"
    RenameUVStagingToVersion  RenameKind = "uv_staging_to_version"
)

func (k RenameKind) String() string
func (k RenameKind) Valid() bool

type RenameRequest struct {
    Kind        RenameKind
    Source      string
    Destination string
    OperationID string
    Version     string
    Reason      string
}

type RenameResult struct {
    MutationApplied bool
}

func (o *Operator) AtomicRename(
    ctx context.Context,
    request RenameRequest,
) (RenameResult, error)
```

`RenameKind` 是封闭枚举，每种用途必须通过 Layout getter 重新得到精确源、目标身份：

| RenameKind | Source | Destination | 附加字段 |
| --- | --- | --- | --- |
| `RenameRepositoryToRetired` | `RepoDir()` | `RepoPreviousDir(operationID)` | `Version` 必须为空 |
| `RenameUpdateToRepository` | `RepoUpdateDir(operationID)` | `RepoDir()` | `Version` 必须为空 |
| `RenameUVStagingToVersion` | `UVStagingDir(version, operationID)` | `UVVersionDir(version)` | `Version` 必填 |

调用方同时传入 Source/Destination 是为了把它已检查的事务现场显式带入请求，但
Operator 必须与表中 getter 结果做物理身份核对；unknown kind、字段不匹配或任一端身份
不一致都在副作用前拒绝。原子重命名只允许同一 volume 内、app root 下的上述受管路径；
不跨卷复制，不覆盖既有目标，也不移动任何受保护持久目录。源、目标父目录及其路径链必须
通过 Reparse Point 检查。目标已存在、源或目标被 Windows 句柄占用时映射为
`DIRECTORY_OCCUPIED`。

底层固定保持源对象和目标父目录 handle，使用 `SetFileInformationByHandle`
`FileRenameInfoEx` 同卷 rename；RootDirectory 是已固定的目标父目录 handle，
flags 为 0，不包含任何 destination 替换标志。Windows SDK 不提供 rename write-through flag；
源对象的数据持久化由具体调用方在 rename 前显式 Flush，本通用目录 rename 不承诺目录项
已经同步到持久介质。若检查后出现竞争者，
Win32 的 `ERROR_ALREADY_EXISTS` / `ERROR_FILE_EXISTS` 仍映射
`DIRECTORY_OCCUPIED`，不得覆盖竞争者。不得关闭已检查的源 handle 后回退到路径版
`MoveFileExW`。调用方负责用事务状态决定 `repo -> retired` 与
`repo.update -> repo` 的业务顺序；filesystem 不擅自恢复或回滚第二步。

SetFileInformationByHandle 返回成功时先冻结
`RenameResult.MutationApplied=true`，再关闭源和目标父目录 handle。若发布后的
CloseHandle 失败，返回该结果与 `FileError`，调用方必须按“目录已经移动”保留现场并进入
恢复流程，不能把请求当作未执行重试。rename 前失败固定返回
`MutationApplied=false`。同理，副作用后恰好发生的 context 取消不能覆盖真实结果。

### 有限重试与 context

默认最多尝试 5 次：首次立即执行，后续等待固定序列
`50ms、100ms、200ms、400ms`。仅 Windows sharing / lock violation 以及短暂 access
denied 进入重试；目标已存在、跨卷、路径非法、Reparse Point 和 context 取消不重试。

等待依赖可注入：

```go
type WaitFunc func(ctx context.Context, delay time.Duration) error

func WithWait(wait WaitFunc) Option
func WithRenameDelays(delays ...time.Duration) Option
```

默认 Wait 使用 timer 与 `select` 响应 context，不调用 `time.Sleep`。空或负延迟、
nil Wait、无限重试配置在构造时拒绝。每次重试前重新验证源、目标父链和保护名单，防止
等待期间目录身份被替换。

## 错误模型

filesystem 提供公共 sentinel 与类型化错误，全部保留底层 Win32 / I/O 错误链：

```go
var (
    ErrInvalidArgument    = errors.New("filesystem argument is invalid")
    ErrClosed             = errors.New("filesystem capability is closed")
    ErrInvalidToken       = errors.New("filesystem token is invalid")
    ErrIdentityChanged    = errors.New("filesystem object identity changed")
    ErrDestinationExists  = errors.New("filesystem destination exists")
    ErrUnsafeHardLink     = errors.New("filesystem hard link is unsafe")
    ErrStateFileNotFound  = errors.New("state file not found")
    ErrStateFileTooLarge  = errors.New("state file exceeds size limit")
    ErrStateRecoveryRequired = errors.New("state file recovery is required")
    ErrPOSIXUnlinkUnsupported = errors.New("filesystem POSIX unlink is unsupported")
    ErrUnsupportedCaseSensitivity = errors.New("filesystem case-sensitive directory is unsupported")
)

type Error struct {
    code      protocol.Code
    Operation string
    Path      string
    Err       error
}

func (e *Error) Error() string
func (e *Error) Unwrap() error
func (e *Error) Code() protocol.Code

type FileError struct {
    Operation string
    Path      string
    Err       error
}

func (e *FileError) Error() string
func (e *FileError) Unwrap() error

type AuditError struct {
    Phase           DeleteAuditPhase
    MutationApplied bool
    Cause           error
}

func (e *AuditError) Error() string
func (e *AuditError) Unwrap() error
```

`Error` 只用于下表已有稳定协议码；`FileError` 用于 create/open/read/write/sync/
close/list/remove/rename 等普通故障，Operation 使用固定小写短名。身份变化、跨实例
token、destination exists 与 hard-link 拒绝分别包装对应 sentinel。

`StateWriteError` 只用于 `StateFiles.WriteAtomic` 已开始 I/O 后的失败，并把消费方需要的
稳定阶段、提交状态、恢复状态、主错误与收口错误显式分离。`StateWritePhase` 的七个合法值
严格限于 `recover`、`create`、`write`、`sync`、`rename`、`finalize`、`close`，
`String` 返回字面量，`Valid` 拒绝零值和未知值。state 等消费方只按该类型和枚举分支，
不解析 `FileError.Operation`；`FileError.Operation` 仅保留为本地诊断字段。
`ErrStateRecoveryRequired` 表示 StateFiles 无法把 fixed intent 现场恢复到稳定 namespace，
或发现未知对象而必须保留现场；它不得映射为 not-exist。`ErrIdentityChanged` /
`ErrUnsafeHardLink` / Reparse Point 错误继续保留在同一错误链中。
`ErrStateFileNotFound` 是 StateFiles 逻辑 stable missing 的唯一公开分类：只有 Read
持有 shared `G`、确认 fixed `I` 与 `D` 均 absent，并成功关闭 gate/相关 handles 后，
返回错误才允许满足 `errors.Is(err, ErrStateFileNotFound)`。底层 root-relative open
返回的 raw `fs.ErrNotExist`、Win32 name-not-found、事务 gap 或祖先缺失都只能保留在
普通 `FileError` / recovery 链中，绝不包装或转换为该 sentinel。
`ErrPOSIXUnlinkUnsupported` 表示 FileDispositionInfoEx 的精确 flags 不受支持或成功结果
无法证明立即 namespace unlink；StateFiles 不回退到 delete-pending 语义。state 写入/
条件删除把它保留在 `STATE_WRITE_FAILED` 链中，不解析 Operation。

`MutationApplied` 只表示当前请求的新 payload 是否越过唯一 commit 点；它为 false 时，
raw `D` 可能已经短暂或持续移动到 `B`。`RecoveryRequired` 表示返回时是否仍有未完成
恢复、不能确认已关闭的 handle 或必须人工检查的 reserved-name 现场。post-commit
finalize/close 失败固定为 `MutationApplied=true, RecoveryRequired=true`。

guard acquire 的 sharing violation 是 context-aware 等待条件，不立即对外映射为
`DIRECTORY_OCCUPIED`，也不使用通用 rename 的有限重试上限。Read 在等待取消、`G`
create/open 或身份预检失败时返回保留 Win32/context 链的 `FileError`；稳定 missing
必须以 `G` 成功关闭为前提，close 失败不得降级为 not-exist。WriteAtomic 从首次
create/open `G` 起已经开始 filesystem I/O，acquire、等待取消和 gate 内 preflight
失败均返回 `StateWritePhaseRecover`；只有方法最初的 context 预检才可原样返回未包装
context error。所有协议 handle 关闭后最后关闭 `G`，该 close 失败归
`StateWritePhaseClose` 且 `RecoveryRequired=true`。conditional remove 同样保留 gate
acquire/close 的底层链和真实 `MutationApplied`，不得因结束时取消改写已经发生的
disposition。

`AuditError.MutationApplied` 在 started 失败时为 false；finished 失败时等于真实
DeleteResult 的 `Removed || Partial`。删除错误与 finished 审计错误并存时返回
`errors.Join(deleteErr, auditErr)`，两条链均可由 `errors.As` 取得。

稳定映射如下：

| 场景 | 协议码 | retryable 语义 |
| --- | --- | --- |
| 目标不在受管根、命中保护目录、kind 与 Layout 身份不符、卷根/app root | `PATH_OUTSIDE_MANAGED_ROOT` | 否 |
| 任一路径组件或递归子项是 Reparse Point，或链接身份无法安全判定 | `UNSAFE_REPARSE_POINT` | 否 |
| 非 StateFiles guard acquire 的 Windows 句柄占用、sharing violation、重试耗尽、重命名目标已存在 | `DIRECTORY_OCCUPIED` | 是 |

审计写失败、hard-link 拒绝、token/identity 变化、UNC/remote root、
case-sensitive directory 和其他普通 I/O 错误不伪装成上述
三类。调用业务层按当前命令语境映射为
`GIT_REPO_SWAP_FAILED`、`GIT_REPO_CLEANUP_FAILED`、`STATE_WRITE_FAILED` 等主错误，
同时保留 filesystem 错误链用于日志。包不发 protocol 事件。

错误字符串使用英文、小写开头、无结尾标点；绝对路径只进入受控本地日志和审计，
不得直接放进面向遥测的公开 details。

## 并发与失败语义

- Operator 本身不创建 goroutine，多个只读规范化调用可并发；
- RuntimeLogFiles 用 mutex 线性化 close/open/list/remove；每个 RuntimeLogWriter
  独立持有文件 handle 和 app-root/logs/runtime 三层祖先 pin，因此父能力 Close 后仍不能
  把活动 writer 的对象移出受管根；单 writer 并发写语义由调用方负责；
- StateFiles 用 RWMutex：Read 从检查 closed、通过固定 state-root handle 相对打开 leaf，
  直到读完并关闭 leaf 全程持有读锁；write/remove/close 持有写锁。Close 先拒绝新操作，
  等待已开始的 Read 完成后才关闭共享祖先 handle，防止 handle value 复用到错误目录；
  同一 Store 的上层 mutex 仍负责 JSON 事务顺序；不同实例/进程不共享该锁，其跨进程
  namespace 决策统一由每 kind 持久 `G` 串行：Read 以 shared gate 选定 payload 或形成
  稳定 missing，WriteAtomic/W0/rollback/finalize/conditional remove 以 exclusive gate
  覆盖从首次判断到最后协议 handle close 的完整区间。`O` strong handle 和 no-replace
  rename 继续固定已选对象并防御忽略 gate 的竞争者，但不承担合作 writer 的主串行语义；
- DownloadFiles 构造后只读；每个 DownloadSession 独占 handle 和状态机，可并发处理
  不同 name，同名 Begin 由 create-exclusive 确定；
- 通用递归删除或业务目录重命名前，调用方必须持有相应 mutation 锁；StateFiles 的
  intent/恢复协议不以 T2.4 Lease 为正确性前提；
- filesystem 仍执行全部安全检查，不能把“已持锁”当作授权证明；
- context 取消只保证不再开始新的副作用，不保证回滚已经删除的普通文件；
- StateFiles 等待 `G` 时通过 timer/select 响应 context；等待中的 writer/remove 尚未
  产生本次副作用，Read 也尚未形成 missing 或选中 payload，进程崩溃则由 Windows 自动
  释放 gate handle；
- 原子重命名单步要么生效要么不生效；两次 rename 组成的 Git swap 不是本包提供的单一
  原子事务；
- StateFiles 的两次 no-replace rename 也不是 raw namespace 原子事务，raw `D` reader
  可能看到 gap；只有 intent-aware `StateFiles.Read` 承诺逻辑 old/new；
- 删除或重命名结果不明确时返回错误并保留现场，不猜测目录身份、不自动执行第二次清理。

    断言 information class 为 `FileDispositionInfoEx`、flags 恰好为
    `FILE_DISPOSITION_FLAG_DELETE | FILE_DISPOSITION_FLAG_POSIX_SEMANTICS`，名称在原

StateFiles 另外冻结以下测试名，全部使用 channel/barrier 和可注入故障点，不使用
`time.Sleep`：

1. `TestStateFiles_IntentPublicationIsSealedAndNoReplace`：在 `J` 写入、flush、重验和
   `J -> I` 前后逐点暂停；发布前 fixed `I` 始终不存在，发布后一次读取即得到完整 sealed
   envelope，竞争者先占 `I` 时不覆盖且 `O` 未移动；
2. `TestStateFiles_ReadIntentABADoesNotReturnNotFound`：用 barrier 驱动 writer 对 fixed
   `I` 完成 publish/remove/re-publish 的 ABA 序列；reader 一旦取得 shared `G`，writer
   就不能改变 `I/D/B/T` namespace，reader 要么在同一 gate snapshot 中选中可证明
   old/new，要么形成稳定 missing，绝不因两次 probe 都碰到 absent 而误报 not-exist；
3. `TestStateFiles_GuardSerializesNamespaceDecisions`：两个实例验证 shared/shared 并行、
   shared/exclusive 与 exclusive/exclusive 互斥。writer 停在 `D -> B` 后，raw path
   open 明确得到 `NOT_FOUND`，StateFiles.Read 必须等待 exclusive `G` 释放，再按 commit
   或 rollback 结果返回 new/old；等待中取消返回 context 链且零副作用，全部同步只用
   channel/barrier 与注入 wait；同一测试还覆盖 missing `G` 的 create-exclusive/open
   竞争、精确 access/share flags、持久 leaf 不被 cleanup 删除，以及 Reparse Point、
   hardlink、错 parent/volume 等未知身份失败关闭；
4. `TestStateFiles_RecoveryMatrix`：表驱动先覆盖 `I` absent + `D` ordinary/missing
   两个稳定态及两者附带未引用 `J/T`，再模拟 sealed `I` + `D=O`、
   `D missing/B=O/T=N`、`D=X/B=O/T=N`、`D=N/B=O`、`D=N/B absent`、`B=X`，
   其中 `X` 正例必须是 same-parent 可打开、ordinary/non-reparse/single-link、身份与
   digest 可查询且已证明非 `O/N` 的 inspectable object；opaque/unopenable、
   Reparse/hardlink/identity 不可证明的 `D` 即使 `B=O` 也进入负例。另注入
   ID/size/digest/root/kind/leaf mismatch；稳定 missing 只返回满足
   `errors.Is(err, ErrStateFileNotFound)` 的逻辑错误并允许 remove 幂等，raw
   `fs.ErrNotExist` 注入明确不匹配该 sentinel；catch-all 只覆盖其他 sealed-intent
   非法组合，其余只返回可证明 old/new，未知现场稳定失败关闭；
5. `TestStateFiles_RecoveryNeverOverwritesForeignObjects`：在 rollback、intent publish、
   backup 和 commit 前用 barrier 抢占 `D/B/I/J/T`，逐一证明普通/Reparse/hardlink
   竞争者不被覆盖、删除或截断；
6. `TestStateFiles_ConcurrentWriterCannotTreatGapAsAbsent`：writer A 持有 exclusive `G`
   并停在 `D -> B` gap 时，writer B 不能进入 W0 或 absent-D 分支；A commit、rollback
   或 crash 释放 gate 后，B 必须在自己的 exclusive `G` 内重新检查 `I/D` 并按稳定现场
   继续，绝不把 gap 当作可直接 `T -> D` 的 missing。测试不取得 T2.4 Lease；
7. `TestStateFiles_OrphanSidecarsAreIgnoredAndNotDeleted`：在 fixed `I` 发布前模拟 crash，
   分别保留 `D` 与保持 `D` missing；Read 前者返回 canonical `D`、后者返回稳定 NotFound，
   remove 对后者幂等成功，后续写选择新随机 leaf，扫描/恢复只报告不按前缀删除孤儿；
8. `TestStateFiles_FinalizeDeletesBackupBeforeIntent`：在 post-commit `B` POSIX namespace
   unlink 与 `I` unlink 两侧设置 barrier，证明 `B` 在自身/old-reader handle 仍打开时
   已无法按名重开，且 `I` 只有在 `B` 名称复查仍 absent 后才 unlink；注入 unsupported、
   语义不明确、`B=X` 或任一失败都保留 intent 与可恢复证据；
9. `TestStateFiles_PostCommitFailureReportsAppliedAndRecovery`：表驱动注入 post-commit
   backup/intent POSIX unlink、名称 absent 重验和 handle close 故障，全部返回
   `MutationApplied=true, RecoveryRequired=true` 且绝不 rollback `D=N`；
10. `TestStateFiles_SourceHardLinkInjectionFailsClosed`：在每个 source identity 重验前
    注入额外 hardlink，检测后保留现场并返回 identity/recovery 错误；不声称原子排除
    重验之后的 same-user 注入；
11. `TestStateFiles_ConditionalRemoveRecoversOrRefusesIntent`：snapshot 来自 `B=O` 时先
    恢复到稳定 `D` 再比较/POSIX unlink；active writer 期间等待 exclusive `G` 或响应
    context，gate 释放后遇到 `D=X`、foreign intent 或 identity mismatch 时拒绝，不把
    gap 当幂等 missing；同时逐行复用 `StateRemoveResult` 真值表；
12. `TestStateFiles_MissingRemoveDoesNotRequirePOSIXUnlink`：在 exclusive `G` 内构造
    sealed `I` absent、`D` absent 及可选 orphan `J/T`，注入明确 unsupported 的 POSIX
    环境并断言 probe hook 调用数恰为 `0`，结果固定 `{false,false}, nil`，orphan
    逐字节不变；最终 `G` close 故障单独断言 `{false,true}`。

### Windows 集成测试

使用 `t.TempDir()` 下的临时 app root，覆盖：

1. Junction、文件符号链接和目录符号链接分别位于祖先、目标与递归子树；
2. 任一 Reparse Point 出现时既不跟随也不删除链接本身，外部目标保持逐字节不变；
3. 大小写、扩展前缀、非 ASCII ordinal 等价形式和可用时的 8.3 短路径无法绕过
   保护名单；组合字符等 ordinal 不等价形式不得合并身份；
4. 打开句柄占用目录时 rename 按有限次数结束为 `DIRECTORY_OCCUPIED`，释放后可成功；
5. 同卷 rename 成功、跨卷 rename 拒绝、既有 destination 不被覆盖；
6. 预检后注入竞争者创建 destination，FileRenameInfoEx flags 保持为 `0` 并返回
   `DIRECTORY_OCCUPIED`，竞争者内容不变；
7. 正常受管缓存删除成功且审计记录顺序为 `started -> finished`；
8. 递归中途注入失败时 `Partial=true`，保护目录和根外夹具均保持不变；
9. app-root、`logs/` 或 `logs/runtime/` 任一级为 Junction/Reparse Point 时，
   RuntimeLogFiles 构造失败且外部目录无新增或删除；
10. 目录句柄存活期间祖先不能被重命名替换，List 只返回直接普通文件，Remove 用 token
    删除原对象且同名竞争者保持不变；
11. Runtime 日志既有文件、List 和 Remove 遇到硬链接均拒绝，外部同卷名称内容不变；
12. RuntimeLogFiles 已 Close 但活动 writer 尚未 Close 时，尝试重命名/替换任一祖先仍
    被 writer 的独立 pin 阻止；writer Close 后才释放最后的祖先约束；
13. StateFiles 在 state 祖先 Junction 下失败关闭；sealed intent 的进程崩溃恢复矩阵、
    raw destination gap、普通/Reparse/hardlink 竞争者与 source hardlink 注入均按上述
    固定测试断言；post-commit close 失败保持新目标并报告 applied + recovery；
    snapshot 后替换或原地改写正式 state 时 conditional remove 不删除当前对象；
14. DownloadFiles 在任一 cache 祖先 Junction 下失败关闭；校验后替换 part 路径不能
    改变 session file ID，final 竞争者不被覆盖；rename 后 close 失败不触发 Abort；
15. 递归删除用 barrier 在“检查子项后”尝试替换为 Junction，固定 handle 使替换失败
    或操作拒绝，外部树不变；
16. rename 用 barrier 在“检查源/目标父级后”尝试替换任一对象，FileRenameInfoEx
    只移动已持有源到已持有父目录；
17. 能力探测允许时创建 per-directory case-sensitive 临时目录，其中 `uv` 与 `UV`
    同时存在；Operator/专用能力拒绝构造且两者均不变。系统不支持该标志时明确 Skip；
18. UNC/remote 临时 share 可用时拒绝危险能力；测试环境无法建立 share 时明确 Skip。
19. 两个独立 RuntimeLogFiles 实例同时打开同一 command/date 文件均成功，两个 writer
    的 append 内容都可读；关闭其中一个 writer 不解除另一个 writer 对 leaf 的
    no-share-delete 约束，最后一个 writer 关闭后才允许后续受控删除。
20. StateFiles 的每个 forward/rollback rename 都在 Win32 调用边界断言 flags 为 `0`；
    竞争者占据 `D/B/I/T` 时无任何覆盖式 fallback，现场对象逐一保持同一 file ID 和内容；
21. 两个真实进程分别持有 shared/exclusive `G`，验证 shared/shared 可并发而其余组合
    等待；hook 证明两类 desired access 都恰为
    `FILE_READ_DATA | FILE_READ_ATTRIBUTES`，reader share READ、exclusive share `0`；
    等待方取消时保留 context 链且没有 namespace 副作用。任一 gate handle 存活期间都
    不能删除、rename 或替换 `G`，正常关闭后固定 `G` 仍存在；
22. fixed `I` 发布前终止 helper 只留下孤立 `J/T`，`D` 保持原 ordinary 文件或 missing；
    后续 helper 分别返回 old/稳定 NotFound，且不删除 sidecar。fixed `I` 被截断、伪造
    或换成 hardlink 时不存在 partial-intent 宽松分支；
23. 真实子进程崩溃覆盖下表全部 durable cutpoint；每例都证明 crash 自动释放 `G`，
    后续 Read/W0/WriteAtomic/conditional remove 不会把 guard 残留误判为长期占用；
24. 真实 old reader 在释放 shared `G` 后继续持有允许 share-delete 的 payload handle，
    writer 对 `B` 执行精确 POSIX flags 后，在 old reader 尚未关闭时相对打开 `B` 已为
    missing，随后才能 unlink `I`；平台不支持或不能证明该语义时测试确认 StateFiles
    失败关闭且不使用 classic disposition fallback。

固定测试 `TestWindows_StateGuardReleasedAtEveryCrashCutpoint` 使用表驱动 helper 模式，
对每个动作的“调用前”和“确认成功后”分别设置命名 cutpoint：

| 路径 | 必须覆盖的 durable cutpoint | crash 后可证明的逻辑结果 |
| --- | --- | --- |
| absent-D 新写 | `T` flush、`T -> D` commit | commit 前为 `I/D` absent 的稳定 missing，可留未引用 `T/J`；commit 后为 new |
| existing-D 正向路径 | `T` flush、`J -> I` publish、`D -> B`、`T -> D`、`B` POSIX unlink、`I` POSIX unlink | `T -> D` 前为 old，成功后为 new；`B/I` unlink 后名称立即 absent，finalize 中断仍为 new |
| 当前请求 rollback | `B -> D`、`T` POSIX unlink、`I` POSIX unlink | rollback 前由 sealed intent 证明 old，完成后为稳定 old |
| W0 pre-commit 恢复 | `B -> D`、`T` POSIX unlink、`I` POSIX unlink，以及 `D=O` 分支的 `T/I` unlink | 全部组合只恢复为 old，不把 gap 当 missing |
| W0 post-commit 恢复 | `B` POSIX unlink、`I` POSIX unlink | 全部组合保持 new，不执行 rollback |
| conditional remove | 权威 `D` POSIX unlink 调用前；调用返回且 relative name absent、原 `D` handle 未关闭后 | 调用前 crash 后仍返回 old；unlink 后 crash 为 stable missing，下一 helper remove 幂等 `{false,false}` |

child 在持有 exclusive `G` 时通过命名 event/pipe 报告已经到达精确 cutpoint；parent 等待
信号后终止 child，并用进程 wait 确认退出，全程不用轮询 `time.Sleep`。下一 helper 以
“若进入 wait hook 则测试失败”的注入证明首次 shared/exclusive gate open 即成功，然后
依次运行 Read，以及带 W0 的 WriteAtomic 或 conditional remove：断言 old/new/stable
missing 与上表一致，foreign 对象逐字节不变，成功结果的
`MutationApplied/RecoveryRequired` 固定为 `true/false`，幂等 missing remove 为
`false/false`；注入的 post-commit/finalize/close 故障仍按真实 commit 事实返回
`true/true`。每个 unlink 动作的“确认成功后”必须位于
`SetFileInformationByHandle(FileDispositionInfoEx)` 返回、相对 name lookup 已证明
missing、但原 leaf handle 尚未关闭的时刻；因此 crash 后矩阵中的 `B absent` /
`I absent` 与真实 namespace 一致。每例最后核对 `G` 仍是同一 ordinary、non-reparse、
single-link leaf，所有 gate desired access/share、disposition flags 与
forward/rollback rename flags 均为冻结值，并逐项断言 `StateRemoveResult` 两个 bool。

需要管理员或开发者模式才能创建符号链接的测试必须探测能力并明确 `Skip` 原因；Junction
用例仍应在普通 Windows CI 上执行，不能用非 Windows 结果替代。

## 验收约束

实现完成后除标准门外，必须执行路径安全定向测试和 Windows 集成测试。代码审查需逐项
确认：

- `CanonicalPath.Equal` / `Contains` 和 volume 身份只通过
  `CompareStringOrdinal(..., TRUE)` 比较规范结构串；任何调用失败都返回 false，且没有
  使用 `==`、map key 或 `strings.HasPrefix` 承担身份授权；
- 没有业务包直接调用 `os.RemoveAll` 绕过 Operator；
- 没有在 filesystem 内硬编码稳定受管目录名；`G/I/T/B/J` 仅作为固定 state-root
  handle 下的私有 relative leaf 存在，且未提升为 `config.Layout` getter；`G` 是每
  kind 固定、持久、永不由 cleanup 删除的 ordinary guard，其余名称只属于事务现场；
- 没有跟随未知 Reparse Point；
- logging 没有绕过 RuntimeLogFiles 直接 open/list/remove Runtime 日志；
- state 和 downloader 没有绕过 StateFiles/DownloadFiles 直接按路径写、删或发布；
- StateFiles `WriteAtomic` 开始 I/O 后的全部生产失败均返回 `StateWriteError`，且
  `WriteAtomicResult` 的 `MutationApplied/RecoveryRequired` 与错误中的同名字段一致；
- StateFiles conditional remove 返回独立 `StateRemoveResult`，active gate cancel、
  pre-I/O、foreign/未恢复 intent、stable missing、snapshot mismatch、POSIX unlink
  commit 和最终 `G` close 的两个 bool 与固定真值表一致；stable missing/mismatch 均在
  零次 POSIX probe 下完成，missing 即使平台 unsupported 也幂等成功；mismatch + close
  失败由 `StateRemoveError` 分离主因/次因，state 没有解析 Operation；
- StateFiles 的 intent 发布、forward rename、rollback 和恢复 rename 的 flags 全为 `0`，
  不存在覆盖已存在 destination 的 fallback；
- WriteAtomic 在任何 W0/`I/D` 判断前取得 exclusive `G`，Read 在 shared `G` 内选定
  payload handle 或形成稳定 missing，conditional remove 在 exclusive `G` 内完成
  恢复、比较与 POSIX namespace unlink；不存在以 intent 双 probe 作为 ABA/线性化
  根基的分支；
- 所有 `G` handle 的 desired access 恰为
  `FILE_READ_DATA | FILE_READ_ATTRIBUTES` 且不含 `SYNCHRONIZE`，CreateOptions 恰为
  `FILE_OPEN_REPARSE_POINT | FILE_NON_DIRECTORY_FILE` 且无 synchronous I/O flag，
  create/open disposition 恰为 `FILE_CREATE` / `FILE_OPEN`，reader/exclusive
  ShareAccess 恰为 `FILE_SHARE_READ` / `0`；四组 native params 在生产和测试一致，
  attributes-only 与 DesiredAccess `0` 无效，真实双向 share-access 检查承担互斥；
- guard sharing violation 通过 timer/select context-aware 等待且没有 `time.Sleep`；
  stable missing 只在 `G` 成功关闭后返回，WriteAtomic 的 acquire/preflight 与最终
  guard close 分别归 `recover` / `close`，错误链和 commit/recovery 事实不丢失；
- commit 只发生于 `T -> D` 成功；`MutationApplied=false` 没有被解释为 raw `D`
  从未移动，post-commit finalize/close 失败保持 applied + recovery；
- StateFiles 的 probe 与每次协议 unlink 都使用
  `FileDispositionInfoEx` 和精确
  `FILE_DISPOSITION_FLAG_DELETE | FILE_DISPOSITION_FLAG_POSIX_SEMANTICS`；在原/old
  reader handle 仍打开时已证明名称 absent，不支持或语义不明确时失败关闭且无 classic/
  path fallback；
- post-commit cleanup 严格先 POSIX unlink `B`、证明名称 absent，再 unlink `I`；
  fixed `I` 从不发布 partial envelope，孤立 `J/T` 只报告不猜删；
- 完整 old/new 只承诺给 StateFiles.Read；raw path gap、foreign `D` 与事务内部 missing
  没有被误写成同一语义；
- 恢复矩阵显式把 `I/D` 均 absent（含 direct-absent commit 前 orphan `T/J`）列为稳定
  NotFound/remove 幂等态；只有该 shared-gate 决策返回
  `ErrStateFileNotFound`，raw `fs.ErrNotExist` 不匹配，catch-all 只处理其他
  sealed-intent 非法组合；
- `D=X/B=O/T=N` 的 `X` 仅限 same-parent 可打开、ordinary/non-reparse/single-link、
  identity/digest 可证明且非 `O/N` 的 inspectable foreign object；opaque、Reparse、
  hardlink 或身份不可证明的 `D` 不得走 old 正例，所有 foreign 对象保持不变；
- `TestStateFiles_ReadIntentABADoesNotReturnNotFound`、
  `TestStateFiles_ConcurrentWriterCannotTreatGapAsAbsent`、
  `TestStateFiles_GuardSerializesNamespaceDecisions` 和
  `TestStateFiles_MissingRemoveDoesNotRequirePOSIXUnlink` 与
  `TestWindows_StateGuardReleasedAtEveryCrashCutpoint` 覆盖 ABA、gap 串行、missing
  remove 零 probe、conditional remove unlink 前后及全部 durable crash cutpoint，并证明
  crash 后下一进程首次 gate open 即成功；
- state 文件读取超限只以 `ErrStateFileTooLarge` 暴露稳定分类，消费方没有解析
  `FileError.Operation`；
- 没有删除 app root、active repo、保护目录或受管根之外的路径；
- 审计起始记录失败时没有副作用；
- rename 重试有限、可取消且没有 `time.Sleep`。
