# T1.5 stdin 控制通道设计

## 1. 目标

为单次 Runtime 顶层操作提供严格、可恢复、可去重的 stdin NDJSON 控制通道，
支持 `cancel`、`shutdown` 和 `status`，且不把后端关闭、生命周期迁移或最终
结果语义下沉到协议包。

本设计采用已批准的方案 A：

> `ControlReader` 顺序读取并验证一行一个控制对象，协议层拥有输入边界、
> commandId 去重、无效命令 warning 和停止接收门；调用方注入窄
> `ControlHandler`，拥有真实副作用和状态快照。

## 2. 范围与边界

T1.5 负责：

- v1 stdin 控制对象、命令枚举和公开 API；
- 有界逐行读取、严格 JSON 校验和坏行后恢复；
- 当前操作允许命令的静态过滤和 handler 动态适用性判断；
- 以 `commandId` 为幂等键的进程内去重；
- `INVALID_CONTROL_COMMAND` warning 的稳定形状；
- `details.controlCommandId` 的无副作用复制辅助函数；
- result 前停止接收的并发门；
- 三种命令、非法输入、不适用命令、重复命令和停止竞态的单元测试。

T1.5 不负责：

- CLI stdin 接线和具体命令注册；
- 更新事务取消、HTTP 关闭、Job Object、进程树清理和后端退出；
- 生命周期状态的创建、迁移或持久化；
- 把 stdin EOF 解释为 Electron 断连；
- `result` 恰好一次且最后、全局 sequence 契约和 warning 汇总；
- 内部异步队列、每行 goroutine 或多请求进程复用。

具体业务动作在后续命令实现中注入。Python 继续拥有插件生命周期；协议层
不得导入 backend、state 或插件包。

## 3. Wire 契约

### 3.1 控制对象

每个物理行恰好包含一个 UTF-8 JSON object：

```json
{"protocol":1,"command":"cancel","commandId":"01J00000000000000000000000"}
```

字段严格限定为：

- `protocol`：JSON 整数，必须精确等于 `1`；
- `command`：区分大小写，仅接受 `cancel`、`shutdown`、`status`；
- `commandId`：规范 ULID，26 位大写 Crockford Base32，首位 `0`～`7`。

三项均为必填且不接受 `null`。v1 拒绝未知字段、重复字段、尾随 token、
非 object、非法 UTF-8 和空白行，不对命令或 ID 做 trim、大小写转换或
容错归一化。

### 3.2 分帧与长度

- `\n` 分帧，兼容 `\r\n`；
- EOF 前没有换行的最后一个非空物理行仍按完整输入处理；
- 正常空 EOF 只结束读取，不产生 warning，也不触发取消；
- 控制 payload 上限为 4096 bytes，不含行尾 LF 和可选 CR；
- 超长行必须丢弃到下一处 LF，产生一次 warning，然后从下一行恢复；
- 不能直接依赖 `bufio.Scanner` 的默认上限，也不能无界读取整行。

4096 bytes 足以容纳 v1 的三个标量字段，同时对错误或恶意输入提供明确
内存边界。

## 4. 公开 API

```go
type ControlKind string

const (
    ControlCancel   ControlKind = "cancel"
    ControlShutdown ControlKind = "shutdown"
    ControlStatus   ControlKind = "status"
)

type ControlCommand struct {
    Protocol  int         `json:"protocol"`
    Command   ControlKind `json:"command"`
    CommandID string      `json:"commandId"`
}

type ControlDisposition uint8

const (
    ControlDispositionUnknown ControlDisposition = iota
    ControlAccepted
    ControlNotApplicable
)

type ControlAction func() error

type ControlHandler interface {
    PrepareControl(ControlCommand) (ControlDisposition, ControlAction, error)
    CurrentControlStage() Stage
}

type ControlWarningEmitter interface {
    EmitWarning(WarningEvent) error
}

func NewControlReader(
    input io.Reader,
    warnings ControlWarningEmitter,
    handler ControlHandler,
    allowed ...ControlKind,
) (*ControlReader, error)

func (r *ControlReader) Run(ctx context.Context) error
func (r *ControlReader) StopAccepting()

func WithControlCommandID(
    details map[string]any,
    commandID string,
) map[string]any
```

构造器拒绝 nil input、warning emitter、handler、空允许集、未知或重复的
allowed kind。接口 nil 检测必须覆盖 typed nil。

`Run` 由调用方决定是否放入 goroutine。reader 自身不创建 goroutine，不
拥有 stdin 的关闭权，也不直接写 stdout。每一行按输入顺序完成解析、去重、
handler 调用或 warning 发射后，才读取下一行，因此天然有界反压。

一个 `ControlReader` 只能调用一次 `Run`。首次调用在处理门内原子登记
started；第二次调用（包括并发调用）立即返回
`protocol control reader already started`。

`PrepareControl` 只判断动态适用性并构造 action，不得产生控制副作用。
accepted 必须返回非 nil action，not applicable 必须返回 nil action。reader
先完成接受状态变更，再在同一处理门内调用 action。action 必须快速提交
控制意图或同步发射 `status` 快照，不得等待后端完全退出。

prepare/action 返回的普通 error 是基础设施/编排错误，`Run` 原样包装返回
并停止，不伪装成无效输入。

## 5. 解析、路由与 warning

结构错误和语义错误均产生 `INVALID_CONTROL_COMMAND` warning 并继续读取。
warning 使用 handler 在发射时返回的 `CurrentControlStage()`；stage 必须是
已登记 stage，否则视为 handler 配置错误并使 `Run` 返回 error。

固定 warning 文案为：

```text
已忽略无效的 stdin 控制命令
```

`details.reason` 使用以下稳定值：

- `empty_line`
- `line_too_long`
- `invalid_utf8`
- `invalid_json`
- `unknown_field`
- `duplicate_field`
- `missing_field`
- `invalid_field`
- `unsupported_protocol`
- `unsupported_command`
- `invalid_command_id`
- `command_not_applicable`
- `command_id_reused`

每个非法物理行最多发射一条 warning。reason 和 details 精确固定为：

| reason | details（除 `reason` 外） |
| --- | --- |
| `empty_line` | `lineBytes` |
| `line_too_long` | `lineBytes` |
| `invalid_utf8` | `lineBytes` |
| `invalid_json` | `lineBytes` |
| `unknown_field` | `field` |
| `duplicate_field` | `field` |
| `missing_field` | `field` |
| `invalid_field` | `field` |
| `unsupported_protocol` | `expectedProtocol`, `receivedProtocol` |
| `invalid_command_id` | `field`，固定为 `commandId` |
| `unsupported_command` | `command`, `controlCommandId` |
| `command_not_applicable` | `command`, `controlCommandId` |
| `command_id_reused` | `command`, `controlCommandId`, `originalCommand` |

校验优先级固定为：行长度 → 空行 → UTF-8 → JSON 语法/object/尾随 token →
按 JSON token 出现顺序发现的首个未知或重复字段 → 按 `protocol`、`command`、
`commandId` 顺序检查缺失字段 → 同顺序检查字段 JSON 类型/null →
protocol 值 → commandId 规范性 → command 枚举 → ID 冲突 → 适用性。
`invalid_field` 指向首个类型错误或 null 字段；JSON 语法、非 object 和尾随
token 统一使用 `invalid_json`。

details 不得包含表外字段，不得回显原始行或底层解析错误全文。

底层 stdin read error 和 warning 输出 error 由 `Run` 返回。它们不是一条
可归因的控制输入，因此不生成 `INVALID_CONTROL_COMMAND`。但任意 read 返回
后必须先进入处理门并按 `stopped → nil`、`ctx canceled → ctx.Err()`、
`EOF/普通 read error` 的顺序判断；因此 owner 在 `StopAccepting` 后关闭
自己的 reader 来解阻不会产生伪 read error。若 read 同时返回非空 fragment
和 `io.EOF`，在未 stopped/cancelled 时先处理该无换行末行，再正常结束。

## 6. 幂等、适用性与关联

### 6.1 commandId 去重

reader 在成功解析并验证命令后，把 `commandId → command` 写入容量为
1024 的先进先出滚动 ledger：

- ledger 内同 ID、同命令重放：不再次调用 handler，不再次产生 warning；
- ledger 内同 ID、不同命令：产生 `command_id_reused` warning，不调用
  handler；
- 合法但静态不允许或动态不适用的命令也占用该 ID，后续同 ID 重放不再
  重复 warning；
- handler 返回 error 时 `Run` 停止，本次 ID 不承诺可在同一 reader 内重试。

写入第 1025 个不同 ID 前先淘汰最早 ID，不能因为 ledger 已满而拒绝新命令，
尤其不能让 status 洪泛阻断后来的 shutdown。淘汰后同 ID 可再次进入 handler；
`status` 本身是无状态快照。cancel 可跨越去重窗口重新路由，但业务状态
所有者的 latch 保证只提交一次取消副作用；accepted shutdown 会立即关闭
reader 接收门，后续 shutdown 不会再进入 handler。

### 6.2 静态和动态适用性

构造时的 allowed 集表示当前顶层命令的静态能力：

- 一般耗时操作通常只允许 `cancel`；
- `backend supervise` 允许三种命令。

handler 返回 `ControlNotApplicable` 表示命令在当前动态状态下不适用。
静态不允许和动态不适用都产生 `command_not_applicable` warning，当前操作
继续运行。

零值或未知 disposition、accepted nil action、not applicable 非 nil action
都是 handler 契约错误，`Run` 返回 error。

### 6.3 commandId 回显

`WithControlCommandID` 创建新的 details map，复制原有键并写入
`controlCommandId`，不得修改调用方 map。handler 按业务语义使用它：

- `cancel`：下一条相关 warning 或最终 cancelled result；
- `shutdown`：第一条相关 `stopping_backend` state；
- `status`：立即返回的当前 state 快照。

`status` handler 只读取当前状态并发射一个普通 `StateEvent`，不得调用
`LifecycleMachine.Transition` 或写持久化状态。

以上回显是 `ControlHandler` action 的 MUST 契约。T1.5 使用三个 fake
handler/event 路径分别证明：shutdown 的下一条 state、status 的立即 state
snapshot、cancel 的后续最终 result 都携带 ID，且关联 helper 不修改原
details。

同 ID 重放复用首次接受的关联语义，不制造额外 state。若不同 ID 的重复
终止请求需要逐个确认，应由未来协议版本增加显式 ack，而不是伪造迁移。

## 7. 停止接收与并发

`ControlReader` 使用同一互斥门串行保护：

- one-shot started 标记；
- 停止状态检查；
- commandId map；
- handler prepare 与 action；
- 无效命令 warning 发射。

读 stdin 本身不持有该门。`StopAccepting` 获得同一门、设置停止状态并返回，
因此它会等待已经进入的 handler 或 warning 完成；返回后不会有新的 handler
调用或控制 warning。阻塞 read 随后得到完整行并进入处理门时，发现 stopped
后 `Run` 立即返回 nil。调用方必须先 `StopAccepting`，再发送最终 result。

`StopAccepting` 可在 `Run` 前调用且可重复调用：两者都安全、幂等；之后
首次 `Run` 立即返回 nil，不读取输入。

对 accepted shutdown，reader 在调用 action 前于同一个临界区内设置 stopped，
从而严格满足“先停止接受新控制，再执行关闭动作”。action 返回后释放门，
同批已缓冲的后续命令不会执行。即使 shutdown action 失败，stopped 也保持。

`StopAccepting` 不承诺中断已经阻塞在 OS stdin 上的读取。调用方可关闭自己
拥有的 `io.ReadCloser`，或让进程退出回收 stdin reader；不得为了等待无法
取消的 stdin 读取而延迟最终 result。

handler 不得从 prepare 或 action 内调用同一个 reader 的 `StopAccepting`，
否则属于重入误用。

`context.Context` 只在开始读取前和每个完整物理行进入处理门后检查。context
取消后不再触发新 handler 或 warning，`Run` 返回 `ctx.Err()`；它同样不
承诺打断阻塞的 `Read`。

## 8. T1.6 边界

T1.5 的停止门只阻止控制通道在最终 result 后继续发事件。T1.6 仍必须在
`ProcessOutput` 的统一写锁内实现并验证：

- hello 首事件；
- result 恰好一次且最后；
- sequence 严格递增；
- 每行一个 JSON；
- 成功、失败、取消三种终点；
- warning 汇总到 `result.details.warnings`；
- 所有来源在 result 后都不能发协议事件。

## 9. 验收矩阵

- 三种命令分别被允许、解析并按顺序分发；
- `status` 测试 handler 发射带 commandId 的快照，生命周期状态机不迁移；
- LF、CRLF、最后无换行和正常 EOF；
- 空行、非法 JSON、非 object、尾随 token、未知/重复/缺失字段；
- protocol 类型和值错误，command 大小写/未知值，commandId 全套边界；
- 恰好 4096 bytes、4097 bytes、超长行后合法命令恢复；
- 静态不允许和动态不适用均 warning 且后续合法命令仍执行；
- 同 ID 同命令一次副作用，同 ID 异命令 warning，不同 ID 正常分发；
- ledger 最多 1024 项，status 洪泛后新 shutdown 仍能分发，cancel 跨窗口
  由业务 latch 幂等；
- warning code/stage/message/retryable/remediation/details 精确；
- warning 输出失败、handler error、未知 disposition 和 read error 返回；
- helper 复制 nil/非 nil details 且不修改原 map；
- `StopAccepting` 等待在途 handler，返回后不再调用 handler 或发 warning；
- `StopAccepting` 前置/重复调用幂等，下一完整行后 `Run` 返回 nil；
- `StopAccepting` 后关闭 owner 的 reader 可解阻，`Run` 返回 nil 而非 read error；
- accepted shutdown 先置 stopped 再执行 action，同批后续命令不执行；
- 两个不同 ID 的连续 shutdown 只执行首个 action；
- 第二次或并发 `Run` 返回 one-shot error；
- cancel result、shutdown state、status snapshot 都回显 commandId；
- context 已取消时不处理输入。
