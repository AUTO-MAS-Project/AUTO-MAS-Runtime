# T1.9 M1 对抗审查修复设计

## 1. 目标

关闭 `doc/审查-T1.8-M1可维护性与逻辑清晰度.md` 中的 9 项 Important 和
4 项 Minor，使 M1 协议实现具备可执行的契约保护、清晰的所有权语义和可维护的测试来源，
并在修复后接受独立复审。

## 2. 范围与边界

本任务只修复既有协议 v1 实现和测试，不新增、删除或改名任何冻结字段、错误码、stage、
state、remediation 或 capability。权威值仍来自 `doc/架构设计.md`、
`doc/契约补充-v1.md` 和 `doc/设计-T1.3-生命周期状态机.md`。

不引入第三方依赖，不修改 CLI 业务行为，不实现 M2 及后续里程碑，也不以生产 test hook
换取并发测试便利。

## 3. 修复设计

### 3.1 Emitter 所有权与 renderer 测试

`NewEmitter` 在入口复制 capability 切片，后续校验和 hello 渲染只使用副本。调用方在构造
期间或构造后修改原切片都不能改变已验证值。未知 capability 在任何 hello 输出前失败。

Human renderer 的恶意文本清洗属于 renderer 单元行为，直接调用 renderer；经 Emitter 的
集成测试只传冻结全集内值，避免构造器校验遮蔽被测路径。

### 3.2 契约校验分层

公共 envelope 校验后，按七种事件分别校验业务必填字段、可选字段类型和冻结值成员关系。
`details` 必须是 object，`remediation` 与 `capabilities` 必须是 array，均不接受 `null`。

warning、error 和失败/取消 result 的 code、retryable、remediation 必须匹配
`protocol.ErrorDefinition`；warning/error 禁止使用 `OK`。成功 result 固定为 `OK`、
`retryable=false`、空 remediation。失败与取消 result 继续要求存在四元组一致的先行 error。
错误定义中退出码为 0 的非 `OK` 项只允许作为 warning，不能成为 error 或失败 result 的主错误。

schema 细节集中在 `contracttest` 的独立文件中，主验证流程只负责事件顺序、终态和汇总编排，
避免单个文件继续膨胀。

### 3.3 文档驱动生命周期测试

测试运行时解析生命周期设计文档的两张迁移表，将 From/To 转为 `StateStatus` 后与生产全集比对。
解析结果必须非空且数量明确为 25；文档缺少标题、表头或非法状态时立即失败。迁移执行、
防御性副本和路径测试共享解析结果，不再维护第二份硬编码全集。

### 3.4 并发测试策略

Emitter 使用可阻塞 renderer 和包内白盒锁观察，确定性证明渲染发生在线性化锁域内，且竞争
result/普通事件只能在释放后得到唯一合法结果。生命周期测试只验证公开原子状态变化和守卫结果；
在不污染生产 API 的前提下无法由测试强制触发的特定调度，继续以锁域审查和确定性状态守卫覆盖，
并用全量 race detector 补充检测；不得用“同时放行 goroutine”或单次 race 通过冒充确定性证明。

### 3.5 测试维护

`AllCapabilities` 加入防御性副本表驱动测试；文档读取统一复用 `readDoc` / `docSection`；
容器断言只检查受约束字段的 JSON 类型，不全文搜索 `:null`；transcript 编码统一走带
`t.Helper()` 的辅助函数。T1.7 计划中的 PowerShell 命令逐条检查退出码，定向测试同时确认
命中目标测试。

## 4. 验收

1. 原审查报告 13 项均有对应代码或测试证据；
2. `gofmt`、`go vet`、`go build`、`go test`、`git diff --check` 全绿；
3. `internal/protocol` 与 `internal/protocol/contracttest` 重复 100 次全绿；
4. 两名独立审查代理分别检查生产逻辑和测试/文档，最终无 Critical/Important；
5. 提升 MSYS2 UCRT64 GCC 的 PATH 优先级后，`go test -race ./... -count=1` 全绿。
