## 1. 背景

M1（T1.0~T1.6）复核结论是符合文档要求，验证门全绿。复核同时发现四处缺口：它们都不违反
T1.x 各自的验收原文，但共同点是「冻结全集在文档里，执行力却没有落到代码上」，会在 M3
开始接线真实命令时放大。本任务在进入 M2/M3 之前把它们收口。

| 缺口 | 现状 | 后果 |
| --- | --- | --- |
| 契约库不校验冻结全集 | `contracttest` 只做类型断言 | demo 与库自身夹具用了 `DOCTOR_FAILED`、`WARN_000`、`review-log`、`action-0` 仍全绿；demo 是「一行注册」的范本，会被照抄 |
| 容器字段输出 `null` | nil 入参时 wire 上出现 `"details":null`、`"remediation":null` | 与架构文档所有示例不一致；每个 CLI 调用方都要额外处理 null 分支 |
| 迁移表未做文档驱动比对 | 25 条迁移在测试内硬编码 | 保护级别低于错误码 / stage / progress / state 四张表 |
| `hello.capabilities` 未冻结 | 架构文档只有示例，协议包无常量 | 调用方无权威来源可校验握手能力 |

## 2. 目标与范围

T1.7 负责：

1. 协议层统一归一化三个容器字段，使 `null` 不可能出现在 wire 上；
2. 契约库对六类稳定值做全集成员断言，并收紧容器字段的类型断言；
3. 冻结 `hello.capabilities` 标识全集并在唯一构造点校验；
4. 生命周期迁移表改为运行时解析设计文档比对；
5. 把三处重复的文档解析 helper 收敛为一套。

T1.7 不负责：

- CLI 参数解析、`--output` 接线与进程退出码（仍属 T3.1）；
- 新增或删除任何错误码、stage、state、progress status；
- 改变事件字段名、字段顺序或既有语义；
- `internal/protocol` 存量英文注释的批量重写（AGENTS.md 8.1 明确豁免）。

**本任务不引入任何协议版本升级**：容器非空是把「示例里一直是 object/array」写成规则并强制执行；
能力标识全集是把架构文档已有的三个示例值升级为正式表格。两者都不删除、不改名、不改变既有语义。

## 3. 容器字段非空

### 3.1 规则

`details`、`remediation`、`capabilities` 在所属事件类型中恒存在，恒为 JSON object 或 array，
空值分别为 `{}` 和 `[]`，不得输出 `null`。调用方只需处理「空集合」一种情况。

### 3.2 归一化位置

归一化发生在语义层、renderer 之前，因此 NDJSON 与 human 共用同一结果：

```text
Emit*  ->  ProcessOutput.mu  ->  normalize()  ->  setCommon()  ->  EventRenderer
```

`eventWithCommon` 增加 `normalize()`，七个事件类型各实现一份；`ProgressEvent` 与 `LogEvent`
没有容器字段，实现为空以保持接口完整。`emitPreparedLocked` 在写入 `Common` 之前调用它。

### 3.3 warning 账本的顺序约束

`EmitWarning` 必须在 `snapshotWarning` **之前**归一化。否则账本快照保留 nil、发出的事件却是
`[]`，`result.details.warnings[i]` 与原 warning 事件不再逐字段相等，而契约库正是按逐字段深
相等校验汇总的。这是本次改动里唯一有顺序要求的地方。

`resultDetails` 同时去掉「无 details 且无 warning 时返回 nil」的分支，恒返回非 nil map；
三个保留键的出现规则不变（无 warning 时仍然三个键都不出现）。

### 3.4 不变的部分

wire 上字段名、顺序、`Common` 内容、sequence 语义、终态门、warning 汇总规则均不变。
只有「nil 容器」这一种输入的投影结果发生变化。

## 4. 契约库的全集断言

### 4.1 断言范围

| 事件 | 校验字段 | 依据 |
| --- | --- | --- |
| `hello` | `capabilities` 每项 | `IsKnownCapability` |
| `progress` | `stage`、`status` | `IsKnownStage`、`IsKnownProgressStatus` |
| `state` | `stage`、`status` | `IsKnownStage`、`IsKnownStateStatus` |
| `warning` / `error` | `stage`、`code`、`remediation` 每项 | `IsKnownStage`、`IsKnownCode`、`IsKnownRemediation` |
| `result` | `stage`、`code`、`remediation` 每项 | 同上 |

明确不校验：

- `result.status`——T1.3 设计已冻结它保持 `string`，协议 v1 没有为它冻结单一枚举；
- `log.source` / `log.stream`——架构文档未冻结取值。

`result.details.warnings[i]` 的成员断言由既有的「与原 warning 事件逐字段深相等」间接保证，
不重复校验。

### 4.2 与「允许追加」的关系

架构文档允许在协议 v1 内追加错误码和 stage。合法追加必须先修订架构文档中的相应全集，
并在任务拆分中登记变更记录，再同步 `errors.go` / `values.go`；错误四元组仍以架构文档为
唯一来源。文档驱动测试会把实现逐行比对回架构文档，因此「断言实现全集」等价于
「断言文档全集」，不会阻塞合法追加。

### 4.3 生产端与契约端的分工

沿用既有分工，不做改变：

- 生产端由构造函数收口——`NewErrorEvent` / `NewWarningEvent` 校验 code，
  本任务新增的 `NewEmitter` 校验 capabilities；
- 裸结构体发射仍然允许（`EmitError(ErrorEvent{...})`），由契约库在 transcript 层兜底。

这保证契约库继续是对「绕过构造函数」的有效防线，而不是把校验重复写两遍。

## 5. 能力标识全集

冻结为三个标识，与架构文档原示例一致：

| 常量 | 字面量 | 含义 |
| --- | --- | --- |
| `CapabilityStdinCancel` | `stdin.cancel` | 本次操作接受 stdin `cancel` 控制命令 |
| `CapabilityStateV1` | `state.v1` | 本次操作发射 v1 生命周期 `state` 事件 |
| `CapabilityLogStream` | `log.stream` | 本次操作把受管进程 stdout/stderr 转发为 `log` 事件 |

追加规则与 stage 相同：可以追加，既有标识不得改名，删除或改变语义必须升级协议版本。
`backend supervise` 在 T6.3 若需要公告 `shutdown` / `status` 能力，按追加规则处理即可，
无需改动本任务的结论。

`HelloEvent.Capabilities` 保持 `[]string`：这与 `Remediation` 的既有形态一致
（枚举类型存在，事件字段仍是 `[]string`），避免改动 `NewEmitter` 的公开签名。
类型安全由 `NewEmitter` 的入口校验提供——hello 是 capabilities 的唯一构造点。

## 6. 迁移表文档驱动

`AllLifecycleTransitions` 的 25 条改为运行时解析
`doc/设计-T1.3-生命周期状态机.md` 的两张表：

- `### 环境准备与恢复迁移` 到 `### 后端监督迁移` 之间的 13 条；
- `### 后端监督迁移` 到 `### 迁移验证 API` 之间的 12 条。

顺序即实现顺序。文档解析 helper（读文件 + 按起止标记切段）从 `errors_test.go` /
`values_test.go` 收敛到新的 `doc_fixture_test.go`，三处共用。

`Transition` 的状态化约束（初态、终态、回滚目标、单次重启）仍由代码断言，
不进入文档驱动——它们是行为而非表格。

## 7. 失败关闭

- 未知 capability 传入 `NewEmitter` → 返回 error，不产生 hello，调用方无法进入协议；
- 契约库发现越界值 → 报告为 contract issue，`Assert` 映射为 `t.Error`；
- 文档解析找不到起止标记或条数不符 → 测试 `t.Fatal`，防止解析静默退化为空集合后「零条也算通过」。

## 8. 验收

1. 七类事件在 nil 容器输入下的 wire 形态被快照锁定，三个键恒存在且为 `{}` / `[]`；
2. nil remediation 的 warning 进入 `result.details.warnings` 后仍为 `[]`；
3. 未知 code / stage / remediation / progress status / state status / capability 各有一条契约负例；
4. 契约库夹具与 demo 全部使用冻结全集内的值，且 demo 改用构造函数；
5. `contracttest.Register` 仍是一行，三场景全绿；
6. 25 条迁移与设计文档逐条比对，条数不符即失败；
7. `gofmt` 无 diff、`go vet ./...` 无告警、`go test ./...` 全绿、`git diff --check` 干净；
8. `internal/protocol` 以 `-count=100` 复跑通过，且 `go test -race ./... -count=1` 全绿。
