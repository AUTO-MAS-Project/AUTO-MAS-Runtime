# T10 可维护性收敛设计

## 目标

在不改变 Runtime 对外契约、Windows 安全语义和既有行为的前提下，降低文档同步成本、
私有实现耦合和后续 M3～M6 的扩张速度。

## 已确认问题

- 已完成任务的 14 份计划约 5.3 万行，其中大部分是代码、命令和静态扫描副本；
- 设计、计划、任务拆分和审查报告同时描述同一实现细节，形成多个真相源；
- `mirror` 和 `filesystem` 存在少数超长、高分支状态机；
- 多数测试使用同包白盒形式，安全细节覆盖充分，但普通重构成本偏高；
- 未来任务尚未形成明确的标准库与第三方依赖优先规则。

## 不负责范围

- 不修改 NDJSON 字段、错误码、stage、state 或退出码；
- 不改变 StateFiles、Windows Mutex、Reparse Point 和 no-replace 语义；
- 不把状态 JSON 迁移到数据库；
- 不在维护任务中顺带实现 M3～M6；
- 不因行数较多而删除有效的安全测试。

## 阶段 1：文档信息架构

1. `doc/` 根目录只保留权威文档、文档入口和测试直接读取的契约夹具；
2. 当前任务文档进入 `doc/current/M<里程碑>/`；
3. 已完成阶段中仍有解释价值的设计与审查记录进入 `doc/archive/M<里程碑>/`；
4. 已完成计划从工作树删除，历史由 Git 保存；
5. 修复全仓链接，并用自动扫描拒绝失效的相对 Markdown 链接。

## 阶段 2：低风险代码收敛

优先处理将在 M4/M5 被继续消费的 `internal/mirror`：

1. 将 `Rotator.Run` 拆分为单次尝试、报告和迁移判断；
2. 将 Downloader 响应读取拆分为传输、进度和错误分类；
3. 保持全部导出 API、错误分类和报告顺序不变；
4. 每个热点独立提交，执行标准门和 `internal/mirror -count=100`。

这一阶段不先重写 `internal/filesystem`。安全内核已有完整 Windows 对抗覆盖，应在更低风险
组件形成稳定重构方法后再处理。

## 阶段 3：测试与安全内核维护

1. 将普通对外行为测试逐步迁移到外部测试包；
2. Win32 参数矩阵、结构大小和故障注入继续保留白盒测试；
3. 按 recovery、write、remove、crash 等职责拆分巨型测试文件，不删除场景；
4. 评估以私有事务上下文收拢 StateFiles 的 leaf、proof、handle 和 cleanup 状态；
5. 单独验证 Go 1.26 `os.Root` 能覆盖的通用边界，仅替换经 spike 证明等价的部分。

## 后续依赖规则

- 标准库能够满足时直接使用标准库；
- CLI 使用 Cobra，Git 使用 go-git，Windows 系统调用使用固定版本 `x/sys/windows`；
- 只有在小型技术验证证明现有库无法满足冻结契约时才自研；
- 新依赖必须检查维护状态、许可证、Windows 支持、传递依赖和固定版本；
- “零第三方依赖”不再作为独立目标。

## 完成边界

阶段 1 只修改文档和必要的文档引用；阶段 2、3 必须分别建立独立任务和验证边界。
任何阶段未完成时，不得把整个 T10 表述为完成。
