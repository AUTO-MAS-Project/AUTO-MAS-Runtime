# T2.4 Windows 命名 Mutex 设计

## 文档状态

- 日期：2026-07-29
- 状态：已批准，采用方案 A
- 任务：[T2.4 lock（Windows 命名 Mutex）](./任务拆分.md)
- 架构基线：[架构设计](./架构设计.md)
- 代码基线：AUTO-MAS Runtime `fb06f57`

本文冻结同一 AUTO-MAS 安装根目录下的后端监督与受管变更互斥语义。
Mutex 是跨进程占用状态的唯一真相；`runtime-state/*.json` 只用于诊断与
中断恢复，文件存在不能代替 Mutex 探测。

## 目标与范围

T2.4 交付以下能力：

1. 从 `config.Layout` 指向的既有 app-root 解析物理根比较 key，并稳定派生
   两把 Windows 命名 Mutex；
2. 以 `backend` Mutex 保证同一安装根只有一个后端监督进程；
3. 以 `mutation` Mutex 串行化 Git、uv、Python 主环境、repair 和 cleanup；
4. 在获取本方 Mutex 后探测对方 Mutex，保证后端监督与受管变更不能同时
   开始；
5. 提供只读 `Probe`、幂等释放和整体 `Close`；
6. 正确恢复 `WAIT_ABANDONED`，并把恢复事实作为结构化结果交给日志调用方；
7. 通过无 `time.Sleep` 的双进程 Windows 集成测试证明进程级互斥。

本任务只实现进程级互斥原语，不创建或删除事务状态文件，不停止后端进程，
不写协议事件，也不替应用服务决定是否重试。

## 命名空间与名称

### 选用 `Local\`

首版固定使用当前 Terminal Services 会话的 `Local\` 命名空间，不使用
`Global\`：

- Electron、Runtime 和受管后端处于同一登录会话，`Local\` 已覆盖产品所需
  的互斥范围；
- `Global\` 会把互斥扩大到其他用户会话，并可能引入额外权限和 DACL 配置；
- 首版没有 Windows Service，也没有跨会话协调需求。

未来若引入系统服务，必须单独设计命名空间、权限和兼容迁移，不能原地改变
本设计的名称语义。

### 物理根身份

`config.Layout.IdentityKey()` 是不访问文件系统的词法身份，无法把 8.3 短路径
和 Junction 等别名归并到同一 Mutex。`lock` 不得直接散列该词法 key。
`NewSet` 必须从 `Layout.AppRoot()` 打开目录并按以下顺序生成只用于同步的
物理根身份：

1. 通过 `CreateFileW` 打开 app-root，desired access 使用
   `FILE_READ_ATTRIBUTES`，使用 `FILE_FLAG_BACKUP_SEMANTICS`，共享模式允许
   read/write 但不允许 delete，并跟随到最终目录；
2. 通过 handle 的文件属性确认目标存在且是目录；
3. 调用 `GetFileInformationByHandleEx(FileIdInfo)` 取得 64 bit
   VolumeSerialNumber 与 128 bit FileId；
4. 将固定 domain separator、little-endian volume serial 和 16-byte file ID
   拼成二进制 identity；
5. Set 在整个存活期保留 app-root handle，直到 worker 已释放/关闭两把 Mutex 后
   才关闭；这样目录对象不会在 Set 存活期被删除或重命名替换。

因此，同一物理目录经大小写、尾部斜杠、8.3、SUBST、多盘符、volume mount
或 Junction 等别名访问时得到相同 identity；仅比较 final DOS path 不满足该
承诺。app-root 不存在、无法打开、不是目录、无法取得 FileIdInfo 或最终关闭
目录 handle 失败时，`NewSet` 失败，不退回词法 identity key。

该 identity 只回答“这些 Runtime 是否应竞争同一把锁”，不授权移动、删除或递归
访问目录。T2.5 仍须独立执行 Reparse Point、受管根和目录身份校验。

### 名称算法

名称算法固定为：

```text
identity = "AUTO-MAS-Runtime/app-root/v1\0"
           || little-endian(volumeSerialNumber)
           || fileId128
digest = SHA-256(identity)
suffix = lowercase-hex(digest[0:16])

Local\AUTO-MAS-Runtime-backend-<suffix>
Local\AUTO-MAS-Runtime-mutation-<suffix>
```

后缀取 SHA-256 的前 128 bit，共 32 个小写十六进制字符。名称不泄露用户
绝对路径；物理根 identity 相同的目录得到同名 Mutex，不同 identity 得到独立
Mutex。未知 Mutex 类型在进入 Win32 调用前拒绝。

## 公开类型与 API

```go
type Kind string

const (
    KindBackend  Kind = "backend"
    KindMutation Kind = "mutation"
)

func (k Kind) String() string
func (k Kind) Valid() bool

type ProbeResult struct {
    Held      bool
    Recovered bool
}

type AcquisitionResult struct {
    // 字段不导出；错误返回时仍保留已经观察到的恢复信息。
}

type Set struct {
    // 具体字段不公开；Set 只能通过指针使用。
}

func NewSet(
    ctx context.Context,
    layout *config.Layout,
) (*Set, error)

func (s *Set) AcquireBackend(ctx context.Context) (AcquisitionResult, error)
func (s *Set) AcquireMutation(ctx context.Context) (AcquisitionResult, error)
func (s *Set) Probe(ctx context.Context, kind Kind) (ProbeResult, error)
func (s *Set) Close() error

type Lease struct {
    // 具体字段不公开；Lease 只能通过指针使用。
}

func (l *Lease) Kind() Kind
func (l *Lease) Name() string
func (l *Lease) Close() error

func (r AcquisitionResult) Lease() *Lease
func (r AcquisitionResult) Recovered() bool
func (r AcquisitionResult) PeerProbe() ProbeResult
```

`Acquire*` 是零等待获取：Mutex 已占用时立即返回稳定冲突错误，不在包内轮询
或退避。`ctx` 在请求入队、执行 Win32 操作前和返回前检查；本设计不把
`context.Context` 保存到 `Set` 或 `Lease`。

`NewSet` 拒绝 nil ctx/layout，并在 app-root I/O、worker 启动和返回前检查取消。
构造成功前发生的 app-root
open/stat/file-id/close 故障返回 `OperationError`，且不启动 worker、
不创建命名 Mutex。

`AcquisitionResult.Recovered()` 表示本次取得的主 Mutex 是否由
`WAIT_ABANDONED` 恢复。`PeerProbe()` 记录获取后的对端探测，其中
`Recovered=true` 表示探测曾取得一个 abandoned 对端 Mutex 并已立即释放。
成功时 `Lease()` 非 nil；冲突、探测故障、返回前取消或主 Mutex 清理失败时
`Lease()` 为 nil，但已经观察到的主/对端恢复信息仍随 result 返回。调用方必须在成功和
失败路径都把这些字段写入操作日志；恢复本身不是 warning 或失败，不能因最终没有 Lease
而丢弃。

`Lease.Close`、`Set.Close` 都必须幂等。`Set.Close` 会先在所有者线程上释放
尚存 Lease，再关闭 Win32 handle 和 worker；其后所有获取和探测返回
`ErrClosed`。`Set.Close` 之后调用旧 `Lease.Close` 返回 `nil`，不能重复执行
`ReleaseMutex`。Lease 内部携带不可复用的 generation，防止旧 Lease 释放
后续新获取的 Mutex。若先前 `ReleaseMutex` 失败导致所有权仍不确定，Close
必须按下文的 pinned-thread 终止路径收口，不能只关闭 handle 后把该 OS thread
交回 Go 调度器。

## Windows 实现

### 依赖选择

实现使用 `golang.org/x/sys/windows` 调用 `CreateFile`、
`GetFileInformationByHandleEx`、`CreateMutex`、`WaitForSingleObject`、
`ReleaseMutex`、`DuplicateHandle`、`GetCurrentThread` 和 `CloseHandle`。这是 Go 官方扩展仓库中维护的 Windows
API 封装，避免自行声明易错的 syscall；该依赖属于 `AGENTS.md` 已规划的
例外。若当前版本没有导出 FileIdInfo 包装，只允许在
`internal/lock` 内通过 `windows.NewLazySystemDLL("kernel32.dll")` 定义这一
个缺失调用，参数和返回值必须有 Windows 集成测试覆盖。

实现文件使用 Windows build constraint。项目首版只支持 Windows，不提供
行为不完整的内存锁作为非 Windows 替代。

### 线程亲和

Windows Mutex 的所有权属于取得 Mutex 的线程，而不是进程或 goroutine。
普通 goroutine 可能迁移 OS 线程，因此不得在调用方 goroutine 中直接
`WaitForSingleObject` 后于另一线程 `ReleaseMutex`。

每个 `Set` 启动一个专用 worker goroutine：

1. worker 启动后立即调用 `runtime.LockOSThread()`，并把
   `GetCurrentThread()` 伪句柄通过 `DuplicateHandle` 复制成由 Set 协调方持有、
   仅授予 `SYNCHRONIZE` 的真实 thread handle；复制成功并完成握手后才创建 Mutex；
2. 在该线程以 `CreateMutex(nil, false, name)` 创建/打开两把 handle；
   `initialOwner=false`，所有权只由后续显式 Wait 取得；
3. 创建、等待、探测、释放和关闭两把 Mutex 的所有操作都通过请求 channel
   串行进入该 worker；
4. worker 记录当前主 Lease 的类型、generation，以及 backend/mutation 各自的
   `maybeOwned`；任意成功 Wait 先置 true，只有成功 Release 才置 false；
5. 关闭时先重试释放每个 `maybeOwned`，再关闭 handle；只有两者均已证明为 false
   才调用 `runtime.UnlockOSThread()`；
6. 任一 `maybeOwned` 仍为 true 时，worker 关闭 handle 后通过容量 1 的退出结果
   channel 告知协调方需要同步终止，然后直接从 goroutine 返回，
   **不得**调用 `runtime.UnlockOSThread()`。根据 Go 的 `LockOSThread` 契约，锁定线程的
   goroutine 未解锁即退出会终止该 OS thread；Windows 因而释放该线程真实持有的 Mutex，
   其他已打开同名对象的线程随后观察 `WAIT_ABANDONED`；
7. 协调方收到“需要同步终止”后，在复制的 thread handle 上
   `WaitForSingleObject(INFINITE)`；只有返回 `WAIT_OBJECT_0`、确认 OS thread 已终止后
   才关闭 thread handle 并允许 `Set.Close` 返回。等待失败或异常返回值并入 Close error，
   但不得伪称同步释放成功；
8. 正常释放路径在发送退出结果前已经调用 `runtime.UnlockOSThread()`；协调方无需等待
   thread signaled，只关闭自己的 thread handle；
9. 请求方只等待本次请求的响应 channel，不接触 Mutex 或 thread 原始 handle。

`NewSet` 必须等待 worker 报告两把 handle 都已成功创建后才返回。第二把创建
失败时，worker 在同一线程关闭第一把 handle 后退出；调用方不会拿到部分
可用的 `Set`。

同一 `Set` 的 `Probe` 若探测到 worker 自己持有的 Mutex，直接返回
`Held=true`，不得递归等待同一 Windows Mutex。不同 `Set` 或不同进程仍由
Windows 内核给出真实结果。

worker 的 channel 生命周期必须有明确退出路径。`Close` 与并发中的
`Acquire`、`Probe`、`Lease.Close` 通过同一请求序列线性化，不关闭仍可能被
发送的请求 channel，也不遗留 goroutine。Close 等待 worker 请求循环结束并缓存
完整收口结果；所有权不确定路径还必须等待复制的 thread handle signaled，确保
Close 返回与 OS thread 终止具有明确先后关系。该 Set 此后不再复用 worker 或 handle。

同一 Set 最多持有一个 live Lease。worker 在任何 Acquire 的 Win32 Wait 前先检查
`activeKind`；已有 Lease 时不得依赖 Windows Mutex 的同线程递归语义：

| activeKind | 新请求 | 返回 |
| --- | --- | --- |
| backend | AcquireBackend | `BACKEND_ALREADY_RUNNING` |
| backend | AcquireMutation | `BACKEND_STILL_RUNNING` |
| mutation | AcquireBackend | `MUTATION_IN_PROGRESS` |
| mutation | AcquireMutation | `MUTATION_IN_PROGRESS` |

只有当前 Lease.Close 已在 worker 上释放并清除 generation 后，下一次 Acquire 才能
进入 Wait。该规则同时禁止重复 Lease 与同一 worker 交叉持有两把 Mutex。

## 获取与交叉竞态

### `AcquireBackend`

顺序固定为：

1. 零等待取得 `backend`；
2. 若 `backend` 已被持有，返回 `BACKEND_ALREADY_RUNNING`；
3. 在仍持有 `backend` 时零等待探测 `mutation`；
4. 若 `mutation` 被持有，释放刚取得的 `backend`，返回
   `MUTATION_IN_PROGRESS`；
5. 若 `mutation` 空闲，立即释放探测时短暂取得的 `mutation`，返回
   `backend` Lease。

### `AcquireMutation`

顺序固定为：

1. 零等待取得 `mutation`；
2. 若 `mutation` 已被持有，返回 `MUTATION_IN_PROGRESS`；
3. 在仍持有 `mutation` 时零等待探测 `backend`；
4. 若 `backend` 被持有，释放刚取得的 `mutation`，返回
   `BACKEND_STILL_RUNNING`；
5. 若 `backend` 空闲，立即释放探测时短暂取得的 `backend`，返回
   `mutation` Lease。

两条路径故意采用相反的“先取得本方，再探测对方”顺序。若两进程恰好同时
分别取得 `backend` 和 `mutation`，双方随后都会看到对方已持有，各自返回
对应冲突并释放本方 Mutex。此时允许双方都失败，但绝不允许双方都成功；
调用方可按稳定错误码重试。

所有“取得本方后”的探测、释放或上下文检查失败，都必须先尽力释放本方
Mutex，再返回错误。释放失败与原错误使用 `errors.Join` 保留，不能因为清理
错误覆盖根因。返回的 `AcquisitionResult` 必须先冻结已经发生的
`WAIT_ABANDONED` 主恢复和已完成的 PeerProbe；后续冲突、探测失败、取消或释放失败不得
把这些字段清零。

`ReleaseMutex` 失败后 worker 无法证明所有权已经解除，必须进入 sticky poisoned
状态并保存第一次失败。poisoned 后 Acquire、Probe 和新的 Lease 操作都在 Win32
调用前返回 `PoisonedError`；不得继续复用两把 handle。触发失败的 Lease.Close 和
后续重复 Close 返回缓存的同一错误。只有 Set.Close 可以进入 worker：它再尽力释放
每个 `maybeOwned` 一次、关闭两把 Mutex 与 app-root handle，并让 pinned worker 退出；
所有收口错误用 `errors.Join` 保留。重试 Release 全部成功时可以
`runtime.UnlockOSThread()` 后正常退出；任一所有权仍不确定时必须走“保持锁线程并退出”
路径，绝不能 Unlock 后让调度器复用该线程。Close 完成后仍以 closed 状态为最终状态，
且返回值保留最初 poison 原因、Close 重试和 handle 关闭错误。

## Wait 结果语义

对主 Mutex 的等待结果：

| Win32 结果 | 语义 |
| --- | --- |
| `WAIT_OBJECT_0` | 成功取得，`AcquisitionResult.Recovered=false` |
| `WAIT_ABANDONED` | 成功取得，`AcquisitionResult.Recovered=true` |
| `WAIT_TIMEOUT` | 已被其他线程持有，按获取路径映射冲突码 |
| `WAIT_FAILED` 或其他值 | 返回带 Win32 原因的 `OperationError` |

对 `Probe` 或交叉探测的等待结果：

| Win32 结果 | `ProbeResult` | 后续动作 |
| --- | --- | --- |
| `WAIT_OBJECT_0` | `{Held:false, Recovered:false}` | 立即在同一线程 `ReleaseMutex` |
| `WAIT_ABANDONED` | `{Held:false, Recovered:true}` | 已恢复所有权，立即在同一线程释放 |
| `WAIT_TIMEOUT` | `{Held:true, Recovered:false}` | 不持有 handle 所代表的 Mutex |
| `WAIT_FAILED` 或其他值 | 无有效结果 | 返回 `OperationError` |

`WAIT_ABANDONED` 表示前一所有者异常结束，但当前等待者已经取得所有权；它
不能被当作失败或“仍被持有”。恢复结果只用于日志和诊断。后续事务状态是否
陈旧由 T2.3 同时检查 PID 和 Mutex，`lock` 包不删除状态文件。

Probe 在 WAIT_OBJECT_0 / WAIT_ABANDONED 后先冻结 ProbeResult，再尝试 ReleaseMutex。
释放失败时仍返回该 result 与 OperationError，并进入 poisoned；尤其
`Recovered=true` 不能因 release error 丢失。调用方必须先记录恢复事实，再按 error
失败关闭。

## 错误模型

预期互斥冲突使用类型化错误：

```go
type ConflictError struct {
    code protocol.Code
    Kind Kind
    Name string
}

type OperationError struct {
    code      protocol.Code
    Operation string
    Kind      Kind
    Name      string
    Cause     error
}

func (e *ConflictError) Code() protocol.Code
func (e *OperationError) Code() protocol.Code

var (
    ErrClosed   = errors.New("mutex set is closed")
    ErrPoisoned = errors.New("mutex set is poisoned")
)

type PoisonedError struct {
    Cause error
}

func (e *PoisonedError) Error() string
func (e *PoisonedError) Is(target error) bool
func (e *PoisonedError) Unwrap() error
func (e *PoisonedError) Code() protocol.Code
```

`ConflictError` 可由 `errors.As` 取得；`OperationError.Unwrap` 返回原始
原因，`ErrClosed` 可由 `errors.Is` 判断。错误字符串保持英文、小写开头且
不含路径。名称只含固定前缀和哈希，可安全进入诊断日志。

稳定冲突映射不得由调用方猜测：

| API 与冲突点 | `protocol.Code` | 退出码 / retryable / remediation |
| --- | --- | --- |
| `AcquireBackend`：`backend` 已持有 | `BACKEND_ALREADY_RUNNING` | 使用协议层冻结定义 |
| `AcquireBackend`：`mutation` 已持有 | `MUTATION_IN_PROGRESS` | 使用协议层冻结定义 |
| `AcquireMutation`：`mutation` 已持有 | `MUTATION_IN_PROGRESS` | 使用协议层冻结定义 |
| `AcquireMutation`：`backend` 已持有 | `BACKEND_STILL_RUNNING` | 使用协议层冻结定义 |

创建 app-root/Mutex handle、查询 FileIdInfo、等待、释放或关闭的 Win32 故障不是
“正常冲突”，统一由 `OperationError` 携带
`protocol.CodeMutexOperationFailed`；四元组固定为退出码 70、retryable=true、
remediation=`retry`/`run-doctor`。上层记录原始 Win32 code，不得借用
`STATE_WRITE_FAILED` 或任一正常冲突码。

## 与状态持久化的边界

两类文件与 Mutex 的对应关系固定为：

| 状态文件 | 真实占用 Mutex |
| --- | --- |
| `backend.json` | `backend` |
| `mutation.json` | `mutation` |
| `update.json` | `mutation` |
| `environment.json` | 无事务占用语义 |

应用服务必须先成功取得 Lease，再写本次事务状态；完成时先清理事务状态，
再释放 Lease。进程崩溃时 Windows 会释放或 abandon Mutex，而 JSON 可能
残留，下一进程按 T2.3 规则分类。任何代码都不能仅因 JSON 存在返回冲突。

## 不负责范围

T2.4 明确不负责：

- CLI app-root 参数解析和词法布局构造；
- 把物理根 identity 用作移动、删除或递归访问授权；
- 创建、校验、清理任何 `runtime-state/*.json`；
- 通过 PID 判断进程存活或按 PID/进程名终止进程；
- 等待另一个 Runtime 完成、自动重试或跨进程发送控制命令；
- 输出 NDJSON、写 stdout、选择用户可见文案；
- 修改 Mutex DACL、使用 `Global\` 或安装 Windows Service；
- 用文件锁、PID 文件或进程名扫描替代 Windows 命名 Mutex。

4. `TestSet_ProbeMapsWaitResults`：四类 Wait 结果和探测后的立即释放；abandoned 后
   ReleaseMutex 失败仍返回 `Recovered=true` 的 ProbeResult 与 error，并 poison Set；
5. `TestSet_AbandonedMutexRecordsRecovery`：主获取与对端探测均保留
   `Recovered`；主 Mutex abandoned 后再遇到 peer conflict、peer probe failure、
   返回前取消或主锁释放失败时，即使没有 Lease，`AcquisitionResult` 仍保留已经观察到的
   recovery metadata；
6. `TestSet_OperationsStayOnPinnedThread`：等待与释放观察到相同的 Windows
   thread ID；
7. `TestSet_CloseIsIdempotent`：活跃 Lease、并发 Close、旧 Lease Close
   均不重复释放且 worker 退出；
8. `TestSet_AcquireFailureReleasesPrimary`：交叉冲突、探测故障和取消后本方
   Mutex 均可再次取得；
9. `TestSet_CloseTerminatesPinnedThreadWhenOwnershipUncertain`：使用真实命名 Mutex
   与注入的 Release 故障让 worker 保持所有权；Close 重试后仍不确定时不得调用
   UnlockOSThread，协调方等待真实 thread handle signaled 后 Close 才返回；另一个已经
   打开同名对象的 worker 在 Close 返回后的**第一次**零等待立即取得
   `WAIT_ABANDONED`，不允许轮询或重试掩盖窗口，且无 goroutine、线程请求、thread handle
   或 Mutex 残留；
10. `TestSet_RejectsSecondLiveLeaseBeforeWait`：四种 activeKind/新 Acquire 组合
   映射既有冲突码，Win32 wait 调用数保持不变；
11. `TestOperationError_UsesMutexOperationFailed`：app-root identity、thread handle
    复制/等待/关闭、Mutex 创建/等待/释放/关闭故障都携带
    `MUTEX_OPERATION_FAILED` 及原始错误链。

Win32 调用通过包内非导出的小接口注入单元测试替身；生产 API 不暴露内核
handle 或测试钩子。

### 双进程 Windows 集成测试

测试使用当前 Go test 可执行文件的 helper-process 模式。父进程先监听随机
`127.0.0.1:0` loopback TCP 端口，把地址和一次性随机 token 通过环境变量传给
helper；helper 连接后用逐行 JSON 控制消息明确同步：

1. helper 首消息携带 token，父进程核对后才接受该控制连接；
2. helper 成功取得指定阶段的 Mutex 后发送 `READY`；
3. 父进程收到 `READY` 才发送 `CONTINUE` 或 `RELEASE`；
4. helper 发送最终结构化结果并退出，父进程等待退出码。

helper 不使用 stdout 传测试协议，避免绕过仓库 stdout 所有权扫描；stderr 只保留
测试诊断。禁止用 `time.Sleep` 猜测 helper 是否已取得 Mutex。内部测试构造器可注入
“已取得本方、尚未探测对端”的 barrier，但该钩子只存在于同包 `_test.go`
代码。

固定集成场景：

- 同一 app-root 的两个进程互斥，且错误码精确；
- 不同物理 app-root 可同时取得同类 Mutex；
- 同一目录的大小写、尾部斜杠、可用的 8.3、SUBST、多盘符或 volume mount
  别名得到同名 Mutex；不可在测试环境创建的别名必须记录明确 Skip 原因；
- 指向同一目标目录的 Junction 别名与真实路径得到同名 Mutex；测试只创建
  和删除自己的临时 Junction，不对其执行递归删除；
- app-root 不存在或指向普通文件时 `NewSet` 失败，且没有创建 Mutex worker；
- 两个进程分别取得 `backend` / `mutation` 后同时继续交叉探测，双方失败
  并释放，随后第三进程可取得任一 Mutex；
- helper 持有 Mutex 后被父进程终止，下一次获取收到 abandoned、成功恢复
  并报告 `Recovered=true`；
- helper 正常释放后无 abandoned；
- 所有场景结束后 `Probe` 均为 free，无 helper 和 worker 残留。

并发测试追加 `go test ./internal/lock -count=100` 和完整 race detector。
实现完成后还需执行仓库标准验证门，并把实现提交号记录到
[任务拆分](./任务拆分.md) 的 T2.4 条目。
