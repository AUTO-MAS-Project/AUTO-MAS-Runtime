本文冻结 `internal/logging` 的 stderr 诊断、JSONL 操作日志、按本地日期自然
轮转、保留策略、并发和关闭语义。该包只管理 Runtime 本地诊断面，不拥有
NDJSON 协议输出。

## 1. 目标与范围

T2.2 交付以下能力：

1. 将 Runtime 自身诊断按 `debug`、`info`、`warn`、`error` 分级写到 stderr；
2. 将诊断和操作记录写入逐行 JSON 的轮转文件；
3. 通过 T2.1 `Layout` 取得日志目录与文件路径，不重复拼接固定路径；
4. 按稳定 command 短名和本地日历日期自然轮转；
5. 始终向调用方提供当前活动文件的绝对 `logPath`；
6. 默认保留 30 个本地日历日，并限制每个 command 最多 30 个文件；
7. 允许注入保留策略与时钟，保证边界测试不依赖真实日期；
8. 保证同一个 Logger 的并发写、轮转、保留和关闭线性化；
9. 由创建 Logger 的当前 Runtime 进程同步触发保留清理；
10. 提供幂等 `Close`，且不关闭调用方拥有的 stderr。

T2.2 不定义协议 `log` 事件，也不把本地日志自动转成 stdout 事件。后续 uv、
process 和 backend 包需要同时转发协议事件与落盘时，分别调用协议 Emitter
和本文的 `Record`，两条路径不能互相替代。

## 2. 方案 A：单个操作 Logger、两类显式写入

每个顶层 Runtime 操作创建一个 `Logger`，固定绑定：

- `Layout`；
- stderr writer；
- 稳定 command 短名；
- operation ID；
- 时钟；
- 保留策略；
- 当前活动日志文件。

公开 API 区分两种用途：

1. `Diagnostic`：Runtime 自身诊断，同时写 stderr 和 JSONL 文件；
2. `Record`：只写 JSONL 文件，用于操作审计以及 uv/backend 原始输出落盘。

这一区分保证 Python、uv 等受管进程的 stdout/stderr 不会被重新复制到 Runtime
stderr。它们仍应转成协议 `log` 事件并调用 `Record` 落盘；stderr 只保留
Runtime 自身诊断。

不采用以下方案：

- 不使用包级默认 logger 或可变全局输出；
- 不让 logging 自行读取 app-root 或拼接 `logs/runtime`；
- 不让 logging 直接用路径调用 `os.OpenFile`、`os.ReadDir` 或 `os.Remove`；
- 不把 stderr 文本原样复制为文件格式；
- 不启动定时轮转、后台清理或异步写队列；
- 不让 logging 持有 `os.Stdout` 或协议 Emitter；
- 不为只有一个实现的 Logger 提前定义接口。

## 3. 公开 API

```go
type Level string

const (
    LevelDebug Level = "debug"
    LevelInfo  Level = "info"
    LevelWarn  Level = "warn"
    LevelError Level = "error"
)

func (l Level) String() string
func (l Level) Valid() bool

type RetentionPolicy struct {
    MaxAgeDays         int
    MaxFilesPerCommand int
}

func DefaultRetentionPolicy() RetentionPolicy

type Option func(*options) error

func WithClock(clock func() time.Time) Option
func WithRetention(policy RetentionPolicy) Option

type WriteResult struct {
    FileWritten   bool
    StderrWritten bool
    Rotated       bool
}

func New(
    ctx context.Context,
    layout *config.Layout,
    stderr io.Writer,
    command string,
    operationID string,
    options ...Option,
) (*Logger, error)

func (l *Logger) Diagnostic(
    ctx context.Context,
    level Level,
    message string,
    details map[string]any,
) (WriteResult, error)

func (l *Logger) Record(
    ctx context.Context,
    level Level,
    message string,
    details map[string]any,
) (WriteResult, error)

func (l *Logger) LogPath() string
func (l *Logger) Close() error
```

`New` 返回具体类型。构造器拒绝 nil `layout`、nil stderr（包括 typed nil）、
空 command、空 operation ID、含 NUL 的标识、非法 option 和无效策略。
command 还必须通过 `Layout.RuntimeLogFile` 的单段路径校验；logging 不对
失败值做字符替换。

`operationID` 的 ULID 语义由 protocol/CLI 上游保证，logging 只要求它非空、
不含 NUL。`message` 可以为空，也可以包含换行；文件编码会转义换行，
stderr formatter 会把它转成可见转义序列，确保每条诊断仍占一个物理行。

`details` 必须能被 `encoding/json` 编码。nil 统一输出为 `{}`。写入在方法
返回前完成，Logger 不保存 details map；调用方不得在同一次调用期间并发
修改该 map。

生产构造器内部通过 `filesystem.NewRuntimeLogFiles(ctx, layout)` 取得专用日志文件
能力。logging 内部定义 `logFiles`、`logWriter` 和私有 retained-file token 等消费方
小接口，由 `filesystemLogFiles` adapter 包装具体 T2.5 类型。测试通过
`newWithDependencies(ctx, ..., files, clock)` 在任何 open/list/remove 前注入替身；
公开 API 不接受任意路径或通用文件系统。

New、Diagnostic 和 Record 拒绝 nil ctx。写方法取得 Logger mutex、完成参数校验和编码
后，在任何 open/remove/write 副作用前最后检查一次取消；若已取消，返回零值
WriteResult。越过该提交点后，方法使用保留 values 的 `context.WithoutCancel(ctx)` 尝试
完成本次规定的文件与 stderr sink，事后发生的取消不能覆盖实际 sink 结果或把已写记录
伪装成未写。调用方若在操作取消后才开始新的收尾诊断，仍必须显式传自己的收口 ctx。

## 4. 构造与资源所有权

`New` 按以下顺序执行：

1. 校验全部参数和 option；
2. 从注入时钟取得一次当前本地时间；
3. 调用 `filesystem.NewRuntimeLogFiles(ctx, layout)`，由它固定并验证 app-root 到日志目录的
   祖先句柄；
4. 通过该能力以 ctx、command 和日期打开当天 append writer，并取得绝对路径；
5. 初始化 Logger 的活动日期、路径和 writer；
6. 通过专用能力列举日志并执行一次保留清理；
7. 返回可用 Logger。

第 6 步的普通保留删除失败按第 8.3 节记录维护 warning 后仍可成功构造。
如果维护 warning 自身也无法写出并使 `New` 决定返回 error，构造器必须先
关闭第 4 步已经打开的 writer 和 RuntimeLogFiles，再使用 `errors.Join`
返回全部错误；`New` 返回 error 的任何路径都不得把句柄交给垃圾回收兜底。

目录和文件权限、Reparse Point 拒绝、句柄固定和 append 打开语义由 T2.5
实现。每条 JSONL 记录编码完成后通过 writer 的单次 `Write` 写入，不使用
用户态缓冲；不对每行调用 `fsync`。

Logger 拥有 RuntimeLogFiles 和自己打开的 writer，并由 `Close` 释放。stderr
writer 由调用方拥有，Logger 只保存并写入它，绝不调用其 `Close`。logging
生产代码不得自行使用 `os` 打开、列举或删除日志，也不得引用或保存 `os.Stdout`。

活动文件在构造时立即创建，因此 `LogPath()` 在 `New` 成功后始终返回一个
绝对路径，即使尚未写入业务记录。

## 5. JSONL 操作日志

每个物理行恰好是一个 UTF-8 JSON object，固定字段如下：

```json
{
  "timestamp": "2026-07-29T18:20:30.1234567+08:00",
  "level": "info",
  "kind": "operation",
  "command": "workspace-sync",
  "operationId": "01J...",
  "message": "仓库校验完成",
  "details": {
    "commit": "0123456789abcdef"
  }
}
```

字段语义：

| 字段 | 规则 |
| --- | --- |
| `timestamp` | 注入时钟值，`time.RFC3339Nano`，保留时区偏移 |
| `level` | `debug`、`info`、`warn`、`error` 之一 |
| `kind` | `Diagnostic` 为 `diagnostic`，`Record` 为 `operation` |
| `command` | 构造时固定的稳定 command 短名 |
| `operationId` | 构造时固定的 operation ID |
| `message` | 原字符串，JSON 编码负责转义控制字符 |
| `details` | 恒为 JSON object；nil 输出 `{}`，不得输出 `null` |

JSON 对象键顺序不是消费契约，测试应解码后断言字段。每条记录编码为单行并
带一个 LF；message 或 details 中的换行必须被 JSON 转义，不能破坏 JSONL
分帧。logging 不解析 message 或 details 的自然语言来决定级别或业务状态。

`Record` 不写 stderr。后续受管进程日志应在 details 中保留稳定来源字段，
例如 `source=backend`、`stream=stderr`；stderr stream 只是原始来源，
不能被 logging 自动推断成 `LevelError`。

## 6. stderr 分级诊断

`Diagnostic` 使用与文件记录相同的一次时钟采样、级别、command、
operation ID、message 和 details，另外写一条无颜色的单行文本：

```text
2026-07-29T18:20:30.1234567+08:00 INFO [workspace-sync] [01J...] 仓库校验完成 {"commit":"0123456789abcdef"}
```

级别在 stderr 中使用大写显示。message 中的 CR、LF、TAB 和其他不可见控制
字符转成可见转义，details 使用紧凑 JSON；因此调用一次 `Diagnostic` 只会
产生一个物理行，不允许日志注入伪造下一条诊断。空 details 仍显示 `{}`，
便于人工区分“没有上下文”和输出被截断。

文件与 stderr 是互补 sink。`Diagnostic` 会尝试两边写入，即使其中一边
失败也不能跳过另一边；方法使用 `errors.Join` 返回全部写错误。JSON 编码
在两个 sink 写入前完成，编码失败时两边都不写，避免同一诊断只留下不同
形状的半条记录。`WriteResult` 独立标记每个 sink 是否已写；调用方遇到部分失败时不得
假定整条记录未发生并盲目重试。`Record` 的 `StderrWritten` 固定为 false。

参数解析失败发生在 Logger 构造前，CLI 可以直接写 stderr；一旦 Logger
创建成功，Runtime 自身诊断都应经过 `Diagnostic`，避免格式和并发规则散落。

## 7. 本地日期自然轮转

默认时钟是 `time.Now`。`WithClock` 注入的函数返回“当前本地时间”，其
Location 是日期归属的唯一依据；实现不读取或改写全局 `time.Local`。测试可
返回带固定时区的时间，精确覆盖 UTC 日期与本地日期不同的边界。

每次 `Diagnostic` 或 `Record` 在 Logger 互斥区内：

1. 只调用时钟一次；
2. 由该时间同时生成 timestamp 和本地 `YYYYMMDD`；
3. 若日期未变，继续写当前文件；
4. 若日期变化，通过 RuntimeLogFiles 以 command 和新日期打开新 writer；
5. 新文件打开成功后关闭旧句柄并切换活动路径；
6. 切换后同步触发一次保留清理；
7. 把当前记录写入新文件。

新文件打开失败时不把记录写进旧日期文件；stderr 诊断仍应尝试写出，
方法返回轮转错误。旧活动句柄保持可用，后续调用可以重试轮转。打开成功而
旧句柄关闭失败时仍切换到新文件，当前记录继续写入新文件，并把关闭错误与
其他错误一起返回；`WriteResult.Rotated=true`，并由 `FileWritten` / `StderrWritten`
准确说明当前记录是否已写，不能把旧 writer close error 表述为“当前记录未写”。

轮转是由下一次写入自然触发的，不启动午夜 timer。没有新记录时保留旧句柄
不影响文件内容；下一条记录到达时才切换。

`LogPath()` 在互斥区内返回当前活动文件的绝对路径：

- 构造后、首次写入前是构造日期文件；
- 成功轮转后变为新日期文件；
- 轮转打开失败时仍是旧活动文件；
- `Close` 后仍返回最后一个活动路径。

跨午夜的长驻操作会产生多个日期文件，协议 `details.logPath` 使用调用
`LogPath()` 时的当前活动文件。较早记录仍可按同 command 的相邻日期文件
找到；首版不把多个路径塞进单一 `logPath` 字段。

## 8. 保留策略

默认值固定为：

```go
RetentionPolicy{
    MaxAgeDays:         30,
    MaxFilesPerCommand: 30,
}
```

两个值都必须大于零。`MaxAgeDays` 表示本地日历日而不是
`30 * 24 * time.Hour`：当天和之前 29 个本地日期属于默认年龄窗口，避免
夏令时造成边界偏移。`WithRetention` 以值复制策略，调用方后续无法修改
Logger 内部配置。

### 8.1 触发时机

保留清理由当前 Runtime 进程同步触发：

- `New` 打开当天文件后执行一次；
- 每次成功切换到新日期文件后执行一次；
- 不启动 goroutine、定时任务、Windows Service 或独立清理进程；
- `Close` 不额外触发扫描。

任意 command 的 Logger 都会扫描 `RuntimeLogDir()` 中全部可识别的 Runtime
日志，并按 command 分组应用同一策略。因此即使某个旧 command 很久没有
再次运行，也会在其他 Runtime 操作启动时得到清理。

### 8.2 可识别文件与删除边界

只处理由 T2.1 规则生成的普通文件：

```text
<valid-command>-YYYYMMDD.log
```

实现从 `RuntimeLogFiles.List` 返回的不可伪造 token 读取文件名，从末尾解析日期
和 command，再调用 `Layout.RuntimeLogFile(command, parsedDate)` 重建期望绝对
路径，并执行大小写不敏感的词法比对。只有两者一致时才进入候选集；普通文件、
祖先句柄和文件 ID 已由 filesystem 核验。

以下内容由 filesystem 不返回或由 logging 忽略：

- 未匹配命名规则的文件；
- 日期无效的文件；
- 子目录；
- 符号链接、Junction、其他 Reparse Point；
- 当前 Logger 的活动文件；
- 不在 `RuntimeLogDir()` 直接子级的内容。

logging 只把 List 返回的原 token 交回 `RuntimeLogFiles.Remove`，不得仅凭路径
字符串删除。filesystem 不导入 logging，因此依赖保持为
`logging -> filesystem -> config/protocol`；任何递归删除仍走 T2.5 Operator。
Remove 返回 `MutationApplied=true` 且 close error 时，保留策略记录维护 warning，但把
token 视为已经删除，不能再次提交同一删除。

### 8.3 清理顺序

对每个 command：

1. 删除日期早于年龄窗口的文件；
2. 对剩余文件按日期从新到旧排序；
3. 超过 `MaxFilesPerCommand` 时删除最旧文件；
4. 当前活动文件占用一个数量名额但始终不作为删除目标；若它落入溢出区，
   改删同组中最旧的非活动文件；
5. 同一文件已被并发进程删除产生的 not-exist 视为幂等成功。

未来日期文件参与数量上限但不会仅因年龄删除。清理顺序必须确定，日期相同
时以规范绝对路径作为次级排序键，便于测试和故障复现。

保留清理是维护动作：某个旧文件因占用或权限无法删除时，不关闭当前日志，
也不让顶层业务操作失败。Logger 把失败汇总为一条 `warn` 级
`diagnostic` 记录，写入当前活动文件和 stderr；不得递归再次触发清理。
如果连这条维护失败诊断也无法写出，`New` 或触发轮转的写方法返回组合错误，
不能静默吞掉。

## 9. 并发模型

`Logger` 内部使用一个 `sync.Mutex` 线性化以下状态：

- 当前日期、活动绝对路径、writer 和 RuntimeLogFiles；
- 时钟采样后的轮转判断与文件切换；
- JSONL 文件写入；
- stderr 诊断写入；
- 保留扫描及活动文件排除；
- closed 状态和首次 `Close` 结果。

同一个 Logger 的多个 goroutine 并发调用 `Diagnostic`、`Record`、
`LogPath` 和 `Close` 时：

- 每个已成功编码的记录在 JSONL 中保持一个完整物理行；
- stderr 诊断不会互相穿插；
- 日期边界只打开并切换一次活动文件；
- `Close` 返回后不再开始新的写入；
- 已经取得互斥锁的写入先完成，随后 `Close` 才关闭句柄。

为保持文件行、stderr 行、轮转和关闭的单一顺序，clock、logFiles、writer 和 stderr
都在 Logger mutex 内同步调用。所有注入依赖必须快速、并发安全且不得回调同一个
Logger；这与 protocol renderer 的锁内回调契约一致。测试使用 barrier 证明另一 goroutine
在 sink 返回前不能穿插记录，并用受控替身验证没有锁外状态修改。生产 API 不暴露测试
钩子。

并发保证以“同一个 Logger 实例”为边界。不同 Runtime 进程可能同时打开
同一 command/date 文件；实现使用 append 和单次 record write 降低交错
风险，但首版不宣称提供跨进程事务性行锁。会修改环境或监督后端的命令还受
T2.4 Mutex 约束；允许并发的只读命令不应依赖文件行顺序表达业务事务。

## 10. Close 语义

`Close` 在互斥区内先关闭当前 writer，再关闭 RuntimeLogFiles，并把 Logger
标记为 closed：

- 第一次调用各执行一次底层 close，使用 `errors.Join` 保留两个错误；
- 后续调用不再次关闭，返回第一次调用缓存的相同结果；
- 即使底层 close 返回 error，Logger 仍进入 closed；
- close 后 `Diagnostic` 和 `Record` 返回 `ErrClosed`，不写任何 sink；
- close 后 `LogPath` 仍返回最后活动的绝对路径；
- stderr writer 永远不由 `Close` 关闭。

当前实现不使用用户态缓冲，因此 `Close` 不需要额外 flush。它也不承诺
`fsync` 到物理介质。

## 11. 错误语义

实现提供以下可由 `errors.Is` 判断的 sentinel error：

```go
var (
    ErrInvalidArgument  = errors.New("logging argument is invalid")
    ErrInvalidLevel     = errors.New("logging level is invalid")
    ErrInvalidRetention = errors.New("logging retention is invalid")
    ErrInvalidTime      = errors.New("logging clock returned invalid time")
    ErrEncodeEntry      = errors.New("encode log entry")
    ErrClosed           = errors.New("logger is closed")
)
```

| 场景 | 行为 |
| --- | --- |
| nil ctx/layout/stderr、空 command/operation ID、含 NUL 标识 | 包装 `ErrInvalidArgument` |
| 未知 level | `ErrInvalidLevel`，不写任一 sink |
| 策略字段小于等于零 | `ErrInvalidRetention` |
| 构造或写入时钟返回零值 | `ErrInvalidTime` |
| details 含无法编码的值或循环引用 | 包装 `ErrEncodeEntry` |
| close 后写入 | `ErrClosed` |
| 创建目录、打开、写入、短写或关闭失败 | 保留底层 error 并增加操作上下文 |
| 旧日志保留删除失败 | 写本地维护 warning，业务写继续 |

所有错误字符串使用英文、小写开头、无结尾标点，包装保留错误链。双 sink、
轮转或 close 同时失败时使用 `errors.Join`，调用方可以判断每个底层原因。

logging 不导入 protocol，也不新增协议错误码。它原样保留
`*filesystem.Error`：`PATH_OUTSIDE_MANAGED_ROOT`、`UNSAFE_REPARSE_POINT` 和
`DIRECTORY_OCCUPIED` 等安全/占用原因由应用服务优先采用，不能一律重写。
普通 writer/stderr 的创建、编码、轮转和写入故障才由应用服务按命令语境映射
`OUTPUT_WRITE_FAILED`。纯调用方误用应在测试中暴露。保留清理失败按第 8.3 节
作为本地维护 warning，不改变协议结果。

## 12. stdout 所有权

`internal/logging` 必须满足：

- 不导入、引用、保存或关闭 `os.Stdout`；
- 不调用 `fmt.Print*`、`log.Print*` 或默认 `log.Logger`；
- 不创建 `json.Encoder` 指向 stdout；
- 不持有 `protocol.Emitter` 或 `protocol.ProcessOutput`；
- `Record` 和 `Diagnostic` 都不发送 NDJSON 事件；
- stderr 只能来自构造参数，文件路径只能来自 `Layout`。

后续命令把 `LogPath()` 的绝对结果放入事件
`details.logPath`。logging 不直接修改协议 details，不依赖事件结构，也不
绕过协议层写 stdout。

## 13. 不负责范围

T2.2 明确不负责：

- NDJSON `log`、warning、error 或 result 事件；
- human renderer 输出；
- CLI 的 `--output`、日志级别参数或 stderr 接线；
- uv/Python 行读取、非 UTF-8 替换和超长行截断；
- 从自然语言日志判断业务状态或错误码；
- 日志压缩、上传、遥测、远程收集或用户隐私脱敏；
- 跨进程强一致行锁和跨机器共享日志；
- 递归删除、Reparse Point 跟随或通用 filesystem 清理；
- 把跨午夜多个文件扩展成新的协议字段；
- 保证每条记录 `fsync` 到物理介质。

调用方负责避免把密钥、访问令牌或无必要的用户业务内容放进 message/details。
本地日志允许记录诊断所需的绝对路径，但任何未来外发功能必须单独设计脱敏
和授权，不能复用本任务作为外发许可。

## 14. 测试与验收

自动化测试必须覆盖：

1. nil/cancelled ctx、构造参数、typed nil、command segment、operation ID、
   option 和策略校验；
2. `New` 只通过 RuntimeLogFiles 和 Layout 创建
   `logs/runtime/<command>-YYYYMMDD.log`，且 `LogPath()` 为绝对路径；
3. 默认策略精确为 30 个本地日历日、每 command 30 个文件；
4. 四个 level 的 `String` / `Valid`、JSONL 字面量和 stderr 大写显示；
5. `Diagnostic` 同时写两边，`Record` 只写文件，WriteResult 精确反映每个 sink；
6. JSONL 七个固定字段、nil details 为 `{}`、每行一个 object；
7. message/details 含 CR、LF、TAB、引号和非 ASCII 时仍保持单行与合法
   UTF-8 JSON；
8. 不可编码 details、未知 level 和零值时钟不产生半条记录；
9. 同一日期多次写不换文件，跨本地午夜的下一次写精确切换一次；
10. 固定 `+08:00` 等时区下 UTC 日期与本地日期不同，文件名仍使用注入时钟
    的本地日期；
11. 轮转打开失败不把记录写入旧日期，后续调用可重试；
12. 旧句柄关闭失败、文件写失败、stderr 写失败和短写均保留完整错误链，
    双 sink 仍各自尝试；轮转已生效或任一 sink 已写时 WriteResult 防止调用方误判；
13. 年龄边界保留当天加前 29 天，删除更早文件；
14. 每 command 数量上限独立计算，策略注入可使用更小边界；
15. 一次扫描清理多个 command，未来日期、同日排序和当前活动文件行为确定；
16. 未知文件、非法日期、目录、符号链接和 Reparse Point 完好；
17. 并发清理遇到 not-exist 幂等，其他删除失败产生本地维护 warning 且
    Logger 仍可继续写；
18. `New` 中维护 warning 写失败会关闭已打开文件；close 也失败时返回值可
    同时由 `errors.Is` 判断两个原因，且没有句柄泄漏；
19. 使用 barrier 并发写入多级别记录，最终行数准确、每行合法且无交错；
20. 并发写与午夜轮转只产生一个新活动文件；
21. `LogPath` 与写、轮转、关闭并发读取无数据竞争；
22. `Close` 首次关闭、重复调用、错误缓存、close 后写入和不关闭 stderr；
23. app-root、`logs/`、`logs/runtime/` 任一祖先为 Junction/Reparse Point 时
    构造失败，外部目录没有新增或删除；
24. 保留清理只把 List 返回的 token 交回 Remove；同名文件被替换时拒绝删除
    新对象并记录维护 warning；
25. 包内静态扫描确认没有 `os.Stdout`、直接日志文件 open/read/remove、
    默认 log 输出或协议发射路径；
26. `newWithDependencies` 在首次 open/list 前注入故障，验证构造失败关闭 writer/store
    和双 close 错误链；
27. barrier sink 证明锁内回调期间其他记录不会穿插，测试替身不回入 Logger；
28. filesystem 的安全协议码错误链未被改写为 OUTPUT_WRITE_FAILED；
29. `go test -race` 下并发、轮转、保留和 Close 场景无数据竞争；
30. barrier 在最后一次副作用前取消得到零值 WriteResult；越过提交点后取消不跳过第二
    sink、不覆盖旧 writer close/error 或已经写入的结果。

测试时钟使用可控序列和 channel/barrier 推进，不使用 `time.Sleep`。文件系统
故障通过 Logger 内部的包私有依赖字段注入，同包测试可以替换 open、read、
remove 和 close 行为，但生产 API 不为测试替身增加公开接口。
