## 2. Important

### I1. `NewEmitter` 校验后继续使用调用方持有的 capability 切片

- 位置：`internal/protocol/emitter.go:105`、`internal/protocol/emitter.go:134`
- 证据：函数先遍历 `capabilities` 做全集校验，之后调用可注入的 `settings.clock()`，
  最终把原切片直接交给 `HelloEvent`。调用方可在 clock 回调中确定性地修改同一底层数组，
  使 hello 发出未经校验的 capability；并发修改还会形成数据竞争。T1.7 计划指定的
  `TestNewEmitterRejectsUnknownCapability` 当前也不存在。
- 影响：`NewEmitter` 的“拒绝未知 capability”保证存在校验与使用之间的缺口，且 API
  的所有权语义不清晰。
- 建议：入口立即复制并归一化切片，只校验和渲染副本；补齐未知值负例和 clock
  回调修改原切片的回归测试。

### I2. 两个 human renderer 测试在进入被测逻辑前失败

- 位置：`internal/protocol/human_renderer_test.go:336`、`internal/protocol/human_renderer_test.go:386`
- 证据：两个测试向 `NewEmitter` 传入恶意的未知 capability；T1.7 的新校验先返回错误，
  `newHumanEmitter` 因而直接终止，消息清洗和 ANSI 控制字符断言没有执行。
- 影响：标准 `go test ./... -count=1` 门禁为红，且测试名称宣称覆盖的安全性质实际未被执行。
- 建议：对 capability 清洗直接调用 `HumanRenderer.RenderHello`；经 `Emitter` 的集成路径只使用
  全集内 capability，并保留其他字段的恶意输入覆盖。

### I3. 契约库仍把 `null` 容器当作合法输入

- 位置：`internal/protocol/contracttest/validate.go:32`、
  `internal/protocol/contracttest/validate.go:393`、
  `internal/protocol/contracttest/contract_test.go:426`
- 证据：schema 文案仍是 `or null`，`validRemediation` 和 `validDetails` 对 `nil`
  返回 true，`failure with null containers` 仍是正例。
- 影响：违反 T1.7 和架构文档已经冻结的 wire 约束；真实命令输出 `null` 时公共契约测试不会拦截。
- 建议：只接受 array/object，调整诊断文案，把 error、warning、result 及 warning summary
  的 `null` 用例改为负例。

### I4. 冻结全集成员断言尚未实现

- 位置：`internal/protocol/contracttest/validate.go:126`、
  `internal/protocol/contracttest/example_test.go:41`、
  `internal/protocol/contracttest/contract_test.go:958`
- 证据：`validateBusinessSchemas` 只校验部分字段类型，没有校验 code、stage、remediation、
  progress status、state status 或 capability 的成员关系；demo 和夹具仍使用
  `OPTIONAL_CHECK_SKIPPED`、`DOCTOR_FAILED`、`review-log`、`WARN_000`、`action-N` 等临时值。
- 影响：T1.7 要求的六类未知值负例均缺失；就地编造的协议字面量会被契约库放行。
- 建议：按事件类型调用冻结全集查询，并先把公共夹具改为基于真实定义的构造器，避免新增断言后
  大面积无关失败。

### I5. `hello`、`progress`、`state`、`log` 的业务 schema 完全未校验

- 位置：`internal/protocol/contracttest/validate.go:126`、
  `internal/protocol/contracttest/contract_test.go:906`
- 证据：schema switch 只处理 result、error、warning；当前 `helloObject` 只有五个公共 envelope
  字段，却被所有 valid transcript 当作合法 hello。
- 影响：缺失 `runtimeVersion`、`command`、`capabilities`，以及 progress/state/log 的必填字段
  都不会让契约测试失败，新命令的一行注册无法提供完整协议保护。
- 建议：为七类事件各自定义业务 schema 和最小负例；可选字段单独描述，不与必填字段混在一起。

### I6. 生命周期迁移测试仍复制生产表，没有对照权威文档

- 位置：`internal/protocol/lifecycle_test.go:13`、`internal/protocol/doc_fixture_test.go:15`
- 证据：测试中的 `wantLifecycleTransitions` 仍硬编码 25 条迁移，新增的文档读取 helper
  没有被生命周期测试使用。
- 影响：生产表和测试副本可以一起偏离设计文档而保持全绿，T1.7 的“文档驱动迁移表”保护未落地。
- 建议：运行时解析 `doc/设计-T1.3-生命周期状态机.md` 的两张迁移表，并让迁移枚举和路径测试
  共用同一份解析结果。

### I7. 错误四元组只验证自一致，没有对照 `ErrorDefinition`

- 位置：`internal/protocol/contracttest/validate.go:371`、
  `internal/protocol/contracttest/contract_test.go:876`
- 证据：`tupleMatches` 只比较 error 与 result 是否相同。取消夹具把
  `OPERATION_CANCELLED` 写成 `retryable=false`，而 `errors.go` 的稳定定义是 true，
  当前契约测试仍通过。
- 影响：error/result 可以携带彼此一致但权威语义错误的 retryable/remediation，
  Electron 会据此展示错误操作；`CodeOK` 也没有在 warning/error 层被明确拒绝。
- 建议：warning、error 和非成功 result 分别对照 `LookupErrorDefinition`；终态 result
  仍额外验证与主 error 一致，成功 result 单独校验 `OK` 空处置。

### I8. 关键并发测试没有制造确定性的冲突窗口

- 位置：`internal/protocol/emitter_test.go:220`、
  `internal/protocol/emitter_test.go:264`、
  `internal/protocol/lifecycle_test.go:570`、
  `internal/protocol/lifecycle_test.go:622`
- 证据：测试只同时放行 goroutine，没有阻塞在“检查后、提交前”的临界位置；错误实现若恰好串行调度
  仍可通过。工具链升级前本机无法运行 race detector；即使补跑 race，重复执行也不能替代确定性证明。
- 影响：result 恰好一次、sequence 线性化和单次自动重启等关键不变量可能在未来重构时静默退化。
- 建议：沿用 `TestEmitter_WarningResultRace` 的阻塞 renderer 模式，增加 result/result
  和普通事件写入的确定性交错；生命周期通过可注入 hook 或包内白盒 barrier 证明守卫原子性。

### I9. T1.7 计划中的验证命令不能可靠阻止失败后继续

- 位置：`doc/计划-T1.7-M1契约收口实现.md:26`、
  `doc/计划-T1.7-M1契约收口实现.md:70`、
  `doc/计划-T1.7-M1契约收口实现.md:228`
- 证据：计划正文要求每条原生命令检查 `$LASTEXITCODE`，定向测试还要检查命中测试，
  但 Task 级命令普遍没有这些检查，最终 `-count=100` 也未检查退出码。
- 影响：PowerShell 7 会继续执行后续命令，测试失败或 `-run` 零命中时仍可能进入提交步骤。
- 建议：把仓库统一的 PowerShell 验证模板提取为可复用脚本，计划只调用脚本；保留定向测试时，
  同时断言退出码、无 `[no tests to run]` 且出现 `--- PASS:`。

## 4. 已确认的优点

- stdout 所有权保持单一：扫描只在 `cmd/auto-mas-runtime/main.go` 发现 `os.Stdout`；
- `ProcessOutput.mu` 把 renderer、sequence、terminal 和 warning 账本放在同一线性化域，边界明确；
- warning 在入账前做快照，result 汇总有明确上限，避免调用方后续修改污染终态；
- 控制通道有输入上限、commandId 去重、停止接受语义和确定性的阻塞测试；
- 生产文件按 event、renderer、emitter、lifecycle、control 分责，命名整体符合 Go 惯例；
- T1.8 注释迁移没有引入逐行复述，关键所有权、锁域和重入限制已显式写出。
