# T1.6 协议契约测试套件设计

## 1. 目标

为协议 v1 建立生产侧终态保证和可复用的原始 NDJSON 契约断言库，使每个
后续 Runtime 命令都能用一行注册证明：

- hello 必为首事件；
- sequence 从 1 开始连续递增；
- stdout 每个物理行恰好一个 JSON object；
- result 恰好一次且最后；
- 成功、失败、取消三种终点语义正确；
- warning 被协议层权威汇总进 result；
- result 后所有经 `ProcessOutput` / `Emitter` 的协议发射都被拒绝，原始
  transcript 同时发现绕过 API 产生的尾随字节。

本设计采用已批准的方案 A：

> `ProcessOutput` 在现有串行化锁内统一拥有 terminal gate 和有界 warning
> ledger；独立 `contracttest` 包只消费真实 stdout transcript，不参与生产
> 发射，也不依赖具体命令实现。

## 2. 范围与边界

T1.6 负责：

- result 成功发射后的生产 terminal gate；
- result 重复和 result 后事件的稳定 sentinel error；
- warning 的深快照、有界账本和权威 result 汇总；
- warning/result 并发的线性化语义；
- 原始 NDJSON 分帧、公共 envelope、终点和 warning 汇总断言；
- success/failure/cancelled 三场景自动注册；
- 一个纯测试 demo runner 和负例自测；
- 把 T1.6 契约接入后续命令所需的 API 冻结为一行注册。

T1.6 不负责：

- 生产 CLI 命令或 demo 子命令；
- 真实命令的进程退出码测试；取消退出码 130 在命令集成测试验证；
- stdin 控制 action、后端关闭或生命周期迁移；
- human 文本的机器解析；
- 异步事件队列、日志轮转、状态持久化或跨进程恢复；
- 对 stdout 以外的 stderr 诊断做 NDJSON 契约断言。

生产命令不得直接调用 renderer 或绕过 `ProcessOutput` 写协议 stdout。

## 3. 生产 terminal gate

### 3.1 API

```go
var (
    ErrResultAlreadyEmitted = errors.New("protocol result already emitted")
    ErrEventAfterResult      = errors.New("protocol event emitted after result")
)
```

两个错误均为公开 sentinel，调用方使用 `errors.Is` 判断。

`ProcessOutput` 在现有 `mu` 保护下增加：

```go
terminal     bool
warnings     []WarningSummary
warningCount uint64
```

### 3.2 精确语义

- result renderer 完整成功后才设置 `terminal=true`；
- terminal 后再次 `EmitResult` 返回 `ErrResultAlreadyEmitted`；
- terminal 后其他五个公开 Emit 方法返回 `ErrEventAfterResult`；
- 被拒事件不得调用 clock 或 renderer，不得修改 sequence、warning ledger 或
  调用方事件；
- 非 sticky encode 失败不封口、不推进 sequence，调用方可修正后重试；
- sticky write/flush 失败继续毒化输出并返回首次 write error；
- 并发 warning/result 或两个 result 由 `ProcessOutput.mu` 决定唯一顺序；
- warning 先获得锁并成功，则 sequence 更小且进入 result 汇总；
- result 先成功，则后续 warning 被 terminal gate 拒绝；
- 生产 gate 保证 result 至多一次，命令 runner 和契约库证明至少一次，两者
  合成恰好一次。

terminal 检查发生在 sticky error、clock、快照和 renderer 之前。

## 4. Warning 权威汇总

### 4.1 WarningSummary

```go
const MaxResultWarningSummaries = 256

type WarningSummary struct {
    Code        string         `json:"code"`
    Stage       Stage          `json:"stage"`
    Message     string         `json:"message"`
    Retryable   bool           `json:"retryable"`
    Remediation []string       `json:"remediation"`
    Details     map[string]any `json:"details"`
}
```

summary 不包含 `Common`，因为 protocol、type、operationId、sequence 和
timestamp 已存在于原 warning 事件中。数组顺序严格等于 warning 成功发射
的 sequence 顺序。

### 4.2 快照与入账

每次 `EmitWarning` 在 renderer 前把六个业务字段只 JSON 编码一次，再用
`UseNumber` 分别解码为两个互不共享的规范对象：

- 形成嵌套 map/slice 的深快照，不与调用方共享可变存储；
- 拒绝 channel、function、循环引用、NaN/Inf 等非 JSON 值；
- 快照失败是非 sticky encode error：不渲染、不入账、不推进 sequence；
- 第一份 `WarningSummary` 用于重建 canonical `WarningEvent` 并交给 renderer，
  因此非确定性 `json.Marshaler` 也只执行一次，原 warning 与汇总不会漂移；
- renderer 完整成功后才增加 `warningCount`，ledger 保存第二份独立 summary，
  renderer 即使违反约束修改嵌套值也不能污染最终汇总；
- 前 256 条成功 warning 保存 snapshot，之后只增加 count；
- renderer 失败不入账；sticky I/O 失败后不会继续伪造 result。

这会把“协议事件 details 必须是 JSON 值”统一应用到 NDJSON 和 human
renderer。human 仍不展示任意 details，但不能接受机器协议无法表达的值。

### 4.3 Result details

发射 result 前，协议层创建新的顶层 details map，不修改调用方 map。
以下键为协议保留键，调用方提供的值总是删除：

- `warnings`
- `warningCount`
- `warningsTruncated`

若没有成功 warning，三个键均不出现，保持现有无 warning 结果格式。

若存在 warning，协议层写入：

```json
{
  "warnings": [
    {
      "code": "INVALID_CONTROL_COMMAND",
      "stage": "backend.run",
      "message": "已忽略无效的 stdin 控制命令",
      "retryable": false,
      "remediation": ["update-desktop"],
      "details": {"reason": "invalid_json", "lineBytes": 12}
    }
  ],
  "warningCount": 1,
  "warningsTruncated": false
}
```

- `warnings` 是最早的 `min(warningCount, 256)` 条；
- `warningCount` 是全部成功发射 warning 的总数；
- `warningsTruncated == (warningCount > 256)`；
- result 的其他 details 保留；
- `nil details + warning` 变为只含三个保留键的 object；
- 调用方伪造的 warnings 不会进入输出；
- result encode/render 失败不清空 ledger，修正后重试仍得到相同汇总。

有界 ledger 防止长驻 `backend supervise` 因无效 stdin 或重复诊断无限增长，
同时用总数和截断标记保留完整性信号。

## 5. 可复用 contracttest

### 5.1 包布局与依赖

```text
internal/protocol/
  emitter_test.go
  renderer_internal_test.go
  contracttest/
    contract.go
    parse.go
    validate.go
    contract_test.go
    example_test.go
```

依赖方向固定为：

```text
command_test -> contracttest -> protocol
```

生产 `protocol` 不得导入 `contracttest` 或 `testing`。protocol 白盒测试不
导入 contracttest；跨包 transcript 测试使用 `package protocol_test` 或
`package contracttest_test`，避免 import cycle。

### 5.2 注册 API

```go
type Terminal string

const (
    TerminalSuccess   Terminal = "success"
    TerminalFailure   Terminal = "failure"
    TerminalCancelled Terminal = "cancelled"
)

type Transcript struct {
    Stdout []byte
}

type Runner func(t *testing.T, terminal Terminal) Transcript

func Register(t *testing.T, command string, run Runner)
func Assert(t *testing.T, command string, terminal Terminal, stdout []byte)
```

后续命令测试只需：

```go
contracttest.Register(t, "dependencies sync", runDependenciesSyncContract)
```

`Register` 自动生成 success、failure、cancelled 三个子测试。runner adapter
负责把具体命令置于对应结果；契约库只接收 stdout bytes。

### 5.3 原始分帧

验证不得先 `TrimSpace`：

- transcript 非空且以恰好一个正常事件行的 LF 结束；
- LF 分帧后不允许空行、CR 或 result 后隐藏字节；
- 每个物理行必须恰好一个 JSON object；
- decoder 使用 `UseNumber` 并拒绝尾随 token；
- 失败诊断包含 command、scenario、1-based line、转义并截断的 raw line 和
  整体类型摘要。

### 5.4 公共 envelope

- hello 恰好一次且只能位于第一行；
- hello sequence 为 1；
- 所有事件 `protocol == 1`；
- operationId 相同且是规范 ULID；
- sequence 严格等于物理行号 `1..N`；
- timestamp 可按 RFC3339Nano 解析；
- result 恰好一个且位于最后一行。

### 5.5 终点

- success：`success=true`、`code=OK`、`retryable=false`、
  `status!=cancelled`，此前不得出现 error；
- failure：`success=false`、code 既不是 `OK` 也不是
  `OPERATION_CANCELLED`、`status!=cancelled`，此前至少一个 error 与 result 的
  code/stage/retryable/remediation 四元组完全相同；
- cancelled：`success=false`、`code=OPERATION_CANCELLED`、
  `status=cancelled`，此前 error 复述同一四元组；
- warning 不把 success result 改为 failure。

failure/cancelled 不要求 error 紧邻 result，允许在终点前输出最后的 state
或诊断，但 result 必须最后。

### 5.6 Warning 汇总

- 没有 warning 时三个保留键必须都不存在；
- 有 warning 时 `warningCount` 等于此前 warning 总数；
- `warningsTruncated` 与是否超过 256 精确一致；
- `warnings` 与此前最早 256 条 warning 的六个业务字段逐项、同序深等；
- 不允许缺失、多余、重排或调用方伪造汇总。

## 6. Demo 与自测

demo 只存在于 `contracttest/example_test.go`：

- 使用真实 `protocol.ProcessOutput` 和 NDJSON renderer；
- 固定 operationId/clock；
- success 场景包含一个 warning，证明成功不被改失败；
- failure 场景发 error/result；
- cancelled 场景发 OPERATION_CANCELLED error/result；
- 用同一行 `contracttest.Register` 注册。

契约库自身把解析和语义验证实现为返回结构化 issues 的内部函数，`Assert`
只负责映射到 `testing.T`。负例表驱动测试逐项破坏：

- 空输出、缺 LF、空行、CR、非 object、尾随 JSON；
- 非 hello 首行、operationId/sequence/timestamp 不一致；
- 第二个 hello、type 缺失/非字符串/未知类型；
- 缺 result、双 result、result 非最后；
- success 前有 error、success/failure 使用 cancelled status、failure 使用
  OPERATION_CANCELLED、cancelled 使用其他 code 等互斥终点错误；
- warning 缺失、重排、伪造、count/truncated 错误。

## 7. 并发和 renderer 边界

- 两个并发 result 只能一个成功，另一个 `ErrResultAlreadyEmitted`；
- warning/result 并发允许两种锁顺序，但每种 transcript 都必须合法；
- result 成功后六个公开 Emit 方法（重复 result + 五个非 result）以及内部
  hello 路径逐个测试，buffer 和 recording renderer 均不变；
- NDJSON 与 human/recording renderer 共用同一 terminal gate；
- human 不展开 result warning 汇总，避免重复展示；
- third-party renderer 仍不得修改事件或重入 emitter。

## 8. 验收矩阵

- sentinel error 支持 `errors.Is`，拒绝路径不调用 clock/renderer；
- result encode failure 可修正重试，成功后封口；
- warning encode/render/write/flush 成功与失败的入账边界；
- warning snapshot 深复制，调用方后续修改不影响 result；
- 0、1、256、257 条 warning 的 details 汇总；
- 调用方伪造三个保留键被覆盖或删除，其他 details 不变；
- result/warning 和双 result 并发重复测试；
- contracttest 所有正负例；
- demo 三场景通过一行注册；
- gofmt、vet、全仓测试、protocol/contracttest 高重复测试和 build 通过；
- result 后无任何经 `ProcessOutput` 的 renderer 调用或新 stdout bytes；
  transcript 负例另外证明绕过产生的尾随 bytes 会失败。
