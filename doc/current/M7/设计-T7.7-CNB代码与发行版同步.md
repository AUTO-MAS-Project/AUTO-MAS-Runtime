# 设计：T7.7 CNB 代码与发行版同步

- 立项：2026-09-17，用户需求「像 AUTO-MAS 那边一样，将 Runtime 的代码和 Release 同步到 CNB」
- 基线：Runtime `main@b7dee4b`；AUTO-MAS `sync-cnb.yml`、`build-app.yml`、`cnb_release.py` 为参照
- 目标仓库：`https://cnb.cool/AUTO-MAS-Project/AUTO-MAS-Runtime.git`（2026-09-17 时为空仓库，无分支无 Tag）
- 相关决策：T7.4（2026-08-10 跳过，当时无 CNB 仓库与凭据）；本任务在条件变化后新增，不改写 T7.4 的历史结论

## 1. 目标

1. GitHub 保持唯一权威源；CNB 是只读镜像。代码 refs（分支 + Tag）经 `sync-cnb.yml` 全量镜像；
2. GitHub Release 发布并冒烟通过后，`release.yml` 的 `publish-cnb` job 把**同一批字节**复制为 CNB 同名 Release；
3. 历史 Release（当前 18 个）由手动 backfill 工作流按需回填；
4. 全链路失败关闭：任何不一致（Tag 指向不同 Commit、资产哈希不同、同名资产已存在）都让 workflow 标红，绝不覆盖、绝不删除 CNB 侧数据。

## 2. 范围与边界

### 负责

- `.github/workflows/sync-cnb.yml`（新）：branch/tag push 与手动触发 → `tencentcom/git-sync` 镜像到 CNB；
- `.github/workflows/release.yml`（扩展）：新增 `publish-cnb` job，`needs: [package, publish, smoke]`；
- `.github/workflows/cnb-release-backfill.yml`（新）：仅手动触发，按 tag 逐个或全量回填历史 Release；
- `scripts/publish-cnb-release.ps1`（新）：PowerShell 7 + CNB OpenAPI 的发布器，两个 workflow 共用；
- `internal/release`：上述 workflow 与脚本的静态契约测试 + 以 Go `httptest` 模拟 CNB API 的脚本集成测试；
- `doc/任务拆分.md`、`AGENTS.md`：登记 T7.7。

### 不负责

- **不**在 CNB 上构建任何东西：不使用 `.cnb.yml`、不触发 CNB CI、不回拉 GitHub artifact 在 CNB 重新构建（AUTO-MAS 现行模式的收敛）；
- **不**代理业务流量、不把 CNB 变成 Runtime 的下载源（直到双链路完成一次真实新版本验收）；
- **不**删除或移动 CNB 的 Tag、分支、Release：分支删除产生的陈旧镜像只由漂移检查报告，处理需单独授权；
- **不**改 AUTO-MAS 仓库的任何工作流；
- **不**为 Windows 之外的平台做适配（M11 之前 CNB 镜像同样只发 Windows 资产）；
- **不**处理 exe 签名（D3 延后不变）。

## 3. CNB OpenAPI 契约（2026-09-17 自 swagger.json 核实）

- 基址 `https://api.cnb.cool`；`Authorization: Bearer <token>`；`Accept: application/vnd.cnb.api+json`；
- `GET /{repo}/-/releases/tags/{tag}` → 200（`api.Release`：`id`/`tag_name`/`name`/`body`/`draft`/`prerelease`/`tag_commitish`/`assets[]`）或 404；
- `GET /{repo}/-/releases` → 分页列表，用于 `all` 回填的 CNB 侧状态核对；
- `POST /{repo}/-/releases`，body `openapi.PostReleaseForm`：`tag_name`、`name`、`body`、`draft`、`prerelease`、`target_commitish`（**填精确 40 位 Commit**，不填分支名）、`make_latest`；
- `POST /{repo}/-/releases/{release_id}/asset-upload-url`，body `{asset_name, overwrite, size, ttl}` → `openapi.ReleaseAssetUploadURL`：`upload_url`（预签名 PUT）、`verify_url`（预签名 POST 确认）、`expires_in_sec`；
- 上传 = `PUT upload_url`（body 为文件字节）；确认 = `POST verify_url`；
- `api.ReleaseAsset` 带 `hash_algo`/`hash_value`/`size`/`browser_download_url`；
- 公开下载端点：`https://cnb.cool/{repo}/-/releases/download/{tag}/{filename}`；
- Tag 查询：`GET /{repo}/-/git/tags/{tag}` → `api.Tag`：`target`（目标对象哈希）、`target_type`（`commit`/`tag`）、`commit.sha`。脚本用它轮询 CNB Tag 是否已同步并剥离 annotated tag，不需要 `git ls-remote` 与 Git 凭据。

## 4. 架构

```
普通 branch/tag push ──→ sync-cnb.yml ──git-sync──→ CNB Git 仓库

v* Tag push ──→ release.yml
                  package → publish(GitHub Release) → smoke
                                                        │
                                                        └→ publish-cnb
                                                             ├─ 下载已发布 GitHub Release 资产
                                                             ├─ 校验 SHA256SUMS 与 GitHub digest
                                                             ├─ 轮询 CNB Tag 指向同一 Commit
                                                             ├─ 创建/校验 CNB Release（精确 Commit）
                                                             ├─ 上传缺失资产（overwrite=false）
                                                             └─ 从 CNB 公开地址回读比对 SHA-256
```

关键原则：

1. **GitHub 权威**：CNB 禁止独立开发或移动发布 Tag；`publish-cnb` 只消费**已发布**的 GitHub Release（不信任 workflow 中间 artifact），天然复用 smoke 已验证过的同一批字节；
2. **失败关闭**：GitHub smoke 不通过则 `publish-cnb` 不跑；CNB 侧任何不一致立即失败，保留现场；
3. **幂等**：CNB 同名 Release 已存在且一致 → 视为成功；缺少资产 → 只补缺失的；重跑永不覆盖；
4. **短链路**：与 AUTO-MAS「CNB 流水线回拉 GitHub artifact 再上传」相比，省一层中转构建、省长期 GitHub PAT、省 Python/tqdm 依赖。

## 5. 组件设计

### 5.1 sync-cnb.yml

以 AUTO-MAS 版本为基础，收敛如下：

- 触发器：`push` + `workflow_dispatch`。**不**叠加 `create`（同一次新 Tag 会 push+create 双触发）；GitHub 自带 `GITHUB_TOKEN` 的 push 不触发新工作流的限制，对「代码同步」无害——真正发版链路的 Tag 由用户本机推送，`publish-cnb` 自己处理 Release 部分；
- `permissions: contents: read`；`if: github.repository == 'AUTO-MAS-Project/AUTO-MAS-Runtime'`；
- checkout `fetch-depth: 0` + `persist-credentials: false`；
- `docker://tencentcom/git-sync@sha256:b7c4672616ddea5b89948dcd034610b29d37d8430e74b4bc83b421c963c25f77`（2026-09-17 复核的 latest manifest digest，与 AUTO-MAS 所用一致）；
- `PLUGIN_TARGET_URL=https://cnb.cool/AUTO-MAS-Project/AUTO-MAS-Runtime.git`、`PLUGIN_AUTH_TYPE=https`、`PLUGIN_USERNAME=cnb`、`PLUGIN_PASSWORD=${{ secrets.GIT_PASSWORD }}`、`PLUGIN_PUSH_TAGS=true`、`PLUGIN_FORCE=true`；
- concurrency 按 `github.ref` 分组，取消同 ref 的旧同步。

### 5.2 publish-cnb-release.ps1

参数（全部显式，无隐式全局态）：

| 参数 | 说明 |
| --- | --- |
| `-GitHubToken` / `-GitHubApiUrl` / `-GitHubRepository` | GitHub API 读取 Release；`GitHubApiUrl` 可注入，测试用 |
| `-CnbToken` / `-CnbApiUrl` / `-CnbRepository` | CNB OpenAPI；`CnbApiUrl`/`CnbRepository` 可注入，测试用 httptest |
| `-Tag` / `-AssetsDir` | 目标 Tag 与本地资产目录（EXE + SHA256SUMS.txt） |
| `-ExpectedCommit` | publish 阶段已验证的源 Commit（backfill 模式下从 GitHub Tag API 现场解析） |
| `-DryRun` | 只报告差异，不创建/上传（backfill 预检用） |

执行顺序（任何一步失败即抛错终止）：

1. 校验 Tag 安全（同 release.yml 的正则与禁用模式）、GitHub Release 非 draft、资产非空；
2. 下载 GitHub Release 全部资产到 `AssetsDir`，逐个校验 GitHub API 的 `digest`（`sha256:...`）；
3. 解析 `SHA256SUMS.txt`：每行 `hash  name` 必须覆盖目录内每个资产，且 EXE 哈希与本地文件一致；
4. `ExpectedCommit` 为空时从 GitHub `git/ref/tags/{tag}` 现场解析（递归 peel annotated tag，复用 release.yml 同款算法）；
5. 轮询 `GET /-/git/tags/{tag}`：404 → 未同步继续等；200 → `target_type=commit` 时直接比对 `target`，`target_type=tag`（annotated）时比对 `commit.sha`，直到指向 `ExpectedCommit`；
6. `GET /-/releases/tags/{tag}`：404 → 以 `target_commitish=<ExpectedCommit>` 创建；200 → 校验 `tag_commitish`、`name`、`prerelease`、`draft=false`，不一致即失败；
7. 对比 Release 资产清单：已存在且 `hash_value` 一致 → 跳过；已存在但不一致 → **失败关闭**；缺失 → `asset-upload-url`（`overwrite=false`）→ PUT → verify → 重新查询确认 `hash_value`；
8. 从 `https://cnb.cool/{repo}/-/releases/download/{tag}/{filename}` 回读每个资产，比对 SHA-256；
9. 全程不打印 token、Authorization、upload_url、verify_url（日志只允许出现资产名、大小、哈希与端点路径）。

退出码 0 = CNB Release 已存在且完全一致或本轮创建/补齐成功。

### 5.3 release.yml 的 publish-cnb job

```yaml
publish-cnb:
  needs: [package, publish, smoke]
  runs-on: windows-latest
  permissions: contents: read
  steps:
    - checkout（persist-credentials: false）
    - 下载已发布 GitHub Release 资产（gh release download，与 smoke 同源）
    - pwsh scripts/publish-cnb-release.ps1 …
      env: CNB_TOKEN=${{ secrets.CNB_TOKEN }}
```

失败语义：CNB 失败 → workflow 标红，GitHub Release 保持已发布状态；修复后手动 rerun 即幂等补齐。

### 5.4 cnb-release-backfill.yml

- 仅 `workflow_dispatch`，输入 `tag`（精确 Tag 或 `all`）、可选 `dry_run`（只报告差异不动 CNB）；
- `all`：`GET /repos/…/releases?per_page=100` 按创建时间从旧到新逐个调用发布脚本；GitHub 无 Release 的 Tag（如 `V0.1.8`）只同步 Git ref（由 sync-cnb 覆盖），不凭空创建 Release；
- 权限 `contents: read`；concurrency 全局单飞，防止两个回填互相踩。

### 5.5 测试（internal/release）

静态契约测试（读文件断言片段，模式同现有 `TestReleaseWorkflow_*`）：

- sync-cnb.yml：目标仓库 URL、`PLUGIN_PUSH_TAGS`/`PLUGIN_FORCE`、digest 固定、`contents: read`、无 `create:` 触发器、secret 名 `GIT_PASSWORD`；
- release.yml：`publish-cnb` job 存在、`needs` 三依赖、`contents: read`（全文 `contents: write` 计数仍为 1）、脚本路径、`CNB_TOKEN`；
- backfill.yml：仅 dispatch 触发、`tag` 输入、无 push 触发器；
- 脚本：关键安全语句存在（`overwrite = $false`、`-cne` 校验、禁止日志词）。

PowerShell AST 测试：新 Go 测试通过 `pwsh -NoProfile -Command` 调
`[System.Management.Automation.Language.Parser]::ParseFile` 解析全部 workflow `run` block 与 `scripts/*.ps1`，任何 parse error 即失败（恢复 T7.2 时代的门禁并以代码固化）。

脚本集成测试（Go `httptest.Server` 模拟 CNB API + 本地静态服务器模拟公开下载）：

| 用例 | 期望 |
| --- | --- |
| 首次创建 + 双资产上传 | exit 0；CNB 收到 create（精确 commit）、两次 PUT 字节正确 |
| 幂等重跑（已存在且一致） | exit 0；不再 PUT |
| 缺一个资产（补齐） | exit 0；只补缺失那个 |
| CNB Tag 尚未就绪 → 轮询后就绪 | exit 0 |
| CNB Tag Commit 不一致 | 非 0，错误信息含 commit |
| 同名资产哈希不一致 | 非 0，不发起 PUT |
| verify 失败 | 非 0 |
| CNB API 401/超时 | 非 0 |
| 日志不含 token/upload_url/verify_url | stderr+stdout 全文断言 |

集成测试用 `runtime.GOOS == "windows"` 守卫（脚本依赖 pwsh），CI 与本机均为 Windows，天然覆盖。

## 6. 凭据

| Secret | 用途 | 形态 |
| --- | --- | --- |
| `GIT_PASSWORD` | git-sync 推 CNB 仓库 | CNB HTTPS Git 密码（用户名固定 `cnb`） |
| `CNB_TOKEN` | 发布脚本调 CNB OpenAPI | CNB 访问令牌，脚本补 `Bearer` 前缀 |

- 建议专用机器人账号 + 两个独立可轮换令牌；Developer 权限即可建 Release/传附件；
- 不用 CNB 部署令牌（官方限制为读操作）；不需要 GitHub PAT；不需要 `.cnb.yml`；
- 配置命令（需用户在有 secrets 管理权限的机器上执行）：

```powershell
gh secret set GIT_PASSWORD --repo AUTO-MAS-Project/AUTO-MAS-Runtime
gh secret set CNB_TOKEN --repo AUTO-MAS-Project/AUTO-MAS-Runtime
gh secret list --repo AUTO-MAS-Project/AUTO-MAS-Runtime
```

## 7. 上线顺序与验收

1. T7.7 文档 + 测试 + 实现，标准门与 `internal/release -count=100` 全绿；
2. 用户配置两个 secrets（上面第 6 节）；
3. 核对 push 提交数后单独授权 push；
4. `main` 合入后首次 `sync-cnb.yml` 灌入 `main` 与 19 个 Tag；
5. `git ls-remote` 双侧比对 refs 无 diff；
6. 单独授权后 backfill `v0.1.10` 试点 → 验证 CNB Release 页面、EXE、checksum、NDJSON；
7. backfill `all` 回填其余 17 个；
8. 下一个新版本 Tag 走完整双发布链路验收。

T7.7 验收清单：

- [ ] 代码 refs 双侧一致（heads + tags）；
- [ ] CNB Release 元数据与 GitHub 一致（tag、name、prerelease、精确 commit）；
- [ ] CNB 资产字节与 GitHub 资产逐字节一致（回读 SHA-256）；
- [ ] 幂等重跑通过且不产生覆盖；
- [ ] 各失败分支均失败关闭且信息可定位；
- [ ] workflow 日志无凭据、无预签名 URL。

## 8. 回滚与故障处理

| 故障 | 处置 |
| --- | --- |
| sync-cnb 失败 | GitHub 不受影响；修凭据后手动 dispatch 重跑 |
| CNB Release 部分上传 | 保留现场；修好后 rerun `publish-cnb`，只补缺失资产 |
| CNB 已存在不同 Commit/不同字节 | 自动化停止且不覆盖；人工核实后决定（可能需要人工删 CNB 侧错误数据，需单独授权） |
| 凭据泄漏 | 立即撤销 CNB token、清理 Actions 日志、重新生成 secret |
| 误同步脏数据 | CNB 侧回滚靠人工，脚本永不删除 |
