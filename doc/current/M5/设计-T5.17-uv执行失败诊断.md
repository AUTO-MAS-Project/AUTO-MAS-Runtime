# T5.17 uv 执行失败诊断

CNB #263 的 bootstrap 日志只有清理和磁盘信息，无法说明 uv 为何不能执行。
`wrapBootstrapError` 保留错误码但丢弃底层 details；命令的日志器在返回前关闭，
会话随后写失败记录时得到 `logging.ErrClosed`，现有内存日志替身未模拟关闭。

## 处理方式

- uv 包装复制已类型化错误的 details，保留原错误链、错误码和现有阶段。
  不添加原始 error 文本、命令行或环境变量。
- 会话在命令收尾后、发射失败终态前，为已经打开过操作日志的命令创建独立日志器。
  沿用命令名、operationId 和受管日志工厂，记录最终分类后的失败，再关闭日志器。
  剥离取消信号并使用现有有界清理预算；日志打开、写入或关闭失败只写本地 stderr，
  不改变主错误、退出码、状态或 remediation。
- 未打开过操作日志的早期失败仍不创建日志目录，保留原有状态写入错误的 stderr 诊断。
- Electron 不改动。Sentry 继续经现有白名单净化，不增加事件或自由文本字段。

将全部业务日志器的生命周期移交会话会改变 workspace、锁和状态收尾的错误优先级，
因此采用独立终态日志器。它只在真实失败且已有操作日志时打开，不增加成功路径 I/O。

## 验证

扩展 bootstrap 的既有失败落盘测试，使用真实日志器并回读 JSON 行，核对错误码、阶段、
失败类别、Windows 错误号与 operationId，且只有一条 error 记录。
uv 包通过缓存自检入口注入可达的执行失败，确认包装保留 details 和错误链。
先确认两项回归在原实现失败，再运行 uv、CLI、日志及全仓标准门。

## 本地证据

- 两项回归在未修复代码上分别因 details 为空、真实日志没有 error 记录而失败；
  修复后相同命令通过，连同离线、下载失败、取消、停采和日志关闭约束重复 10 轮通过。
- 新编译 EXE 在隔离目录中执行损坏的受管 uv 文件，离线且关闭遥测。
  先直接启动同一文件取得 Windows 原始错误号，再核对 Runtime 的结果和日志。
  实测退出码 50、`UV_EXEC_FAILED`、`start_failed`、Windows 错误号 216；
  `debug/runtime/bootstrap-20261110.log` 中同一 operationId 恰好一条失败记录。
- `go vet ./...`、`go build ./...`、固定版本 `govulncheck@v1.9.0` 均退出 0。
- 未修改基线 `116a045` 使用 `go test -p 1 ./... -count=1` 退出 1，
  出现 runtime-state 临时目录清理失败和 SUBST 夹具的 W: 盘未就绪。
  修复版相同命令也退出 1，失败仍为这两类；CLI、uv、日志、协议及遥测包通过。
  这些本机限制不作为本次改动通过全量测试的证据，完整门禁仍需远端 CI 确认。
