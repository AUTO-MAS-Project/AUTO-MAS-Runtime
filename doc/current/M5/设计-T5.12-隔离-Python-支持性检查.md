# T5.12 隔离 Python 支持性检查与宿主解释器设计

## 1. 背景与根因

AUTO-MAS b3 的项目契约固定 Python `3.12.13`，该版本存在于 Runtime 固定 uv 0.12.3
的下载目录中。现有 `PythonService.checkSupported` 却执行不带版本过滤的
`uv python list --managed-python --output-format json`。在特定 Windows 宿主环境中，uv
会同时探测 `PATH` 中的 Python 启动器；任一无关启动器因不受信任装入点等原因无法检查，
整条命令便非零退出。

现有代码随后把 uv 的所有执行失败包装成 `PYTHON_VERSION_UNSUPPORTED`，把宿主环境探测
故障误报成目标版本不受支持。用户看到不可重试的“更新桌面端”处置，实际重试或清理无关
宿主路径才可能绕过问题。

## 2. 目标、范围与边界

本任务只修改 `internal/uv` 的 Python 支持性检查及对应测试：

- 向 `uv python list` 传入项目精确版本，并使用 `--only-downloads`，只查询 uv 的可下载目录；
- 保留 `--managed-python`、JSON 输出与离线执行，既不读取系统 Python，也不触发网络；
- uv 执行失败原样保留 `UV_EXEC_FAILED`；
- JSON 语法无效视为 uv 输出契约故障，映射 `UV_EXEC_FAILED`；
- JSON 有效且目录中没有目标版本时，才返回 `PYTHON_VERSION_UNSUPPORTED`；
- Python 安装、安装后 `python find`、镜像轮换及依赖同步行为不变。

本任务不修改 CLI、NDJSON 字段、错误码、stage、退出码、retryable、remediation、受管目录
或固定 uv 版本，不解析 uv 自然语言输出，也不改 AUTO-MAS 仓库。

## 3. 失败语义

`PYTHON_VERSION_UNSUPPORTED` 表示 uv 的结构化可下载目录成功返回，但其中没有项目要求的
精确版本。uv 进程无法启动、非零退出、输出读取失败等执行器故障已经由 `UVRunner` 映射为
`UV_EXEC_FAILED`，支持性检查不得覆盖该结构化原因。

若执行器替身返回非零退出但没有结构化错误，支持性检查仍构造 `UV_EXEC_FAILED`，以保持
失败关闭。JSON 语法错误同样属于执行/输出契约失败，而不是“目录中确认不存在目标版本”。

## 4. TDD 与验收

先增加以下红灯测试，再写最小实现：

1. `TestPython_SupportCheckScopesUVInventory`：断言精确版本与 `--only-downloads`；
2. `TestPython_SupportCheckPreservesUVExecutionFailure`：断言保留 `UV_EXEC_FAILED`；
3. `TestPython_SupportCheckRejectsMalformedInventory`：断言无效 JSON 为 `UV_EXEC_FAILED`；
4. 既有缺少目标版本用例继续断言 `PYTHON_VERSION_UNSUPPORTED`。

完成后运行 `internal/uv` 定向测试、真实 uv 0.12.3 对照、标准验证门与完整 race detector。
