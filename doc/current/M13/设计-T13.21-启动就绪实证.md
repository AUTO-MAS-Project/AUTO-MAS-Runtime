# T13.21 启动就绪实证

## 问题与范围

Runtime v0.1.14 的真机日志显示 `uv run --no-sync` 忽略了指向失效 Python 的 venv，重建后后端因缺少 loguru 退出。当前主线的 `bootstrap --if-needed` 仍只验证状态、revision、pyvenv.cfg 和 python.exe 是否存在，无法发现此类损坏。

本任务只修 Runtime 快速返回条件。解释器最初为何失效无法由现有日志定性；不改 MAS 旧模式哈希服务、不解析 pyvenv.cfg 或 uv 自然语言、不在 supervise 内安装依赖、不自动删除用户数据。

## 设计

候选快速返回保持既有结构和 revision 条件。在 mutation 锁内读取项目 Python 契约，调用已有 CheckDependencies，使用独立离线策略保证 lock 与 sync 两次检查均禁止网络。检查阶段发 dependencies.check 的 running/succeeded；健康环境不安装 Python、不执行依赖同步、不改写就绪状态。

只有检查成功且明确返回 LockfileChecked/Synchronized 才快速返回。DEPENDENCY_SYNC_FAILED 且 uv 进程实际以非零退出码完成表示环境未同步，回到原 Python 准备与锁定同步流程；其他错误直接返回并回滚临时生命周期，取消优先。原镜像/离线策略仍用于真正的准备流程。检查输出写入 bootstrap 操作日志。

不新增字段、stage、state 或错误码；不能证明依赖就绪时绝不短路。uv 检查使用现有服务、执行器与受管路径，防止引入第二条 Python 执行通道。

## 验收

CLI 矩阵覆盖结构文件仍存在但基础解释器失效、缺依赖、正常环境、更新、检查返回空结果、离线检查策略、取消、uv 执行基础设施与输出失败。真实 uv 黑盒对照正常环境、空环境、配置指向不存在解释器，证明检查不删除/创建 venv、不安装依赖；损坏检查失败后正常同步可以恢复。
