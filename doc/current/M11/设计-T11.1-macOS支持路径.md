# T11.1 macOS 支持路径与实施方案

## 1. 状态与范围

- 日期：2026-10-17。
- 基线：Runtime 本地 `main`，`c34bc97`。
- 状态：macOS 子设计进入实施，对应 T11.2~T11.9；GitHub Actions 原生运行及发布尚未验收。Linux 专项设计另行开展，T11.1 不标完成。
- 已确认：首期 Apple Silicon（`darwin/arm64`），Intel 后续；用户没有本地 Mac，主要通过 GitHub Actions 验证；最低系统版本按届时仍可用的最低原生 ARM64 托管 Runner 确定。
- 当前基线：macOS 14 Sonoma，固定 `macos-14` Runner；其退役时间及后续处理见第 2 节。
- 权威边界：架构设计、契约补充 v1 及两份增补、T10.12；macOS 同 UID 信任边界已于 2026-10-17 经用户确认并写入架构设计，私有 IPC 布局仍须先登记再实施。

目标是完成 Runtime 的核心控制面：诊断、工作区同步及暂存、uv/Python/依赖部署、managed/development 后端监督、健康检查、单次重启、关闭、修复、清理与错误观测。公开 CLI、NDJSON v1、错误码四元组及业务数据保护规则继续共用。

本方案不承担 Linux、Intel 首发、AUTO-MAS 全部业务功能或游戏脚本的跨平台改写。Electron 的 Runtime 定位、下载和安装目录调整是接入配套任务；Runtime 不增加自身自动更新职责。

| Git | 保留 go-git `v5.19.2`、go-billy `v5.9.0`；不新增运行时系统 Git 依赖 |

| 构建 | macOS 原生构建；允许以最小 cgo 桥调用公开 `libproc` API，优先使用现有 `x/sys/unix` 能力；不依赖私有 macOS API |
| 进程回收 | 优先验证临时用户级 `launchd` guard job；其失败语义通过后才接入正式 supervisor |

GitHub 当前列出 `macos-14`、`macos-15` 等 ARM64 Runner，但 macOS 14 已进入弃用期，官方公布 **2026-11-02** 退役，并存在预定停机窗口。若实施或发布时已退役，按用户确认的政策将新版本支持下限、固定 Runner、部署目标和本文件同时调整为当时最低仍可验收的版本，预计为 macOS 15，并重新取得该下限的完整结果。

每次发布冻结自己的最低系统版本。Runner 更新不能追溯改写旧版本的支持记录，也不能把 macOS 15 上的通过结果登记成 macOS 14 验收。弃用窗口的基础设施失败必须与代码失败分别记录；缺少下限结果时，该下限不得标为已验收。

## 4. 实现结构

### 4.1 平台差异的落点

保留现有包边界，公共结果、业务编排及协议保持共用。Windows 句柄字段和调用收进 `*_windows.go` 的私有实现；Darwin 提供对应私有实现及 `*_darwin.go` 文件。公共对象通过少量操作方法转交平台资源，不建立一个包含全部系统调用的通用 platform 大接口。

`config` 是路径知识的唯一来源，`uv` 集中维护制品和 Python 目标描述，`process` 集中负责平台进程边界。新增平台不通过复制一套 CLI、supervisor 或 Git 服务实现。

平台可编译与能力可用分开判断：补齐类型和失败关闭实现后可以先运行 `version`；未通过验收的环境部署、变更或监督能力仍返回既有 `UNSUPPORTED_MODE`。不以把 `process.Supported()` 改成 true 作为适配完成标志。

### 4.2 路径、身份与受控链接

1. POSIX 根目录、相对路径、大小写、Unicode 文件名与系统目录别名独立处理；不得继续用统一小写字符串作为物理身份。
2. 使用设备号和 inode 等原生对象身份识别目录、文件与锁范围；词法路径只用于显示和初步拒绝越界。
3. 可信根在打开时解析并记录物理身份，后续受管 I/O 通过已打开的根能力或目录 FD 进行；涉及保护目录的操作仍需独立身份和用途授权。
4. managed venv 的解释器链接只有解析到本次已验证受管 Python 范围内时才允许；任意用户构造链接、悬空链接或越界链接不能借此放行。
5. development 模式校验显式源码、现有 venv 和其基解释器；对外部基解释器只读校验，不把它纳入 repair/cleanup。
6. Python 解释器位置由 uv 的结构化安装清单与验证后的路径给出，不能假定 Python 安装目录内只有一个平铺的 `python`。
7. macOS 采用用户已批准的同 UID 信任边界：同账号进程不主动篡改受管路径。FD 固定对象身份而不冻结位置；发现位置或身份改变即中止后续操作、保留未知现场。外部 uv/解释器的绝对路径参数也依赖这一前提，并叠加入口、祖先与对象身份检查。

### 4.3 文件系统与状态事务

优先复用 Go 已有的 `os.Root`，需要 no-follow、no-replace、精确身份及持久化语义时在 `filesystem` 内补 `x/sys/unix` 操作。Go 1.26 已包含所需的基础 Root API，不以升级 Go 为前提。

`os.Root` 允许根内链接，并且 POSIX 打开目录 FD 后目录仍可被重命名。因此它只是实现基础，不能直接代替现有的链接拒绝、保护目录判断或条件删除协议。

必须完成以下验证；同 UID 主动并发替换的反例作为已知平台边界保留：

- 正常协作并发及故障恢复中，根外哨兵、用户数据和未知对象不被写入、移动或删除；链接、硬链接、越界与未知身份始终失败关闭。
- 根被重命名后，FD 仍只针对原已授权对象，不向同名替代对象转移授权。能够检测的位置或身份变化中止后续操作；不承诺对同 UID 主动移动消除在途副作用或强制冻结位置。
- `DirectoryLease.Path()` 不能在 Darwin 上被当成后续字符串路径 I/O 的安全授权。下载器、日志、状态文件以及 Git/uv 外部路径入口逐条盘点。
- go-billy 的根文件系统不能简单使用 `osfs.New(lease.Path())` 绕开能力边界。调查已有 `billy.Filesystem` 接口，提供 rooted adapter；限制 `.git` 与工作树访问范围，不开放 escape。
- uv 接收绝对目录参数的竞态另行验证；不把 advisory lock 当成对非协作同用户进程的强制隔离。

上述保证范围由用户在 [目录授权边界评审](./评审-T11.4-macOS目录授权边界.md) 选择方案 B 后冻结。它不是 Windows 的完全等价实现。超出该边界的安全能力不得假报通过；未完成本节验证的写入、删除和自动修复仍保持不支持。对被移动或身份不明的现场，不根据路径重建身份、不猜测删除。

状态文件保留 schema v1、固定 guard、sealed intent、旧/新身份与摘要、条件删除快照，以及 `MutationApplied` / `RecoveryRequired` 的含义。平台实现采用 FD 相对操作、独占 guard、同卷原子发布和身份复验；每个持久化阶段与子进程中断点都有故障测试。

`fsync`、目录同步和必要的 Darwin 持久化调用需实测并登记保证边界。进程被杀后的恢复证据与整机断电耐久性分别记录，不把前者当后者。

### 4.4 互斥与 PID 身份

- `backend` 与 `mutation` 保留两类业务锁和现有 staging 例外。
- 用稳定普通锁文件和 `flock` 持有跨进程 Lease；释放只关闭 FD，不删除重建锁文件。
- 获取本锁、检查对端及 staging 例外通过短时协调门完成，避免分散探测引入双持有竞态；锁目录与根身份必须共同验证。
- POSIX 没有 Windows 的 abandoned Mutex 返回值。恢复事实通过事务、owner 身份和 PID 创建时间证明；仅因 flock 成功不能报告恢复完成。
- 使用 `x/sys/unix` 的结构化进程信息及必要的公开 `libproc` API 获取 PID、PPID、PGID、创建时间和可执行路径；不解析 `ps` / `pgrep` 文本。
- PID 被复用、查询被拒绝或身份不明时保守保护现场，不删事务、不按进程名杀进程。

### 4.5 进程监督：临时 launchd guard

推荐先验证如下结构：公开 Runtime 仍由 Electron/CLI 通过 stdin/stdout 调用；Darwin 平台实现按操作建立临时用户级 `launchd` job，运行同一个 Runtime 二进制的私有 guard 入口，由 guard 启动 uv，并持有其回收边界。

guard 与 uv 的普通后代留在 launchd 管理的同一进程组。guard 不自行 `setsid`，不使用 `AbandonProcessGroup=true`；用户明确允许保留的游戏进程在 AUTO-MAS 对应启动边界显式脱离。Runtime 不通过后台常驻或登录启动项获取额外生命周期。

公开协议不增加事件或命令。guard 不创建公开 Emitter，也不向宿主 stdout 写第二套协议；控制、退出事实和两路日志经私有 IPC 交给唯一 Runtime 输出 owner。

私有 IPC 推荐使用有界 Unix domain socket 会话，必须包含创建代次、对端身份、owner 生命周期和启动确认。端点路径长度、0700/0600 权限、对象身份、关闭及遗留现场处理在首个原型中锁定；如果需要在系统临时目录建立独立 IPC 受管根，先在权威布局中登记其身份和清理范围。不得临时拼目录绕开 `config`。

启动必须先建立 owner 关系与回收边界，再允许 uv 执行业务。`UVRunner.Run` 与 `StartManaged` 共用经过验证的 Darwin 启动实现，不能在普通 uv 调用中保留先运行再尝试归组的窗口。

| 场景 | 要求 |
| --- | --- |
| 正常 shutdown | 原 HTTP close 和既有预算优先；超时后回收受管组，区分主进程强杀和残留后代回收 |
| Electron 退出或 stdin EOF | 公开 Runtime 按既有 C13 进入 shutdown |
| Runtime 被强杀 | guard 的 owner 会话断开；执行有界关闭与清理，随后退出临时 job |
| guard 被强杀 | 验证 launchd 的同组清理；公开 Runtime 失败收口，不继续宣告 running |
| uv 根退出、后代持管道 | 根退出通知不等待 EOF；清理后代后有界收口日志 reader |
| 重启 | 旧代完全回收后创建新代，避免 PID、PGID 和旧 IPC 复用误伤 |
| 显式脱离 | 仅业务明确允许的进程保留，普通 worker 仍在回收边界 |

用真实内核事件和确认屏障证明以上行为。launchd 只覆盖同进程组，并不等于不可逃逸的 Job Object；不能以一次进程列表快照证明所有未来后代都受管。GUI 宿主域、Actions 无桌面域、job 注册/卸载、启动失败及 guard 自身异常必须在原型中验证。若候选方案未满足安全条件，不静默退回普通 `Setpgid + kill`。

`Snapshot`、`WaitEmpty`、健康身份与 uv 根 PID 继续按业务树定义；私有 guard 不被误当成业务残留进程。确认空树与释放 job 的顺序需形成独立线性化证明。

### 4.6 uv、Python、依赖与中继

- 新增 `uv-aarch64-apple-darwin.tar.gz` 的官方固定 SHA-256、受限 tar/gzip 解压和版本实测；拒绝目录穿越、重复条目、链接及超量解压，保留镜像顺序和哈希校验。
- `uv`、venv `bin/python`、基解释器路径与探针目标按平台集中选择；Python JSON 清单中的 OS/架构字段映射单独测试。
- Python 版本仍由目标仓库指定，安装到 Runtime 的受管目录；不改成依赖用户预装 Python、Homebrew 或在线安装脚本。
- 实际依赖选择继续由 `uv sync --frozen` 决定。PEP 508 marker 和 wheel 规划按真实目标解释器、OS、架构及系统版本构造，覆盖 ARM64 与 universal2 标签。
- 锁规划不完整时明确标为不可估算，走已有逐源轮换路径；不能拿 Windows wheel 清单登记严格中继白名单或显示错误百分比。最终需要分别验收直接轮换、可精确规划时的中继、多源回退与取消。
- 保留 `UV_NO_CONFIG=1`、受控 `UV_*`、`PYTHON*` 隔离、回环 NO_PROXY 和 TLS 校验；环境键大小写规则按平台审查。
- `UVRunner` 仍是唯一 uv 执行入口。运行池只复用基础设施，Runtime 不接管插件或池 venv 的安装与删除。

## 5. GitHub Actions 验证与发行

### 5.1 工作流分工

| Job | 运行内容 | 证据 |
| --- | --- | --- |
| Windows 基线 | 原有格式、vet、build、test、漏洞检查；并发变更补完整 race | 既有行为未回退 |
| macOS 下限 ARM64 | 固定最低可用 Runner，原生 build/test/race、协议及系统 E2E | 当前最低系统上的实际运行 |
| macOS 前向 ARM64 | 固定下一档 Runner，执行相同关键场景 | 较新系统兼容 |
| 官方工具集成 | 固定 uv 资产和受管 Python，在独立受控网络 job 跑安装及离线复跑 | 工具链与网络真实可用 |
| 发行资产 smoke | 对最终签名后下载资产执行 version、doctor、完整最小闭环 | 发布物与测试构建一致 |

初期平台尚未可编译时，先用独立原型 job 验证系统机制；不对全仓测试标假绿或用 `continue-on-error` 掩盖必需能力失败。native job 记录 `go env`、机器架构、系统版本和 Runner image 信息，防止仅凭标签认定 ARM64 或最低版本。

Go、外部 action 和校验工具固定版本/完整提交；PR job 无发布密钥。公网依赖仅出现在显式集成 job，单元/组件使用临时根、本地 HTTPS smart-git、假 uv 与假后端。

macOS 使用 Runner 自带 Clang 和 PowerShell 7。cgo 构建时设置与本轮下限一致的 `MACOSX_DEPLOYMENT_TARGET`，并检查最终 Mach-O 的架构、部署版本和动态库依赖；不把环境变量本身当作二进制已兼容的证据。

### 5.2 原生验收矩阵

| 范围 | 必测事实 |
| --- | --- |
| 协议 | hello、严格 sequence、逐行 flush、恰好一次且最后的 result、warning 汇总；所有命令复用 contracttest |
| 目录 | 空格/中文/Unicode、深路径、系统别名、大小写敏感与不敏感 APFS、根目录拒绝、链接/硬链接/并发替换、根外哨兵零变化 |
| 锁 | 双 Runtime、backend/mutation/staging 组合、别名同锁、holder 被杀、锁文件替换和 PID 复用 |
| 状态 | 每个事务阶段的 child crash、旧/新/未知身份、ABA、条件删除、取消及错误副作用标志 |
| Git | HTTPS 浅克隆、alpha/正式分支、排除策略、暂存、版本校验、原子切换、升级/降级、中断恢复；执行位与受控链接 |
| 工具部署 | 资产和哈希错误、解压攻击、Python 精确版本、解释器链接、venv 完整性、依赖失败及离线缓存复用 |
| 网络 | 官方/镜像策略、测速、回环中继、未知总量、慢源与哈希错误、多源耗尽及取消 |
| 监督 | managed/development、健康/身份、动态端口、一次重启、二次失败、HTTP close、EOF、Runtime/guard 被杀、后代持管道与显式脱离 |
| 日志与遥测 | UTF-8/行界、完整文件与协议截断、128 MiB 上限、sink 失败收口、离线与关闭遥测零外发 |
| 资源收口 | 操作结束后无受管进程、临时 launchd job、IPC、锁 Lease 或未解释事务残留；用户数据保留 |

实施计划需将架构原测试矩阵逐行映射为共用、Darwin 替换或明确不适用的测试；Windows 专属断言保留在 Windows job，不通过删除原测试取得跨平台通过。

### 5.3 发布与 Electron 配套

建议新增 Darwin 原生可执行资产 `auto-mas-runtime-<tag>-darwin-arm64`，安装后文件名为 `auto-mas-runtime`。若提供归档包，归档与其中二进制的校验对象必须在清单中区分。Windows 既有资产名继续保留。

在 macOS 构建/签名 job 中完成 Developer ID 签名和适用的公证流程，签名后生成哈希、发布资产、下载复验，再同步 CNB。当前只筛 EXE、使用 Authenticode 或请求 SignPath 的步骤拆为 Windows 分支；不能让 Darwin 跳过校验后共用 Windows 成功标记。签名身份和凭据在正式发行任务中准备，不能把 ad-hoc 签名 smoke 宣称为用户发行验收。

Electron 配套需要按平台/架构选择 Runtime 名称和资产，设置执行权限，并将可变数据、受管仓库及可更新 Runtime 放到用户可写位置。已签名 `.app` 内的捆绑工具作为初始版本，不由现有 updater 直接覆盖包内文件。该项只调整 Runtime 接入，不承担业务前端或脚本改写。

## 6. 实施顺序与可独立验收的交付

以下工作包对应 T11.2~T11.9；编译准备允许先行，生产能力开放仍依赖 P0 的原生证明。逐步计划固定 TDD 测试名及暂存清单。

| 顺序 | 工作包 | 主要落点 | 通过条件 |
| --- | --- | --- | --- |
| P0 | 原生机制验证及最小 CI 原型 | `process`/`filesystem` 的隔离原型、Actions 设计 | launchd 生命周期与目录竞态有反例和通过证据；确认用户域、IPC、父子进程归属、FD 安全及必要 cgo 边界 |
| P1 | 编译边界与平台描述 | `config`、`doctor`、filesystem 公共类型、平台 stub | 原生 version 可用；未实现能力结构化失败；Windows 基线全绿 |
| P2 | 根能力、下载、日志、重命名与删除 | `filesystem`、`logging`、`mirror` | APFS 双大小写模式与攻击矩阵通过；外部适配不绕过 FD/身份边界 |
| P3 | 锁、状态、PID 和恢复 | `lock`、`state`、`cleanup` | 双实例冲突、holder crash、事务中断恢复、条件删除和 PID 复用通过 |
| P4 | Darwin 启动与监督边界 | `process`、`uv/runner`、`backend`、`health` | fake uv/backend 下完整生命周期、Runtime/guard 被杀、单次重启、日志收口及空树证明通过 |
| P5 | 官方 uv、Python、依赖与网络规划 | `uv`、`config`、`cli`、`mirror/relay` | 官方 ARM64 工具真实部署；锁定依赖、离线、镜像与进度/中继通过 |
| P6 | 命令全链路与故障矩阵 | `gitrepo`、`cli`、`backend`、contracttest | development 后 managed；初始化、暂存、升降级、修复/清理、取消及宿主退出闭环通过 |
| P7 | 发行与宿主接入 | release/CNB、AUTO-MAS Runtime 接入 | 最终签名资产 smoke、双侧哈希、用户可写目录及 Electron 端协议闭环通过 |

P0 先解决两项高风险假设。P1 之后每包按失败测试、最小实现、原生/Windows 回归推进；并发测试使用屏障、channel 和超时，增加指定用例 100 次与完整 race。P2/P3 的安全基础完成后才接真实受管目录变更，P4 不依赖公网即可验证监督。

每个工作包形成独立代码提交、独立审查与验收记录，修复独立提交；关键缺陷清零再进入依赖它的工作包。按既有 worktree 流程开展实现，保留无关本地报告和改动。完成设计草案不等于允许直接合并、推送、注册服务或发版。

## 7. 完成标准与当前缺口

完成首期 Runtime 支持，需要同时取得：最低可用 macOS ARM64 Runner 与前向 Runner 的全部必需结果、Windows 原标准门、实际官方工具与离线闭环、真实进程/文件系统故障证明，以及最终发行资产的运行证据。仅编译、只有新系统结果或只有 fake backend 都不能代替全部验收。

当前尚未取得 P0 的原生证据，因此本方案选择的是优先验证路线，不宣称 launchd、FD 或 advisory lock 已证明与 Windows 完全等价。最容易导致方案调整的事项是：非协作同用户目录替换、外部 uv 的绝对路径竞态、launchd 无桌面用户域和私有 IPC、显式脱离、guard 退出后的空树证明，以及 macOS 14 Runner 即将退役。

Intel 后续另行增加 `darwin/amd64` 工具制品、原生 Runner、依赖 wheel 与完整系统矩阵。当前双架构 go-git 编译证据可以复用作输入，但不能作为 Intel 整体支持完成的证据。
