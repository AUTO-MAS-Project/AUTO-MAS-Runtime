# T11.4 macOS 目录授权边界评审

状态：待用户裁决的设计提案，不修改当前生产契约。日期：2026-10-17。

## 已确认的差异

原生 run `39043093838` 在 macOS 14/15 ARM64 上通过 `TestRoot_PathReplacement`：
打开目录后把它重命名，`os.Root` 继续操作原 inode，而不是原词法位置。
同一轮在两种 APFS 大小写模式下通过链接拒绝/根内链接行为观察；这些结果只能说明 Root 的边界，不能证明 Runtime 的所有安全条件。

补充探针 `TestRoot_IdentityCheckDoesNotPinLocation` 将进一步固定这个顺序：

1. Runtime 打开 staging 目录 FD，并取得独占 flock。
2. 校验 FD 与原路径的设备/inode 一致，原路径确实位于 runtime 下。
3. 同用户独立进程把目录移入 data，未参与 Runtime 的 advisory lock 协议。
4. 继续使用原 FD 写入，观察写入是否落到 data 下的同一个目录；检查无关用户哨兵不变。

这是针对「身份预检 + Root + advisory lock 足够替代 Windows 禁止重命名句柄」的反例。
补充探针未取得原生结果前，不把它登记成已复现；即使复现，也不声称已经排除所有其他公开内核方案。

## 当前冻结要求

T11.1 §4.3 要求：根的位置或身份不能继续满足冻结边界时，拒绝进一步副作用；
无法证明与 Windows 安全语义等价时，变更、删除和自动修复保持不支持并先做设计评审。

目录 FD 固定对象身份；flock 协调协作方。两者都不能仅凭一次操作前/后的路径检查就提供原子的位置冻结。
因此不能靠补一轮检查、0700 权限或事后发现路径变化来宣布满足当前严格契约。

## 可选方向

| 项目 | A：维持当前严格要求 | B：明确采用 macOS 同 UID 信任边界 |
| --- | --- | --- |
| 同用户非协作移动/替换 | 必须提供等价强制隔离；未证明时保持不支持 | 不承诺强制隔离主动修改受管路径的同 UID 进程；能检测则中止，不承诺消除已在途操作的副作用 |
| 已打开 FD | 位置变化后不得继续产生副作用；目前候选方案没有证明 | 授权绑定设备/inode 与用途；沿原已授权对象操作，不把替换后的路径对象视为已授权 |
| 符号链接、硬链接、越界与用户数据 | 保留现有严格要求 | 仍实现 no-follow、设备/inode、普通文件/链接数、受控用途和数据分类门禁；不把路径预检当原子能力 |
| 普通多 Runtime 并发、崩溃恢复 | 既有锁与事务要求 | 同样保留，flock 与事务用于协作进程和故障恢复 |
| 工具的绝对路径参数 | 必须证明同用户替换期间零误操作 | 明确外部 uv/解释器等环境依赖同 UID 不主动篡改，叠加身份检查；不能声称具备 Windows 的重命名排他性 |
| 交付结果 | 未取得等价证明前不能开放核心部署/清理 | 用户批准并先修订权威文档后，可以继续完成实用的 macOS 控制面 |

建议 B，但必须由用户明确接受其保证范围。它改变的是 macOS 的同 UID 威胁边界，不能表述成与 Windows 完全等价。
Windows 契约、对业务用户数据的常规保护、跨进程事务、NDJSON v1 与 CLI 保持原有要求；Linux 暂不开放。

## 如果选择 B，实施前必须修改的文档

1. 架构设计「平台支持策略」第 4 条与 macOS 目录/进程范围，明确上述同 UID 边界。
2. T11.1 §4.2~4.3，区分能力身份保证与词法位置保证；记录外部 uv 路径的信任前提。
3. T11.4 的安全验收矩阵，继续验证链接、硬链接、未知对象、别名、状态身份和外部哨兵；把同 UID 主动移动的反例作为已知平台边界保留。
4. 受管数据与恢复文档中记录被移动对象的现场保护规则，不根据路径重建或猜测删除。

选择尚未确认时，相关生产能力继续返回 UNSUPPORTED_MODE。本提案不自行放宽契约。
