# T12.10 后端失败分组与诊断

## 范围

Sentry `AUTO-MAS-RUNTIME-5` 混合了多个后端失败码。离线探针确认普通失败没有独立 fingerprint，净化还会丢弃调用方设置的 fingerprint，并把所有栈帧的 `in_app` 清零。事件只记录 Runtime 版本，无法关联受管后端提交；清理失败优先时，最初失败的分类也会丢失。

本任务只修正诊断，不改变启动判定、错误优先级、取消、重启、清理顺序与错误码四元组。完整错误、日志、命令行和路径仍不上传。不访问生产 Sentry 验收。

## 分组与栈帧

可配置服务端分组规则，也可在 Runtime 净化出口生成 fingerprint。选择后者，使不同 Sentry 项目遵循相同规则，并由现有 fake transport 验证最终事件。

普通失败在 `BeforeSend` 内以净化后的 command、stage、code 生成固定前缀 fingerprint。缺失维度使用固定占位值；不复制传入 fingerprint，不引入版本、PID、路径或自由文本。内部错误与 panic 保留默认堆栈分组。

吸收 PR #32 独有的诊断意图：普通失败的 exception value 在固定文案后追加已校验错误码，便于 Sentry 列表识别，Message 和分组规则保持原约定。状态诊断放在实际读取失败的边界：`state.Store` 在解码时只接受稳定环境状态，非稳定 status 无法进入 bootstrap 的状态机构造分支。因此不照搬 #32 在该分支改成 INTERNAL_ERROR 的做法，而为读取到的 status 校验失败附带固定 reason `invalid_lifecycle_state`，保持 STATE_WRITE_FAILED、既有退出码与损坏文件不变。

栈帧按净化后的模块名识别 `main` 与本仓库模块前缀，恢复 `in_app`；第三方模块不属于应用栈。路径、源码和局部变量仍清空。

panic 栈的采集源从 Go 完整函数符号中提取包路径，填入既有 Module 字段，避免普通 SDK 栈与 panic 栈的模块信息不一致。复用版本源、命令执行与控制读取器三条真实 panic 路径验证采集结果，fake transport 验证最终应用栈分类。

## 后端诊断所有权

后端监督器在返回边界用可解包的错误包装附带 mode 和已经校验的后端 version、commit。结构化 `DiagnosticDetails()` 只供 CLI 观察器读取，不改变协议 result 的 details 或错误选择。尚未取得身份时不编造版本；development 不读取 Git 补身份。控制路径与无控制路径都接入，自动重启使用当次检查得到的身份。

CLI 继续使用既有最终错误分类，仅对 `backend supervise` 补充诊断。错误链同时保留启动/运行失败与清理失败时，记录至多两项 `failures`，以 phase 区分 primary、cleanup，保存稳定 code 和 stage。primary 取错误链中最具体的后端非清理分类，cleanup 保留既有优先分类；不上传 message 或 cause。

进程清理的 `terminationRequested` 通过可解包的专用诊断包装交给监督观察器，不加入共用的协议 details。它表示是否曾针对根进程请求强制终止，不是终止成功证明，也不代表已退出根进程的孤儿回收。清理失败和清理成功后的原始失败都能携带该事实；wrapper 不改变错误顺序，所有 warning、state、error、result 保持原契约。

受控后端意外退出后清理失败时，将退出分类作为清理错误后的原因保留。既有清理错误仍优先，控制流程仍直接失败，不触发重启；CLI 因而能生成 primary/cleanup 诊断，协议 details 不增加该摘要。

遥测 schema 仅新增协议 stage 与上述布尔字段；mode、version、commit、failures、phase、code 复用现有白名单。普通失败诊断仍经过 CLI 与 BeforeSend 二次净化，内部错误/panic 仍不携带 diagnostics。

## 验证

复用 Sentry fake transport 检查相同分类稳定归组、不同分类分离、恶意 fingerprint 丢弃、应用栈与第三方栈分类，以及原隐私限制。复用后端夹具验证已知身份、自然退出与强制终止事实；复用 CLI recorder 验证错误优先级和失败链摘要。先运行针对性红灯，再实现并复跑。最后执行 gofmt、vet、build、全仓测试、diff check 与依赖边界扫描。
