## T3.7 功能缺口修复

### Task 1 — F1 `help` 子命令自 T3.1 起不可用

**根因**：`root.go` 用 `SetHelpCommand` 注册了自定义 `help`，但 Cobra 的
`SetHelpCommand` 只写 `c.helpCommand` 字段，真正把它挂进子命令列表的是
`InitDefaultHelpCmd()`，而后者只在 `ExecuteC()` 内部调用。`Execute` 的预解析走
`probeRoot.Find(args)`，此时 `help` 还不在命令列表里 → `legacyArgs` 判定根命令
有子命令且有位置参数 → 报 `unknown command "help"`，exit 2。

**文件**：`internal/cli/cli.go`、`internal/cli/root_test.go`

**红灯**：
- `TestExecute_HelpCommandDelegatesToTarget` —— `help doctor` exit 0，stdout 含 doctor 用法；
- `TestExecute_HelpCommandBareShowsRootHelp` —— `help` exit 0，stdout 含根命令清单；
- `TestExecute_HelpCommandRoutesToStderrInNDJSON` —— `--output ndjson help doctor` 帮助文本进 stderr，stdout 为空。

**绿灯**：`newRoot` 在 `AddCommand` 之后调用 `InitDefaultHelpCmd()`。放在 `newRoot`
而非 `Execute`：同一行代码同时让预解析树与正式执行树的命令集合一致，直接消除 F7 指出的
「两棵树不等价」不变量缺口；Cobra 的 `InitDefaultHelpCmd` 内部先 `RemoveCommand` 再
`AddCommand`，与 `ExecuteC()` 的二次调用幂等。

**不回退**：`TestExecute_HelpCommandHiddenFromTree`（help 仍不出现在清单里）。

**验证**：`PKG=internal/cli`，`PATTERN=TestExecute_Help`。
**提交**：`fix: 恢复 help 子命令可用性 (T3.7)`

### Task 2 — F2 `repo.update-*` Junction 被静默忽略

**根因**：`enumerateRepoUpdates` 用 `!entry.IsDir()` 过滤，而 Windows 下 Junction
的 `DirEntry.IsDir()` 为 false（`ModeIrregular`），因此名为
`repo.update-<合法 ULID>` 的 Junction 被跳过：exit 0、无条目、无 warning。
这与 T3.6 F2 刚为 `__pycache__` 确立的失败关闭语义在同一文件里自相矛盾。

**文件**：`internal/cleanup/cleanup.go`、`internal/cleanup/cleanup_test.go`

**红灯**：
- `TestService_JunctionRepoUpdateRecordedAsFailed` —— 名为 `repo.update-<ULID>` 的
  Junction 产生 `repo-update-invalid-<n>` failed 条目，`details.code=GIT_REPO_CLEANUP_FAILED`，
  命令失败（exit 40 语义），Junction 与其目标均原封不动；
- `TestService_JunctionRepoUpdateNotFollowed` —— 不进入 Junction 目标目录。

**绿灯**：抽私有 `isLinkDirEntry(entry fs.DirEntry) bool`（`__pycache__` 分支与
`repo.update-*` 分支共用，消除第三次重复），`enumerateRepoUpdates` 在名称前缀命中后
先判链接：命中即记 failed 条目并 `continue`。

**不回退**：`TestService_JunctionPycacheRecordedAsFailed`、`TestService_JunctionPycacheNotFollowed`。

**验证**：`PKG=internal/cleanup`，`PATTERN=TestService_Junction`。
**提交**：`fix: repo.update-* 链接目录失败关闭 (T3.7)`

### Task 3 — F3 doctor 把 `missing` 显示成 `succeeded`

**根因**：`emitCheck` 只有 `StatusError → ProgressFailed`，`StatusOK` 与
`StatusMissing` 都映射到 `ProgressSucceeded`。human 是默认模式且 human renderer
不渲染 `details`，所以 `result.details.checks` 这张唯一的结构化检查表在默认模式下
完全不可见，用户只能靠中文 message 后缀分辨——正是架构 605 行 / AGENTS 8.11 禁止
依赖的东西。

**文件**：`internal/doctor/doctor.go`、`internal/doctor/doctor_test.go`

**红灯**：
- `TestService_MissingCheckEmitsSkippedProgress` —— `missing` 检查项发射
  `ProgressSkipped` 而非 `ProgressSucceeded`；
- `TestService_EmitsSummaryProgress` —— 全部检查项之后追加一条汇总 progress，
  文本包含 total/ok/missing/error 计数；健康夹具下汇总状态为 succeeded。

**绿灯**：`progressForStatus(Status) protocol.ProgressStatus` 私有映射
（ok→succeeded、missing→skipped、error→failed，均在冻结全集内）；`Run` 在循环
结束后发射一条汇总 progress。

**契约影响**：`ProgressSkipped` 已在冻结全集内，不新增值；设计 §11
「running → succeeded/failed」补一条修订注记。

**验证**：`PKG=internal/doctor`，`PATTERN=TestService_(MissingCheck|EmitsSummary)`。
**提交**：`fix: doctor 缺失项不再显示为成功 (T3.7)`

### Task 4 — F4 cleanup 对不存在的 app-root 返回可重试错误

**根因**：`lock.NewSet` 的 `openRootIdentity` 打不开 app-root 目录句柄 →
`mapLockError` 兜底成 `MUTEX_OPERATION_FAILED`（exit 70、`retryable=true`、
`remediation=[retry,run-doctor]`）。真实原因是 app-root 不存在，重试永远不会成功，
`retryable=true` 会驱动 Electron 无意义重试循环。

**决策**（已获用户确认）：映射为 `INVALID_ARGUMENT`（exit 2、`retryable=false`、
`remediation=[run-doctor]`）。该错误码已在冻结全集内，不改架构文档错误码表。

**文件**：`internal/cleanup/cleanup.go`、`internal/cleanup/cleanup_test.go`

**红灯**：
- `TestService_MissingAppRootRejectedAsInvalidArgument` —— app-root 不存在时
  `Code()==INVALID_ARGUMENT`，且不创建任何目录；
- `TestService_AppRootNotDirectoryRejectedAsInvalidArgument` —— app-root 是文件时同上。

**绿灯**：`Run` 在 `lock.NewSet` 之前做只读前置校验（`os.Stat` + `IsDir`），
只有 `fs.ErrNotExist` 与「存在但非目录」两种情形映射为 `INVALID_ARGUMENT`；
其余 stat 错误保持既有 `MUTEX_OPERATION_FAILED` 路径不变。

**验证**：`PKG=internal/cleanup`，`PATTERN=TestService_(MissingAppRoot|AppRootNotDirectory)`。
**提交**：`fix: cleanup 缺失 app-root 映射参数错误 (T3.7)`

### Task 6 — F6 stdout 所有权扫描正则永远漏报

**根因**：门禁正则 `fmt\.F?Print` 大小写敏感，而 `fmt.Fprintf` 第 5 个字符是小写
`p`，永不匹配。实测全仓扫描 4 处命中，`internal/cli/cli.go:181`、
`internal/cli/audit.go:26` 两处 `fmt.Fprintf` 都没被命中。`os\.Stdout` 那一支仍能
兜住真实风险，但这条门禁给出的覆盖感是假的。

**文件**：`AGENTS.md`（§8.9）、`doc/代码审查清单.md`

**红灯**：无（纯文档/门禁修正，Go 代码不变）。验证方式是新旧正则命中数对比：
旧 4 条、新 6 条，新增的两条正是上面两处 `fmt.Fprintf`。

**绿灯**：正则改为 `os\.Stdout|fmt\.F?[Pp]rint|log\.[Pp]rint|json\.NewEncoder`。

**提交**：`docs: 修正 stdout 所有权扫描正则 (T3.7)`

### Task 7 — F7 `Execute` 手工复刻 Cobra 分发

`cli.go:105-168` 手工复刻了 Cobra 的分发流程：建两棵树 → `Find` →
`InitDefaultHelpFlag` → `ParseFlags` → 预校验 → help 路由 → `Runnable` 判定 →
再建树 → `ExecuteContext`。三条注释都在解释 Cobra 内部实现细节。这是
T3.5 F5 → T3.6 F1 → T3.6 F3 三轮补丁叠出来的，F1 就是它的直接产物：预解析树与
执行树的命令集合不一致，却没有任何不变量或测试守住「两棵树必须等价」。

**做法**：
1. ~~`newRoot` 内部调用 `InitDefaultHelpCmd()`~~ —— 已在 T3.7 Task 1 完成，两棵树已同构；
2. 抽 `type invocation struct { target *cobra.Command; mode outputMode; help bool }`
   与 `resolveInvocation(probeRoot *cobra.Command, args []string) (invocation, error)`；
3. `Execute` 收敛为「解析 → 分派 → 收口」三段。

**新增测试**：`TestResolveInvocation`（表驱动，用例至少覆盖 bare / `--help` /
`help <cmd>` / 组命令+未知子命令 / 叶子命令+多余参数 / 未知 flag / 非法 output /
协议不匹配）。

**提交**：`refactor: 收敛 Execute 命令分发 (T3.8)`
