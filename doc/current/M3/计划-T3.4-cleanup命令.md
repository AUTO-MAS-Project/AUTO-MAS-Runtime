## 3. RED 测试与预期失败原因

先落测试：

1. `internal/cleanup` 包不存在 → 编译失败；
2. 正常清理：未实现删除 → 目标目录仍在，断言失败；
3. 保护名单：未实现保护 → 用户数据被删/断言失败（测试本身先证明
   filesystem 拒绝，再断言 cleanup 不调用受保护目标）；
4. Junction：未实现 → 错误地删除或跟随，断言失败；
5. repo.update 匹配：未实现状态读取/身份校验 → 误删或拒绝，断言失败；
6. 锁冲突：未获取 mutation 锁 → 冲突场景没有返回稳定错误，断言失败；
7. 契约测试：runner 未接入 → 编译/断言失败。

红灯原因均为「目标行为不存在」，符合 TDD 要求。

## 4. 最小 GREEN 实现

1. `cleanup.Service{layout, auditor}`；`Run(ctx, emitter)`：
   - `lock.NewSet` → `AcquireMutation`（冲突原样返回；ctx 取消 →
     `OPERATION_CANCELLED`）→ `defer lease.Close()` + `set.Close()`；
   - `filesystem.New(ctx, layout, auditor)`；
   - 按 `plan.go` 枚举条目并逐个执行（progress running → RemoveTree →
     succeeded/skipped/failed）；
   - 汇总 Report；任一条目 failed → 返回 `GIT_REPO_CLEANUP_FAILED` 错误
     （details 含非敏感条目清单与计数）；
2. 可删目标与 DeleteKind 一一对应（uv-cache/download-temp/python-cache/
   repo-update-*）；`DeletePythonCache` 先对候选目录做
   `filesystem.Canonicalize` 验证（拒绝 Junction/Reparse），再 RemoveTree；
3. repo.update-*：目录名 → `config.RepoUpdateDir` 精确校验；`state.Store`
   读 update 事务；`OperationID` 不匹配或事务缺失 → failed（失败关闭）；
   匹配后用 `state.InspectTransaction` + PID 探针 + 对端恒未持有适配器
   分类：stale 删除，inconsistent/unknown failed；
4. 审计：cli 的 stderr Auditor 记录 started/finished；测试注入内存 auditor；
5. result.details 只含条目 ID、状态、计数、简短原因，不含绝对路径。

1. 所有递归删除只经 filesystem.Operator；无 `os.RemoveAll` 旁路；

   与诊断日志在测试中证明完好；

7. 结果与审计不泄漏敏感路径；
8. 不创建/移动用户数据；空根幂等；
9. context 贯通 filesystem/lock/state；
10. 未引入新生产依赖。
