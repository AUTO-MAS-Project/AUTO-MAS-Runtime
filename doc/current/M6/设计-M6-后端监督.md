# M6 设计：后端进程监督

## 1. 目标与边界

M6 在 Windows 上实现唯一的长驻后端监督路径：Runtime 以挂起状态创建 `uv run`，在恢复
主线程前把 uv 加入启用 `KILL_ON_JOB_CLOSE` 的 Job Object，转发并落盘 stdout/stderr，
按固定地址完成健康与身份检查，处理 stdin 控制、一次自动重启和确定性关闭。

Runtime 不直接运行 Python/pip，不通过 Shell 拼接命令，不按进程名或全局 PID 杀进程，
不修改 Python 后端业务接口。managed 模式只消费 M4/M5 已验证的仓库和环境；development
模式只监督开发者显式指定的现有源码与 `.venv`，不执行同步、修复、清理或任何仓库写入。

一次 `backend supervise` 只拥有一个 `operationId`、一个 `protocol.Emitter` 和一个最终
`result`。Python 输出先完整写入 Runtime 轮转日志，再以有界 `log` 事件发送；Runtime
自身诊断只写 stderr。发送最终 `result` 后不得再产生协议事件。

## 2. 组件与依赖方向

```text
cli/backend supervise
  └─ backend.Supervisor                 生命周期唯一线性化域
       ├─ lock backend Mutex            整个监督周期持有
       ├─ state backend transaction     诊断与崩溃恢复
       ├─ gitrepo/state preflight       managed revision 门禁
       ├─ uv.ManagedStarter             唯一 uv 长驻入口
       │    └─ process.StartManaged     Windows 挂起创建与 Job/管道
       ├─ health.Checker                HTTP、身份、Job 存活与连续成功
       ├─ logging.Logger                完整原始日志和轮转
       └─ protocol.ControlReader        cancel/shutdown/status
```

依赖保持单向：`cli -> backend -> health/uv/state/lock/logging/protocol`，
`uv -> process`。`backend` 不导入 `os/exec`，`process` 不解释 health 或协议错误，
`health` 不创建进程，业务包不直接持有 stdout。

## 3. Windows 进程模型

`process.StartManaged(ctx, StartSpec)` 接受可执行文件、参数数组、工作目录、完整环境和
流记录 sink。Windows 实现以参数数组调用 `os.StartProcess`，并在 `SysProcAttr.CreationFlags`
设置 `CREATE_SUSPENDED | CREATE_NO_WINDOW`：

1. 创建带 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 的 Job；
2. 把 child stdin 显式绑定 `os.DevNull`，绝不继承 Runtime 的 NDJSON 控制 stdin；建立仅子端
   可继承的 stdout/stderr 管道；
3. 以挂起状态创建 uv；
4. 通过 Go 1.26 `os.Process.WithHandle` 取得受保证有效的 process handle 并完成
   `AssignProcessToJobObject`；
5. 进程仍挂起时用 `x/sys/windows` 的 Toolhelp thread snapshot 找到该 PID 唯一初始线程，
   `OpenThread(THREAD_SUSPEND_RESUME)` 后才 `ResumeThread`；线程 handle 只由 starter 持有并
   在 Resume 成功或失败后立即关闭，不提取或猜测 `os.Process` 内部 handle；
6. parent 在 Start 返回后关闭 DevNull 与两个 child pipe ends；Toolhelp snapshot 与 thread
   handle 在每条成功/失败路径关闭；任一步失败都终止尚未恢复的进程并关闭全部 Job、
   `os.Process`、DevNull、snapshot、线程和管道句柄；
7. 非 Windows 或 Job 能力不可用时失败关闭，不降级为普通 `exec.Command`。

命令行只在 Windows API 适配层由 Go 参数数组使用 Windows quoting 规则编码，不经过 Shell。
uv 的长驻入口固定执行：

```text
uv run --project <repo> --no-sync main.py
```

`ManagedProcess` 暴露根 uv PID、只关闭一次的 `Exited()` 根进程通知、幂等 `Wait(ctx)`、
Job 树快照、`Terminate`、`WaitEmpty` 和 `Close`。内部 root waiter 在 uv 退出时先发布
`Exited()`，不等待可能仍被后代持有的 pipe；`Wait(ctx)` 缓存最终结果，并且必须等待 OS
进程和两路 reader 全部结束、提交无换行尾部并返回流 sink 错误。sink 接收不可变
`StreamRecord`：stream、lineId、fragment、最多 64 KiB 的完整 UTF-8 replacement 文本片段、
endOfLine；最后一个片段另带包含 marker 的有界事件文本、truncated 和 originalBytes。sink 首次失败
时记录原错、终止 Job 并继续 drain 两路管道到 EOF，避免子进程阻塞和 goroutine 泄漏。

starter 只创建一个 ctx owner goroutine：运行中 ctx 取消时调用 Job `Terminate`，随后仍由
同一个幂等 `Wait(ctx)` join 进程与两路 reader；Job 查询/关闭使用有界
`context.WithTimeout(context.WithoutCancel(ctx), ...)` 收口。若没有更高优先级的 sink、Job
或输出错误，返回链必须保留 `context.Canceled`/`DeadlineExceeded` 供上层映射取消。

Job 树快照包含 PID、parent PID 与可执行文件身份；根 uv PID 必须存在，并且至少一个位于
同一 Job 的后代可验证为当前 project venv/受管 Python 的解释器。这里不要求 Python 必须是
uv 的直接子进程，允许 uv 的合法包装层。协议 `details.pid` 固定为 Runtime 直接监督且持有
句柄的 uv 根 PID；Python PID 只进入本地诊断，不新增 v1 字段。Electron 不直接终止该 PID。

资源顺序固定为：优雅等待成功时 `Wait -> WaitEmpty -> Close`；强制收口时
`Terminate -> Wait -> WaitEmpty -> Close`。`WaitEmpty` 必须在 Job handle 仍有效时通过
`QueryInformationJobObject` 证明成员为零；不得 Close 后再查询。若 Terminate/WaitEmpty
失败，仍在独立 cleanup context 中尝试 Close 触发 KILL_ON_JOB_CLOSE，但由于无法证明空树，
最终必须失败为 `BACKEND_SHUTDOWN_FAILED`，不能发 force warning 成功。

stdout/stderr 分别并发 drain，并在进程退出后 flush 尾行。两路内容先用 UTF-8 replacement
把非法字节替换为 U+FFFD；完整的规范化文本逐行写入现有 JSONL 轮转 Logger，不丢行、不做
协议长度截断，但不承诺非法原始字节的 byte-exact 保存。协议事件 `message` 最多 1 MiB，
超出时先为稳定的 `...[truncated]` 标记预留字节，再在合法 UTF-8 边界截取前缀，标记计入
1 MiB 上限。reader 使用增量 UTF-8 decoder，只保留最多 64 KiB 当前日志片段、1 MiB 事件
前缀和不超过 3 bytes 的未完成 code point；超长物理行通过带 lineId/fragment/endOfLine 的
多条 Logger record 完整保存，禁止为完整行做无界内存分配。截断不能终止后端。
Logger/Emitter 对并发流各自串行化，保留每个 stream 的顺序。

M5 的一次性 `UVRunner.Run` 保持原接口；M6 从现有 runner 提取唯一的 resolved options、
参数与环境构造器，新增长驻 `UVRunner.StartManaged`，后者只能把同一构造结果交给
`process.StartManaged`。`backend` 既不能拼 uv 路径/环境，也不能把生命周期句柄塞入一次性
结果。环境构造器按 Windows 大小写不敏感键去重，先移除宿主全部 `UV_*` 和
`AUTO_MAS_UV_EXE/AUTO_MAS_RUNTIME_PROTOCOL/AUTO_MAS_EXPECTED_VERSION/
AUTO_MAS_EXPECTED_COMMIT/AUTO_MAS_SUPERVISED`，再各注入唯一受控值；development 不注入的
expected 两项也必须从宿主移除。

## 4. 健康检查

地址固定为 `http://127.0.0.1:36163/api/core/health`，HTTP transport 禁用代理。默认总预算
60 秒、间隔 500 毫秒、单请求 2 秒、连续成功 2 次；全部通过 `Clock.Now`、
`Clock.NewTimer` 与 options 注入，不新增 CLI timeout 参数。响应 body 以 `io.LimitReader`
限制为 64 KiB，并始终关闭；实现读取至 64 KiB+1 后判断超限，超限为
`BACKEND_HEALTH_INVALID`。

managed 的一次成功必须同时满足九项：HTTP 200、`ready=true`、
`backgroundStatus=ready`、`backgroundError` 为 `null` 或空字符串、protocol 精确等于 1、
version 精确等于目标完整版本、commit 精确等于 40 位小写受管 HEAD、uv/Python 均仍在
同一 Job、上述事实连续成功两次。development 使用同一检查，只跳过 version/commit 比较。

- 连接失败以及 `starting`/`running` 继续轮询，并重置连续成功计数；
- 有 HTTP 响应但非 200、坏 JSON、`ready/backgroundStatus/backgroundError` 缺失或类型
  错误、未知状态立即 `BACKEND_HEALTH_INVALID`；
- managed 的 `protocol/version/commit` 任一缺失、类型错误或不匹配为
  `BACKEND_IDENTITY_MISMATCH`；development 只要求 protocol 字段存在、为 JSON 整数且与
  v1 兼容，不读取或比较 version/commit；
- `failed` 或非空 `backgroundError` 立即 `BACKEND_HEALTH_INVALID`；本地 cancel/shutdown
  latch 必须先于 health body 求值：本地 cancel 返回 `OPERATION_CANCELLED`，本地 shutdown
  进入关闭流程；只有未收到本地控制时后端自报 `cancelled` 才是异常 health，映射
  `BACKEND_HEALTH_INVALID`；
- 进程先退出为 `BACKEND_EXITED_BEFORE_READY`；总预算耗尽为
  `BACKEND_HEALTH_TIMEOUT`。

## 5. managed 前置与启动

CLI 必须显式提供 `--mode managed` 或 `--mode development`。缺少 mode 为
`INVALID_ARGUMENT`，未知 mode 为 `UNSUPPORTED_MODE`；协议 v1 不提供 `--port`。

managed 在创建 Job 或进程前完成：

1. 规范化 app-root 并取得 backend Mutex；冲突立即 `BACKEND_ALREADY_RUNNING`；
2. 在互斥保护下处理 stale backend transaction；
3. 验证受管 `repo` 目录及普通、non-reparse 的 `main.py`；
4. 读取稳定 `environment.json`，状态必须为 `ready_to_start`；
5. 从已验证 active repo 读取版本和 40 位小写 HEAD；
6. `lastSuccessful.version/commit` 分别与 active revision 逐字相等；
7. 校验受管 uv，并在 spawn 前最后重读环境/revision 关键事实。

入口缺失为 `BACKEND_ENTRY_NOT_FOUND`。环境缺失、不可读、broken、非 ready 或 revision
不一致统一为 `ENVIRONMENT_BROKEN`，details 保留 field/state/reason，且 starter 调用次数
必须为零。backend Mutex 从监督开始一直持有到 Job 清空、backend transaction 条件删除和
日志收口完成；冲突为 `BACKEND_ALREADY_RUNNING`。

managed 注入固定环境：

```text
AUTO_MAS_UV_EXE=<已验证规范绝对路径>
AUTO_MAS_RUNTIME_PROTOCOL=1
AUTO_MAS_EXPECTED_VERSION=<完整目标版本>
AUTO_MAS_EXPECTED_COMMIT=<40 位小写 HEAD>
AUTO_MAS_SUPERVISED=1
```

宿主同名变量和未批准的 `UV_*` 变量不得泄漏。启动成功发
`backend.spawn/starting_backend`，健康成功发 `backend.run/running`，details 至少包含
uv 根 `pid`、固定 `baseUrl` 和 `logPath`。就绪前退出或检查失败先等待管道 drain 并
flush 日志，再发 `backend.cleanup/backend_failed`、主 `error`、唯一失败 `result`。

## 6. 控制、关闭与一次重启

长驻 CLI 使用独立控制 session，不复用只支持一次性 cancel 的 helper。ControlReader 接受
`cancel`、`shutdown`、`status`；hello capability 保持现有白名单
`stdin.cancel/state.v1/log.stream`，不擅自新增 capability 字面量。

- `status` action 只把 commandId 投递给 Supervisor loop；loop 通过同一 mutex 下的
  `Snapshot()` 原子复制 stage/status/details，随后在锁外发只读 `state` 并回显
  `controlCommandId`，不共享可变 map、不产生额外 result；
- ControlReader action 在其内部 mutex 下只把不可变命令放入有界 FIFO mailbox，必要时使用
  control context 做背压等待，不执行 HTTP/Job；Supervisor loop 按接收顺序消费。mailbox
  不使用会丢命令的 `select default`。control context 由 Supervisor 独立持有；收口时必须先
  cancel 它以唤醒等待中的 producer，再调用需要 ControlReader mutex 的 `StopAccepting`，
  禁止 Stop 与满 mailbox send 形成同锁死锁；
- 首个有效 `shutdown` 停止接受新命令；cancel 使用幂等 latch，不关闭 reader，后续 status
  和重复 cancel 仍可路由，直到 Supervisor 进入最终 reader 收口；
- shutdown 进入 `stopping_backend`，POST 固定 close 地址并等待优雅退出；
- HTTP 失败、拒绝或超时后终止/关闭自己持有的 Job；确认空树才发
  `BACKEND_FORCE_TERMINATED` warning，最终仍为 `OK/stopped`；
- 无法确认空树为 `BACKEND_SHUTDOWN_FAILED/backend_failed`；
- cancel 同样必须清空进程树，但最终为 `OPERATION_CANCELLED/cancelled`、退出码 130；
- backend transaction、Mutex 或日志收口失败保留实际结构化错误，不用 force warning
  掩盖。

CLI goroutine 是 ControlReader 的唯一 owner。Supervisor 终止时调用 `StopAccepting`，关闭
可关闭且非真实 `os.Stdin` 的 reader，并最多等待 1 秒 join；保留 `Run` 的首个 read/handler
错误以及最后一个已接受 commandId。控制基础设施错误优先于业务错误并映射
`INTERNAL_ERROR`，协议写失败仍以 `OUTPUT_WRITE_FAILED` 最高优先。join 超时不能遗留由
Runtime 自己创建的 pipe/goroutine owner。

cancel 与 shutdown 共用 first-wins 的 terminal-control latch：最先被 FIFO 接受的终止命令
决定最终语义和 `controlCommandId`，后续不同 commandId 的 cancel/shutdown 幂等且不得覆盖；
每个 status commandId 都必须各返回一次快照。Supervisor 在健康、等待和 restart timer 期间
始终 select mailbox，不能用同步长调用饿死控制队列。

首次进入 running 后意外退出：flush 第一次日志，进入 `restarting` 并立即消耗唯一预算，
通过可注入 timer 等待 2 秒，再执行当前模式的完整只读 preflight：managed 重读
environment/active revision，development 只重验显式 repo、普通入口/pyproject、现有
.venv 和受管 uv，绝不读取 environment.json。重启尝试在
再次 running 前失败统一 `BACKEND_RESTART_FAILED`；重启已经再次 running 后第二次意外
退出为 `BACKEND_EXITED_UNEXPECTEDLY`，不得第三次 spawn。主动 shutdown/cancel 永不消耗
或触发重启。

事件顺序固定为：

```text
首次启动:   hello -> state(starting_backend) -> log* -> state(running)
首次崩溃:   log tail -> state(restarting) -> log* -> state(running)
失败收口:   log tail -> state(backend_failed) -> error -> result
正常关闭:   state(stopping_backend) -> log tail -> state(stopped) -> result
```

## 7. development 边界

development 必须显式 `--repo`，接受相对输入但立即规范化为存在的绝对目录；检查普通
`main.py`、普通 `pyproject.toml`、已有且 non-reparse 的 `.venv` 目录和受管 uv。它不要求 app-root 下的
managed repo、发布分支、清洁工作区、版本/HEAD、`.python-version`、`uv.lock`、managed
venv 或持久化环境状态。

在创建 Logger/StateFiles 或其他目录前，必须验证规范化 app-root 不是 development repo
自身或其后代；否则 Runtime 的 `logs/runtime`、`runtime-state` 等写入会落进源码目录，立即以
`INVALID_ARGUMENT/backend.spawn`（details.reason=`runtime_root_inside_development_repo`）
零副作用拒绝。repo 位于 app-root 的某个子目录可以接受，但后续所有副作用仍只能落在 repo
外的 Runtime 专用路径。

`UV_PROJECT_ENVIRONMENT=<repo>/.venv`，只注入 protocol、supervised 和 uv 路径，不注入
expected version/commit，并显式移除宿主遗留的这两个变量。监督、健康、日志、关闭和一次
重启规则与 managed 相同。整个流程不得创建、删除、移动或改写 repo 内任何文件，测试以前
后文件哈希、目录位和条目清单证明这一点。

development 错误映射固定为：缺/非法 `--repo` 为 `INVALID_ARGUMENT/backend.spawn`；
源码允许位于 app-root 外，遇 reparse/身份不安全才为 `UNSAFE_REPARSE_POINT/backend.spawn`；缺少
main.py 为 `BACKEND_ENTRY_NOT_FOUND/backend.spawn`；缺少/非普通 pyproject 或缺少/不安全
.venv 为 `ENVIRONMENT_BROKEN/backend.spawn` 并带 field/reason；受管 uv 缺失或版本错误沿用
对应 `UV_*` code；CreateProcess/Job 失败为 `BACKEND_SPAWN_FAILED/backend.spawn`。

## 8. 状态与恢复

生命周期严格使用：

```text
ready_to_start -> starting_backend -> running -> stopping_backend -> stopped
running -> restarting -> running | backend_failed
starting_backend/restarting -> stopping_backend | backend_failed
stopping_backend -> stopped | backend_failed
```

development 也构造进程内状态机，但不读取或写入 environment 稳定状态。`backend.json`
记录 operationId、`backend supervise`、Runtime supervisor 的 `os.Getpid()`、startedAt、
backend.* stage；managed 另记录 targetVersion，development 的 targetVersion 为空。child
PID 只写事件/日志诊断，不改变 transaction owner 语义。文件存在不代表活跃。

启动先取得 backend Mutex，再在 exclusive gate 下用现有 transaction inspection 处理 stale
候选；acquire 已排除其他 Mutex owner，inspection probe 必须像 M5 一样把“当前进程持有的
本次 backend lease”视为 free，避免把自身误判 active。旧 transaction owner PID 仍活但
Mutex 已由本次 acquire 证明此前不占用时属于 inconsistent/失败关闭，PID reuse 不单独构成
active。身份不明则失败关闭。终态后条件
删除自己的 transaction，不删除其他 operation 的文件。

## 9. 错误与结果

所有错误四元组使用 `protocol.Lookup` 冻结值。后端失败 result 的 status 为
`backend_failed`，正常 shutdown 为 `stopped`，cancel 为 `cancelled`；不能套用通用
`failed` 状态。失败 details 统一包含可用的 `logPath`，并按事实附加 pid、exitCode、
health reason 或 cleanup reason。warning 进入 result 的 warnings ledger，最终 result 唯一且
最后。

错误 stage 与收口优先级固定如下：

| 事实 | code | stage |
| --- | --- | --- |
| 入口/环境/创建进程失败 | 对应 `BACKEND_ENTRY_NOT_FOUND`、`ENVIRONMENT_BROKEN`、`BACKEND_SPAWN_FAILED` | `backend.spawn` |
| 就绪前退出/health/身份失败 | 对应 `BACKEND_EXITED_BEFORE_READY`、`BACKEND_HEALTH_*`、`BACKEND_IDENTITY_MISMATCH` | `backend.health` |
| 重启未再次 running / 第二次 running 后退出 | `BACKEND_RESTART_FAILED` / `BACKEND_EXITED_UNEXPECTEDLY` | `backend.restart` / `backend.run` |
| HTTP/Job 无法确认清理 | `BACKEND_SHUTDOWN_FAILED` | `backend.cleanup` |
| transaction 状态写/条件删除失败 | `STATE_WRITE_FAILED` | `backend.cleanup` |
| Mutex 操作或 release 失败 | `MUTEX_OPERATION_FAILED` | `backend.cleanup` |
| Logger 文件/stderr sink 写入或关闭失败 | `INTERNAL_ERROR`（details.sink=`runtime_log`） | 当前 backend stage 或 `backend.cleanup` |
| ControlReader/read/join 基础设施失败 | `INTERNAL_ERROR` | 当前 backend stage |
| Emitter/renderer 输出失败 | `OUTPUT_WRITE_FAILED` | 当前 backend stage |

`OUTPUT_WRITE_FAILED` 最高优先，其次控制基础设施；已发生的 state/mutex/Job/log 收口事实不被
普通 context 取消覆盖。所有清理使用 `context.WithTimeout(context.WithoutCancel(ctx), ... )`
的有界独立 context，组合 error 保留全部底层原因，最终 result 复述所选主错误四元组。

## 10. 验收原则

每个 T6.x 严格红灯、最小绿灯、定向重复、race、全仓门、diff/staged scope、规格审查、
代码质量审查、Critical/Important 清零后复审。使用 36163 的跨包测试必须取得同一个
Windows 测试命名 Mutex；fixture 自测优先使用可配置临时端口，禁止仅靠端口预检规避
TOCTOU。测试不使用
`time.Sleep` 做同步。Windows E2E 必须证明事件顺序、完整日志、Job 树、Mutex、管道句柄和
backend transaction 都无残留；非 Windows 单测不能替代 Windows 证据。
