# T9.5 beta.4 development 黑盒回归修复设计

## 1. 背景与问题

`v0.1.0-beta.4` 在纯 development app root（不存在受管 `runtime/repo`）上执行
`backend supervise --mode development --repo <repo>` 时，固定版本 uv 已存在且直接执行正常，
Runtime 仍在 `backend.spawn` 返回 `UV_EXEC_FAILED`。失败只产生 `hello/error/result`，details
为空。

根因是 development 预检虽然跳过受管仓库检查，却让 `uv --version` 继续继承受管
`runtime/repo` 作为工作目录。Windows `CreateProcess` 在该目录不存在时先于 uv 启动失败。

## 2. 目标与边界

- development 的 uv 版本预检必须以显式源码目录和既有 `.venv` 为路径上下文；
- 仍使用 app root 内固定版本 `uv.exe`、受管 Python/cache 目录和既有 Job 监督；
- 不创建、同步或修改源码目录，不放宽 C5 的 `main.py`、`pyproject.toml`、`.venv` 身份检查；
- managed 模式继续使用受管 repo/venv 上下文；
- uv 创建失败必须保留稳定的 `operation`、路径上下文和 Windows 错误码，不回显外部输出或完整宿主环境。

本任务不改变 NDJSON 字段、错误码、stage、状态、固定端口、健康身份或关闭契约。

## 3. API 与错误语义

backend 消费方的 uv 依赖新增显式预检选项，调用方必须传入本次模式的 `ProjectDir` 与
`ProjectEnvDir`。生产 adapter 将选项传给唯一的 `UVRunner` 版本检查入口。

uv 启动前错误 details 只包含稳定白名单：

- `operation`：固定为 `start`；
- `projectDir`、`projectEnvDir`、`pythonInstallDir`、`cacheDir`；
- 可取得时包含 `windowsError` 数值。

backend 保留 uv 的 `UV_EXEC_FAILED` 四元组；成功启动后的 health/cleanup 失败继续按 M6 既有
契约映射。

## 4. 验证策略

1. 先用缺少受管 repo 的 app root 写红灯，证明旧实现仍从错误 cwd 运行预检；
2. 单元测试覆盖 development/managed 两种预检上下文和稳定 diagnostics；
3. 官方 uv 0.12.3 + 真实受管 Python/venv 的 Windows 集成测试覆盖 health 连续两次成功、
   status、shutdown、环境清洗、源码 SHA-256 快照不变和进程树清理；
4. 覆盖终止、shutdown、health 失败的清理路径；
5. 执行定向 100 轮、全仓标准门和完整 race detector。
