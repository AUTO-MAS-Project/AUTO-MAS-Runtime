## 决策总览

| 编号 | 事项 | v1 结论 |
| --- | --- | --- |
| C1 | 后端端口 | 固定 `36163`，不提供端口参数或端口环境变量 |
| C2 | 身份注入 | 使用 `AUTO_MAS_RUNTIME_PROTOCOL`、`AUTO_MAS_EXPECTED_VERSION`、`AUTO_MAS_EXPECTED_COMMIT`，后端回显 Runtime 注入值 |

| C4 | 受监督标记 | 固定为 `AUTO_MAS_SUPERVISED=1` |
| C5 | development 依赖检查 | 只保留启动与协议安全所需检查，跳过 managed 工作区、版本、锁文件和环境状态门禁 |

## C1：固定后端端口与地址

协议 v1 固定使用 TCP 端口 `36163`。Runtime CLI 不提供 `--port`，也不注入端口环境变量。

Runtime 使用以下规范地址：

| 用途 | 地址 |
| --- | --- |
| 健康检查 | `http://127.0.0.1:36163/api/core/health` |
| 优雅关闭 | `http://127.0.0.1:36163/api/core/close` |
| `ready` / `state:running` 的 `details.baseUrl` | `http://127.0.0.1:36163` |
| 由调用方派生的 WebSocket 根地址 | `ws://127.0.0.1:36163` |

`baseUrl` 不带结尾斜杠。机器协议使用 `127.0.0.1`，不使用可能受 hosts、代理或 IPv6 解析影响的 `localhost`。未来若需要动态端口，必须作为协议升级单独设计。

## C2：身份注入与 health 回显

Runtime 启动后端时使用以下环境变量：

| 环境变量 | managed 模式 | development 模式 |
| --- | --- | --- |
| `AUTO_MAS_RUNTIME_PROTOCOL` | 必填，十进制字符串 `"1"` | 必填，十进制字符串 `"1"` |
| `AUTO_MAS_EXPECTED_VERSION` | 必填，调用目标的完整版本，例如 `v5.4.0-beta.1` | 不注入；后端返回治理后的单一版本源值 |
| `AUTO_MAS_EXPECTED_COMMIT` | 必填，受管仓库 HEAD 的 40 位小写十六进制哈希 | 不注入；后端返回空字符串 |
| `AUTO_MAS_SUPERVISED` | 必填，固定为 `"1"` | 必填，固定为 `"1"` |
| `AUTO_MAS_UV_EXE` | 必填，已校验 `uv.exe` 的规范化绝对路径 | 必填，已校验 `uv.exe` 的规范化绝对路径 |

`GET /api/core/health` 增量字段的类型固定为：

```json
{
  "protocol": 1,
  "version": "v5.4.0-beta.1",
  "commit": "0123456789abcdef0123456789abcdef01234567"
}
```

规则如下：

1. 在 supervised managed 模式下，后端不调用 GitPython 或 Git 命令重新推断身份，而是把三项 Runtime 注入值解析并原样返回；Runtime 在启动进程前已从已验证仓库得出版本和 HEAD。
2. `protocol` 是 JSON 整数；`version` 和 `commit` 是 JSON 字符串。
3. managed 模式下，Runtime 对三项值做精确比较；任一字段缺失、类型错误或不相等都返回 `BACKEND_IDENTITY_MISMATCH`。
4. development 模式下，后端返回自身支持的协议整数、治理后的单一版本源值和空 `commit`。Runtime 只要求 `protocol` 兼容，不比较 `version` 或 `commit`，不能据此拒绝脏工作区。
5. 无 Runtime 监督的兼容启动路径使用与 development 相同的返回规则；旧 Electron 不依赖新增字段。正式 Runtime managed 路径不接受这种降级。

## C3：后台初始化状态字面量

协议 v1 的 `backgroundStatus` 取值与 `dev_v2` 现有状态机一致：

| 值 | Runtime 语义 |
| --- | --- |
| `starting` | 核心 API 已启动，后台初始化尚未开始或正在排队；继续轮询 |
| `running` | 后台初始化正在执行；继续轮询 |
| `ready` | 后台初始化完成；同时满足其他 health 条件后可判定就绪 |
| `failed` | 后台初始化失败；立即结束启动 |
| `cancelled` | 后台初始化在就绪前取消；结束启动或进入关闭流程 |

失败字面量固定为 `failed`，不使用 `error`。`backgroundError` 非空始终视为失败，即使 `backgroundStatus` 值异常或尚未更新。未知 `backgroundStatus` 视为 `BACKEND_HEALTH_INVALID`，不得无限等待。

## C4：受监督进程标记

Runtime 在 managed 和 development 两种监督模式下都注入：

```text
AUTO_MAS_SUPERVISED=1
```

Python 后端只把精确字符串 `"1"` 识别为受监督模式，并遵守以下规则：

1. 受监督且当前权限不足时，不得通过 `ShellExecuteW(..., "runas", ...)` 创建脱离 Job Object 的新进程；必须记录明确错误并以非零状态退出。
2. `AUTO_MAS_SUPERVISED=1` 对关闭行为的优先级高于 `AUTO_MAS_DEV=1`。受监督 development 模式收到 `POST /api/core/close` 时必须真实设置 `Config.server.should_exit`。
3. 只有未受监督且显式启用 `AUTO_MAS_DEV` 的裸开发进程可以保留“忽略关闭请求”的兼容行为。
4. Runtime 不把是否管理员作为健康成功条件；权限错误应由进程退出和完整 stderr/log 事件上报。

## C5：development 模式检查边界

development 模式的目标是监督开发者明确指定的现有源码和环境，而不是把它转换成 managed 工作区。

### 必须检查

1. `--repo` 已显式提供，能够规范化为存在的绝对目录；
2. `<repo>/main.py` 和 `<repo>/pyproject.toml` 是普通文件；
3. Runtime 管理并注入的 `AUTO_MAS_UV_EXE` 存在、可执行且版本正确；
4. `<repo>/.venv` 是已存在的开发环境目录；Runtime 将 `UV_PROJECT_ENVIRONMENT` 指向该目录，但不创建或同步它；
5. 使用参数数组执行 `uv run --project <repo> --no-sync main.py`；
6. 后端进程成功进入 Job Object，health 协议兼容，`backgroundStatus` 最终为 `ready`；
7. shutdown、日志、超时、单次重启和进程树清理规则与 managed 模式一致。

### 明确跳过

1. 不要求源码目录位于 `--app-root/repo`；
2. 不要求分支名为 `release/<版本>`，不要求工作区干净，也不拒绝未跟踪文件；
3. 不比较 `res/version.json`、目标版本或 Git HEAD；
4. 不要求 `.python-version`、`uv.lock`、managed venv、`ready_to_start` 或非 `environment_broken` 持久化状态；development 只消费已存在的 `<repo>/.venv`；
5. 不执行 `workspace sync`、`dependencies sync/rebuild`、`repair` 或 `cleanup`。

### 失败关闭

Runtime 不创建、删除、移动或改写 development 源码目录中的任何文件，也不清理 `.git`、`__pycache__` 或未跟踪内容。缺少现有可运行环境时直接返回结构化启动错误，由开发者显式准备环境；Runtime 不以自动同步作为降级路径。
