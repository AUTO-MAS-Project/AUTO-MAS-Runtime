## C16：网络源测速排序

### 结论

**同一进程内，每个 Kind 在第一次需要网络时做一次有界并行测速，尝试顺序按实测结果排列。**

1. **触发**：Kind 首次被网络操作需要时触发——uv 在下载前、git 在克隆前、python 在安装前、package-index 在同步前，
   各自的 `network.probe` 事件紧贴在对应 stage 之前出现；结果在进程内缓存（供 `backend supervise` 这类长驻进程复用），
   缓存有效期 30 分钟，过期后下一次需要时重测。不做统一预热：uv 已缓存、仓库已是目标 Commit 这类不需要联网的阶段
   不会为了测速而联网（2026-09-11 实施期修订，原文写的是「bootstrap 在第一个网络 stage 之前显式预热全部 Kind」）。
   `backend supervise` 例外：中继先按目录顺序起来、后端立即启动，package-index 的测速在后台完成后再替换中继上游顺序，
   不让每次启动都多等一轮探测。
2. **方法**：对该 Kind 目录中的每个源**并行**发一次 `GET`，带 `Range: bytes=0-262143`（256 KiB 窗口），
   总预算 3 秒；记录首字节时间（TTFB）、窗口内吞吐（bytes/s）、是否返回 `206`（`Accept-Ranges` 能力）。
   探针目标按 Kind 固定：

   | Kind | 探针路径（拼在源 base 之后） | 说明 |
   | --- | --- | --- |
   | `uv` | `<固定版本>/uv-x86_64-pc-windows-msvc.zip` | 就是要下的制品 |
   | `python` | 由 `uv python list <精确版本> --output-format json --only-downloads` 的 `url` 字段去掉官方 base 得到 | 就是要下的制品；uv 的 JSON 是机器输出，不是自然语言，不触红线第 8 条。取不到时该 Kind 不测速，按目录顺序 |
   | `package-index` | 本次锁内规划集合里**最大**制品的 PyPI 原路径（C18 的规划器给出） | 拼在 `packages` 前缀之后 |
   | `git` | `info/refs?service=git-upload-pack` | 只看 TTFB，不看吞吐 |

3. **排序**：显式 `--mirror <kind>=<key>` 的源**钉在最前**，不参与排序（用户意图高于实测）；其余源按吞吐降序、
   吞吐相同按 TTFB 升序；探测失败（超时、非 2xx、连接错误）的源排在**最后但不剔除**——探针失败不等于源不可用。
   官方源参与测速并可以排到任何位置；`--mirror-only` 仍把官方源整个排除；`--offline` 不测速也不联网。
4. **可观测**：测速经 `network.probe` stage 报告（形态见 C18）；测速本身**永远不会**让操作失败，
   全部探针失败时退回目录顺序并在操作日志记 warning。
5. **下发**：增补 1 C11 下发给后端的两份有序列表改为**实测顺序**（含 C17 的回环首项）。

### 依据

- 「镜像与网络策略」规则 2「未指定时按项目配置顺序尝试」和规则 6「所有镜像失败后再尝试官方源」把顺序写死为
  「国内镜像优先、官方兜底」。这个顺序对国外用户全部是反的：2026-08-31 欧洲出口实测 PyPI 官方 TTFB 92 ms、
  numpy 12.8 MB 0.28 s，阿里云 934 ms / 2.9 s，清华 2.33 s，中科大 2.42 s（AUTO-MAS #499）；而对国内用户，
  目录里也有按连接限速到 200 KB/s 量级的源。静态顺序在两边都选不出最快的。
- 换源的唯一信号是失败（`internal/mirror/rotation.go` 的 `Run` 只在 attempt 失败后前进），一个「活着但很慢」
  的源会被从头拉到尾。测速把「慢」变成了可以提前看见的量。
- 3 秒预算 + 256 KiB 窗口足以把 200 KB/s 与 5 MB/s 的源区分开，也不会让首装多等太久；
  比这更精细的判断留给 C17 的逐文件失速回退。

## C17：回环中继

### 结论

**Runtime 自己成为下载方；uv 只从 `http://127.0.0.1:<port>` 取文件并照旧校验。**

1. **形态**：Runtime 在 `127.0.0.1` 上绑定一个临时端口（`:0` 由系统分配），只在操作期间存活；
   `backend supervise` 期间常驻，进程退出即关闭。三个路由：

   | 路由 | 上游（按 C16 实测顺序） | 用途 |
   | --- | --- | --- |
   | `/packages/<PyPI 原路径>` | `package-index` 各源的 `packages` 前缀 | 主项目依赖（锁内制品，`size` / `sha256` 已知）与运行池 `pip`/`uv` 请求的任意制品（含 `.metadata` 旁车文件，大小哈希未知） |
   | `/simple/<包名>/` | `package-index` 各源的 `simple` 前缀 | 运行池的索引页；响应体内各源自己的 `packages` 前缀被改写回 `/packages/`，其余内容原样透传 |
   | `/python/<tag>/<asset>` | `python` 各源 | `uv python install` 的分发包（`%2B` 等百分号编码原样转发） |

2. **锁副本改写**（修订增补 1 C10 结论第 3 条）：改写目标从「某个镜像 base」改为中继地址：
   `https://files.pythonhosted.org/packages/` → `http://127.0.0.1:<port>/packages/`，
   `https://pypi.org/simple` → `http://127.0.0.1:<port>/simple`。临时项目目录、`--frozen`、
   `UV_PROJECT_ENVIRONMENT` 指向真实 venv、不改写 `repo/` 内任何文件——这些全部不变。
   外层的「按源逐轮 `uv sync`」轮换收敛为**一次**经中继的 `uv sync --frozen`；换源在中继内部逐文件发生。
   C10 第 4 条的「全部镜像失败后用原锁 `--locked` 直连」保留为**中继不可用时**（绑定端口失败等）的回退路径；
   `--mirror-only` 时不做该回退；`--offline` 完全不起中继。
3. **Python 分发包**：`UV_PYTHON_INSTALL_MIRROR=http://127.0.0.1:<port>/python`，外层按源逐轮
   `uv python install` 的轮换同样收敛为一次；中继不可用时退回今天的环境变量轮换。
4. **逐文件策略**：
   - 已知 `size` 与 `sha256` 的文件（锁内制品）：下载到受管暂存目录，**校验通过后**才作为响应交给 uv；
     哈希不符视为该源对该文件失败，换下一个源重来，源在同一操作内两次哈希不符即被排除；
   - 未知大小的文件（`/python/`、运行池请求）：先 `HEAD` 取 `Content-Length`，随后同上暂存后交付，无哈希可校验时不校验（uv/pip 按索引哈希自校）；
   - 单个源失败（连接错误、非 2xx、读空闲 15 秒失速）只影响该文件在该源的尝试，按实测顺序换下一个源；
     所有源都失败才向 uv 返回 `502`，由 uv 让本次 `sync` 失败，Runtime 映射为既有 `MIRROR_EXHAUSTED`，
     `details` 列出失败文件与逐源结局；
   - **分片**：已知大小 ≥ 8 MiB 且至少两个源支持 `Range`（探针或 `HEAD` 见到 `206` / `Accept-Ranges: bytes`）时，
     按 2 MiB 分片，最多 4 个源并行取片，失速或失败的片重新排队交给其它源；分片完成后拼接、校验、交付；
   - 上游并发上限：同时下载的文件不超过 6 个、每文件不超过 4 片；超出的请求在中继内排队，uv 侧感知为响应变慢。
5. **暂存目录**：`runtime/cache/downloads/relay/`，归数据分类的「可丢弃缓存」，`cleanup` 与既有 `downloads` 同类处理；
   操作结束即清空，不跨操作复用（uv 自己的缓存负责跨操作复用）。
6. **uv 环境**：经中继下载的 uv 调用追加受控键 `UV_HTTP_TIMEOUT=900`——中继是「整文件就绪后才响应」，
   uv 默认 30 秒的读超时会把正常的大文件等待判成超时；有界性由中继自己的失速判定保证，
   任何一个请求都会在有限时间内得到 `200` 或 `502`，不会挂死 uv。
7. **修订规则 8**（「默认禁止关闭 TLS 校验，不自动使用 `--allow-insecure-host`」）：追加一句——
   「Runtime 自身在 `127.0.0.1` 上提供的纯 HTTP 中继是显式例外：它不是 TLS 放行，中继到上游的每一跳仍是
   经校验的 HTTPS，且不设置 `--allow-insecure-host` / `UV_INSECURE_HOST`（uv 0.12.3 对回环纯 HTTP 不需要它，见实验依据第 2、3、4 条）。」
8. **下发给运行池**（修订增补 1 C11 结论第 3 条与「新增注入环境变量」第 3 条）：受监督时
   `AUTO_MAS_MIRROR_PACKAGE_INDEX` 的首项是 `http://127.0.0.1:<port>/simple/`，`AUTO_MAS_MIRROR_PYTHON` 的首项是
   `http://127.0.0.1:<port>/python`，其后仍是实测顺序的上游源；「每项是绝对 HTTPS URL」放宽为「每项是绝对 URL，
   回环首项为 HTTP，其余为 HTTPS」。后端的按序重试不变：中继不可达（Runtime 已退出）时自然落到后面的直连源。
   Runtime 仍然**不**解析池的依赖声明、不决定装什么——中继是基础设施，与 C11 的分工一致。
9. **安全边界**：中继只监听 `127.0.0.1`，不接受非回环连接；只接受上述三个前缀且路径经规范化后不得含 `..`；
   上游 URL 只能由目录内源的 base 拼出，请求方无法指定上游主机；重定向沿用既有下载器策略（≤ 10 跳、禁止降级到 HTTP）。

### 实验依据（2026-09-11，uv 0.12.3，Runtime 固定版本）

1. 四个纯 Python 小包的 PyPI 锁，逐包把 wheel URL 分别改到阿里云、清华、中科大和官方（`source.registry` 不动），
   `uv sync --frozen` 成功，`-v` 日志显示四个 host 各自被请求——**证明同一份锁里各包指向不同 host 被 `--frozen` 接受**；
2. 同一份锁把 `packages` 与 `simple` 两个前缀全部改到 `http://127.0.0.1:39170`（Python 写的临时反向代理），
   `uv sync --frozen` 成功、无 warning、未设置任何 insecure 选项——**证明回环纯 HTTP 不需要 `--allow-insecure-host`**；
3. `uv pip install --index-url http://127.0.0.1:39170/simple/ six idna` 成功；日志显示 uv 先取 `/simple/<包>/`，
   再取 `/packages/...whl.metadata` 旁车文件与 wheel 本体——**证明运行池路径可行，且中继必须透传任意 `/packages/` 路径**；
4. `UV_PYTHON_INSTALL_MIRROR=http://127.0.0.1:39170/python` 下 `uv python install 3.12.13` 成功，
   请求路径为 `/python/20260807/cpython-3.12.13%2B20260807-x86_64-pc-windows-msvc-install_only_stripped.tar.gz`——
   **证明 Python 分发包可经回环下载，且路径带百分号编码须原样转发**。

### 为什么不做「静态分包」

把 108 个包按测速结果静态分到各镜像后一次 `uv sync` 也能多源并行，改动更小；否掉它的原因是三条同时不满足：
uv 在 `UV_NO_PROGRESS` 下是黑盒，拿不到逐文件进度与文件名；某个镜像缺一个包（镜像同步有延迟）整轮失败只能重跑；
单文件仍是单源，限速 200 KB/s 的源拖住的那个 38 MB 包还是要等 3 分钟。中继一次解决三条。

## C18：进度事件的字节字段与细目

### 结论

1. **`progress` 事件追加三个可选字段**（v1 内追加，缺失即无信息，不得输出 `null`）：

   | 字段 | 类型 | 含义 |
   | --- | --- | --- |
   | `item` | string | 当前正在处理的条目：文件名（`opencv_python-4.12.0.88-cp37-abi3-win_amd64.whl`）、源 key（测速时）等 |
   | `source` | string | 当前字节来自哪个源的 key（`aliyun`、`github`…）；分片并行时报贡献最多字节的源 |
   | `bytesPerSecond` | number | 最近 1 秒窗口的吞吐，整数字节；测速时是该源的实测吞吐 |

2. **新增 stage `network.probe`**（领域 Runtime）：每个源探测完成发一条 `running`，`item` 与 `source` 均为源 key，
   `current`/`total` 为已完成源数/源总数，`message` 形如「测速 aliyun：3.2 MB/s」；全部完成发 `succeeded`，
   `message` 给出最终顺序。探测失败不发 `failed`。`bytesPerSecond` **三态**（2026-09-11 复核修订）：正数为实测吞吐；
   `0` 为探测失败；**缺失**表示探测成功但只测了首字节（git 类源只看 TTFB，没有吞吐可报）——调用方不得把缺失当作失败。
3. **`dependencies.sync` 的真实字节进度**：`total` 是锁内**本平台可安装制品**的字节总和，由 Runtime 从
   `uv.lock` 自己的 `size` 字段计算（C10 的锁副本本来就在内存里）：从根项目的 `dependencies` 出发，沿依赖边
   按 `marker` 求值可达的包（环境固定为 `sys_platform=win32` / `platform_system=Windows` / `os_name=nt` /
   `platform_machine=AMD64` / `implementation_name=cpython` / `platform_python_implementation=CPython` /
   精确 Python 版本），每包取本平台匹配的 wheel（`win_amd64` 配 `cp312` / `abi3` / `py3`，否则 `none-any`，
   都没有取 sdist）。这不是「从输出行数、耗时或阶段顺序推算」，是锁文件声明的数据；求值失败的 marker 一律按可达处理（只会高估）。
   `current` 是中继已校验交付的字节；uv 请求了规划外的文件时其大小并入 `total`。
   uv 缓存命中的文件不会被请求，`current` 因此可能停在 100% 以下，由 `succeeded` 收口——Electron 已按「100 只由段收口发」处理。
4. **`python.install` 的真实字节进度**：`total` 取中继 `HEAD` 得到的 `Content-Length`，`current` 为已交付字节；
   `item` 为分发包文件名。
5. **`uv.download`** 不变（已按 T13.12 发真实字节），追加 `item`（制品文件名）、`source`（本次尝试的源 key）与
   `bytesPerSecond`（按相邻两次回调的字节差与时钟差计算，第一条没有）。
6. **Git 克隆继续不发数值**：go-git 不给可信总量，`workspace.clone` 仍是 T13.14 的时间心跳。
7. **`result.details`**：本次操作做过测速时含 `networkProbe`：`{ "<kind>": [ { "source", "ok", "ttfbMs", "bytesPerSecond", "acceptRanges" } ... ] }`，
   顺序即最终尝试顺序；经中继下载时含 `relay`：`{ "files", "bytes", "bySource": { "<key>": bytes }, "failures": [ { "item", "attempts": [ { "source", "outcome" } ] } ] }`（失败列表上限 32 项）。

### 依据

- 「NDJSON 公共结构」写的是「Git、Python 安装和依赖同步等无法取得稳定总量的外部过程仍只发不带数值的 running」。
  依赖同步的前提不成立：`upstream/dev@cca4ac486` 的 `uv.lock` 有 108 个包、Windows 侧约 151 MB，
  **每个制品都带 `size` 与 `sha256`**（0 个缺失），总量在下载前就是确定的；Python 分发包是单文件，`Content-Length` 可信。
  真正没有稳定总量的只剩 Git。
- 这三个字段是用户明确要的「测速、进度、在拉什么」；把它们塞进 `message` 会逼 Electron 解析文案，违反红线第 8 条的调用方半边。
- 「不解析 uv 的自然语言输出」不受影响：字节来自中继自己写下的数据，uv 仍是黑盒。

### 落点

Runtime `T14.4`（规划器与字节接线）、`T14.6`（protocol 字段、stage、renderer）；AUTO-MAS `TODO-EL-14`（桥接与展示）。
